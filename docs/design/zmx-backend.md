# Portal on zmx

Portal moves from tmux to [zmx](https://github.com/neurosnap/zmx). Each session becomes one zmx session: a background process that holds the program and a copy of its screen, with bytes passed straight to the terminal. The terminal (Ghostty, rootshell, Blink) renders natively and keeps its own scrollback. tmux is removed at the end; nothing runs both.

Board: sitrep `sr-fpq124` (Portal on zmx). Branch: `zmx-backend`. Base: v0.12.5.

## Settled

- **zmx only.** No dual backend. Rollback means reinstalling v0.12.5 and putting back `state-tmux/` and the saved `hooks.json` (see Migration).
- **One interface, at Portal's level.** Portal code talks to a `Backend` that speaks in Portal's terms: a session is a persistent terminal with a name, a directory and a command. Only a zmx implementation is built. Windows, panes, layouts, hooks, servers and options exist nowhere above the driver. A later tmux driver would map one Portal session to one single-pane tmux session.
- **Portal stores nothing on zmx sessions.** Everything Portal knows about a session is in Portal's own state, keyed by the session name. zmx's key=value tags (`zmx set`, `zmx clear`) are never used.
- **Scrollback is still saved and restored.** zmx keeps scrollback in memory only, so a reboot still loses it.
- **Kills.** A session you didn't kill comes back after a reboot. A killed session normally stays gone, but nothing heavy is built to guarantee it.
- **Keys.** Portal runs `zmx attach` itself and adds these keys, the same from every terminal, each configurable (see Key config):
  - **Alt+D:** detach, back to the picker.
  - **Alt+Shift+D:** detach, straight to the shell.
  - **Alt+Q:** ask to kill the session. It detaches to the picker, which opens on the kill prompt for that session: `y` kills it, `d` keeps it and stays in the picker, Esc keeps it and goes back into it. A mistaken Alt+Q costs a key, never a session.

  zmx's own `ctrl+\` detaches the way plain zmx does, straight to the shell, never the picker. The runner wraps `zmx attach` rather than speaking zmx's attach protocol itself; no floating menu, no pinned status bar.
- **Picker rows.** No window count. The session label, plus the attached and waiting dots.
- **Preview (Space).** The session's live screen and history from zmx, up to zmx's 10,000 lines, instead of the saved file, read again about once a second while the preview is open, so it shows the session live, holding the place the user scrolled to by the rows at the top of the view, found again near where they were, and by the row number when they can't be; a read that fails once the preview shows the session keeps what it shows, and one opened on a session listed as not answering reads it again on the same tick, so it comes alive once the session answers; a session whose resume-pending flag is raised shows the transcript its index entry names, since its History holds only the panel's screen. Window and pane cycling go.
- **One terminal at a time.** Opening a session takes it from every other terminal showing it before Portal attaches, so zmx sizes and draws it for the opening terminal from its first frame. A Portal it is taken from lands on a screen saying the session is open on another device and where, offering to take it back or watch it; a raw `zmx attach` goes to its shell. Only terminals are taken, so nothing that only reads a session sets a take off, and nothing is killed. See Taking a session.
- **Opening several sessions in new windows (`m`).** Works as today: Ghostty on the Mac opens them, and Blink and rootshell get today's refusal. See Attach runner.
- **Esc on the resume panel.** Detaches to the picker, as today.
- **Version.** Lee's call at release.
- **Out of scope:** the workflows tool.
- **zmx's socket protocol, on official zmx.** The driver speaks zmx's socket protocol (protocol version 1, frozen on 16 Oct 2026 and first released in zmx 1.0.0 on 6 Nov 2026) for listing, kill, detach and history, so nothing parses text meant for people; zmx declined machine-readable CLI output (#220). Creating and attaching still run the `zmx` binary, since creation isn't a protocol message. Portal runs on official zmx, installed as a Homebrew dependency of Portal's formula (`neurosnap/tap/zmx`); it bundles, pins and forks none. Homebrew can't hold a dependency to a version range, so zmx upgrades freely: Portal names the sessions whose daemons speak a protocol it doesn't, and a zmx release that changes the protocol is caught up with in a Portal release, as a tmux change would have been. The README states the zmx release Portal supports. A weekly GitHub Action runs the backend contract suite against the macOS build zmx publishes for its latest release, the one Homebrew installs, and against a build of zmx's main, so a breaking release shows up before users meet it. Development and tests use a build of the zmx commit pinned in `scripts/zmx-commit`, v1.0.1's. Support is judged by the protocol version, never the version string.
- **Leave Portal better than found.** The move is also the refactor: simpler structure, lower complexity, cleaner code. Each phase simplifies what it touches, and nothing tmux-shaped survives above the driver.
- **Output quality.** Rendered output is tested properly, and the README gets a demo recording to the standard Switchboard's has. Switchboard grew its capture and VHS tooling out of Portal's harness; Portal borrows it back (see Output and visuals).

## Names

- **Session name:** the zmx session's name, such as `dotfiles-PpaTER`. Portal sets it once, at creation, and it never changes, since zmx has no rename. Portal-made names carry a nanoid, so they're unique. It keys everything Portal stores about the session: the index, `hooks.json` and the scrollback file. Restore recreates a session under the same name. zmx itself and rootshell's own zmx picker show it.
- **Session label:** what Portal shows: the picker, the preview and `portal current`, which footers and Claude's `--name` read. It defaults to the session name and takes any text. `r` in the picker sets it, and so does `portal rename <text>` from inside the session. It lives in Portal's index.
- **Telling a recreated session apart.** A session that ends and is recreated under the same name outside Portal is a new session. Portal tells it apart by zmx's created time, which the index records and nothing can clear. A session whose created time differs from its entry, and that Portal didn't create or restore, starts clean, without the old session's label, hook or scrollback. Every claim of an entry (a mint, a rename, `hook set`, the saver) judges by one rule, `state.ClaimRule`: an entry is replaced, and what it kept forgotten, only when both creations are known, both are from this boot, and they differ. An entry recording no creation, one saved before this boot (with a few seconds' leeway, as the boot time is read against the wall clock), and one whose session has its hydrating or resume-pending flag raised is taken over, keeping its label, dirs, scrollback and hook. A claimer that knows no creation leaves the entry as it is, and a rename or `hook set` refuses a session that reports none. What a replaced or removed entry kept is forgotten under the commit lock its write held, so no claim lands between the write and the forgetting. `hook set` writes its hook under its claim's lock as well, once that forgetting is done, so no kill lands between the claim and the hook, and the forgetting of an earlier creation's entry never takes the hook just set.

## Backend interface

`internal/backend` defines the interface and the session model. `internal/backend/zmx` implements it over zmx's socket protocol, running the `zmx` binary only to create and attach. A fake implementation backs unit tests. Every method that does I/O takes a context, with per-operation ceilings beneath it.

- `List(ctx)` returns every session in zmx's dir, found from its sockets and probed concurrently for name, cwd, attached client count, pid, created time and command. A session that doesn't answer is kept with only its name (`Answered` false), never dropped from the list. A socket that refuses is stale, and left out, on Linux, where a full listen backlog fails a connect with EAGAIN, so a refusal proves no listener; elsewhere when it predates this boot, or when the process table proves no process holds its name: none, whatever the kernel names its executable, whose argv is a subcommand that starts a daemon (`attach` or `a`, `run` or `r`, `write` or `wr`) and the name, with `ZMX_DIR` the backend's dir, compared canonically (`/tmp` and `/private/tmp` are one dir). A zmx renamed or wrapped is still counted, which errs towards a holder, the safe side, and so is a process whose environment the kernel hides, as macOS does a hardened binary's, when the socket's name ends with the one its argv starts, its prefix and dir unknown; one whose argv starts no name holds none. Each variable is read first entry winning, as zmx's `getenv` reads it. A daemon and its attach clients aren't told apart: a live client keeps a socket refusing, which is safe, and exits on the closed socket. A process whose arguments can't be read, as one caught forking or exec'ing can't for a moment, is read again every 5 ms for up to 100 ms, and skipped if it goes meanwhile. One still unreadable then counts as a possible holder only when its kernel name contains `zmx`; any other is skipped. Under load about one scan in ten catches a live process unreadable, and some stay so for seconds, so a longer wait would only move the failures; what is left is a renamed zmx, unreadable for the whole wait while its live daemon's backlog is full. The scan and those waits end with the probe's ceiling, so a table of many unreadable processes can't hold a listing past it. A socket from this boot that refuses with a holder, or with a process named zmx it can't read, or whose process table can't be read, or whose scan the ceiling cut short, is kept as not answering. A daemon SIGKILLed or SIGHUPed leaves its socket behind, and that reads as no session; SIGTERM and `zmx kill` both unlink it. A session that doesn't answer, whether its socket refuses or its daemon stays silent, fails every per-session call with a timeout, and `Create` refuses its name. Portal never deletes zmx's files; `zmx list` and `zmx attach` delete a refused socket, and `Create` replaces a stale one. Only an unreadable dir is an error; a missing one means no sessions. Sessions whose names start with `_` are Portal's own. `List` returns them with the rest; every surface the user sees reads the listing without them (`cmd`'s `userSessions`), and so does the hook sweep's judgement (`hooksweep`'s `listedNames`), so a running `_portal-saver` never counts as a session that protects a hook. Doctor's protocol check and the saver's own lifecycle read them.
- `Exists(ctx, name)`.
- `Create(ctx, name, dir, command)` creates a detached session: `zmx attach <name> <cmd…>` with no terminal attached, succeeding only when zmx reports it created the session. A name already held, under any spelling the filesystem folds together, is refused with the held name. It starts 120×24 and reflows on attach. A session made that gives no Info within the read-back but answers zmx 0.8.1's framing is ended by the zmx that made it (`zmx kill`), and nothing else, and refused (`backend.ErrUnsupportedProtocol`), so no caller keeps a session it can't talk to. One that kill can't end is left, and the refusal says so: no signal backs the kill up, since no proof of which daemon the create made is safe from reaching a session Portal didn't make, and restore counts the name held for that boot. The judgement and the kill run past a caller that gives up once the session is made, each within its own ceiling. A mint fails with the older-zmx fatal and a non-zero exit, on the command line and in the picker alike. In the picker, a direct mint shows it on the loading page's error frame: the fatal alone where no loading step ran in this process (a warm picker, or a cold one that only waited out another Portal's bootstrap), and with the steps a cold one ran. A pick held for the bootstrap is always a command-pending picker's, which quits at once, the fatal printed on stderr. Any other create error in the picker flashes "Portal couldn't start that session: <error>" and the picker stays open. Restore stops with it before making more, as a 0.8.1 first on PATH (inside a session `path_helper` puts Homebrew's there) makes every create fail alike.
- `AttachCommand(ctx, name)` returns the argv the attach runner starts, for a session that answers. Inside a session (`$ZMX_SESSION`, in the backend's dir) that answers, the command keeps `ZMX_SESSION`, so zmx switches that session's clients instead of nesting (`Switches`). Inside one that is definitely not there, no socket or a name no session can have, it drops `ZMX_SESSION`. Inside one that doesn't answer in time, it fails, naming the session typed in, as no fault of the target's: either guess may be wrong, and a `zmx attach` nested in the session it attaches feeds that session's output back into itself until it is killed. The session typed in is asked at most once, and not at all when it is the target, whose answer stands for it.
- Every zmx Portal runs drops `TMUX` and `TMUX_PANE`, since a session zmx makes inherits the run's environment and must not take itself to be inside the caller's tmux. Run from inside tmux (`TMUX` set), it drops `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and a `TERM` naming tmux or screen (`tmux`, `screen`, or either followed by `-…`) as well, so zmx, which keeps the creator's `TERM` unless it is unset or `dumb`, sets its own. So the sessions `portal migrate` restores from a tmux pane, and its saver, never take themselves to be inside tmux.
- `Kill(ctx, name)`: done only when the session's socket is gone; a timeout says the kill may still land.
- `Detach(ctx, name)` detaches every client of a session.
- `History(ctx, name, rows)` returns the screen plus up to `rows` of scrollback (all of it when `rows` is 0), with colours, through the protocol's bounded capture. Never empty: a daemon that doesn't answer is an error. An answer over the 64 MiB a zmx frame holds is its own error, naming its size, never a timeout: zmx caps scrollback in lines (10,000 by default, raised by config), not bytes, so a wide, heavily styled history can pass it.
- `Current()` returns the session this process runs in, from `$ZMX_SESSION`.

Names follow zmx's limits. A socket path is capped at 104 bytes, which leaves about 70 bytes of name with `ZMX_DIR=$HOME/.local/state/zmx`. Generated names stay `{project}-{nanoid}`.

## State

- The zmx version owns `<config>/portal/state/`. `portal migrate` builds this version's state in `state-migrating/` beside the tmux version's `state/`, then moves `state/` to `state-tmux/` and the staging dir into its place (see Migration).
- While `state/` still holds a version 1 `sessions.json`, or a migration is cut short between its renames (see Migration), every command except `migrate`, `version`, `init` and `current` stops with one line pointing at `portal migrate`; `init` reads no state, so a new shell's `eval` of its script keeps working; `current`, which footers read, shows the session's name when it can't read the index. The hidden `state` helpers a restored session runs (hydrate and the resume chain) are exempt too: a refused helper exits, and the session it runs in ends with it. `doctor` is exempt as well, so it can report a version 1, corrupt or newer `sessions.json` itself.
- `sessions.json` version 2: `{version, saved_at, sessions: [{name, label, dir, cwd, created_at, pid, scrollback_file, owed, resume_lazy}]}`. `label` is omitted while it's the default, and `owed` and `resume_lazy` while they're false. `resume_lazy` marks an entry migrate made, until its first restore completes (see Migration). Members a version doesn't model, on the root or an entry, are kept through every rewrite. Rename writes through the same locked commit as the saver.
- A session's files are named by its stem, `<name>-<hash>`, the hash the first 12 hex digits of the SHA-256 of the exact name, so names a filesystem folds together (`Foo`, `foo`) never share a file.
- `scrollback/<stem>-<creation>.bin`, the creation its UTC created time and pid, so each creation of a name writes its own and forgetting one removes no other's. The entry names its file; forgetting an entry removes only that one. All positional re-filing goes.
- Per-session flags, as files named by the session's stem:
  - `hydrating/<stem>`: written before restore creates the session, removed when the scrollback replay finishes; a replay that fails leaves it, for the next bootstrap to remove once the session has ended.
  - `resume-pending/<stem>`: present while the resume panel waits.

  A session's flags are removed when it's dropped from the index, and bootstrap removes any for sessions that aren't live.
- Flags that were tmux server options become files:
  - `restoring`: present only while restore's creates are in flight.
  - `bootstrapped`: the record that the last bootstrap finished, holding the boot id and the version, replacing the per-server latch.
  - `zmx-dir`: the zmx directory, canonical, the state directory belongs to, written by the first bootstrap that finds none. A Portal running against another refuses to bootstrap against that state, with a fatal naming both and the way out, and changes nothing; a record it can't read or write is a fatal naming the file, the read's telling the user to delete it: otherwise it would find no saver there, mark every saved session owed and restore it into the other directory, whose entries the first directory's saver would later replace, forgetting their scrollback and hooks. The gate reads it on the warm path too, so a warm command against another directory's state bootstraps and is refused rather than recording a mint in the wrong index. The commands that skip the bootstrap but write state (`hook set`, `hook rm`, `rename`) make the same check, recording nothing, and `doctor --fix` repairs nothing under a mismatch or a record it can't read. Doctor reads it and reports a mismatch or an unreadable record as a failure, naming the file. A state directory with no record owes the bootstrap that records one, so a deleted record is written again at the next command, and the exempt writers and doctor pass it meanwhile. Directories compare canonically, equal only when they are one directory: symbolic links resolved, and for a directory since removed, its deepest prefix that resolves resolved as the OS does, so a recorded `/private/tmp/x` still matches `/tmp/x` once it is gone; a `..` past a missing directory keeps its spelling, equal to nothing else.
  - `spawn-acks/`: one empty file, `<batch>-<token>`, per window a burst opened, written by that window once its attach has begun. The burst removes its own, and any an hour old, as a burst that died leaves them. The directory is 0700 and each file 0600.
  - `runners/` (see Attach runner)
- `hooks.json` stays where it is, keyed by session name. `prefs.json`, projects and aliases are unchanged.
- A hook goes with its session's entry; as a backstop, the daemon's hourly sweep and `doctor --fix` remove a key naming neither a session the backend lists, answering or not, nor an entry in `sessions.json`, and remove nothing while `restoring` is raised, while neither names any session, when either read fails (a migration cut short between its renames counts as an index unread), or, until migration has moved the tmux version's state to `state-tmux/`, while a key they would remove has the tmux version's shape, a pane token or `<session>:<window>.<pane>`, which a scratch state beside the shared `hooks.json` would otherwise judge stale, saying why with one warning (a `state-tmux/` that can't be read counts as not yet moved); once it exists, a key in that shape is an ordinary name, judged as any other. Nor do they remove anything when three keys or more, at least half of `hooks.json`, would go in one sweep: `hooks.json` belongs to no state dir or zmx dir, and since a hook goes with its session's entry a sweep in ordinary use removes none or one, so a mass removal is the file judged against a state dir and zmx dir it wasn't written beside (a scratch state or `ZMX_DIR` beside the real `hooks.json`), and the sweep holds every key, saying why with one warning, as the saver holds sessions that vanish at once. A `hooks.json` that can't be read or doesn't parse is a failure, never a stand-down.
- Every file Portal replaces is replaced in order: the temp file is synced before its rename and the directory after it, so after a power loss each file is its old version or its new one, never empty, and no later write persists ahead of a rename. On darwin both syncs are `F_BARRIERFSYNC`, which orders without flushing the drive's cache (fsync where a filesystem has no barriers); on linux, fsync. That costs about 0.5 ms a write on an M1 Max's internal SSD, where `F_FULLFSYNC` cost 10 ms. A filesystem that makes no such sync is written to without it. A write has landed once its rename has: a directory sync that fails after it is a warning, never an error, so no caller undoes or repeats a change already in place.
- Before switch-over, a dev build runs beside the installed tmux Portal with `PORTAL_STATE_DIR`, `PORTAL_HOOKS_FILE` and `ZMX_DIR` pointed at scratch paths, so its sessions and its `_portal-saver` stay out of the real zmx directory.

## Saver

- **Host.** `portal state daemon` runs inside a `_portal-saver` zmx session, which keeps it alive the way tmux did. The session runs Portal's own binary by its absolute path, never a `portal` found on PATH, which beside an installed Portal would be the installed one. The daemon refuses to start on a version 1, corrupt or newer `sessions.json`. The singleton lock, pid and version files and the orphan sweep stay. Self-supervision compares the saver session's pid from `Session("_portal-saver")` with its own. A SIGTERM or SIGHUP ends it through a final flush, which saves the scrollback of sessions whose history changed and claims and drops nothing: from the signal, what it has in flight and the flush get about 6 s before it exits without them, and a second signal exits at once. A poll the signal finds waiting for commit.lock writes nothing, so a drop never lands without its forgetting; one already holding the lock finishes within the bound. It holds its lock until the process exits.
- **Proof.** Portal signals the saver's daemon, or an orphan of it, only once it has proved the pid one, as each signal is sent: `IdentifyDaemon` names a portal state daemon, and one read of the process's exec'd argv and environment finds an argv naming a daemon and the saver session's three marks: `ZMX_SESSION=_portal-saver` (which zmx sets), and the saver's `ZMX_DIR` and `PORTAL_STATE_DIR`, which Portal's create sets in the environment of the session's zmx daemon and so of the daemon it runs. A mark set more than once must hold its value every time, and a directory compares canonically, as the zmx-dir record does. `ZMX_SESSION` alone tells the saver from a daemon a shell exporting `ZMX_DIR` started, and the state dir tells this state's saver from another state's in the same zmx dir, so no mark is ever dropped. A proof that fails or can't be read, as off darwin, sends nothing more. One that finds the other marks and another absolute state dir, the same every time it is set, proves the saver another state dir's: Portal neither keeps, replaces nor stops it, and the bootstrap, `uninstall` and doctor name that state dir (see Bootstrap).
- **One at a time.** The ensure and the stop (the recycle's and `uninstall`'s) hold `saver.lock` in the state dir for their whole run, so no two judge, stop or create the saver at once: two windows at login, or an ensure racing `uninstall`. The wait for it is bounded at 79 s: another holder's longest run, 64 s with every wait at its bound and every backend call at its ceiling, a run of the zmx binary with a second more for its output to close once killed at it (a starting saver's 10 s, a stop's 8 s and 2 s, the session's kill, the create, the judgement of the saver made, ended by `zmx kill` and then a signal when Portal can't use it, a new daemon's 10 s, and the reads between them), with 15 s over for the proofs' `ps` calls. A lock held past that fails the run with nothing read or sent. With no state dir, `uninstall` creates one for the lock only when a saver runs without it. The bootstrap's own lock, where one wraps it, is taken first.
- **Stop.** One sequence, for a recycle and for `uninstall`, of the pid read under the lock: nothing is sent to this process, or to a pid the session no longer runs. SIGTERM on proof; a wait of 8 s, past the daemon's 6 s bound; proof again, then SIGKILL; a wait for the pid to finish exiting, which a pid a proof finds gone may still be doing; and only then a kill of the session, unless a newer saver runs in it. A proof that fails before the SIGTERM sends nothing; one that fails before the SIGKILL leaves the daemon with its SIGTERM alone. Either way the session is left and the stop fails. So a saver another state dir's, which the proof before the SIGTERM finds, is sent nothing.
- **Up.** The bootstrap ensures the saver is this binary. It first judges whose a saver it finds is, and whose one another process created first, and judges again while it waits for the new daemon, since a create another state dir's Portal won may be read before that Portal's daemon has exec'd: one proved another state dir's is neither waited for, kept nor stopped, and the ensure fails with the bootstrap's refusal of it; one proved this state's, as when `daemon.pid` is lost, or one that can't be read goes on as any other. A wait proves the session's process when it first reads it, never again once it is proved a saver's daemon either way, and one proved neither way, not yet exec'd or unreadable, again once a second. A saver still starting, `daemon.pid` not yet naming the session's process or `daemon.version` not yet written, is waited for, up to 10 s, before it is judged, so an ensure that gave up on it under load doesn't leave the next to stop it on its way up. It keeps one whose daemon records this version, a dev build's included, since a dev version names its build (its VCS revision, whether that tree was modified, and when its executable was written), but never on an unidentified build's bare `dev`; replaces any other through the stop; and waits for the new daemon's `daemon.pid` to name the session's process and its `daemon.version` to hold this version, which counts a saver another process created first only at this version. There is no warm-path create: a missing saver runs the full bootstrap, restore included, so the lifecycle offers the warm path only a check that `_portal-saver` runs the daemon this state's `daemon.pid` names (see When).
- **Index.** Polled every 5 s; committed when it changes. Portal records the created time and pid of every session it creates, restore included; zmx keeps created time in whole seconds, so the pair tells a recreated session apart (see Names). Every zmx session in the directory is saved, made through Portal or not, as the tmux version saved every tmux session; but one made outside Portal under a name Create refuses, such as `logs`, `-x` or `foo*`, is never saved, since restore could never make it again. No writer of `sessions.json` keeps such a name: the claim every writer makes refuses it by the rule Create refuses it by, held in one place, so a rename, a label from the picker, a `hook set` or the helper's claim fails on it, and a `hook set` registers no hook. A claim with no creation is refused too, so a mint whose Create read back none asks for the session once more, a probe's ceiling later, as restore does, and one that still reports none is left for the saver to record once it reports one.
- **Scrollback.** Captured at most once a minute per session, and only when its content has changed. Sessions flagged hydrating or resume-pending are skipped. A session on the alternate screen (vim, less, htop) is skipped too, since zmx's history then holds that screen alone, led by its mode (`?1049h`, `?1047h` or `?47h`), and never its main screen or scrollback: the saved transcript is kept, and the session is asked again a minute on, like any other. A history too large to read keeps the saved transcript too, and is asked for again a minute on; the saver warns of it once for each session in its run, naming the session and the size, since the transcript then goes stale. A poll starts no capture once about 3 s of its captures have passed, and never cuts one short; a session it doesn't reach is captured at the next poll.
- **Drops.**
  - A session missing from two polls at least 10 s apart is dropped. An entry created before this boot, recording no creation, or owed a restore (see Restore) is never dropped, so a session whose restore failed or never finished comes back at the next bootstrap. The hydrating flag plays no part in a drop: those already keep every unfinished restore, and a flag stuck up must not turn the user's close into a resurrection; it only stops captures. An owed entry whose session the saver finds live is owed no longer, once its hydrating flag is down.
  - If at least three of the entries the saver may drop, and at least half of them, are missing at once, whether they went in one poll or over several, it drops none of them while it runs, unless one is listed again, and logs a WARN. That covers a zmx upgrade or a mass crash. The hold keeps those entries until the next bootstrap that finds no saver running, which restores them, or a reboot. The entries it holds count no further, so a session ending on its own later is still dropped.
  - A kill from inside Portal commits at once.
- **Removed, because they only existed for tmux:**
  - the "own server answers" check and the empty-capture check,
  - positional pane keys, pane tokens and the re-filing of moved transcripts,
  - rename detection,
  - the environment capture.

## Restore and resume

- **Restore** writes the hydrating flag, then creates each saved session that isn't live with `Create(name, dir, portal state hydrate --session N [--lazy] [--file S])`, `--lazy` for an entry marked `resume_lazy`, where dir is the session's last working directory, else the directory it was made in, else HOME. It brings back entries owed a restore and entries that may predate this boot: one from this boot whose session is gone, and owed nothing, ended while a saver watched, and is the saver's to drop, so a second bootstrap within a boot never brings back a session the user ended. When the bootstrap finds no saver, the saver's world ended with the sessions (a logout, every zmx daemon dying, a crash), so no saver saw them end: before any saver can commit, it marks every entry not live owed in `sessions.json`, under commit.lock, and those come back, this boot's included. An entry stays owed, and no saver drops it, until its restore completes, so a restore that fails for one entry, or can't list the sessions, loses nothing. A restore completes at its helper's claim: restore leaves owed the entry of each session it makes, and while the session's hydrating flag is up only the helper's claim, made once its replay is done, repays it. A session that ends before its helper's claim, its helper dying after Create or the user closing it, leaves the entry owed and its hook kept: restore's later listings find it gone and make it again within the same bootstrap's retries, as below, and failing that the next bootstrap brings it back. A helper whose replay fails leaves the entry owed too, and once that session ends, the next bootstrap, its sweep lowering the flag of a session no longer live, brings it back. Once the flag is down, a saver finding the session live repays the entry too, so a session the user closes after its restore finished is dropped as any other. The mark is an `owed` member, omitted when false, so an older `sessions.json` reads with nothing owed. With no boot time to read, every entry not live comes back too. Wherever restore looks a name up, another spelling holds it, as a filesystem folding case holds `foo`'s socket as `Foo`'s, only while that spelling is live, listed or answering then: a socket a session gone left under it, which Create replaces, holds nothing, so it skips no entry, and a Create that failed beside it may pass and is tried again. An entry whose name a live session holds under another spelling is skipped up front, logged at DEBUG, neither counted failed nor named in the warning, and stays as it is, made once that session ends; only an entry the listing holds under another case is looked up for it. An entry under a name Create refuses is counted failed, never tried. A Create that fails may have made the session all the same, so restore looks the name up, asking once more a probe's ceiling later if it finds none, since a Create cut short after zmx forked the session's daemon leaves a session that answers to no one yet: a session running its helper counts restored, and any other holder fails the entry and lowers its flag. A Create that reports the session made but no creation is asked about again a probe's ceiling later: gone, the entry fails and its flag is lowered; present running its helper, it counts restored. A session that failed for a reason that may pass is tried again before the restore returns, in rounds about 1 s then 3 s apart, within a budget of about 15 s from the end of the first pass, a try that starts inside it running to its end; a name Create refuses and a name another session holds are not retried. A create refused as a session Portal can't talk to stops the retries as it stops the first pass: those left to try again count as failed, and that name is never looked up again, so no retry remakes it or restores a session its kill left. Restore never raises a flag on a name unless a lookup has just found no session there: the first pass has its listing, and a retry looks the name up first, since an earlier try may have made the session after all and its helper lowered the flag. Found free, the name is made again only while its entry is still due and records the creation restore read: one a helper has claimed since, or the user's end dropped, is left alone. A session running its helper counts restored as it stands; another holding the name fails for good; one that can't be looked up waits for the next round, nothing raised and nothing made, and fails once the budget is spent. Restore lists the sessions again after its first pass: one it made that is gone, its entry still owed and recording the creation restore made, had a helper that died before finishing, so it is warned of and tried again with the rest, counted failed if still unmade. It lists them once more when the retries end: one it couldn't make that is there running its helper counts restored, as a create that timed out under load may have made it, and one its retries made that is gone by the same rule had a helper that died too, so it is warned of and counted failed, its entry left owed. A session counts as running its helper when its command, as zmx reports it, reads as the helper's would at the portal-named path it starts with; zmx cuts the command it reports at 256 bytes, so a cut within the helper's arguments shows as they do alone, and one after them shows them whole, then what fits of the transcript's. Those it still couldn't make stay owed, and the bootstrap's warning says they are kept for the next restore.
- **The helper** refuses to fire anything when `$ZMX_SESSION` names another session. Otherwise it replays the transcript's rows straight away, without zmx's leading modes or closing state; there's no FIFO, because nothing else races it. A session that will wait raises `resume-pending`, and the helper claims the session's index entry while the hydrating flag is still raised, which finishes its restore. Then it lowers the flag and runs the eager hook, the resume chain or a login shell. Given `--lazy`, a session with a hook waits on the resume chain whatever the hook's mode; one with none gets its login shell as ever, as does one whose park fails, its hook unfired. A transcript it can't replay, wholly or part way, is kept: the helper writes one line into the session saying where it is, leaves the hydrating flag raised, so no capture replaces the transcript and no clean reaps it, and its claim leaves the restore unfinished; the session is still handed on. That session is not captured until it ends.
- **The resume chain** keeps its draw, wait and recover steps, its keys and its discard. Its tmux calls become flag-file reads and writes. The alternate-screen pin goes. Its processes catch SIGTERM, so a shutdown leaves a waiting session waiting, its transcript saved; the disposition is caught, never ignored, since an ignored one would survive the exec into the user's hook and shell. Esc asks the session's runners to detach to the picker; with no runner attached, it detaches through the backend.
- **Repaint.** zmx sends a session's process group SIGWINCH on every attach, a switch's included, even at an unchanged size, so a waiting panel redraws in the current theme as its session is opened. There is no attach hook, and Portal sends no signal. `TestResumeChainAgainstZmx`, which the weekly zmx check runs, holds zmx to it.

## Bootstrap

Six steps, in this order:

1. Check `zmx` is on PATH and runs, then refuse a zmx directory whose saver is another state dir's, then claim the state directory for the zmx directory Portal runs against (`zmx-dir`, see State), before anything changes. Fatal otherwise. A saver proved another state dir's (see Saver) is sent nothing and nothing in its state changes; this Portal claims no `zmx-dir` and leaves its own latch as it was, writing only its lock and log; and the fatal names both state dirs and the ways out: "The _portal-saver running in this zmx directory saves Portal's state in <other>, not this Portal's state in <this>. Run it with PORTAL_STATE_DIR=<other>, or give it a zmx directory of its own with ZMX_DIR. If the state in <other> is gone, end its saver with zmx kill _portal-saver." It comes before the claim, which would otherwise tie a new state dir to the zmx dir that `ZMX_DIR` is the way out of. A saver that can't be read goes on to the claim and step 4.
2. Remove the `bootstrapped` latch, before anything changes, so a bootstrap cut short anywhere after leaves none and the next command finishes its work. Under `bootstrap.lock` no restore's creates are in flight, so a `restoring` file a bootstrap cut short mid-restore left is removed here too. Fatal if either can't be removed.
3. Sweep orphaned daemons and stale flags: the flags of a session that isn't live, and a hydrating flag on a live session that isn't running restore's helper.
4. Judge the saver running, or end it; mark owed; ensure `_portal-saver`. A saver running is judged first. A saver Portal can't use is ended, and the bootstrap goes on as if none ran. The ensure judges whose the saver is once more under `saver.lock` (see Saver), so one another state's Portal brought up since step 1 is the same fatal, sent nothing. With none, the entries not live are marked owed, before any saver can commit, then the saver is made and judged before the wait for its daemon. Restore runs only once the saver is judged to speak Portal's protocol, so Portal creates no session on a zmx it hasn't proved it speaks. The judgement:
   - Portal's protocol: carry on.
   - Another protocol version: Portal can't use it.
   - No answer to Portal's protocol, but an answer to zmx 0.8.1's framing (its header a packed tag byte and a 4-byte length, its Info record 552 bytes): Portal can't use it, as an older zmx. One probe recognises it; Portal never drives it.
   - Neither: Portal can't judge, and the restore is left unfinished.

   A saver Portal can't use that it finds is ended the same way whatever protocol it speaks: SIGTERM to the one process the process table proves is that session's zmx daemon in this `ZMX_DIR` (its argv naming `_portal-saver` through a daemon-starting subcommand, its `ZMX_DIR` canonically the backend's, its `PORTAL_STATE_DIR` canonically this state dir, each the same every time it is set, its parent launchd, no controlling terminal), that pid alone read again just before the signal and refused unless its parent, terminal, argv and environment read as they did when proved, then a wait, within the kill ceiling, for its socket to go and the daemon to exit, which it does once it has hung up its program and, half a second later, SIGKILLed it, so the end never waits out the program's own shutdown. A daemon gone or exiting by that second read, as another's SIGTERM such as a concurrent `uninstall`'s leaves one, is waited for the same way, not failed. In the proof's scan, a process it can't read keeps the signal back only when its kernel name contains `zmx`, as in the holder proof; the second read and the wait read their one pid whatever the kernel names it. The zmx on PATH never ends a saver found: it may speak another protocol than the saver's daemon. No proof, more than one such process, or a process table that can't be read (off darwin) signals nothing, and the bootstrap fails with its own message for a saver it can neither use nor end: "Portal can't use the _portal-saver session left running on another zmx, and couldn't end it. End it with that zmx (zmx kill _portal-saver), or restart your computer." The judgement's message would send the user to install a zmx, after which every command would find the same saver and fail the same way. A zmx daemon proved but for its `PORTAL_STATE_DIR`, set every time to another absolute directory, is another state dir's saver that step 1 couldn't read through Portal's protocol: it is sent nothing, and the bootstrap, and `uninstall` with it, fails with step 1's refusal naming that state dir, since this message would have the user end it.

   A saver it made that Portal can't use is ended first with `zmx kill`, run by the zmx on PATH that made it and so speaks its protocol, which needs no process table and so works on Linux too, and by the proved SIGTERM when that kill fails. It is fatal with the judgement's message either way, so a zmx Portal can't use on PATH fails every command until the supported one is first on PATH, which the next command then recovers on; a saver it made and couldn't end is then one found, whose fatal tells the user how to end it. A saver it made that is gone at once is a saver down as well as one it can't judge.
5. Write `restoring` just before restore's first create, the saver judged and the owed marks written; restore; remove `restoring` once restore returns, finished or cut short. Fatal if it can't be written or removed.
6. Write the `bootstrapped` latch, last and never after a fatal. A latch it can't write, or a boot id it can't read, is a warning.

The other steps warn and carry on. A pass that leaves the restore unfinished (the protocol not judged, the owed marks not written, the sessions not listed, or the pass cut short) skips steps 5 and 6, so no latch is written and the next command bootstraps again.

- **When.** A command runs the bootstrap when the latch is missing or isn't this boot's and this binary's, when the state dir's zmx-dir record is missing, names another zmx dir or can't be read (the bootstrap records the one in use, or fails naming the mismatch or the unreadable record), or when `_portal-saver` is absent or runs a process other than the one the state dir's `daemon.pid` names, or `daemon.pid` can't be read: a saver that isn't this state's is judged by the bootstrap, never run on warm. A finished bootstrap has waited for its daemon to record itself in `daemon.pid`, so in ordinary use the check owes nothing; a daemon that hadn't recorded itself when that wait ran out owes one more bootstrap, which waits for it again and keeps it. A missing latch is a bootstrap under way, or one cut short or failed before it finished: a Ctrl+C, a closed window or a fatal leaves none, and only a bootstrap that finished writes it. `restoring` owes nothing: the saver and the hook sweep stand down under it, and nothing earlier needs them to, since an entry owed a restore and one that may predate this boot are never dropped, so a saver that commits before restore drops nothing restore will bring back. A logout or a crash ends the saver with the sessions, and the bootstrap brings them back. A warm command reads the latch, the zmx-dir record, the saver's session and `daemon.pid`, reading no process table, and does nothing else.
- **One at a time.** The bootstrap holds `bootstrap.lock` in the state dir, taken before `saver.lock`. A second bootstrap waits, then checks again and skips if nothing is owed. The latch goes before anything changes, so a command started while another bootstrap runs waits for it rather than running warm on half the sessions. A wait past about a second is shown: the picker's loading page leads with "Waiting for another Portal", and a CLI command prints one line to stderr. The wait is bounded by the longest run the holder can make, which grows with the entries `sessions.json` holds and takes restore's retry budget, with one more lookup and session's restore, once; past it the command fails.

The concurrent cold-path picker and its progress page stay, with three labels: Checking zmx, Starting the saver, Restoring sessions `n/m`, and the waiting label ahead of them when there was a wait. A picker quit from its loading page, as on Ctrl+C mid-restore, cancels the bootstrap and waits up to 2 s for it to return, so restore lowers `restoring` before Portal exits; the latch stays absent, so the next command finishes the work. A picker reopened after a detach never runs the bootstrap. The tmux server anchor, hook registration, eager FIFO signalling and stale-marker sweeps go.

## Attach runner

Portal starts `zmx attach <name>` as a child in a pseudo-terminal it owns:
- It puts the real terminal in raw mode and copies bytes both ways unchanged.
- It forwards size changes to the child.
- It watches input for the bound keys, each recognised in both its legacy escape form and its newer encoded (CSI-u) form:
  - **detach:** writes `ctrl+\` to the child, which detaches; the picker follows.
  - **detach to shell:** the same, then Portal exits to the shell.
  - **kill:** detaches as detach does; the picker follows, open on the kill prompt for the session (see Keys). Unsure which session the terminal shows (see Runner registry), the runner first confirms through zmx; unconfirmed, the picker opens without the prompt and flashes why.
- The picker follows when Portal asked for it (one of its keys, or Esc on the resume panel through the registry) and when the attach was taken (see Taking a session). `ctrl+\` and the session ending exit to the shell, as plain `zmx attach` does. zmx ends its client with status 0 for all three and for a detach from elsewhere, so the runner reports a drop when its child so ends with no detach of Portal's own and no `ctrl+\` passed on to zmx, in any of its forms, a press anywhere in the attach counting, and the runner is sure of its session, since a child zmx switched may be dropped from another; an unsure runner's drop exits to the shell. Portal then judges the drop by the session (see Taking a session).
- A switch asked for through the registry ends the attach as detach does, and the session it names attaches next, with no picker between.
- When the attach ends, Portal resets the terminal unless zmx's own reset is known to have reached it. Restoring the terminal (`TCSAFLUSH`) waits for the terminal to take its output, reset or not, and ends early only if the terminal hangs up.
- The picker that follows is the plain one: no filter, no search, no pending command, no bootstrap, even when the first picker carried a pending command or a search, which is spent by then. Picking attaches again, and quitting exits 0. A pick, a switch, the kill prompt's Esc or the taken screen's Enter whose session can't be attached for a fault of its own (gone, held under another spelling, refusing connections or not answering) reopens it, with why, worded as `portal kill` words it; that holds for every pick, the first picker's included. A kill key refused because the runner can't confirm its session reopens it on that refusal, with no kill prompt. A failed kill at the prompt's `y` flashes there, as `k`'s does.
- **Portal inside Portal over ssh.** From a session Portal attached, ssh to another machine and run Portal there, and every key passes through the local runner first: the bound keys act on the local session, never reaching the remote Portal. Nothing is lost, since a detach only detaches and the kill key asks. Documented, not built around: the remote machine's `prefs.json` can bind other keys, which the local runner passes through.
- Every other end exits with the runner's code, silently: the child's, or 128 plus a signal's. zmx attach exits 0 however the session's program ended, so a session's own end exits 0.
- With no terminal to own (input or output isn't one), Portal execs the attach command instead, as before the runner.

### Taking a session

Every attach of a user session, wherever the connector makes one (the first attach, a pick, a switch through the registry, Esc on the kill prompt, Enter on the taken screen), takes it first. Portal's own `_` sessions are never taken.
- **One at a time.** A take of a session holds that session's lock, `state/runners/takes/<stem>.lock`, named by the session's stem as the state dir's per-session flags are, from before its first ask until its own attach's client leads the session (the leader carries the runner's token), within 2 s of the attach beginning, or the attach ends. So no take judges a session while another's attach is still on its way to it, and of two at once the later is left attached; takes of other sessions, as a burst's windows make, hold locks of their own. The wait for another take's hold is bounded by that take's longest hold, each step at its ceiling: its asks of the runners (a request's 2 s deadline and its answer's 0.5 s grace), a read of the leader and of Info, a detach, the 2 s wait for the session to be alone and the 2 s wait to lead, with 5 s over; past it the take goes on without the lock, logged, its attach at worst drawn for the other terminal until its first keystroke. The bound is each waiter's own, from its own start, and the lock serves waiters in no order, so of three takes of a session at once the third may wait out two holds and go on beside the second. The release removes the lock's file, and a take that finds the file it locked no longer the one there locks the one there now, so the lock leaves nothing behind and is never held twice.
- Portal asks every runner on the session but its own process's to let it go, with a `take` request saying where it went (see Runner registry). A runner that accepts ends its attach as taken.
- **Terminals only.** A terminal holds the session while zmx names a client leading it (`LeaderEnv`, naming each variable the leader tracks, set or lacking: a Portal runner's client always tracks `PORTAL_ATTACH`, and a raw `zmx attach` zmx's default list, which is not empty; a raw one started with an empty `ZMX_TRACK_ENV` tracks nothing, so leads answering none, and holds the session only as the process table shows it, which a client zmx switched there it misses), or while the process table shows a `zmx attach` on a terminal naming it in the backend's zmx dir (`AttachClients`) and Info counts a client. Only a `zmx attach` sends zmx its environment: readers (the saver's capture, a preview, a listing's probe, a `zmx run`) send none, so even one zmx makes the leader, as a `zmx run`'s resize can, answers none, and none shows in the process table, so none holds a session. The leader counts a client zmx switched onto the session from another, whose arguments still name the session it left and which no runner's entry names; in the session it left, the count, zero once nothing else is connected there, sets those arguments aside. So no read ever sets a take off, though a take's detach closes every client, a read under way at that moment among them: the saver's capture reads again at its next poll, and a preview keeps what it shows until its next read. Either reading the session as held is enough; one that can't be read leaves it to the other, and with neither saying so and either failing, what holds the session can't be told, so nothing is detached.
- Then, while a terminal holds the session, Portal records where it went and detaches every client through the backend: a raw `zmx attach`, a runner that refused or failed, as another version's does, or one whose child is still going.
- Then it waits, within 2 s, for no terminal to hold the session, detaching every client again at each read that finds one still there, as one that connected since; then it attaches. zmx makes a client the leader as it attaches only while none leads, and sizes the session and draws its first frame for the leader alone, so an attach that began beside another client would be drawn for that client's terminal until its first keystroke. Past the bound it logs and attaches anyway.
- A take that fails anywhere is logged and the attach goes ahead. Nothing is killed and nothing is sent to the session's program.
- **A drop.** A runner whose client zmx dropped while it was sure of its session judges the drop by the session: gone, it ended (zmx removes its socket before it closes its clients), and exits to the shell; live, a take of it recorded since the attach began lands on the taken screen saying where; otherwise the taken screen, saying nothing of where, shows only while another terminal holds the session, and anything else, as a `zmx detach` typed in the session or a session that can't be judged, exits to the shell. Each judgement is logged. A runner unsure of its session judges none and exits to the shell, as one zmx switched onto a session that a take then detaches does.
- **Where.** From the taking Portal's environment, in one place (`tui.WhereFrom`): `SSH_CONNECTION`'s client address as `SSH from <address>`; else `TERM_PROGRAM`'s app as `<App> on this Mac`, `ghostty` named Ghostty; else `another terminal on this Mac`.
- **The record.** `state/runners/takes/<stem>.json` holds where the session's last take said it went and when, each take of it replacing the last, so takes of two sessions at once keep their own. A runner dropped by the backend while its session lives on reads its session's: a take recorded since its attach began says where; anything else says nothing. A record an hour old is read by nothing, and a runner registering removes it, with any lock's file as old that no take holds, which only a take that died holding it leaves.
- **The taken screen.** The picker opens on a modal for the session as its first listing lands, keys typed before then dropped, on a cleared canvas as the kill prompt is, in no destructive colour, since nothing is lost. Its header is `⇄ Open on another device`, drawn as the help modal's title: the glyph `accent.primary`, the title `text.primary`, both bold. Its body is the label, bold `accent.primary`, then a blank line and `Taken by <where>.` in `text.muted` when where is known; its footer `⏎ take it back   space watch   esc picker`. Under `NO_COLOR` the glyph and the bold carry it. Enter attaches the session, taking it back; a session gone by then brings the picker with why, as any pick does. Space opens the preview on it, attaching nothing, and Esc from the preview comes back to the modal; Esc on the modal goes to the picker, its cursor on the session's row. A session no longer listed as the picker opens shows no modal.

### Key config

In `prefs.json`; a missing entry keeps its default:

```json
"keys": {
  "detach": "alt+d",
  "detach_to_shell": "alt+shift+d",
  "kill": "alt+q"
}
```

- A value is one key or a list of keys; an empty list turns the action off.
- A key is `ctrl`, `alt` or `shift` modifiers plus a letter, digit, punctuation mark or `f1`–`f12`. It needs `ctrl` or `alt`, so a binding never swallows plain typing. `ctrl+shift+<letter>` is refused: without the newer encoding it sends the same bytes as `ctrl+<letter>`. `ctrl+\` is refused: it's zmx's. Under Portal it always detaches, since the runner detaches zmx through it, so `ZMX_NO_DETACH_KEY` isn't honoured.
- A binding that doesn't parse, or a key bound to two actions, falls back to that action's default with a WARN; doctor reports it. A `prefs.json` that can't be read keeps every default, with a WARN.
- Read at each attach.
- On macOS the terminal must send Option as Alt for these keys (Ghostty `macos-option-as-alt`, kitty `macos_option_as_alt`, iTerm2's Esc+, Terminal's "Use Option as Meta key", Blink's Option-as-Meta); otherwise Option+D types `∂`, which no binding matches, as it depends on the layout. The README says so.

### Runner registry

zmx doesn't list its clients, so the runners list themselves, taking the part tmux's client list played (`internal/runnerreg`). While it is attached, each runner has an entry in `state/runners/`: `<token>.json` holding its pid and session, and beside it its control socket, `<token>.sock`. It registers once its attach has begun, moves the entry to the next session when a switch attaches it, and removes it when an attach ends any other way. The directory is 0700 and the socket 0600.
- **Which terminal.** zmx already knows which of a session's clients the user is typing in: its leader, the client that last sent keyboard input (terminal replies, mouse and focus events don't count, and a client attaching to a session with no leader becomes it). It routes an in-session `zmx attach <x>` to that client. Portal asks zmx rather than guessing: each runner starts its `zmx attach` with `PORTAL_ATTACH=<token>` among the variables zmx tracks (`ZMX_TRACK_ENV`: the inherited value, else zmx's own default list, plus `PORTAL_ATTACH`), and zmx's EnvGet answers the leader's tracked variables. A leader carrying a token is that runner's terminal; one without is a raw zmx client. A contract test pins Portal's copy of zmx's default list against what zmx tracks for a client that sets none. `PORTAL_ATTACH` and the extended `ZMX_TRACK_ENV` also reach the shells of a session zmx creates through a runner's client (a `zmx attach <new>` typed in a Portal attach), and show in `zmx print-env`. Portal can't strip them, since zmx reads the tracked variables from the client's own environment. They're harmless: Portal never reads its own `PORTAL_ATTACH`, only the leader's, and asks a runner only when its entry names the session typed in (see Switching).
- **Liveness.** An entry is live only when its pid is running and its socket answers as that pid. It is removed with its socket only on proof its runner is gone: its pid not running, or its entry from another boot. Each entry records the boot id its runner registered in, since the state dir outlives a reboot and a recycled pid would keep a dead runner's entry looking alive; an entry naming another boot or none is stale, and a reader that can't read the current boot id judges by the pid alone. Everything else leaves it: a socket that refuses (on macOS a live runner's full listen backlog refuses too) or is missing, an answer from another pid, no answer in time, an entry that can't be read, or a refusal, as the runner may be busy or another version's. Within one boot, a reused pid can so keep a dead runner's entry until the process reusing it exits; that is accepted. A runner sweeps the registry as it registers: stale entries, on any session, and sockets with no entry that refuse a connection. Reading the registry for a session's runners sweeps every session the same way.
- **Socket paths.** A socket's path must fit a unix socket's address, 103 bytes on macOS. A state dir too deep for that holds no runner: the registration fails with a WARN and the attach runs unlisted. A path is never cut short.
- **Control protocol.** A connection carries one request, a JSON line such as `{"version":1,"request":"switch","session":"<x>","deadline":…}`, and one answer, `{"version":1,"ok":true,"pid":…}` or a refusal saying why. Keys match exactly and nothing may follow the line: the caller half-closes after it. A runner refuses another version, an unknown request or field, and a session given to a request that takes none or missing from one that needs it, so a Portal upgraded while attached never acts on a request it doesn't understand. A runner takes a request only while its attach waits to end, and refuses one sent between attaches, once the attach is ending, or past the caller's deadline, so it never takes a request its caller has given up on.
  - `switch`: answered once the runner has taken it, not once the new attach is up. The runner ends its attach as the detach key does, by `ctrl+\` to its child, and attaches `<x>`, as the picker's pick is attached. A target that can't be attached for a fault of its own (gone by then, held under another spelling, refusing connections or not answering) brings the picker, with why, worded as `portal kill` words it. Any other failure ends Portal, as a first attach's does.
  - `detach-to-picker`: ends the attach as the detach key does; the picker follows.
  - `confirm-session`: accepted when the runner's attach under way is on the session named and the runner is sure of it: it has seen no switch since the attach began, or, having seen one, it confirms through zmx as it is asked (see Switched outside Portal). It ends nothing. New windows ask it (see below).
  - `take`: carries the session and `by`, where it went. Accepted when the runner's attach is on the session named, and, unsure, once it confirms through zmx; it ends the attach as the detach key does, and the picker follows on the taken screen saying where (see Taking a session). A runner that doesn't know it refuses it as an unknown request, and the take falls back to the backend's detach.
- **Switching.** `portal open <x>` inside a session, a mint there (created first) and a pick in a picker running there ask zmx for the session's leader. A runner leading is asked to switch, if its entry names the session typed in, and Portal exits 0 once it accepts. Otherwise (a raw client leading, no leader, a token naming a runner on another session, or a runner that can't be reached or refuses) Portal execs `zmx attach <x>`, which zmx routes to the leader. Opening the session typed in does nothing and exits 0: a switch would detach and re-attach it. With the session typed in not answering, it opens nothing and says so (see `AttachCommand`), on the command line and from a pick alike.
- **Switched outside Portal.** zmx can switch a runner's child under it: a `zmx attach <x>` typed by hand in a Portal attach, or the fallback above when the leading runner didn't answer. zmx's client re-attaches in the same process, so the runner sees only its output: zmx's terminal reset followed by its screen clear, with, between them when the switch makes the session it switches to, the line zmx prints for a session it creates, `session "<name>" created` and a newline, the name at most a socket path's length and holding no escape or newline. Nothing else zmx writes falls between them: its logs go to its log file, and the daemon a switch forks writes to /dev/null. Anything else between the reset and the clear is no switch. A zmx inside the session switching its own client writes the same bytes, as one reached over ssh does, since zmx sends a session's output to every client. So on that signature the runner becomes unsure for the rest of the attach, and stays listed.
  - Unsure, the runner confirms through zmx each time it is asked to act on the session it shows: the kill key as it is pressed, a `detach-to-picker`, a `take` or a `confirm-session` as it comes, never when the signature was seen, so zmx has long since seen a client that left. It acts only if the session's leader carries the runner's token, and refuses otherwise: the kill key opens the picker without its kill prompt and flashes why, a request is answered with why. A confirmation leaves the runner unsure; the next asks again. So the runner never offers to kill, detaches or vouches for a session the user has left. This is sound because a client that has left a session can't lead it: zmx clears the leader as its client disconnects, and zmx's client closes the old socket before it writes the reset. When another terminal on the session has typed more recently, a real attach that is unsure is refused: narrow, and failing safe.
  - A switch request is taken without confirming: it reaches a runner only when zmx says its token leads the session typed in and its entry names that session, which proves it still shows it. The detach keys still detach.
- **New windows (`m`).** Portal asks zmx for the session's leader. A leader carrying a token is that runner's terminal, once its entry names the session and the runner accepts `confirm-session`: Portal walks the runner's process tree up to the terminal app. A token the registry doesn't hold or naming a runner on another session, a runner that refuses (between attaches, or unsure and unconfirmed), no leader, or any read that fails opens nothing, saying Portal can't tell which terminal it is running in; a leader whose terminal is on another machine opens nothing as remote. Doctor detects the same way but removes no registry entry, even a dead runner's.
  - Each window runs `portal open` with what its opener resolved by: its `PATH`, its zmx directory and state directory as resolved, and `XDG_CONFIG_HOME`, Portal's path variables and its log settings as the opener has them, a path made absolute against the opener's directory and one the opener lacks unset. A window's shell starts from the terminal's environment, which need not match. `ZMX_SESSION_PREFIX` needs no carrying: Portal removes it from every zmx it runs. `ZMX_SESSION`, `TMUX` and `TMUX_PANE` are removed from the window and from the command that asks the terminal for it.
  - A session counts as the one Portal runs in only when the environment's zmx directory is the backend's; inside a session of another directory, detection takes the route from outside one.
- **Detach to the picker.** The resume panel's Esc asks every runner on the session, all at once. Each request has its own deadline: 2 s after it is sent, or the asker's deadline less the 0.5 s answer grace, whichever comes first. So a runner confirming through zmx (see Switched outside Portal) costs the others nothing. With no runner registered, Esc detaches through the backend, and a raw client goes to its shell; a runner whose pid is found not running as it is asked counts as none. With runners registered and none accepting, nothing is detached, and the panel says why: each runner's refusal or failure.
- **Read-only.** Doctor's read-only registry refuses to ask a runner to switch or to detach, since either moves the user's terminal. Its refusal means do nothing: a caller must not fall back to moving the terminal itself. It still asks `confirm-session`, which ends nothing.
- Known limits:
  - The backend's detach takes every client at once, so detach to the picker uses it only when no runner is registered, and a raw client attached to the same session as a runner stays attached. A take uses it whenever a client is left, since it takes the session from every one.
  - An entry the registry can't read is left out of the session's runners. A session whose only runner wrote such an entry, as a newer binary's during an upgrade, falls back to the backend's detach.
- **No runner** (a raw `zmx attach`, or rootshell's own zmx picker). When the leader carries no token, `m` looks for the session's `zmx attach` processes in the process table: this user's, on a terminal, the kernel naming their executable `zmx`, whose argv names the session as zmx's `parseAttachArgs` reads it (`attach` or `a`; `--labels` with its value or `=`, any number of times, only before the name; no name at all meaning the prefix alone), after `ZMX_SESSION_PREFIX`, with `ZMX_DIR` resolving to the backend's dir. zmx's daemon keeps the argv it forked from but has no terminal, so it is never one. Of those it passes over any carrying `PORTAL_ATTACH`, a runner's own client, and any whose variables zmx tracks for the leader differ from the leader's (a variable the leader lacks must be absent too), so a client over ssh, with `SSH_CONNECTION`, never stands in for a local one. It refuses unless exactly one is left, and when a `zmx` process it would read can't be read, or shows no environment.
  - Known limits: zmx switches a raw client in-process, Portal's own exec fallback included, so the process table still shows it under the session it first attached.
    - When no other raw client names the session it now leads, `m` refuses in that terminal until it attaches afresh. That fails safe, and an attach through Portal's runner is unaffected.
    - When another raw client whose tracked variables equal its own still names that session, the leader is mistaken for that other client. With zmx's default tracked list, local raw clients on one Mac usually share their tracked values, so the windows open on that Mac, though maybe in the other terminal app; they could land on another machine only if `ZMX_TRACK_ENV` drops the SSH variables.

## Commands

- **open:** the resolution chain matches session names, not labels. Exact-name matches come from `List()`. Next, before path, alias and zoxide, comes an exact name whose saved entry is kept: one the next restore would bring back, owed or from before this boot, under a name Create accepts, not Portal's own, with no listed session holding it under that name, nor a live one under another spelling of it (restore skips such an entry, which stays as it is until that session ends). Like a live name, it comes before a path, so `x .notes` brings back a kept `.notes`. `-s` reaches it too; globs, the search form and the picker never do. A target with glob characters, which Create accepts but for a trailing `*`, is first read as an exact kept name, bare or pinned, and expanded over live sessions only when it is none. A name Create refuses, its length aside, is never looked up. It is brought back under `bootstrap.lock`, taken with the bootstrap's bound and wait notice, and judged again once the lock is held: live by then, it is attached; kept no longer, a target opened alone resolves exactly as it would have had it never been kept, a glob-like name as its glob; a burst's trigger, its other windows open by then, attaches only a live session of its exact name. A wait past the bound is the bootstrap's own fatal. A window a burst spawned, its `open` carrying `--ack`, resolves its one target exactly, live or kept, and never as a glob, so it never bursts again; `--ack` beside more than one target is a usage error. Otherwise restore makes it through its own path, as it makes each session it restores, and it is attached. It is one try, with no retry: a failure is one line, "Portal couldn't restore <name> — kept for the next restore: <why>", the entry left kept, and a refusal of a session an older zmx made is the older-zmx fatal. No `restoring` is raised for it: its hydrating flag keeps the saver from capturing it or repaying its entry, and no saver drops a kept entry, while a `restoring` left by a run that died would stand the saver down until a bootstrap no warm command runs. In a burst, a kept name's window runs `open --session <name>`, which takes the same path; the trigger's own connect brings back a trigger the pre-flight judged kept, and attaches any other as it is. Mints use `Create` and record the session in the index (name, dir, created time), then the runner. A generated name always carries a project part, never a bare nanoid. Inside a session, it switches through the registry.
- **picker:** rows from `List()` joined with the index. The filter and the search form match labels as well as names. Grouping uses the index's dir, falling back to the git root of the session's cwd. Kill, rename and preview as settled above; a kill also removes the session's index entry. A session that doesn't answer is listed dimmed and marked as not answering; opening or killing it flashes why. A failed kill or rename flashes and the picker stays open.
- **list, kill, completion, uninstall:** re-pointed to the backend. `list` prints names; `--long` adds label, attached and dir. `kill` of a saved session that isn't running discards it as a kill would, saying so in one line, and exits 0; one whose name another spelling holds removes nothing. It judges such a session again under `bootstrap.lock`, held through the discard, so the discard never races `x <name>`: a session brought back meanwhile is killed as a live one, and an entry gone meanwhile is no session found. Portal's own `_` sessions are no session found too, asking zmx nothing, as every listing hides them. Completion offers names, Portal's own left out. `uninstall` stops the saver through the proved stop (see Saver): SIGTERM, a wait past the 6 s bound, proof again, SIGKILL, then the session kill. Holding `saver.lock`, it waits out an ensure in flight and stops the saver that ensure brought up. A saver the stop can't read because its daemon speaks a protocol Portal can't use is judged and ended as the bootstrap ends one it finds, still holding `saver.lock`, so never in place of a saver a bootstrap makes meanwhile, and reported stopped. One it can neither stop nor end fails with the bootstrap's message for one, which tells the user how to end it. One proved another state dir's is sent nothing, and `uninstall` fails with the bootstrap's refusal of it. It touches no file but that lock and keeps the latch.
- **hook set/rm/list:** the current session comes from `$ZMX_SESSION`. `hook list` keeps its columns, with the session's label as the location. `--pane-key` keeps its name.
- **doctor:** zmx present, the sessions whose daemons speak a protocol other than 1 named, saver up, daemon alive (both failing on a saver proved another state dir's, naming that state dir, by the bootstrap's judgement, which sends nothing), state dir, stale hooks and projects, pending resumes, the kept sessions (an info line naming them; with no saver running, every saved session not live, Portal's own aside, as the next bootstrap marks them all owed; absent when there are none, and when the state's zmx-dir check fails, since the sessions were listed in another dir), key config. A missing saver is a failure while there is anything to save, and info on an install with nothing to save yet. Beside a migration cut short, `sessions.json` fails, naming where the migrated state waits, and `--fix` repairs nothing; beside a saver proved another state dir's, `--fix` repairs nothing either, naming that state dir, since its prune would judge the shared `hooks.json` against a scratch state beside another's sessions. The stale-hooks line reads the sweep's own stand-downs, a mass removal held among them, as not evaluable, saying why.
- **current (new):** prints the current session's label. Works however the session was attached. Outside a session it prints nothing and exits 1.
- **rename (new):** `portal rename <text>` sets the current session's label, its arguments joined with spaces; empty text resets it to the session name.
- **spawn:** spawned windows run with `ZMX_SESSION` removed, so each attaches in its own terminal, and with what the opener resolved its sessions, state and config by. Detection inside a session uses the registry. Each window acks in `spawn-acks/`.
- **migrate (new):** see Migration.

## Migration

`portal migrate` turns the tmux version's saved state into this version's. It is the only code that knows tmux, and carries the little tmux it needs itself: `internal/migrate/tmux.go` is the one production source that runs the tmux binary, and `cmd/migrate.go` the one that builds its client (`internal/migrate/tmux_owner_guard_test.go`). It is exempt from the version 1 stop and from the root's bootstrap, and runs the bootstrap itself once the state is this version's. It takes no flags. One run at a time: a run holds an exclusive lock on the state dir's parent, and another is refused.

**Before it runs.** Upgraded, the path the tmux server's hooks and parked resume chains name is this binary, and they run it until migrate removes them. `portal state notify`, `commit-now` and `signal-hydrate` are hidden, take any arguments and flags, print nothing, log nothing above DEBUG and exit 0, past the version 1 stop and the bootstrap like every `state` command, so no help screen lands over a pane. `state hydrate`, `resume-draw`, `resume-wait` and `resume-recover` handed the tmux version's form, known by a flag only it passes (`--fifo`, `--hook-key`, `--pane`, `--pane-key`, registered hidden), hold before their required flags are checked or their body runs: they draw nothing, catch SIGTERM as the panel does, leave SIGHUP at its default, and on each SIGWINCH exec their own executable with the identical argv. So a waiting pane stays parked with its hook unrun, and after a rollback the tmux version's panel draws again at the next resize. A flag both versions pass means the same in each.

1. **The checks.** Before it touches tmux, migrate makes every check that can be made up front, so a refusal among them leaves the tmux version saving as it did; the daemon's bound and any failure later still stop the run once tmux is touched. The checks read the hooks the plan reads (the backup a run cut short kept, else `hooks.json`), decoded as strictly as the tmux version read them; `hooks.json` beside a backup, which must be byte for byte the backup or a file a run's rewrite wrote from it, since anything else holds hooks registered since, as after a run cut short and a rollback to the tmux version, which the rewrite would lose: the run is refused, naming both files, and told to keep the hooks wanted in `hooks.json` and move the backup aside, so a re-run backs it up afresh; `state/`'s version 1 index, read as the plan reads it; and zmx's session list. Neither file can pass now and fail later: the tmux version's writers refuse a `hooks.json` that doesn't parse, and its daemon's last flush writes an index the plan reads again.
2. **The tmux side.** When a tmux server answers (plain `tmux`, so the server `$TMUX` names when run inside one of its sessions, otherwise the default socket's), migrate reads Portal's global hooks event by event on the nine events the tmux version managed, since the whole-scope `show-hooks -g` doesn't list the `pane-*` and geometry `window-*` ones. It unsets each hook whose command holds one of the tmux version's fingerprints (`portal state notify`, `commit-now`, `signal-hydrate`, and the older `migrate-rename`) by its index, in the order listed: tmux's hook arrays are sparse, so an unset moves no other hook. Every other hook is left. Then it kills `_portal-saver` by its exact target, `=_portal-saver:`. tmux and its other sessions keep running. With no server answering there is nothing to unset or kill: they ended with it. A hook it can't unset, or a saver it can't kill, stops the run with nothing written.
3. **The tmux version's daemon.** Killing the saver sends its daemon tmux's SIGHUP, which starts its final flush into `state/`. Migrate waits for the daemon `state/daemon.pid` names to exit, within 30 s, reading it every 50 ms; it signals nothing. Each read proves the pid the daemon, its argv a `portal state daemon`'s; a pid naming no process, or another process, has exited. The tmux version never bounded that flush: it waits up to 5 s for commit.lock, then captures every pane and commits, a tmux call or two and a file write a pane, so 30 s covers the lock's whole wait and a capture pass of some 40 panes at half a second each under load. A daemon still running at the bound, or one whose process can't be read until then, stops the run with nothing written; Portal's tmux hooks are gone and its saver stopped by then, so the tmux version saves nothing more on its hooks, and the next run waits again. The refusal says whether a saver was stopped: with none to stop, the daemon got no SIGHUP from migrate. No `daemon.pid`, or one that isn't a number, names no daemon.
4. **hooks.json's backup.** `hooks.json` is read and decoded again, then copied byte for byte to `state/hooks.json.tmux`, unless that file exists: a backup is never overwritten, since a run cut short may have rewritten `hooks.json` since. A fresh backup first removes any `state/hooks.json.tmux.rewrites`, which belonged to a backup moved aside, so no earlier rewrite's digest vouches for `hooks.json` against it; removed first, a run that dies between the two leaves no backup beside a stale record. No `hooks.json` makes no backup.
5. **The plan,** from `state/`'s version 1 index, read again now the daemon has flushed, and the backup's keys, its names clear of every session zmx listed and judged by the backend's rule (below).
6. **The build,** into a fresh staging dir beside `state/`, `state-migrating/` (`state.MigrationStagingDir`), wiping first any a run cut short left: the new `sessions.json` and each session's scrollback, copied.
7. **hooks.json's rewrite,** from the backup by the plan, in one atomic write under its lock, every value byte for byte. It never reads the live file, so every run writes the same file. Before the write lands, the file's SHA-256 is added to `state/hooks.json.tmux.rewrites`, one digest a line, so a later run knows it as a rewrite's; a digest that can't be recorded writes nothing. No backup writes nothing.
8. **The commit point.** `state/` is renamed to `state-tmux/` (`state.TmuxStateDir`), then the staging dir to `state/`, the parent dir synced after each; a sync that fails is a warning, the rename having landed. Nothing logs between the two renames, since every Portal process's log makes the state dir for its own file.
9. **Bootstrap, then report.** The bootstrap is the one any command runs: none when none is owed, so a re-run forces no restore.

Until the commit point `state/` is still version 1, so every other command stops on it and the zmx saver and hook sweep stand down; a run stopped anywhere before it is redone whole by the next, with a fresh plan. A failure that stops a run says what a re-run does: starts over once the run has gone past its checks, finishes the migration once `state/` is renamed; and, once the run unset Portal's tmux hooks and stopped its saver, that tmux isn't saving. Between the renames `state/` holds no index of the migrated sessions, and a bootstrap would start the saver on it while the hook sweep, with `state-tmux/` there, reaped every rewritten key. So while the staging dir holds anything beside `state-tmux/` (`state.MigrationCutShort`, the one check all of them make), every command but the state check's exemptions stops with one line, "<staging dir> holds a migration cut short; run portal migrate to finish it", the daemon refuses to start, the hook sweep stands down under `index-unusable`, doctor fails its `sessions.json` line saying where the migrated state waits, and `doctor --fix` skips every repair. A check that can't tell counts as cut short. What a run finds decides what it does:

| What migrate finds | What it does |
|---|---|
| a version 1 `state/`, no `state-tmux/` | migrates in full |
| `state-tmux/` and a staging dir holding anything, `state/` absent or holding no `sessions.json` | finishes the second rename, bootstraps, reports |
| `state-tmux/` and a version 2 `state/`, no staging dir | skips to the bootstrap and reports |
| `state-tmux/` beside a version 1 `state/` | refuses, naming both: move `state/` aside and keep `state-tmux/`, from the earlier migration; moved aside instead, the next run would back up the rewritten `hooks.json` and strip every key it moved |
| a staging dir beside `state-tmux/` and a version 2 `state/` | refuses, naming both, deleting nothing: something wrote `state/` between the renames |
| `state-tmux/` beside a `state/` absent or holding no `sessions.json`, and no staging dir | refuses, naming both: no run leaves that, since every build writes an index |
| no `state/` and no `state-tmux/`, or a version 2 `state/` with no `state-tmux/` | nothing to migrate, exit 0, no bootstrap |
| a `sessions.json` that can't be read | refuses |

A `state/` found beside `state-tmux/` and a staging dir is one a log made between the renames, of a run cut short or of the re-run itself. The staging dir's entries are moved into it, `sessions.json` last, beside Portal's logs and what a move cut short already brought (the scrollback dir and `commit.lock`, which staging then no longer holds); anything else in it is refused, naming it and where the migrated state waits. An empty staging dir, all but itself moved by a move cut short as it ended, is removed.

**Sessions.** One for each tmux pane, in the order version 1 saved the sessions, each session's panes in window order then pane order.
- The name is the whole tmux name, trimmed, when Create accepts it and it is free. zmx accepts spaces and `·`, so `dotfiles-PpaTER · user-search` comes across as it is.
- A name Create refuses is made compatible, not replaced. Each character zmx refuses (`zmx.RefusesRune`, the rule on single characters `ValidateName` applies: `/`, NUL and control characters) becomes `-`, a run of `-` that joins one collapsing to a single `-`, and a `-` or space it would start with is dropped. A name too long (`backend.ErrNameTooLong`) is cut to fit, a character at a time, never ending in a space or punctuation. Only a name with nothing left, or one Create still refuses, such as the reserved `logs` or a trailing `*`, falls back to a generated `{project}-{nanoid}`, the project the entry's dir's last part. So `flow-v1-api-fv1-45/27` becomes `flow-v1-api-fv1-45-27`.
- A name that clashes, folding case, with a live zmx session, an entry, an earlier migrated session or an earlier pane's numbered name, keeps its stem and takes a fresh nanoid: a trailing `-<nanoid>` of a pane token's width is dropped from a name holding no whitespace, then `<stem>-<nanoid>`, the stem cut to fit, drawn again while taken. A name holding whitespace was typed, not generated, so its ending is kept whatever its shape. So a clashing `folio-bGDWc0` becomes `folio-<new id>`, a clashing `kit` becomes `kit-<new id>`, and a clashing `kiln · user-search` becomes `kiln · user-search-<new id>`.
- A tmux session's other panes become `<name>-2`, `<name>-3`, and so on, on the final name, a taken number skipped for the next. A numbered name too long takes a fresh nanoid on the first pane's stem instead.
- The label is the full tmux name, the tmux name with its number for a further pane, omitted when it is the name, and dropped, saying why, when the index refuses it. So a name that comes across unchanged stores no label, and `flow-27 · api`, made of `flow/27 · api`, is labelled `flow/27 · api`.
- The entry's dir is `session.GroupingDir(cwd)`, the cwd's git root as a canonical key, else the cwd; its cwd is the pane's.
- A pane's scrollback file, when found, is copied to the file this version names for the session's creation, taken to be version 1's `saved_at`. One named but gone, outside the state dir or not a regular file is reported, and the session made without it.
- A tmux session with no panes is skipped, saying why.
- Every entry is owed a restore, records no creation, and is marked `resume_lazy`.

**Hooks.** Only token keys are carried: a key that is a saved pane's `@portal-pane-id` moves to the name of that pane's session. On the tmux version restore fired a hook by its saved token alone, so a pre-token key (`<session>:<window>.<pane>`, `<@portal-id>:<w>.<p>`, `%N`) hasn't fired since tokens arrived, and its coordinates name whatever pane sits there now. Those, a token no saved pane carries and any other key are removed from the live file, kept in the backup, and listed in the report with what each was.

**The first restore waits.** The tmux sessions still run their programs, so an eager hook firing at once would resume the same conversation twice. Restore passes the helper of an entry marked `resume_lazy` `--lazy`, and the helper parks a session with a hook on its resume panel whatever the hook's mode; one with no hook restores as any other. The mark ends when the entry is repaid: at the helper's claim, which finishes the restore, or a saver's claim once the hydrating flag is down. Later restores take the hook's mode. Until then it rides every restore the entry is owed: `x <name>` bringing back a kept migrated entry parks it too, an entry whose restore failed keeps it for the next, and one whose claim never comes stays owed and lazy. Owing an entry again never sets it. A park that fails under `--lazy` (the executable unresolved, the `resume-pending` flag not raised) never fires the hook: the session gets its login shell, with one WARN saying why.

**Report.** A summary line, then the restore, then a block each, those with nothing to say left out: the sessions left to restore; every session, its name unchanged or not, as `tmux name → name`, old on the left and new on the right, its window and pane named when its tmux session made more than one (`ws-folio-dev (window 1, pane 2) → ws-folio-dev-2`), under "Sessions (tmux name → name):"; names made compatible, as `tmux name → name: why`, in plain words (`'/' isn't allowed in a session name, so it became '-'`, `too long, so it was cut to 75 characters`, `kit was taken, so it has a new id`), a numbered pane carrying its first pane's; labels dropped and why; sessions skipped and why; scrollback not carried and why; hooks moved; hooks removed and what each was; then where `state-tmux/` and the backup are. A run that skipped to the bootstrap says what it can: the restore and where the backup is.
- The restore's line says how it ended: the sessions it made; the sessions made before the bootstrap's fatal stopped it, or that the fatal came first (the fatal follows the report); or that it couldn't read `sessions.json` or list zmx's sessions (the bootstrap's warning says which). A bootstrap owed none says nothing of it.
- What it left is read from the index after the bootstrap, never assumed: each entry still owed whose session zmx doesn't hold, by name, under "N sessions left to restore. x <name> brings one back now; otherwise they come back at the next restore after a reboot"; after a restore the bootstrap's fatal stopped, "N sessions left to restore. Once the error below is fixed, x <name> brings one back; otherwise they come back at the next restore after a reboot"; or, with none, "Every saved session is restored." An owed entry zmx holds is restored, its helper finishing. An index that can't be read then says so.
- "Each migrated session with a resume hook waits on its resume panel the first time you open it" shows when an entry marked `resume_lazy` has a resume hook, read before the bootstrap, since a helper finishing its restore clears the mark. A character a terminal wouldn't show as itself is escaped. Every line migrate shows, refusals included, is a constant in `internal/migrate/copy.go`. The tmux sessions stay until Lee ends them.

Kit follow-ups at switch-over: `session-label` moves to `portal current` and `portal rename`, and the `xc`, `xcc` and `xcr` aliases take `--name "$(portal current)"`.

## Phases

1. Golden frames for today's screens. Backend interface, zmx driver and `zmxtest`. open, picker, list, kill, completion, hook, current, rename and doctor on zmx. No save or restore yet. ## Risks to watch

- **macOS only.** Portal ships for darwin alone. Off darwin the process table can't be read, so no proof holds: `uninstall` can't stop the saver, and after an upgrade the old saver can't be replaced, so every command bootstraps again and warns until a reboot. Linux needs a process reader from `/proc` before it ships.
- **zmx bugs:**
  - #294: crash on session exit on macOS.
  - #295: part of the scrollback lost on reattach.
- **Sessions started by zmx 0.8.1** speak the older protocol and don't answer Portal: they list as not answering until killed. A zmx 0.8.1 on PATH (Homebrew's tap shipped it until 1.0.0) is refused by every create, whose session answers 0.8.1's framing and is ended by its own `zmx kill`: the saver's at the bootstrap, before restore makes anything, a restore's under a saver found, and a mint's, warm or from the picker. So the next command with the supported zmx first on PATH recovers. A saver left behind is ended by the proved SIGTERM on macOS, its proof targeting only `_portal-saver`; off it, or without the proof, every command fails telling the user to end it with that zmx or restart. A 0.8.1 daemon waits on each of Portal's frames for payload that never comes, so a connection carries one frame, enforced in the driver: a second would complete the first and be read as frames of its own.
- **A zmx built with the hardened runtime**, as the bundling fallback (below) would sign one, has its environment hidden by macOS, and both process-table proofs then degrade: its sockets' holders count only by the name their argv starts, and none of its daemons can be proved, so a saver on it can't be ended by signal. Bundling must keep zmx's environment readable, or these rules be revisited.
- **The kernel's name for zmx.** A process the process table can't read stops a proof only when its kernel name (`p_comm`) contains `zmx`. `p_comm` is the basename of the executable with its symbolic links resolved, truncated to 16 bytes, so a bundled zmx, the bundling fallback, must have `zmx` in the first 16 bytes of its name: otherwise one unreadable is skipped, and a refusing socket it holds can read as stale.
- **What zmx's history returns for a session showing the alternate screen** (the resume panel, an editor, a pager): that screen alone, led by its modes. Waiting sessions are skipped, and the saver skips any capture of the alternate screen. A zmx that changed this would change what a saved transcript holds.
- **zmx's release.** Portal runs on official zmx 1.0.1 (6 Nov 2026). 1.0.0 was the first release to carry protocol 1, and zmx's changelog says v1 freezes the IPC contract, but its published macOS builds carried Linux's ioctl numbers: zmx cross-compiles its releases on Linux, and the release step translated `src/c.h` once, for the host. A session on them never resized. 1.0.1 translates per target (zmx #308). Homebrew's tap installs zmx's own release build, which is ad-hoc and linker-signed, without the hardened runtime, so its environment stays readable. A fault in how a release is built shows only in the published build, which is why the weekly check tests that and not a build of the release's source.
  - **No zmx 0.8.1 support.** The driver speaks protocol 1 only. 0.8.1 is another wire format (no version byte, a length where protocol 1 keeps the version), and it lacks fixes Portal's flow needs: the snapshot on attaching to a session started detached, leader selection, and input dropped on hangup. Portal recognises a 0.8.1 daemon only to refuse it.
  - **If zmx's releases stop serving Portal,** Portal bundles a pinned, unmodified upstream build of zmx, never a second codec. The hardened-runtime and kernel-name risks above hold for it.
  - **Version dispatch only once protocol 2 exists.** When zmx ships a protocol 2, Portal builds per-session codec dispatch, so an upgrade with sessions still live on the older daemons keeps working. Until then, one protocol.
