# CLAUDE.md

Guidance for agents working in this repository. The code is the source of truth for how things work; this file holds what the code won't tell you quickly: how to build and test without damaging the developer's machine, where things live, and the invariants that look removable but aren't. Most mechanisms carry doc comments and source guards that explain and enforce their own rules — read those at the named site before changing one.

## Build & Test

```bash
go build -o portal .                        # build binary
go test ./...                               # unit lane: fast, hermetic
go test -tags integration -p 1 -timeout 30m ./...   # integration lane: real zmx + daemons + built binaries; -p 1 is REQUIRED
go test ./cmd -run TestOpenCommand_PathArgument_SkipsTUI   # single unit test
go test -tags integration ./cmd -run TestPortalBinaryZmxMissing   # single integration test
golangci-lint run                           # lint (config sets the integration tag, so tagged files are covered)
scripts/zmx-build [ref]                     # build the zmx commit pinned in scripts/zmx-commit (or a tag, branch or commit) into .cache/zmx/<commit>/zmx; the zmx integration tests need the pinned one
```

- **Lane rule.** Any test that *builds* a `portal` binary, spawns a `portal state daemon`, execs a built `portal` binary or runs a real zmx (`zmxtest.New`) carries `//go:build integration`. The unit lane's one real-tmux file is `internal/migrate/tmux_realtmux_test.go`: migrate's tmux client against disposable `tmuxtest` servers (`-S <tmpdir>/ptl-*/s`) — no daemons, no portal binary. Build `portal` in a test only through `internal/portalbintest`, which builds with `-tags integration` and so compiles in the daemon-pgrep sandbox; never hand-roll `go build`.
- **`-p 1` is load-bearing.** The only CI is the weekly zmx check (below); daemon-timing suites flake when packages run in parallel on one machine.
- **`-timeout 30m` too.** `./cmd` alone takes about 10 minutes under load, and a package timeout kills the test binary before its cleanups run, leaking `zmxtest` daemons and the portal processes under them.
- **No `t.Parallel()`.** `cmd` injects mocks through package-level mutable state. Stage `*Deps` structs with the `withXDeps(t, …)` helpers and function-var seams with `withFuncSeam(t, &seam, fn)` (both in `cmd/testhelpers_test.go`, both self-restoring). `cmd/seam_guard_test.go` fails any test that assigns a seam directly.
- `golangci-lint` cannot see files gated `//go:build !integration`. It is not wired into CI. There is no code generation.
- **Weekly zmx check** (`.github/workflows/zmx-check.yml`, macOS, Mondays and on dispatch). zmx is a Homebrew dependency that upgrades freely, so it builds zmx's latest release and main with `scripts/zmx-build <ref>` and runs every test that runs a real zmx (`internal/backend/zmx`, `internal/runner`, `internal/saverhost`, `internal/spawn`, `internal/vtcapture`, `internal/restore`, `internal/portaltest`, `internal/zmxtest`, and `cmd`'s, each named `*AgainstZmx`) on each. It is enforced where a test takes a real zmx: `zmxtest.Binary`, which `New` calls, fails any test the workflow doesn't run (its package, the test binary's directory, and its top-level name against the line's `-run`), naming the line it needs (`internal/zmxtest/weeklycheck.go`). The workflow's parse is strict: each `go test` line may hold only `-tags integration` (required), `-p 1`, `-timeout <d>`, one single-quoted `-run` pattern with no `/`, and `./` packages, and must sit in a `run: |` block holding only `go test` lines; `GOFLAGS` or `working-directory` anywhere in the file, an inline `run: go test`, or anything else fails every zmx test with "can't judge". The release leg skips with a notice while the release is no newer than the pin. A failed run is the alert; it posts nothing. Locally, `PORTAL_TEST_ZMX_BINARY=<absolute path to a zmx>` points `zmxtest.Binary` at another build; a test fails if it isn't an executable file named `zmx`.

### Visual capture harness

`cmd/capturetool` is a separate offline program (not a `portal` subcommand) that renders a named deterministic TUI fixture through `tui.Build` with the backend and every remaining seam faked (`internal/capture`, test-only, so the production binary never links it). It is the only way to see a visual change before release — a scratch build of Portal disturbs the running daemon and touches real state.

```bash
go run ./cmd/capturetool --fixture <name> [--theme <slug|path>]          # live view; capture.FixtureNames() lists fixtures
go run ./cmd/capturetool --fixture <name> --print [--ansi] [--size WxH]  # its frame once, as text or in colour
go run ./cmd/capturetool --frames testdata/vhs/frames [names…]           # regenerate golden frames (all without names)
vhs testdata/vhs/<tape>                                                 # re-capture a still
```

- **Golden frames.** `testdata/vhs/frames/` keeps a `.txt`/`.ansi` pair per fixture, standalone surfaces included, drawn in `tokyo-night` at the size in the stem (`sessions-flat-120x40`). `internal/capture`'s frame tests hold every fixture to its frame cell for cell: glyph, colours, bold and hyperlink. They also check each fixture draws the same twice.
- **The terminal background.** An unpainted cell shows whatever background the screen sets. The picker fixtures and the swatch set their canvas with OSC 11, so there it counts as the canvas. The resume surfaces and colourless fixtures set none, so there it matches only an unpainted cell.
- **Regenerating.** A change that alters a screen regenerates its frames with `--frames` in the same change. Never edit a frame by hand; an unintended frame change is a regression to fix, not a frame to rewrite. A new fixture keeps a frame from the start.
- **Nothing personal, nothing from the environment.** Fixture data is invented: no real project or person names. Fixtures pin their home directory through `tui.Deps.Home`, so no frame reads `$HOME`, and the capture tests refuse to run with wide East Asian widths (`capture.RunNarrow`).
- `testdata/vhs/*.tape` and `*.png` are scaffolding: written while work is in progress, deleted after sign-off. `testdata/vhs/reference/*.png` are committed design exports and are kept — nothing in Go points at them, so a sweep must not treat them as orphans. Retention table: `testdata/vhs/README.md`.
- Fixture definitions in `internal/capture` are permanent: the swap-and-diff completeness guard enumerates them, so deleting one silently shrinks coverage. Standalone surfaces that aren't picker fixtures (contrast swatch, resume panel screens) are enumerated through `capture.StandaloneNames()`; a new one joins every guard at that one edit.

## Test safety — ABSOLUTE INVARIANT

**A test must never mutate or affect the real system:** not the filesystem outside its temp dirs, not the developer's zmx sessions or tmux server, not any process it did not spawn. Tests run on the developer's machine, where their live sessions, `_portal-saver` and `portal state daemon` are always running, and the installed tmux Portal's server and daemon may be too. All six boundaries are mandatory:

1. **Filesystem/state.** Any test that runs `portal state daemon` — directly or via `portal open`/bootstrap — calls `portaltest.IsolateStateForTest(t)` and sets the returned env on every subprocess (`cmd.Env = env`). It scrubs `HOME`/`XDG_CONFIG_HOME`, poisons `TMUX` and `ZMX_DIR` (dropping `ZMX_SESSION` and `ZMX_SESSION_PREFIX`), enables the pgrep sandbox, and registers a fingerprint-diff cleanup. The fingerprint is defence in depth, not a substitute: it walks the state dir under the scrubbed `HOME`, so it catches a process that took the scrub and still resolved the default path, not one that escaped the scrub.
2. **Command bodies.** A test that Executes a real Cobra command body inherits its production wiring, which reaches the developer's real sessions, saver and processes, so stage every seam the body touches: the backend (`withBackendDeps`), the bootstrap (`withBootstrapDeps`) and any other `*Deps`. `cmd`'s `TestMain` makes every missed injection fail loudly: it poisons `ZMX_DIR` (item 4), `TMUX` and every `PORTAL_*` path, and makes `bootstrapExe`, `signalProcess`, `osExit` and the terminal adapters panic. A test asserting inside/outside-a-session behaviour stages it (`backendtest.Fake.SetCurrent`, or `ZMX_SESSION` with `t.Setenv`), never inheriting it. *(Incident, from the tmux version: an uninjected command body killed the developer's live `_portal-saver` and unregistered their global hooks on every `go test ./cmd`.)*
3. **Processes.** The daemon is identified machine-wide by argv (`state.PortalDaemonArgvPattern`: `portal state daemon`, the program bare or at an absolute path whose base name is `portal`, no space in the path) and `ucomm`, so file isolation does not make a test daemon distinguishable from the real one, nor the zmx Portal's from the installed tmux Portal's. Production never signals on argv alone: the orphan sweep, the saver's stop and the end of a saver Portal can't use each prove their target from its environment first (see Server bootstrap). `state.PgrepPortalDaemons` is further filtered by a default-deny sandbox (`internal/state/pgrep_sandbox.go`, integration-tagged, absent from production) that surfaces only test-registered daemons, and reaches test-spawned binaries through `state.SandboxRegistryEnv` (`PORTAL_TEST_SANDBOX_REGISTRY`), a file of test-owned state dirs. Never run the production orphan sweep, `PgrepPortalDaemons`, or any `pgrep`/`pkill`/broad signal in a test without `IsolateStateForTest` active. A test signals only a process it started, through `proctest`, or a zmx daemon `zmxtest` proves its own (item 4). *(Incident: a global-pgrep sweep test repeatedly SIGKILLed the developer's live daemon.)*
4. **zmx.** Only per-test directories from `zmxtest.New` (`/tmp/zx-*`), never the developer's `ZMX_DIR`, which their shell exports. Every package whose tests run zmx has a `TestMain` that sets `ZMX_DIR=zmxtest.PoisonedDir` and unsets `ZMX_SESSION` and `ZMX_SESSION_PREFIX`, and every package whose tests exec a portal binary hands it the same through `IsolateStateForTest`'s env. The poison sits under `/dev/null`, so a missed injection fails loudly with ENOTDIR rather than listing no sessions; a subprocess that needs sessions appends its own `ZMX_DIR` (last wins); `zmxtest.New` fails, not skips, without the pinned build (or the one `PORTAL_TEST_ZMX_BINARY` names) or the poison. A test never signals a zmx daemon it didn't start: teardown proves ownership by `ZMX_DIR=<dir>` in the process's environment, or in an ancestor's (macOS hides a platform binary's environment, `/bin/sh`'s included); a chain ending at pid 1, a read error or a repeat proves nothing, so a reparented orphan leaks rather than risk a wrong kill. It reads with `kern.procargs2`, re-proves before each signal, and fails when it can't read processes. By hand, prefix every `zmx` command with a scratch `ZMX_DIR=`. A session's shell is a login shell, so macOS's `path_helper` puts `/opt/homebrew/bin` ahead of the pinned build's directory: a line a test types into a session that runs zmx (a `portal` included) sets `PATH` itself, or it runs the developer's installed zmx.
5. **Terminal windows.** A test never asks the developer's terminal for a window. Detection walks a test's own ancestry to that terminal whatever the environment says, so every package whose tests reach adapters calls `spawn.PoisonAdaptersForTest` in its `TestMain` (`cmd` and `spawn` also scrub `spawn.IdentityVars`), making every adapter panic. A `spawn` test whose adapter runs only programs of its own lifts it with `realAdapterExec(t)`. Integration builds, the portal binaries tests build among them, run an adapter program only from a directory named in `spawn.AdapterSandboxEnv` (`internal/spawn/adapter_sandbox.go`, absent from production): an integration test opens windows through a `terminals.json` recipe (`withRecipeTerminal`) whose script, in a directory it registers, hands it the command.
6. **tmux (portal migrate only).** Only `portal migrate` runs tmux (`internal/migrate/tmux_owner_guard_test.go`, within the reach Architecture states), and only its tests, migrate's and `cmd/migrate_*_test.go`, import `tmuxtest` (`internal/tmuxtest/leaf_guard_test.go`). Those use only per-test `tmuxtest` servers (`-S <tmpdir>/ptl-*/s`, `-f /dev/null`), never the default socket: migrate's client reaches one as `migrate.Tmux{Socket: …}`, and a built portal through `TMUX=<test socket>,<pid>,0` appended after the isolated env (last wins). Plain `tmux` honours `$TMUX`, so migrate's and `cmd`'s `TestMain`s poison it, `IsolateStateForTest` poisons it for subprocesses, and `cmd`'s makes the production `migrateTmux` panic, leaving `MigrateDeps.Tmux` the only way in.

For a daemon in a test, use `portaltest.StartSaverDaemon` (integration-tagged): it runs `IsolateStateForTest`, the teardown guard and `zmxtest.New` in that order, starts `_portal-saver` running the built binary with only the isolation's env (`zmxtest.WithEnv`), and stops it through proved signals; `portaltest.NewSaverDir` is the same directory and state with no saver, for a test that brings the saver up itself. `IsolateStateForTest` points every per-file and per-dir `PORTAL_*` path into the scratch config. Reap any subprocess a test spawns with `portaltest.RegisterSubprocessCleanup` (SIGKILL + Wait + reap — on macOS an unreaped subprocess holds state-dir fds past cleanup). Fixtures whose sessions can host writers at teardown also call `portaltest.RegisterStateDirTeardownGuard(t, stateDir)`, after `IsolateStateForTest` and before `zmxtest.New` (or `tmuxtest.New`). Integration tests that set `PORTAL_LOG_LEVEL` assert it propagated with `portaltest.AssertLogLevelResolved`.

### Cleaning up after a test run (human-invoked; never from a test)

Test runs leak `zmxtest` daemons with the portal processes under them, portal migrate's tests can leak `tmuxtest` servers, and an agent faking CPU load can orphan `yes`/busy loops to PID 1. Leaked load manufactures timing flakes and gets them blamed on the code under test, so sweep after a session that ran the integration lane, and before trusting any timing result while the load average is far above core count. The developer's own sessions, saver and daemon must never be touched.

For zmx, test dirs are `/tmp/zx-*`. Tests whose runners register keep their state dirs (`/tmp/ps-*`, `/tmp/rr-*`) short for the sockets' 103-byte limit and remove them at cleanup; the portal processes behind them carry the test's `ZMX_DIR`, so the listing below finds them. List bound processes with `ps -x -ww -E -o pid=,command= | grep -F "ZMX_DIR=/tmp/zx-"` and treat the developer's own (`ZMX_DIR=$HOME/.local/state/zmx`) as protected. For each leaked dir run `ZMX_DIR=<that dir> <zmx> kill '*'` with `$(scripts/zmx-build)`, never without the prefix. Unit-test fake daemons also use `/tmp/zx-*` dirs but start no processes. Re-check each remaining pid's `ZMX_DIR` right before a SIGTERM, SIGKILL stragglers, remove the dirs, then confirm the developer's sockets and daemons are unchanged.

For tmux, the developer's server must never be touched:

1. Read `$TMUX` (`<socket>,<server-pid>,<session-id>`), or the default socket's server pid outside tmux. That socket and PID are protected.
2. Select targets by an explicit test socket in argv (`-S <tmpdir>/ptl-*/s`). The real server carries no socket flag. Never match on `tmux` or session names — those exist on both.
3. Exclude the protected PID explicitly and assert it is absent from the kill list.
4. Re-verify each PID's argv immediately before signalling it (PIDs get reused).
5. SIGTERM first, SIGKILL stragglers. Afterwards confirm the developer's server is alive with its session count unchanged.

For load generators, match the exact command (`ps -eo ppid,command | awk '$1==1 && $2=="yes"'`), never `pkill -f yes`. Better not to create them; if load is needed, bound it (`timeout 60 yes`).

## Architecture

Cobra CLI + Bubble Tea v2 TUI + Lipgloss v2, over zmx (see `docs/design/zmx-backend.md`). `main.go` → `cmd/root.go` → subcommands. `PersistentPreRunE` runs:
1. the `sessions.json` stop, refusing a version 1, corrupt or newer index, or a migration cut short between its renames (`state.MigrationCutShort`), which the daemon refuses to start on too (every command but `version`, `doctor`, `current`, `migrate` and the `state` tree);
2. for the exempt commands that write state (`exemptStateWriters`: `hook set`, `hook rm`, `rename`), the bootstrap gate's `zmx-dir` check, recording nothing (`refuseOtherZmxDir`, the fatal `ZmxDirOwner.Refusal` names; doctor's `--fix` makes the same check after its diagnosis);
3. the `bootstrapExempt` check (`__complete`, `alias`, `current`, `doctor`, `help`, `hook`, `init`, `migrate`, `rename`, `state`, `theme`, `uninstall`, `version`; a match anywhere in the parent chain exempts);
4. for `open`, the zmx binary lookup;
5. `bootstrapFor`.

`bootstrapFor` runs the bootstrap a command owes (see Server bootstrap). Commands reach zmx through `cmd/backend.go` (`withBackendDeps` in tests; `userSessions` hides `_` names). Only `portal migrate` knows tmux: `migrate.Tmux`, built only by `cmd/migrate.go`'s `migrateTmux`; nothing else runs the tmux binary (`internal/migrate/tmux_owner_guard_test.go`: a Go string literal naming tmux as a word, in any case, appears only in the files it lists, and of those only migrate's client and tmuxtest hand one straight to an exec call; its doc states the reach). Across the module, only `cmd/state_daemon.go` (the idle-tick sweep) and `cmd/doctor.go` (the count, and `--fix`'s prune) may reach `hooksweep` or `(*hooks.Store).CleanStale` (`cmd/hook_sweep_caller_guard_test.go`, judged by type-checked object).

### Commands

- **`open`** (`cmd/open.go`; the `x` shell function from `portal init`) — the main entry. A bare positional runs the resolution chain (exact session → kept saved session → glob → path → alias → zoxide) and creates or attaches, through the attach runner (see Connecting to a session below). A kept saved session (`restore.Kept`: owed or from before the boot, held by no listed session under its name nor a live one under another spelling, not Portal's own, under a name Create accepts) is brought back under `bootstrap.lock` and attached (`cmd/open_kept.go`). Judged again under the lock and kept no longer, a target opened alone resolves as if never kept, a glob-like name as its glob; a burst's trigger, its other windows open by then, attaches only a live session of its exact name. `-s` reaches it, and a name with glob characters is read as that kept name before its glob. `-s/-p/-a/-z` pin one domain and hard-fail on a miss; `-f` opens the picker pre-filtered; no args opens the picker. A positional starting with `/` and containing no further `/` is the **search form** (`resolver.IsSearchSigil`, `cmd/open_search.go`): never resolved, composes with nothing. Two or more targets, or a glob that may expand to two, run the multi-target burst (`cmd/open_burst*.go`; see Multi-window spawn), as the picker's `m` does. The hidden `--ack <batch>:<token>` is a spawned window's receipt, refused as a usage error unless both ids are ones a burst could have minted. An `open` carrying `--ack`, a window a burst spawned, resolves its one target exactly and never bursts again; `--ack` beside more than one target is a usage error.
- **`doctor [--fix]`** (`cmd/doctor.go`) — read-only health catalog with a scriptable exit code (0 iff no check fails; info and not-evaluable lines never fail it). It checks zmx (binary, directory, and every session's daemon answering protocol 1); the saver and its daemon (`daemon.pid` naming the process `_portal-saver` runs, proved Portal's daemon, which may wait for one still starting; a missing saver is info while there is nothing to save and a failure otherwise, and a daemon on another version is info, since the next bootstrap replaces it); the state dir and `sessions.json`; stale hooks, a count that never reaps; projects; pending resumes, a count; the kept sessions, an info line naming them (with no saver running, every saved session not live, as the next bootstrap marks them owed), left out when the state's zmx-dir check fails, the boot read through `state.SilentClaimRule`; the key config (`prefs.json` `keys`, read as an attach reads them: a binding that falls back to its default is info, never a failure); the host terminal and resume mode. `--fix` prunes stale hooks through the daemon's sweep, prunes stale projects and sweeps logs, then re-diagnoses; in a state dir whose `zmx-dir` record names another zmx dir or can't be read, or beside a migration cut short (`sessions.json` fails, naming where the migrated state waits), it repairs nothing and exits non-zero (`fixRefusal`). It must start nothing and heal nothing on the read-only path.
- **`uninstall`** — stops the saver through `saverhost.Host.StopOr`, which reads its pid under `saver.lock`, so an ensure in flight is waited out and its saver stopped, and nothing more: no file touched but that lock, the latch kept, nothing started. A stop that fails exits non-zero, saying what was sent: a proof that fails before the SIGTERM sends nothing, one that fails before the SIGKILL leaves a daemon that has had the SIGTERM. A saver the stop can't read because its daemon speaks a zmx protocol Portal can't use is judged and ended as the bootstrap ends one it finds (`saverDaemon.End`), in `StopOr`'s `orElse`, so still under `saver.lock`, never reaching a saver a bootstrap makes meanwhile, and reported stopped. One it can neither stop nor end fails with `bootstrap.SaverLeftMessage`, the bootstrap's way out, and both reasons.
- **`hook set/rm/list`** (`cmd/hooks.go`; `hooks` is a permanent silent alias) — see Resume hooks. `hook list` is a machine interface: tab-separated key, event, command, location, mode. Never add columns before the existing ones, or header/footer lines.
- **`current`** prints the current session's label (its name when it has none); outside a session it prints nothing and exits 1. **`rename <text>`** sets that label; empty text resets it.
- **`migrate`** (`cmd/migrate.go`, `internal/migrate`) — turns the tmux version's saved state into this version's (spec: Migration). Exempt from the `sessions.json` stop and from the root's bootstrap, it runs the bootstrap itself once the state is this version's (none when none is owed: a re-run forces no restore), then prints the report on stdout, whose restore lines come from the index read after the bootstrap. In order: every read that may refuse the run (the hooks the plan reads, decoded strictly; the version 1 index; zmx's sessions), so a refusal leaves tmux untouched; Portal's tmux hooks unset and `_portal-saver` killed when a tmux server answers (plain `tmux`, honouring `$TMUX`, through migrate's own client, `migrate.Tmux`, the one production runner of tmux, as `internal/migrate/tmux_owner_guard_test.go` holds); a bounded wait, signalling nothing, for the daemon `state/daemon.pid` names; `hooks.json` backed up to `state/hooks.json.tmux`, never overwritten; the plan, from the index read again; the build into `state-migrating/`; `hooks.json` rewritten from the backup; then `state/` renamed to `state-tmux/` and the staging dir to `state/`. Before that commit point `state/` is still version 1, so a run cut short is redone whole; between the renames nothing logs, since a log line makes the state dir again, every other command stops on the migration cut short, and a re-run finishes the move into a `state/` holding only Portal's logs and what that move had already brought. One run at a time, by a lock on the state dir's parent. Tests reach the tmux server only through `MigrateDeps.Tmux`; cmd's `TestMain` makes the production `migrateTmux` panic, as the `TMUX` poison would read as no server. Every line it shows is a constant in `internal/migrate/copy.go`.
- `list`, `kill`, `alias`, `theme export`, `version`, `init`, and the hidden `state` subcommands (`daemon`, `hydrate`, `resume-draw`, `resume-wait`, `resume-recover`).

Connecting to a session (`cmd/open_attach.go`): `attachConnector` runs the backend's `AttachCommand` (`zmx attach <name>`) through `runner.Run` on Portal's stdin and stdout, watching for the keys `prefs.json` binds, read afresh at each attach. While attached the runner is listed in the runner registry (`runnerreg.Listing`, through the `OpenDeps.Runners` seam), its zmx client carrying its token in `PORTAL_ATTACH`, tracked through `Backend.Track`. Detach and the kill key open the plain picker (`reopenPicker`: no filter, search, command or bootstrap) and attach its pick, until it is quit. The kill key never kills from inside the session: its outcome asks (`runner.Outcome.AsksKill`), and the picker opens on the kill prompt for that session (`pickerLanding.kill` → `tui.Deps.KillAsk`) as its first listing lands, dropping keys typed before then. There `y` kills through `tui.Deps.AskedKiller` (`askedKiller`: a session already gone counts as killed, `goneCountsKilled`; `k`'s own `y` never does) and stays, Esc keeps it with the cursor on its row, and Enter attaches it again; a kill the runner refused, unsure, opens the picker on that refusal as its flash and no prompt. A switch request attaches the session it names; a pick, from any picker including a bare `open`'s first (`ConnectPick`), and that switch are attached through `attachOrPicker`, which brings the picker back when the session can't be attached for a fault of its own, gone, held under another spelling, refusing or not answering, worded as `portal kill` words it (`sessionFault`; any other failure returns, as a first attach's does); any other end exits with the outcome's code, silently, through `ExitCodeError`, which `main.go`'s `classify` maps. Inside a session (`Command.Switches`), Portal reads the session's leader (`Backend.LeaderEnv`, zmx's own record of the client last typed in) and asks the runner its token names to switch, exiting 0 once it accepts; with no token (a raw client or none leading), a token the registry doesn't hold or whose runner's entry names another session, a refusal or a failure, it `syscall.Exec`s the command, which zmx routes to the leader; the session typed in is left as it is. A runner whose output shows a switch, zmx's own or a nested zmx's, becomes unsure for the rest of the attach: it stays listed and takes switch requests, and asks for a kill, detaches to the picker or accepts a `confirm-session` only once `runner.Config.Confirm` (`Listing`'s: the session's leader carries its token) confirms, asked afresh as the kill key is pressed or the request comes; a confirmation leaves it unsure. `runner.ErrNoTerminal` also execs. An open carrying `--ack` writes its receipt once, as its first attach begins (`runner.Config.Began`) or just before an exec takes the attach's place.

### Packages

| Package | Role |
|---|---|
| `backend` | Session backend interface in Portal's terms: `Session` (`Answered` false means only `Name` is known), `Command`, `ClientEnv` (a client's tracked variables), `ClientProcess` (a client's process and the environment it was exec'd with), `Backend` (every capability a caller needs, `AttachClients` and `ReachEnv` among them, so none reaches the driver by type assertion), `SessionExistsError` and `HeldAsError`, its errors (`ErrNoSuchSession`, `ErrSessionExists`, `ErrInvalidName`, `ErrTimeout`, `ErrHistoryUnavailable`, `ErrUnreadableClient`, `ErrUnsupportedProtocol`), and the second ask of a session a Create read back no creation of (`AskAgain` after `RecheckAfter`, waiting through `Pause`), which restore and the mint share |
| `backend/zmx` | The zmx driver over zmx's socket protocol, against the build pinned in `scripts/zmx-commit`: socket discovery and concurrent `Info` probes (a refused socket is stale on Linux, where a full backlog is EAGAIN, so ECONNREFUSED proves no listener; elsewhere when its mtime predates boot, or when the process table proves no holder: no process, whatever the kernel names its executable, whose argv is a daemon-starting subcommand, `attach`/`a`, `run`/`r` or `write`/`wr`, and the name, with `ZMX_DIR` the backend's dir compared canonically, or, its environment hidden as a hardened binary's is, on a non-empty name the socket's ends with; a holder found, or a table that can't be read, keeps it `ErrRefusing`). Environment variables are read first entry winning, as zmx's `getenv` reads them. ### Logging

All logging goes through `internal/log`. Bind once per package (`var logger = log.For("<component>")`) and log with slog attrs.

- **Closed taxonomy.** Component names, attr keys and levels are spec-governed. Never invent a component or attr key at a call site. Production default level is INFO.
- `main.go` calls `log.Init` first and owns the single `os.Exit`. Bare `os.Exit` elsewhere is prohibited. `cmd`'s `osExit` seam is the one sanctioned exception, serving the hydrate helper's exec-failure path and the daemon's self-eject, and each call pairs itself with `log.Close`. The `process:` lifecycle markers bypass the level filter.
- No discard-backed `*slog.Logger` outside `internal/log` — use `log.Discard`/`log.OrDiscard`. A guard enforces this in test files too. `internal/log` must not import `internal/state`; `internal/prefs` must not import `internal/log`.
- Store mutations log from the store method (the chokepoint), not the caller. A cycle emits one INFO summary, with per-item detail at DEBUG.
- The `theme` component records where a theme is *used*, never where one is diagnosed: `doctor`, `theme export` and `capturetool` load through `theme.NewSilentLoader()`.
- Env: `PORTAL_LOG_LEVEL`, `PORTAL_LOG_ROTATE_SIZE`, `PORTAL_LOG_RETENTION_DAYS`. `portal.log` is a symlink to the current day's file.

### Server bootstrap

`cmd/bootstrap`'s Orchestrator runs six steps, wired in `cmd/bootstrap_wiring.go`. The order is load-bearing: check zmx; remove the latch; sweep; judge or end the saver, mark owed, ensure; raise `restoring`, restore, lower it; write the latch.

1. **CheckZmx** — `zmx` is on PATH and runs (`zmx version`); then the state dir is claimed for the zmx dir Portal runs against (`bootstrap.ZmxDirOwner`): its `zmx-dir` record, the canonical `ZMX_DIR` (`zmx.CanonicalDir`, the holder proof's comparison: a path that doesn't exist has its deepest prefix that resolves resolved as the OS does, `..` after links taken physically, and the rest appended, cleaned unless it holds a `..`, which keeps it as written and equal to nothing else, so a recorded dir since swept still matches another spelling of it) written with `fileutil.AtomicWrite0600` by the first bootstrap that finds none. A state dir recording another is the fatal `bootstrap.OtherZmxDirMessage`, and a record it can't read or write is `ZmxDirUnreadableMessage` or `ZmxDirUnwritableMessage`, each naming the file, before the latch goes, so nothing changes: run against another dir, the bootstrap would find no saver there, mark every saved entry owed and restore it into that dir, and the first dir's saver would later replace those entries and forget their scrollback and hooks. The gate reads the record on the warm path as well (`Gate.ZmxDir`), so a warm command against another dir's state owes the bootstrap that refuses it rather than recording a mint in the wrong index. Doctor's `state's zmx dir` line reads it, recording nothing.
2. **RemoveLatch** — the `bootstrapped` latch goes before the first change, so a pass cut short anywhere after it leaves none and the next command finishes the work. Under `bootstrap.lock` no restore's creates are in flight, so a `restoring` a pass cut short mid-restore left raised is lowered here too, with an INFO `restoring flag lowered`; left up, it would stand the saver down until some later pass finished a restore.
3. **Sweep** — orphan daemons, then stale flags. The orphan sweep SIGKILLs only a pid pgrep found that `saverhost`'s proof names a daemon of this backend's saver, never the saver's own pid or its own process, proved just before the kill and waited for after it, counted only once it has finished exiting; a saver pid it can't read kills nothing. The flag sweep lowers `hydrating` and `resume-pending` for a session not live, and `hydrating` on a live session not running restore's helper (`Restorer.RunsHelper`, the rule restore's own retry judges by: a binary named `portal`, wherever it is, then `state hydrate --session <name>`, so a bootstrap run by a dev build or another install keeps a kept transcript's flag).
4. **EnsureSaver** — `Present` first. A saver found is judged before anything is made. The judgement: Portal's protocol carries on; another version, or an answer to zmx 0.8.1's framing (`OlderZmx`), is a saver Portal can't use; neither leaves the restore unfinished. A saver Portal can't use, found or made, is ended, so installing the supported zmx recovers on the next command without a reboot. One found is ended by `saverDaemon.End`, which is `zmx.Backend.EndDaemon` signalling through `signalProcess`, never by the zmx on PATH, which may speak another protocol than the saver's; ended, it is as none found, with an INFO `saver ended`. One found that can't be ended (no proof, or off darwin, where the process table can't be read) is the fatal `bootstrap.SaverLeftMessage`, which tells the user to end it with the zmx that runs it (`zmx kill _portal-saver`) or restart, never the judgement's own, which would send them to a zmx that leaves it running; its cause names the verdict and the saver left. With none, `Restorer.MarkOwed` marks owed every entry not live, before any saver can commit; then `Ensurer.EnsureSaver`, judging the saver it makes before the readiness wait. A made saver Portal can't use is ended by `saverDaemon.EndMade`: `zmx.Backend.KillByCLI` first, the zmx on PATH having made it and so speaking its protocol (the only way off darwin), then `End`'s proved signal when that fails. It is fatal with the judgement's own message either way, so a zmx Portal can't use on PATH fails every command until the supported one is first, which the next command recovers on, or tells it the way out of a saver left; a made saver gone at once (`ErrSaverGone`) warns as a saver down as well as unjudged. Every create judges what it made, the saver's included: a session that gives no Info within the read-back but answers 0.8.1's framing is ended by `KillByCLI` and nothing else, and refused with `backend.ErrUnsupportedProtocol` (`zmx.Backend.Create`'s `refuseOlder`, the judgement and the kill run past a cancelled context, each within its own ceiling), so the made judgement never sees a 0.8.1 saver. No signal backs up a kill that fails (decision 80): every proof of which daemon a Create made could be fooled into reaching a session Portal didn't make, so that session is left, the refusal says so, and restore counts the name held for that boot. `saverDaemon.EndMade` keeps its signal fallback because its proof targets only `_portal-saver`'s daemon, Portal's own. The bootstrap maps that refusal to the same fatal (`bootstrap.UnsupportedCreate`), ending nothing again. `createFatal` in `cmd/root.go` is the one mapping, shared by `Execute`, so a warm mint on a 0.8.1 first on PATH fails the same way, and by the picker (`tui.Deps.CreateFatal`). A picker's mint the backend refuses ends the run non-zero: a direct mint on the loading page's error frame, the fatal alone where no step reached this process's loading page (a warm picker, or a cold one that only waited out another Portal's bootstrap) and with its steps where some did; a staged mint, always in a command-pending picker, by quitting at once, `Execute` printing the fatal on stderr. Any other create error flashes `tui.MintFailedFlash`. Restore runs only on a judged saver.
5. **Restore** — raises `restoring` just before restore's first create, the saver judged and the owed marks written, and lowers it once restore returns, finished or cut short. Progress `n/m` on the loading page. Sessions whose create failed for a reason that may pass are tried again before the step ends, within `restore.RetryBudget`. An unreadable `sessions.json`, an unlisted backend and sessions it couldn't make each surface a warning; the sessions it couldn't make keep their entries, an owed one still owed and one from before this boot never dropped, for the next restore. Restore's own sessions stay owed until each one's helper claims it. A create the backend refuses as a session it can't talk to (`backend.ErrUnsupportedProtocol`) stops restore there, its retries included, and is the older-zmx fatal.
6. **WriteLatch** — last, and never after a fatal. A latch it can't write, or a boot id it can't read, is a warning.

Steps 1 and 2 (a state dir of another zmx dir among them), raising and lowering `restoring`, a saver Portal can't use that it made, one it can't end, and a restore's create refused as unsupported are fatal; the rest log WARN and surface warnings, each saver failure worded by its cause (`saverWarning`). Steps 5 and 6 finish the restore: a pass that leaves it unfinished (the protocol unjudged, the owed marks unwritten, the sessions unlisted, or cut short) skips them with an INFO `step skipped`, so no latch is written and the next command bootstraps again, while the saver goes on saving. A saver that may still run another version's daemon restores but skips step 6 the same way (`withholding`), so the next command tries the replacement again: one whose old daemon couldn't be replaced (`saverhost.ErrNotReplaced`), and one unread (`ErrUnread`) whose `daemon.version` doesn't name this version or can't be read (`ErrVersionUnproved`). An unread saver whose `daemon.version` names this version writes the latch.

**The gate** (`bootstrap.Gate`). A command outside `bootstrapExempt` owes the bootstrap when the `bootstrapped` latch is missing or isn't this boot's and this binary's, the state dir's `zmx-dir` record is missing, names another zmx dir or can't be read (`ZmxDirOwner.Claimed`; a missing one owes the bootstrap that records it, so "delete it" in the unreadable record's fatal holds at the next command), or `_portal-saver` is absent. The latch is the record that the last bootstrap finished: a missing one is a bootstrap under way, or one cut short or failed before it finished, which only a bootstrap finishes. `restoring` means only that restore's creates are in flight, and owes nothing: the saver and the hook sweep stand down under it, and nothing before restore needs them to, since owed entries and those that may predate the boot are never dropped. A logout, every zmx daemon dying, or a crash ends the saver with the sessions, and no saver saw them end, so the bootstrap brings this boot's sessions back too. The warm path is the latch read, the `zmx-dir` record's read and one `Exists` of the saver: no lock, no other backend call.

**`bootstrap.lock`** (`state.AcquireBootstrapLock`, `bootstrap.Locked`). The bootstrap runs under an flock in the state dir, taken before `saver.lock`. `open` bringing back a kept session takes it too, through `Locked.Hold` (`holdBootstrapLock`), with the same bound, notice and fatal, and so does `kill` of a session not running: it judges the session again under the lock and holds it through the discard, so the discard never races `x <name>`, killing as live a session brought back meanwhile and saying `No session found` of an entry gone. A bootstrap that waited asks the gate again once it holds the lock, and skips when the other left nothing owed, so two windows opening at once restore each session once; the latch, removed before the first change, makes a command started during a bootstrap wait rather than run warm. A wait past `bootstrap.LockNotice` (1 s) is told once to the progress emitter: the loading page leads with `LabelWaiting`, and a CLI command prints one stderr line (`waitNotice`). The wait is bounded by `bootstrap.LockWait`: the holder's longest run, every step at its backend ceilings, `saverhost.JudgeRun` (the end of a saver Portal can't use included) and `saverhost.LockWait` twice for the saver, `commit.lock`'s bound for the owed marks, restore's listings (`restore.Listings`, which restore's tests hold it to: before its first session, after its first pass, once its retries end), a lookup (a read, and a read of the spelling another holds the name under), a create plus `commit.lock`'s bound, and a second `commit.lock` bound (the last listing's record of a session made after all, which the first pass recorded too before its helper died) for each entry `sessions.json` holds, and once, however many it retries, `restore.RetryBudget` plus a read and one more such run, for the retry, its lookup first, that starts as the budget ends, with 15 s over. Past it the command fails with `ErrBootstrapLockHeld`, naming the lock.

The saver and every restored session run `bootstrapExe`, the absolute path of Portal's own binary; restore refuses one not named `portal`. `cmd`'s TestMain makes it panic, so a cmd test reaching the cold path unstaged fails loudly; `withBootstrapDeps(t, BootstrapDeps{})` owes none.

**Cold-path flip.** When a bootstrap is owed and the launch is a picker (`shouldRunConcurrentBootstrap`, `isTUIPath`), the bootstrap runs concurrently with the TUI and streams progress messages (`cmd/bootstrap_progress.go`; labels in `internal/tui/loading_progress.go`). A fatal becomes an in-TUI error frame naming its step and a non-zero exit; warnings become a post-load notice band. The search form holds the loading page until bootstrap completes; a command-pending pick is held (`stagedMint`) and minted on completion. A picker that returns with its bootstrap still running, as on Ctrl+C from the loading page, cancels it and waits up to `unwindWait` (2 s) for it to return (`bootstrapProgressPipe.unwind`), so a restore cut short lowers `restoring` before Portal exits; past that the exit cuts it short, as a kill does, and the latch, never written, owes the next command the work. A CLI command runs an owed bootstrap synchronously; a warm one runs none. A picker reopened after a detach or the kill key (`reopenPicker`) never bootstraps, and the kill prompt opens once its listing lands. The loading page runs only behind a bootstrap's receiver (`tui.WithBootstrapping` takes it, and a nil one opens no loading page), so its landing is decided by the post-restore listing alone.

**The daemon** (`cmd/state_daemon.go`). It refuses a version 1, corrupt or newer `sessions.json` before taking anything; then lock, pid, version. A 1 s tick: self-supervision first (`Session("_portal-saver").PID` must be its own; three consecutive gone-or-other-pid reads eject it with `log.Close(0)` and the `osExit` seam, no flush, `daemon.pid` left stale on purpose; a timeout or PID 0 neither counts nor resets), the saver's poll every 5 s, hourly project cleanup and the hourly hook sweep (`hooksweep`). One INFO summary only for a poll that claimed, dropped, captured or removed. From the first SIGTERM or SIGHUP everything in flight gets `shutdownBound` (6 s) in all, then the run ends; a second signal ends it at once; a poll that takes commit.lock after the signal writes nothing. `daemon.lock` is held until the process exits. `zmx kill` asks the session's zmx daemon, which unlinks its socket, sends the session's process group, this daemon among it, SIGHUP and an uncatchable signal about 0.5 s later, then exits, so it leaves no stale socket; a SIGTERM to the zmx daemon does the same, which `EndDaemon` relies on; Portal's own stops SIGTERM the daemon and wait (`saverhost.TermWait`) before killing `_portal-saver`.

## Invariants

These encode incidents and data-loss traps. Most have a source guard.

### Session names and labels

- Session names are zmx's and never change, since zmx has no rename; `session.SanitiseProjectName` and the driver's name check keep generated ones valid.
- Labels take any printable text: `sessionindex.ErrLabelUnprintable` carries the refusal wording `portal rename` and the picker's `r` both show, mirrored in README's `hook` section, so change both together.

### tmux (portal migrate)

- tmux prefix-matches `-t`, so a bare `-t _portal-saver` reaches a live `_portal-saver-2`, and reads a colon-free `=name` as a window's. Migrate's client addresses the saver only as `=_portal-saver:` (`saverTarget`) and unsets hooks by index, which moves no other hook in tmux's sparse arrays; a test asks after a session through `tmuxtest`'s `HasSession`.

### Saving

The rule: a session the user kills never comes back. Detach, reboot, and a logout or crash that ends every zmx daemon with the saver leave everything restorable, with no Portal shutdown step.

- `internal/saver` is the cycle: every decision on the index as read under commit.lock, and every write of `sessions.json` under it (`commitlock`). A poll does nothing while `restoring` is raised or can't be read, nor when the listing fails, so a failed listing never reads as no sessions.
- **Drops.** An entry is dropped only once its session is missing from two listings at least 10 s apart. An entry from before this boot, one recording no creation, and one owed a restore are never dropped. The `hydrating` flag plays no part: owed and before-the-boot already keep every unfinished restore, and a flag stuck up must not turn the user's close into a resurrection. When at least three droppable entries, and at least half of them, are missing at once, none of them is dropped while the saver runs unless one is listed again, with one WARN. Every dropped session logs `session dropped session=<name>` at INFO, and `state.Forget` removes what it owned in the same commit.lock hold.
- **Owed.** The bootstrap marks owed every entry not live when it finds no saver, before any saver can commit (see Server bootstrap); restore leaves owed every entry it makes, and so does a claim adopting one while its session is flagged `hydrating`. A restore completes at its helper's claim: while `hydrating` is raised, only the hydrate helper's claim, once its replay is done (`Index.Hydrated`), repays the entry. With the flag down, a saver or claim finding the session live repays it too. Repay it sooner and a helper that dies, or a logout followed by one failed restore, loses the session.
- **Names.** No writer of `sessions.json` records an entry under a name Create refuses, or one with no creation: `Claim` refuses both (`ErrNameRefused` by the `Rule`'s name rule, which `state.ClaimRule` takes from the backend's `ValidateName`; `ErrNoCreation`). A mint whose Create reads back no creation asks once more (`backend.AskAgain`) and records the entry when that ask answers; only when it too reports none does the mint record nothing, warning `unrecorded`. Rename, the picker's `r` and `hook set` fail with the refusal (`nameRefusedCopy`, or `nameRefusedNamedCopy` when the backend's reason names the session), and `hook set` registers no hook.
- **Scrollback.** Captured only when changed, to per-creation files the entry names, never over the saved transcript from a session on the alternate screen, and never from a session flagged `hydrating` or `resume-pending`. A transcript the helper can't replay is kept: the helper leaves `hydrating` raised, so nothing captures over it, the entry keeps naming it, so no clean reaps it, and the session shows one line saying where it is (`replayFailedNotice`). The cost: that session is not captured until it ends and the next bootstrap's sweep lowers the flag.

### Resume hooks

- **A hook key is the zmx session's name.** `hook set` keys by `$ZMX_SESSION`, which never changes; nothing is stamped. The hydrate helper looks the hook up by the `--session` name in its argv, and fires nothing when `$ZMX_SESSION` names another session.
- **A hook goes with its session.** `state.Forget` removes it on kill, drop or replace, and the daemon's hourly sweep is the backstop: `hooks.StaleKeys` reaps a key naming neither a session the backend lists (answering or not) nor an entry in `sessions.json`. The sweep removes nothing when the listing fails, the index is unusable (a migration cut short between its renames counts, its index still in the staging dir), a restore is in progress, or nothing is listed or saved, since a fresh state and zmx dir beside a real `hooks.json` would otherwise lose every hook; nor, with one WARN `clean-stale-skipped` (`reason` `tmux-keys`), while any key it would reap has the tmux version's shape (a pane token, `nanoid.IsTokenShaped`, or `<session>:<window>.<pane>`) and migration has not yet moved the tmux version's state to `state-tmux/` beside the state dir: a dev build's scratch state beside the `hooks.json` both versions share would otherwise reap every tmux-era hook. `state.TmuxStateDir` owns that path; a stat that fails, however it fails, counts as not migrated, so the guard holds. Once `state-tmux/` exists, migration has moved or removed every tmux key (`portal migrate` moves a key that is a saved pane's `@portal-pane-id` token to that pane's session's name, and drops the rest), so a key in that shape is an ordinary zmx name, judged as any other. Doctor's count and `--fix` stand down alike, saying why. Portal's own `_` sessions are left out of the listing it judges by (`listedNames`, for the sweep and doctor's count alike): the sweeping daemon runs in `_portal-saver`, so counting it would keep that stand-down from ever firing. It reads the index under the hooks lock, because `hook set` claims the entry before it writes.
- **A registration that lands in the enumeration gap is never reaped.** `CleanStale` snapshots `hooks.json` before the unlocked listing, and `narrowToSnapshot` may only drop candidates from the delete set, never add them.
- `hooks.json` values may be a string or an object; both shapes are permanently valid, with no migration. The codec re-emits untouched entries byte-for-byte, so attributes it doesn't model survive a sibling's rewrite.
- The `hooks.json.lock` sidecar is created by the first mutation and is absent on most installs, so the unlocked read (`load-unlocked` DEBUG) is the common path, not contention. A read never fails for want of the lock.
- `hook rm` exits 0 only if the removal itself removed something. The panel's discard (`hooks.Store.Discard`) removes only when the stored command still matches what the confirmation showed, compared under the lock.
- Hooks fire only in the hydrate helper (`cmd/state_hydrate.go`), in a session restore brought back. The mode is `resumemode.Resolve` of registration → `prefs.json` `resume_mode` → shipped default **lazy**. Eager sessions exec `/bin/sh -c 'trap : TERM; <HOOK>; exec <shell> -l'`. Every hand-off ends in a login shell, and a `$SHELL` that can't be found becomes `/bin/sh`, exported as `$SHELL`, with one WARN. Lazy sessions park in the resume-panel chain (`cmd/state_resume_{draw,wait,recover,chain,flag,back,report}.go`), which runs under the existing `hydrate` role and log component. The chain waits on the session's `resume-pending` flag file; its shell gate and its Go reads share one rule: lowered only when nothing is at the flag's path and its directory is searchable, or that directory is gone and the state dir is searchable. Anything else counts as raised, so a waiting session is never closed on a doubt.
- The lazy-session ordering in `state_hydrate.go` is load-bearing: the `resume-pending` flag is raised before `hydrating` clears, since a gap lets the saver capture the panel over the transcript. Any failure there downgrades the session to eager with one WARN, after one best-effort lowering of a flag the failed raise may have left.
- The helper claims its session's creation before it lowers `hydrating`, and that claim, made under the raised flag once its replay is done, is the one that finishes the restore. A replay that fails keeps `hydrating` raised and the entry owed (see Saving), and the session is still handed on; a claim that fails still lowers the flag, leaving the saver to repay the entry once it finds the session live.
- Portal's resume sessions *catch* SIGTERM so a shutdown saves a waiting session still waiting. Never use an ignored disposition — it survives `exec` into the user's hook and shell. SIGHUP stays uncaught so a kill still ends the session at once.

### TUI

- **Owned canvas.** Every cell is painted from the active theme's `canvas`. The outer full-terminal fill (the last layer in `model.go`'s `View`) stays outside the list's height budget. The terminal default background is set with OSC 11 and restored on exit (`internal/tui/restore.go`).
- **Canvas-echo guard — don't drop it.** The exit set-back is skipped when the captured original equals the canvas, compared against `startupCanvasHex` (the canvas the light/dark gate selected at startup). Never re-derive it from the active theme: after a mid-session theme change that would leave a colour the user never chose stuck in their terminal. The swap-and-diff guard can't see this path.
- **Light/dark.** A constant theme paints from frame one. An adaptive pair arms a single-resolution gate: OSC 11 query against a ~50ms timeout, dark on no answer, never paint-then-flip. `NO_COLOR` paints nothing and keeps every state glyph- or letter-backed, never colour-only.
- **Grouping pagination.** Group headings are real, non-selectable `HeaderItem` rows (`FilterValue()==""`), one delegate line each, injected by `injectGroupHeaders`. Drawing extra lines inside a row breaks `bubbles/list` pagination and scrolls the title off-screen. Don't route the picker through `lipgloss/tree`. `rebuildSessionList` is the single re-render chokepoint. Grouped modes read each session's dir from the session index, falling back to the git root of the session's cwd (`session.GroupingDir`), cached in memory only and never written anywhere.
- No raw hex in `internal/tui` (`colour_literal_guard_test.go`, no exemptions); every colour is a theme token. The 19 token names are a public contract for drop-in theme files.
- The keymap descriptor (`keymap.go`) drives the footer, help and theme-panel footer; dispatch is separate, and `keymap_dispatch_guard_test*.go` catches drift. Navigation is arrows only: `pinArrowOnlyNav` strips vim and page aliases from all three lists (in the theme panel the defaults also collide with commit keys).
- The theme slide-over is an opaque layer over the composed page, which is not re-laid-out, so a swap is an O(1) restyle with no reflow. Notice bands go through the single-slot arbiter in `notice_band.go`.
- `prefs.json`'s legacy `appearance` key must stay declared as a preserved raw string: every writer re-encodes the whole struct, so dropping the field erases the user's value on the next write.

### Multi-window spawn

- One service (`internal/spawn`) reached by the `open` burst and the picker's multi-select (`m`). Both run detect → pre-flight → spawn N−1 → self-connect the trigger window. **Net N windows, never N+1.**
- Inside a session (`ZMX_SESSION`, in the backend's zmx directory), detection walks up to the terminal app from the session's leader, the client zmx says last sent keyboard input (`Backend.LeaderEnv`): the runner its `PORTAL_ATTACH` token names, once that runner accepts `confirm-session` (on the session, and sure of it or confirmed through the leader); with no token, the one `zmx attach` process on the session (`AttachClients`) that can be the leader — carrying no `PORTAL_ATTACH` (a runner's own client) and every variable zmx tracks for the leader as the leader has it (`ClientEnv.Matches`; `SSH_CONNECTION` keeps a remote leader from matching a local client). No leader, a token the registry doesn't hold or on another session, an unsure runner the leader doesn't confirm, zero or several raw clients that can lead, a `zmx` process that can't be read, an unresolvable terminal or a transient error is unsure (`Identity.Unsure`: "can't tell which terminal Portal is running in"); a leader with no terminal app on this machine is remote. Both are unsupported — never spawn on uncertainty. Outside a session it reads Portal's own environment and ancestry. Doctor detects over `runnerreg`'s `ReadOnly` registry.
- Spawned windows run `/usr/bin/env -u ZMX_SESSION -u TMUX -u TMUX_PANE <window env> <os.Executable()> open --session|--path … --ack <batch>:<token>`: stripped, a window attaches in its own terminal rather than switching its opener's session; the window env (`cmd`'s `windowEnv`) is what the opener resolved by — its `PATH`, its resolved state dir, its backend's `ReachEnv` (the bound `ZMX_DIR`), and each `xdg.Variables` and `log.Variables` name as it has it, paths made absolute against its directory and any it lacks `-u`'d — since a window's shell starts from the terminal's environment, which need not match (Ghostty's `bash -lc` reads no zsh rc); `os.Executable()` keeps each window version-identical with its opener. The adapter's own command (osascript, a recipe) runs without the three stripped variables. Confirmation is the window's ack, `state/spawn-acks/<batch>-<token>` (dir 0700, file 0600, both ids validated before they reach a path), written once its attach has begun, not osascript success. A burst's `Clean` removes its own acks and any an hour old, which a burst that died before cleaning leaves.
- Pre-flight is all-or-nothing. Past it, failures are leave-what-opened, and permission-required stops the burst. Classification, messages and logging are single-sourced for both callers.
- Ghostty wraps the command as `bash -lc '<cmd>; exec "$SHELL" -il'` so a window lands at a shell; `terminals.json` recipes get the plain command. Spawn persists nothing beyond the transient ack files.
