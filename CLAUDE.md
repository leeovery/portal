# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test

```bash
go build -o portal .                        # build binary
go test ./...                               # unit lane: fast, hermetic — no real tmux servers*, no daemons, no portal binary built or run
go test -tags integration -p 1 ./...        # integration lane: real tmux + real daemons + built binaries. -p 1 is REQUIRED
go test ./cmd -run TestOpenCommand_PathArgument_SkipsTUI   # run single unit test
go test -tags integration ./cmd -run TestCommitNowSymptom   # run single integration test
```

*The unit lane still includes a handful of fast real-tmux **client** tests (`internal/tmux/*_realtmux_test.go` — per-test `-L` sockets, no daemons, no subprocess binaries). **Every test that builds a `portal` binary, spawns a `portal state daemon`, or execs a built `portal` binary lives behind `-tags integration`**, where the daemon-pgrep sandbox is compiled in — do not add such a test to the unit lane. **Building counts, not just running:** the fast lane builds no portal binary, and every consumer of `portalbintest`'s build helpers already lives in the integration lane — so `internal/portalbintest`'s own build test is integration-tagged, while `ProjectRoot` (which compiles nothing) keeps its unit-lane test. The reason is lane purity, not speed: measured, the build adds ~0.2s warm (~1.6s and ~13 MB of build cache the first time the integration-tagged configuration is built) and is invisible in `go test ./...` wall time, which is dominated by a single long-running package (`internal/tui`).

`-p 1` on the integration lane is load-bearing, not a preference: with no CI, all packages otherwise run in parallel on one machine and the daemon-timing tests (composite e2e suites, hysteresis measurement) flake under mutual contention.

Lint via `golangci-lint run` (config in `.golangci.yml`: the standard set plus the `modernize` linter). The config sets the `integration` build tag and uncaps both issue limits, so one bare invocation covers the integration-tagged files too and reports every finding — there is no second `--build-tags integration` run to remember. What it cannot see is a file gated `//go:build !integration`, which that tag swaps out of the build. Not wired into CI — it's run locally / from the Mint release step. No code generation.

Tests **must not** use `t.Parallel()` — the cmd package injects mocks via package-level mutable state (`bootstrapDeps`, `openDeps`, `doctorDeps`, etc.), staged through the `withXDeps` helpers in `cmd/testhelpers_test.go`, which register their own `t.Cleanup` restore.

### Visual capture harness

`cmd/capturetool` is a **separate offline program** (NOT a `portal` subcommand) that renders a named deterministic fixture of the real TUI through the shared `tui.Build` constructor with every tmux seam faked (`internal/capture`) — it opens no tmux server and reads no real config (an import guard keeps `internal/capture` out of the production binary). `testdata/vhs/` holds a **`vhs`** `.tape` plus its rendered PNG for each screen under active work; `vhs testdata/vhs/<tape>` re-captures a screen. To view a screen live: `go run ./cmd/capturetool --fixture <name>` (`--theme <slug|path>`, default `tokyo-night` — a built-in slug or an explicit path to a `.theme` file, which is an input rather than config discovery; `capture.FixtureNames()` lists fixtures). It is the only route to seeing a visual change before release — a scratch build of Portal itself disturbs the running daemon and touches real state.

**The images and the tapes that produce them are scaffolding, not a durable asset**: there is no visual-regression obligation, so `testdata/vhs/*.png` and `testdata/vhs/*.tape` are written as work proceeds and cleared out after sign-off rather than living in the repo. **`testdata/vhs/reference/*.png` is the carve-out and is kept**: those are committed design exports — the frames the code was built *against*, not renders *of* the code, so they don't rot the way a capture does, and for some screens they are the only reference that exists. Nothing in the Go source points at them (code comments carry no artifact paths), so a sign-off sweep must not treat them as orphans. `testdata/vhs/README.md` holds the full retention table. **The Go fixture definitions in `internal/capture` and the harness itself are permanent** — the swap-and-diff completeness guard drives the fixture renderer and its coverage assertion enumerates whatever fixtures exist, so deleting one silently shrinks the guard rather than failing it.

## Architecture

Portal is a CLI for interactive tmux session management, built with **Cobra** (CLI) + **Bubble Tea v2** (TUI) + **Lipgloss v2** (styling). The TUI is reskinned to the **Modern Vivid** design — an owned canvas painted from the active theme, a closed colour-token layer, restyled chrome/modals/loading, and a concurrent cold-boot flip (see "Modern Vivid TUI" and "Cold-path startup flip" below).

### Command flow

`main.go` → `cmd/root.go` → subcommands. Root's `PersistentPreRunE` handles tmux server bootstrap (auto-starts server if not running) and injects a shared `tmux.Client` + `serverStarted` flag into `cmd.Context()`.

**Key command:** `cmd/open.go` — the main entry point (`portal open` / the `x` shell function from `portal init`). A bare positional runs the resolution grammar (exact session → glob → path → alias → zoxide) and creates/attaches directly; domain-pinning flags force a single domain (`-s/--session` attaches an existing session/glob and never mints, `-p/--path` mints at a literal dir, `-a/--alias`, `-z/--zoxide` — a pinned miss hard-fails rather than falling through to the picker); `-f/--filter <text>` skips resolution and opens the picker pre-filtered; with no args it launches the TUI picker. Two-or-more targets (or a single glob that may expand to K≥2) route through the multi-target burst below. The former `portal attach` command is retired — a spawned burst window now runs `portal open --session <name>`.

**Multi-target burst:** `cmd/open_burst.go` / `cmd/open_burst_run.go` — when `portal open` receives 2+ targets (or one glob that may expand to K≥2), `orderedOpenTargets` recovers the true left-to-right target order from the raw argv, `dispatchOpenBurst` runs an atomic read-only pre-flight (any unresolvable target aborts the whole set before anything opens), and `runOpenBurst` opens the surfaces via `spawn.SplitTriggerFirst`: the FIRST surface (the trigger) absorbs the invoking terminal and self-connects LAST, while the N−1 non-trigger surfaces are spawned FIRST into host-terminal windows over `internal/spawn` (see "Multi-window spawn" below). Each spawned window runs the composed argv `portal open --session <name> --ack <batch>:<token>` (or `--path <dir>` for a mint surface); `--ack` is a hidden internal flag on `open` (`cmd/open.go`) — the spawned window writes its `@portal-spawn-<batch>-<token>` server-option marker as its last act before the attach/mint handoff so the burst can confirm it came up. There is no `portal spawn` CLI.

**Diagnostics:** `cmd/doctor.go` — `portal doctor [--fix]` runs an ordered catalog of read-only health checks across the resurrection machinery, renders one line per check, and drives a scriptable exit code (0 iff all pass). It is bootstrap-exempt (starts no server, heals nothing on the read-only path), subsumes the retired `state status`, replaces `clean` (via its `--fix` repairs), and folds in the retired `spawn --detect` as a host-terminal check line. `--fix` applies low-stakes, reversible-by-reconstruction repairs — prune stale `hooks.json` entries, prune stale `projects.json` records, sweep old logs — then re-diagnoses, with the exit code driven solely by the post-repair pass.

**Teardown:** `cmd/uninstall.go` — `portal uninstall` removes ONLY Portal's tmux-runtime footprint: it kills `_portal-saver` (delivering SIGHUP so the daemon flushes a final atomic state) then unregisters the global hooks, and touches NO files — saved sessions and config survive, and `portal open` re-bootstraps the runtime on the next run. Bootstrap-exempt.

**Resume-hook command:** `cmd/hooks.go` — `portal hook set/rm/list` manages per-pane resume hooks (see "Resume hooks" below). `hook` is the canonical verb; `hooks` is retained as a permanent, silent cobra alias (back-compat for machine-written `portal hooks set …`). Bootstrap-exempt: it starts no tmux server. Its one write outside the config directory holding `hooks.json` is `hook set`'s best-effort touch of `save.requested` in the state directory, which asks the daemon to capture the new pane token on its next tick. `hook list` resolves each entry's location through **one** live `tmux.ListAllPaneHookKeys` enumeration per invocation (none at all when there are no entries), rendered as a fourth tab-separated column after key/event/command; that column is empty when no live pane carries the token, when the key is not token-shaped, and when the read itself fails (no server running) — the listing still succeeds in all three cases.

### Resolution chain (cmd/open.go → internal/resolver/)

Path arguments go through: direct path detection → alias lookup → zoxide query → TUI fallback with filter text.

### Session connection (two modes)

- **Outside tmux (bare shell):** `AttachConnector` uses `syscall.Exec` to hand off the process to `tmux attach-session -A` (atomic, replaces the portal process)
- **Inside tmux:** `SwitchConnector` uses `tmux switch-client` (two-step: create detached session, then switch)

Every per-session `-t` is pinned to an **exact-match target** rather than passed bare, because tmux prefix-matches and would silently resolve `-t foo` to a live `foo-2` once `foo` is gone — on the kill path, destroying the wrong session with no error. Which helper a call site takes is decided by the kind of target the *command* parses, not by what it writes, and it is decided by **measurement per command** rather than by the shape of the string: measured against tmux 3.7c with a prefix-extension sibling live, every per-session `-t` Portal composes parses a window or pane target first, so every one of them takes `CoordTargetExact` (`=name:`) — has-session, kill-session, rename-session's `-t`, switch-client, show-environment, set-environment, list-clients, list-panes, display-message, respawn-pane, `set-option -t` (a session-option write reached through a pane target), and the two hand-composed `attach-session` argvs in `cmd/open.go` and `internal/session/quickstart.go`. The trailing `:` is what makes tmux read the leading component as a session name; a bare `=name` there is read as a window or pane name and misses (list-panes falls through to the same fuzzy lookup; display-message returns empty at exit 0 for a live session as much as a gone one), and a colon-free `=my.app` is split on the `.` into window and pane before the session lookup is reached at all — so any live session whose name extends `my` answers in its place, which is how a live period-bearing session used to be read as vanished and dropped from `sessions.json` with all its scrollback. `SessionTargetExact` (`=name`) is therefore taken by no production call site; it stays in the vocabulary for the command a future measurement shows takes a bare session target, and the validator is deliberately **not** widened — `a.b` remains a legal session name. `PaneTargetExact` (`=name:w.p`) and the unexported `windowTargetExact` (`=name:w`) are the coordinate-bearing siblings — the four share one `<kind>TargetExact` shape; the `=` pins the session half only, so a renumbered window or pane is caught by neither form (their unpinned counterparts `PaneTarget`/`windowTarget` remain, for display, name-based keys, and a target whose session is known live). Every one of these returns the named **`type Target string`**, alongside `PaneIDTarget` (`%7` — tmux's own `$TMUX_PANE` value, server-unique and never prefix-matched, so it carries no `=`), and every `-t` parameter takes one: the methods handed an already-composed target (`SetPaneOption`, `RespawnPane`, `CapturePane`, `NewWindow`, `SplitWindow`, `ResolveHookKey`) declare `Target`, and the name-taking ones compose it internally — so a hand-composed string no longer type-checks where a pinned target is required, and neither a rename nor a helper hop launders one (which is why a parameter may again be named for what it holds, `liveTarget` rather than `target`). `internal/state`'s `PaneCapturer`/`CaptureAndHashPane` seam is parameterised over the target type (`[T ~string]`) rather than importing `internal/tmux`, which it cannot — that package imports it. A `Target` is spent back as a string at the single argv boundary that consumes it (`c.cmd.Run`, and the exec'd chains in `cmd/open.go` and `internal/session/quickstart.go`), which is exactly why `internal/tmux/target_composition_guard_test.go` survives the type as a **reduced** scan: an argv is a `[]string` all the way down, so a literal `-t` followed by a concatenation — inside the client or in an exec'd chain — is the one shape the compiler cannot refuse. Its old name-based pass-through allow-list is gone: a parameter, result or argument holding a target is recognised by its **declared type** now, which is what restores the reach the type does not have — an untyped constant (`RespawnPane(PortalSaverName, …)`) and an explicit `tmux.Target(name+":")` conversion both compile, and both are findings. Because the pinning is only as good as the name, `ValidateSessionName` refuses a name tmux cannot be handed back — one containing `:` (tmux's target separator), beginning with `$` (its session-ID prefix), or beginning with `-` (which a command parses as a flag, since a new name is passed as a bare positional) — returning an error wrapping `ErrUnaddressableSessionName` (identity-equal to the leaf `tmuxerr` sentinel) plus `ErrSessionNameSeparator` / `ErrSessionNameIDPrefix` / `ErrSessionNameFlagPrefix` for the rule that refused, so a caller choosing its own wording discriminates on `errors.Is`. `RenameSession` runs it **before composing its argv**, so an unaddressable name is never written; the picker's `r` modal runs the same check and reports the refusal in its notice band (`internal/tui/sessions_flash.go`, wording mirrored in README's `hook` section) — user-visible copy, so a change to either must move both. `wrapSessionTargetErr` also checks the name first when classifying a failure, because tmux answers an unaddressable name with the same "no such session" stderr a vanished one produces |

### Config path resolution (cmd/config.go)

All config files (`projects.json`, `aliases`, `hooks.json`, `prefs.json`, `terminals.json`) resolve via `configFilePath`: per-file env var → `XDG_CONFIG_HOME/portal/` → `~/.config/portal/`. `terminals.json` (the host-terminal spawn escape hatch, `PORTAL_TERMINALS_FILE`) is user-authored and read-only at spawn time, loaded once via `buildResolver`; like `prefs.json` it maps to the empty log component (outside the closed log-component vocabulary). On first access, `migrateConfigFile` performs a one-shot move from the old macOS path (`~/Library/Application Support/portal/`) — never overwrites existing files at the new path. Each file's log component for that breadcrumb comes from its `xdg.ConfigFileID`, alongside the env var and filename that name it; `prefs.json` carries the empty component (`""`), which suppresses the migrate log emission while still performing the move (prefs is outside the closed log-component vocabulary). `prefs.json` resolves via `prefsFilePath` / `loadPrefsStore` (`cmd/config.go`, alongside `loadProjectStore`), wired into the TUI at construction through the `WithInitialMode` / `WithModePersister` / `WithThemePersister` options, which `internal/tui/build.go` applies from the `tui.Deps` fields `cmd/open.go` populates. The canvas comes from the loaded theme **nomination** handed to `tui.Build` — read once at construction, with the raw persisted theme keys alongside it (the nomination is what paints; the keys are what the panel's badges mark). `loadPrefsStore` also owns the one-shot `appearance` → theme translation (it can log; `prefs` is a leaf that must not), and `cmd/config.go` exposes `loadPrefsStoreNoMigrate` beside it: the **non-migrating** read `portal doctor` uses, so a read-only diagnosis never triggers the translation as a side effect. It must stay inert — anything added to it lands on doctor's read-only path invisibly.

**The themes directory is deliberately not a `configFilePath` member.** `themesDirPath` resolves a *directory* through `xdg.ConfigDirPath` — `PORTAL_THEMES_DIR` → `XDG_CONFIG_HOME/portal/themes/` → `~/.config/portal/themes/` — which is what the `_DIR` suffix marks against the `_FILE` of `PORTAL_TERMINALS_FILE` and its siblings, and it has **no** one-shot Application Support migration (the directory is new; nothing exists there to move), so it is an `xdg.ConfigDirID` rather than a `ConfigFileID` — no log component, and no migrate breadcrumb. It returns a path and nothing more — it never creates, seeds or stats the directory, so an absent themes dir is the common silent case (which is why the published drop-in workflow starts with `mkdir -p`).

### Logging & observability

All logging flows through `internal/log` — bind a component logger once per package via `var logger = log.For("<component>")`, then call `logger.{Debug,Info,Warn,Error}(msg, attrs...)` with slog attrs. `main.go` calls `log.Init` first thing (before Cobra parses argv, so `process_role` is resolved from `os.Args`) and owns the single `os.Exit` via a panic-recovering exit shape — **bare `os.Exit` outside `main` is prohibited** (the daemon self-eject is the one sanctioned exception, and it pairs itself via `log.Close`). `process:` lifecycle markers (`start` / `exit` / `exec` / `panic` / `log-level resolved`) bracket every run and **bypass the level filter** so they are always present as forensic tripwires.

- **Format & rotation:** human-readable text with a `component:` prefix, so `grep "<component>:" portal.log` reconstructs a subsystem's behaviour at the production-default level (JSON also available from the handler). `portal.log` is a symlink to a calendar-daily `portal.log.<date>`; a size-cap valve overflows to `portal.log.<date>.N`; past-day files are sealed `chmod 0400`. Retention defaults to 30 days with one INFO breadcrumb per deleted file.
- **Closed taxonomy:** 18 component names (the `spawn` component was added by the multi-window-spawn feature, the `resolve` component by the cli-verb-surface-redesign feature, and the `theme` component by the theming-system feature — all spec-governed amendments, not call-site inventions) + a closed attr-key vocabulary + four levels (production default **INFO**). New components/attrs require amending the spec — never invent at call-site. The `spawn` component's attr keys (`batch`/`terminal`/`bundle_id`/`resolution`/`session`/`ack`/`opened`/`total`/`detail`) are likewise spec-governed. The `resolve` component (bound + emitted only in `cmd/open.go`; `internal/resolver` stays a pure, log-free library) carries the `open` resolution-decision line — message `resolved`, attr keys `target` (raw input) / `domain` (session/path/alias/zoxide, or `miss`) / `resolved_path` (resolved directory, or session name for a session hit; empty on a miss) — one INFO line per bare positional resolved through the guessing chain; glob (and pinned) targets are deterministic and emit no line. The `theme` component's attr keys (`slug`/`slot`/`reason`/`path`/`token`/`count`/`rejected`) are spec-governed the same way, and it is legally emitted from three sites across two packages — `internal/theme`'s loader (through an injected `EventLogger` seam that also holds the per-process WARN dedup state, so `portal doctor`, `portal theme export` and `capturetool` construct it via `theme.NewSilentLoader()` and write nothing: the component records where a theme is *used*, never where one is *diagnosed*), `cmd/config.go`'s `appearance` translation, and the `cmd`-owned theme persister — because the rule is bind once **per package**, which `spawn` and `bootstrap` already span several files under; `cmd` holds the single `log.For("theme")` binding. Baseline attrs (`pid` / `version` / `process_role`) are injected per-record by the handler.
- **Env:** `PORTAL_LOG_LEVEL` (`debug`/`info`/`warn`/`error`, invalid → `info` + WARN), `PORTAL_LOG_ROTATE_SIZE` (e.g. `500M`/`1G`, default 500 MiB), `PORTAL_LOG_RETENTION_DAYS` (default 30). `portal doctor --fix` forces a full log-retention sweep as a maintenance side-action.
- **What's instrumented:** every `hooks.json` / `aliases` / `projects.json` mutation emits a breadcrumb from the **store method** (the chokepoint, not the caller), including one INFO line per key the hooks clean-stale sweep removes, carrying the removed `on-resume` command so a reaped hook is recoverable at the production default level; cycle summaries (`capture: tick complete`, `bootstrap: orchestration complete`, `restore: skeleton/geometry complete`, `spawn: opened N/N`, the `clean:` sweeps) emit one INFO per cycle with per-item detail at DEBUG; saver/daemon lifecycle and the hydrate exec chain have closed event catalogs.

### DI / testing pattern

All external dependencies use small interfaces (1-3 methods). Commands expose package-level `*Deps` structs (e.g., `bootstrapDeps`, `openDeps`, `hooksDeps`) — tests install mocks through the `withXDeps(t, deps)` staging helpers in `cmd/testhelpers_test.go`, each of which registers its own restore in the same breath — `cmd` carries a second seam family alongside those structs: the package-level **function vars** a command body calls through (`openTUIFunc`, `daemonTickLoopFunc`, `osExit`, `versionChecker` and their siblings), staged through the single generic `withFuncSeam(t, &seam, replacement)` in the same file — one helper rather than one per seam, because the type parameter carries what a per-seam helper would spell out, and its restore puts back the **captured production default** rather than nil (unlike a `*Deps` pointer, a function seam's default is a real value, and restoring the zero value would leave a nil func for every later test to call). A source guard (`cmd/seam_guard_test.go`) fails any `*_test.go` assigning either kind of seam directly, and **derives** both families from the production sources so a new seam is covered the day it appears: the `*Deps` arm reads `var xDeps *XDeps` declarations, and the function-var arm takes any package-level var whose declaration says on its face that it holds a function — an explicit `func(…)` type, the name of a func type the package declares, a function-literal initialiser, an initialiser naming a package function, or a qualified `pkg.Name`. That last arm is deliberately generous, since a qualified non-function value is indistinguishable from a function without type information the guard does not have: a var holding one must therefore state its type (as the `io.Writer`-typed `fatalErrorStderr` does), because a spurious seam only costs a helper call while the opposite mistake drops a real seam out of the guard's vocabulary. The one exemption is `TestMain`, which installs package-wide and has no `*testing.T` to restore into. A test that Executes a real command body MUST inject every tmux-touching `*Deps` seam (see the tmux boundary bullet under "Test isolation" — cmd's `TestMain` poisons `TMUX` and the `PORTAL_*` paths package-wide so a missed injection fails loudly). Integration-tagged tests that exec the built binary (e.g. `cmd/root_integration_test.go`, the commit-now suite) build it via `portalbintest` (never a hand-rolled `go build` — the `-tags integration` sandbox must not be dropped) and drive it as a subprocess.

#### Test isolation for daemon-spawning tests

**Lane rule first:** every test that **builds** the `portal` binary, spawns a `portal state daemon`, or execs a built `portal` binary MUST carry `//go:build integration` — a build belongs there for lane purity rather than safety (the fast lane builds no portal binary; the wall-time cost is negligible), the other two for safety as well. The unit lane (`go test ./...`) contains no such tests; the integration lane runs serially (`go test -tags integration -p 1 ./...`).

Any test that runs `portal state daemon` directly OR via `portal open` / bootstrap MUST call `portaltest.IsolateStateForTest(t *testing.T) (env []string, stateDir string)` (in `internal/portaltest/isolated_env.go`) and apply the returned env to every spawned subprocess (`cmd.Env = env`). Without this, the spawned daemon inherits the developer's `$XDG_CONFIG_HOME` and writes to the real `~/.config/portal/state/` — the slow-open / empty-previews / zombie-session incident is the canonical example of how a leaked test daemon corrupts the live install. The helper also registers a `t.Cleanup` fingerprint-diff backstop and fails on any delta. Its reach is narrower than "the developer's install" and deliberately so: the snapshot is taken **after** the helper re-points `HOME` and clears `XDG_CONFIG_HOME`, so it walks the state dir under the per-test temp `HOME` — resolving the real install instead would let the developer's live daemon's own tick writes false-trip the backstop mid-test. So it catches a process that took the scrub and still resolved the default path, not one that escaped the scrub entirely; the backstop is **defence-in-depth, not a substitute** for the env override. No lint or CI enforcement exists — the rule is contributor-discipline plus the structurally-mandatory `*testing.T` parameter (which prevents importing the helper from non-`*_test.go` code).

The returned env slice also carries a **poisoned `TMUX`** (`portaltest.PoisonedTmuxSocket`): the test process usually runs inside the developer's real tmux, and a subprocess inheriting the ambient `TMUX` (or falling back to the default socket) silently attaches to the REAL server — a real orphan daemon was observed capture-paning the developer's live sessions this way. Every subprocess that needs a server must append its own `TMUX=<test socket>,0,0` AFTER the slice (`exec.Cmd` env dedupe is last-wins); one that forgets fails loudly at connect time. `SpawnIsolatedDaemon` does this via its required `tmuxSocketPath` parameter.

For daemon-spawning tests, prefer `portaltest.SpawnIsolatedDaemon` (which pins both `PORTAL_STATE_DIR` and `TMUX`) + `portaltest.RegisterSubprocessCleanup` over hand-rolling `exec.Cmd` / `cmd.Wait`. These helpers wrap the canonical SIGKILL+Wait+reap pattern that prevents zombie subprocesses and ensures the test's `*testing.T` sees deterministic teardown order — both are load-bearing on macOS where unreaped subprocesses can hold open the state dir's file descriptors past the test's `t.Cleanup` window. Fixtures whose tmux server can host writers at teardown (a saver daemon's SIGHUP flush, session-closed hook subprocesses) should also call `portaltest.RegisterStateDirTeardownGuard(t, stateDir)` — registered after `IsolateStateForTest`, before `tmuxtest.New` — so the bounded quiescence wait runs between kill-server and the TempDir RemoveAll (fixes the "TempDir RemoveAll: directory not empty" teardown flake).

**ABSOLUTE INVARIANT — a test must NEVER mutate or affect the real system: not the filesystem outside its temp dirs, not the default tmux server, and NOT any OS process the test did not spawn.** All tests run on the developer's machine (there is no CI), so the developer's live `portal state daemon` is always present during a test run. Isolation therefore spans three boundaries, all mandatory:

1. **Filesystem / state** — `IsolateStateForTest` (above); the fingerprint backstop backs it up.
2. **tmux** — only a per-test `-L <unique>` socket via `tmuxtest`; **never** the default socket — including **indirectly**: a test that Executes a real Cobra command body (no `*Deps` injection) inherits that body's production wiring, and several bodies build `tmux.DefaultClient()`, which honours the ambient `TMUX` — the developer's REAL server when tests run inside tmux. *Incident of record #2 (pre-redesign history — `portal state cleanup` was since folded into `portal uninstall` and one of the two tests, `TestStateUserFacingSubcommandsExitZero`, removed; the surviving `TestVersionGuard_NotInvokedForExemptCommands` now Executes the `uninstall` body with its `*Deps` injected): two cmd tests ran the real `portal state cleanup` body uninjected — on every `go test ./cmd` it kill-sessioned the developer's live `_portal-saver` (SIGHUP'ing the real daemon) and unregistered the real global hook table. This was the saver-churn mystery in the developer's portal.log.* Any test Executing a real command body must inject the command's `*Deps` seam for every tmux-touching dependency. **Enforcement is structural:** the cmd package's `TestMain` poisons `TMUX` package-wide (the tmux-boundary counterpart of its `PORTAL_*_FILE` path poison), so a missed injection dials a dead socket and fails loudly instead of silently reaching the real server — this poison immediately caught two further offenders when introduced (an uninjected full-production-bootstrap `portal list` Execute — the creator of the phantom 0.8.3 saver daemons — and a partially-injected commit-now deps struct whose nil `IsRestoring` defaulted to a live `DefaultClient` query). Tests that assert inside/outside-tmux *behaviour* must `t.Setenv` `TMUX` themselves; tests needing a real server use `tmuxtest`'s explicit `-S` sockets, which override `TMUX`.
3. **Processes** — the daemon is identified **machine-wide by argv** (`pgrep -fx '^portal state daemon( |$)'`), so state/file isolation does **NOT** make a test daemon distinguishable from the developer's real daemon at the process level. An unscoped sweep in a test will SIGKILL the real daemon. **Enforcement is structural, not disciplinary:** `state.PgrepPortalDaemons` is filtered by a **default-deny daemon-pgrep sandbox** (`internal/state/pgrep_sandbox.go`, `//go:build integration`, compile-time absent from production) that surfaces only daemons the test registers. `IsolateStateForTest` enables it; `SpawnIsolatedDaemon` (orphans, by pid + state dir) and the saver-read helpers (by live `_portal-saver` pane_pid — respawn- and daemon.pid-manipulation-immune) register ownership. Because the sweep only SIGKILLs PIDs its `Pgrep` seam returns, an unregistered PID (the real daemon — including after its own churn respawns) can never be a kill candidate. `TestPgrepSandbox_ExcludesUnregisteredPID` proves the exclusion. **Do NOT** run the production orphan sweep, `state.PgrepPortalDaemons`, or any `pgrep`/`pkill`/broad-signal path in a test without `IsolateStateForTest` active, and never reintroduce a machine-global destructive process op in a test. *Incident of record: a global-`pgrep` sweep integration test repeatedly SIGKILL'd the developer's live daemon (unpaired `process: start` with no `exit` in portal.log) — file isolation held; process isolation did not exist until this sandbox.*

   **The sandbox crosses the process boundary via a registry file.** A test-spawned `portal` binary runs its bootstrap orphan sweep in its own process, where in-process registrations don't exist — and the sweep runs at step 4, *before* `EnsureSaver`, so its legitimate set is empty and an unfiltered enumeration would SIGKILL the real daemon (verified with a pgrep-shim canary harness during the fix). Two pieces close it: `portalbintest` builds every test-staged binary with **`-tags integration`** (compiling the sandbox in; the shipped release binary never carries it), and `IsolateStateForTest` sets **`state.SandboxRegistryEnv`** (`PORTAL_TEST_SANDBOX_REGISTRY`) — the path of a file listing test-owned state dirs, re-read on every enumeration (`SpawnIsolatedDaemon` appends each orphan's dir). Env set + file unreadable ⇒ enabled with zero owned dirs (subprocess sweeps kill nothing). `TestPgrepSandbox_RegistryEnvActivatesCrossProcess` pins the contract. Never hand-roll `go build` for the portal binary in a test — route through `portalbintest` so the tag is never dropped.

#### Cleaning up after a test run

Test runs leak. A `tmuxtest` socket whose server outlives its test keeps running (measured: 113 leaked `ptl-*` servers accumulated over ~18 hours of runs, alongside a live `portal state daemon` each), and an agent that spawns synthetic CPU load (`yes`, busy-loop subshells) to probe a flake orphans it to PID 1 when `kill %1 %2 …` silently fails in a shell with no job control — twice observed in one session, 14 processes each time. The cost is not tidiness: a saturated machine makes timing-sensitive suites fail on budgets that pass when idle, so leaked load **manufactures flakes and misattributes them to the code under test**. Sweep at the end of a session that ran the integration lane, and treat a load average far above core count as a reason to sweep before trusting any timing result.

**The developer's live tmux server must never be touched, and identifying it is not optional.** It hosts their real work (~47 sessions at the time of writing) and Portal's own `_portal-saver`. Before signalling anything:

1. **Read `$TMUX`** — its format is `<socket>,<server-pid>,<session-id>`. The middle field is the live server's PID and the first is its socket (`/private/tmp/tmux-501/default` on this machine). Both are protected values.
2. **Match targets on an explicit test socket in argv**, never on the process name: every disposable server carries `-L ptl-<something>` or `-S <tmpdir>/ptl-*/s`. The developer's server carries **no socket flag at all** (`tmux new-session -d -s _portal-bootstrap`), so a pattern keyed on `ptl-` cannot select it. Do not match on `tmux`, on `_portal-bootstrap`, or on session names — `_portal-bootstrap` and `_portal-saver` exist on both the real server and the test ones.
3. **Exclude the protected PID explicitly**, as a guard independent of the pattern, and assert it is absent from the kill list before sending a single signal.
4. **Re-verify each PID's argv immediately before signalling it** — a PID enumerated seconds ago may have exited and been reused. Confirm it still matches the test-socket pattern at signal time.
5. **SIGTERM first, SIGKILL only stragglers**, and afterwards assert the developer's server is still alive with its session count unchanged and their `portal state daemon` still running.

For orphaned load generators, match the exact command (`ps -eo ppid,command | awk '$1==1 && $2=="yes"'`) rather than a substring — `pkill -f yes` would match any command line containing those three letters. Better still, do not create them: prefer running a suite under a real integration lane than simulating load, and if load is genuinely needed, spawn it with a bounded lifetime (`timeout 60 yes`) so a failed cleanup cannot outlive the experiment.

This sweep is a **human-invoked maintenance action, not something a test may do**. The ABSOLUTE INVARIANT above still holds without exception: no test, helper or fixture may enumerate or signal a process it did not spawn.

### Server bootstrap

`PersistentPreRunE` runs a ten-step `bootstrap.Orchestrator` (in `cmd/bootstrap/`) for commands needing tmux (all except the bootstrap-exempt `skipTmuxCheck` set: `version`, `init`, `help`, `alias`, `hook`, `doctor`, `theme`, `uninstall`, `state`, and the internal `__complete` completion verb). Step ordering is load-bearing; "Return" is the post-step boundary, not a numbered step:

1. **EnsureServer** — start the tmux server if not running. `StartServer` creates the server with an initial detached session named `_portal-bootstrap` (`tmux.PortalBootstrapName`) — an **intentional, permanently-present anchor**, not a leak. A tmux server with zero sessions exits immediately, so this session keeps the freshly-started server alive long enough for the rest of bootstrap (notably `EnsureSaver` and `Restore`) to run. It is created on every cold server start and is **never killed by production code**; like `_portal-saver`, its leading-underscore name is filtered out of `ListSessions` and excluded from `sessions.json` capture, so it is invisible to the picker and never saved/restored. Do **not** mistake its lingering presence in raw `tmux list-sessions` output for an orphan to clean up — it is load-bearing.
2. **RegisterPortalHooks** — install global tmux hooks (e.g. `client-attached` running `portal state signal-hydrate`) idempotently. Registration is declarative per-event "ensure exactly one": each managed event is read via `ShowGlobalHooksForEvent` (`show-hooks -g <event>`) and converged to a single Portal entry carrying the current desired body. Per-event reads are mandatory because the no-arg global `show-hooks -g` is blind to `pane-*`/geometry `window-*` events on tmux 3.6b — the blind spot that previously let duplicate `portal state notify` hooks stack unbounded on `pane-focus-out`/`window-layout-changed`; any pre-existing stack now self-collapses to one on the next bootstrap (no dedicated cleanup migration). `UnregisterPortalHooks` (invoked by `portal uninstall`) reaps via the same per-event seam, and `managedEvents` is the single source of truth from which both the teardown event set and the teardown fingerprint set are derived. The former `migrateHydrationHooks` / `migrateSessionClosedHook` one-shot helpers are folded into this unified convergence path.
3. **Set `@portal-restoring`** — must precede saver/restore so the daemon and hydrate helpers can detect they are inside a restoration window.
4. **SweepOrphanDaemons** — best-effort `pgrep -fx '^portal state daemon( |$)'` enumeration; identity-checked SIGKILL of any candidate that is not the `_portal-saver` pane's PID. Runs before `EnsureSaver` so the new saver-pane daemon's first tick is uncontested by leftover daemons from prior server lifetimes. Composes with the kill-barrier in `EnsureSaver` (which handles the single recorded `priorPID`) to converge multi-orphan installs to a singleton in one bootstrap. Errors log at WARN under `ComponentBootstrap` and are swallowed; never escalates to a fatal abort.
5. **EnsureSaver** — bootstrap (or version-upgrade) the `_portal-saver` detached session that hosts `portal state daemon`. Best-effort; failure surfaces as a `SaverDownWarning`.
6. **Restore** — invoke `internal/restore` to reconstruct skeleton + geometry + scrollback FIFOs from the saved state. Never escalates to a fatal abort; corrupt state surfaces as a warning.
7. **EagerSignalHydrate** — best-effort write of the hydrate signal byte to every freshly-armed `@portal-skeleton-*` pane's FIFO. Production wiring uses `state.DefaultFIFOSignaler` / `state.SendHydrateSignal` — the no-seam entry point that pins `OpenFIFOForSignal` + `time.Sleep`. The lower-level `state.WriteFIFOSignal` is the seam-bearing variant used only for retry-ladder unit tests. Runs while `@portal-restoring` is still set so daemon `captureAndCommit` suppression remains in force during helper-driven scrollback replay. Eliminates the per-session signaling gap that would otherwise leave N-1 saved sessions' helpers waiting on `client-attached` events that never fire for non-attached sessions. A non-nil return logs at WARN under `ComponentBootstrap` and is swallowed; never escalates to a fatal abort.
8. **Clear `@portal-restoring`** — fatal on failure (the marker must not leak past bootstrap).
9. **CleanStaleMarkers** — best-effort cleanup of `@portal-skeleton-*` server-option markers whose paneKey is no longer represented by a live pane. Runs after Clear so it observes post-restore tmux state, and before Sweep so any stale markers protecting orphan FIFOs are unset first, allowing those FIFOs to be reclaimed in the same bootstrap.
10. **SweepOrphanFIFOs** — best-effort cleanup of orphan `hydrate-*.fifo` files whose paneKey is no longer represented by a live `@portal-skeleton-*` marker.

(The former step 11 **CleanStale** — hooks stale-entry cleanup — was removed from the orchestrator and re-homed on the `_portal-saver` daemon, which runs it (alongside a throttled stale-`projects.json` prune) on a throttled idle-tick cadence; `portal doctor --fix` is the manual backstop.)

After step 10 the orchestrator returns the accumulated warnings. How they (and the per-step progress) reach the user depends on the path — see **Cold-path startup flip** below: the warm / CLI path runs the bootstrap synchronously and drains warnings post-bootstrap (or after the `LoadingMinDuration` = 1.2s loading-page pad), while the cold + TUI path runs it concurrently and warnings ride the progress channel to a post-load notice band.

### Cold-path startup flip (concurrent bootstrap)

On the **cold + TUI path** — a fresh tmux server *and* the TUI picker, decided by a cheap `tmux has-server` probe (`shouldRunConcurrentBootstrap`) — the ten-step bootstrap runs **concurrently** with the TUI instead of synchronously in `PersistentPreRunE`. Bubble Tea launches immediately on the honest loading page; the orchestrator runs in a goroutine streaming a `tea.Msg` per real step (and per restored session) over a **progress channel** (`cmd/bootstrap_progress.go`, `cmd/bootstrap/progress_emitter.go`) carrying `serverStarted` + progress, and the model transitions to Sessions on `BootstrapCompleteMsg`. The ten real steps map to **5 friendly labels** (`internal/tui/loading_progress.go` is the single mapping authority); only `Restoring sessions` carries the `N/M` counter, fed by a per-session callback injected at `internal/restore/restore.go`. A **fatal** step becomes a `tea.Quit` with an in-TUI `state.destructive` error frame + non-zero exit (not a `PersistentPreRunE` error return); **soft warnings** ride the channel and surface as a post-load notice band after the picker appears (replacing the old stderr/alt-screen flush). The first real paint gates on the detect-or-timeout appearance gate whenever the loaded nomination is an adaptive pair (a constant paints from frame one), so the correct canvas shows from frame one.

The **warm path** (server already up — `serverStarted=false`) and the **CLI / direct-path** (`!isTUIPath`) keep today's untouched synchronous bootstrap with no loading page and zero new risk. The TUI is inert during loading (animation only), which contains the restore/daemon race surface. Startup-ordering and warm-path parity are covered by `cmd/concurrent_*_test.go` (daemon-spawning tests under `IsolateStateForTest`).

### Daemon self-supervision

The `portal state daemon` runs a per-tick **saver-membership self-check** before each `captureAndCommit`. On every ticker fire (1s `TickerPeriod`), the daemon asks "am I still the pane process of the live `_portal-saver` session?" via `tmux.SaverPanePIDOrAbsent` plus a `pane_pid == os.Getpid()` comparison. A failing probe (saver absent, pane pid mismatch, or transient tmux error) increments an in-process consecutive-absence counter. A passing probe resets it to 0.

When the counter reaches `selfSupervisionHysteresisTicks = 3` consecutive ticks (declared in `cmd/state_daemon.go`; clamp-floor + clamp-ceiling pinned by `TestSelfSupervisionHysteresisTicks_ClampInvariant`), the daemon ejects in a fixed, load-bearing order:

1. Emits `daemon: self-eject ticks=N threshold=3` (INFO under the `daemon` component).
2. Calls `log.Close(0)`, which emits the paired `process: exit code=0` lifecycle marker (and does **not** itself exit) — so the self-eject stays a *marked* termination and the four-way `process:` classification holds (no unpaired `process: start`).
3. Calls `os.Exit(0)` immediately (via the `osExit` seam) — bypassing `daemonShutdownFunc` so the divergent-view daemon does **not** execute one more `captureAndCommit` / `gcOrphanScrollback` cycle on its way out (same reasoning as Component A's straight-to-SIGKILL choice). No `daemon: shutdown` line fires on this path.
4. Leaves `daemon.pid` stale on disk. The next acquire's Component C pre-check handles this correctly (recorded PID is dead → pre-check skips → new daemon acquires cleanly). Cleanup logic to delete `daemon.pid` before the eject would be racy against a concurrent pre-check and would invert the layered-enforcement contract — **do not add it**.

The hysteresis value justification is documented in-source above the constant (measured tick counts against real tmux 3.6b, 2× safety factor, clamp result, measurement date). The integration-tagged harness `cmd/state_daemon_hysteresis_measurement_test.go` re-runs the experiment to verify the safety-factor invariant whenever it executes.

### Resume hooks

Per-pane hooks are registered via `portal hook set --on-resume "cmd"` and persisted in `hooks.json` (the CLI verb is `hook`; `hooks` remains a permanent, silent cobra alias — the `hooks.json` filename and the `hooks` log component keep the plural, unchanged). `portal hook rm --on-resume` removes the entry for the current pane (resolved from `$TMUX_PANE`); pass `--pane-key <key>` as a literal pass-through to remove an entry for any hook key, bypassing the `$TMUX_PANE` requirement (enables pruning of entries whose pane no longer exists). **`hook rm` exits 0 iff it removed an entry** — the answer comes from the removal itself, never from a read taken before it — so removing nothing is always non-zero: tmux's own words for a pane no live pane answers to, `no resume hook registered for this pane` for a live pane carrying no token (decided before the store is consulted, so no empty key reaches a mutation), and `no resume hook registered for <key>` for any key naming no entry, on either path. Removal neither mints nor unstamps a token and touches no dirty flag.

**A hook key is the pane's own durable token and nothing else** — the value of its `@portal-pane-id` pane user-option (`state.PortalPaneIDOption`, the sole home of the literal), carrying no session component and no `window.pane` coordinates, so no rearrangement tmux can perform — within a window, across windows, or across sessions — changes it, and renaming a session cannot desynchronize it. Stamping is **lazy**, because Portal does not create panes and a pane with no hook needs no token: `portal hook set` reads the pane's token first and mints one (`nanoid.NewPaneTokenGenerator`, the width `IsTokenShaped` reads) and stamps it with `set-option -p` only when it reads back empty — a pane already carrying a token keeps it, and re-registering issues no `set-option`. There is no inheritance: a pane created by `split-window`/`new-window` from a stamped pane reads back empty. The stamp lands **before** the `hooks.json` write and a failed stamp ends the command non-zero with nothing written; the mirror state — stamp succeeded, write failed — is left exactly as it is, with **no rollback and no unstamp** (unstamping races a concurrent registration that already read the token), and the next registration reuses the token. Key-producing sites: registration and the `$TMUX_PANE` removal path read the token live via `tmux.ResolveHookKey` (`HookKeyFormat`), stale-cleanup and `hook list`'s location column both enumerate live tokens via `tmux.ListAllPaneHookKeys` (one row per live pane), and restore bakes its keys from **saved** state by reading `Pane.PortalPaneID` off `sessions.json` (a struct field read, not a formatting call — an empty saved token bakes no key and the pane restores with no hook).

They fire **only inside the hydrate helper's exec chain** (`portal state hydrate`), launched as the initial process of each restored pane via `respawn-pane -k` during bootstrap step 6. After scrollback replay the helper looks up the baked `--hook-key` in `hooks.json` and exec's either `sh -c '<HOOK>; exec $SHELL'` or a bare `$SHELL` — meaning hooks fire on reboot recovery, not on every detach/reattach inside the same tmux server lifetime. The firing path **must never read the live pane token** (an ordering trap): the baked key is a pure function of saved state, so firing is correct independent of the restore re-stamp's timing. The baked key is the pane's own saved token, so a lookup stays addressable however tmux renumbers windows and panes on restore. Stale hook entries are cleaned lazily by the daemon and explicitly via `portal doctor --fix`.

**A key the staleness rule cannot judge is retained forever — deleting one is data loss.** The rule (`internal/hooks`'s `StaleKeys`, the single home every reader routes through — the daemon's throttled sweep, `portal doctor --fix`, and `doctor`'s read-only count) calls a persisted key stale only when it is absent from the live token set **and** its shape is one the rule can judge: token-shaped per `nanoid.IsTokenShaped`, or empty. Any other shape is left untouched on every run, permanently. In practice that is the pre-token `<session>:<window>.<pane>` key, which always carries `:` and `.` — neither in the id alphabet — so it can never be mistaken for a token: it names no pane any enumeration can answer for, so its liveness is unknowable and reaping it would be a guess. The entry holds a user-authored `on-resume` command with no other copy anywhere, and there is no route back once it is gone; the only sanctioned removals are the user's own `portal hook rm --pane-key <key>` and a hand edit. Such an entry is **inert but not cruft** — it can never fire (a fired key is always a token baked from saved state) and it may sit beside a token-keyed entry for the very same pane, which is the expected steady state after an upgrade, not a duplicate to reconcile. Do not add an expiry, a migration, or a "tidy old-format keys" pass: the retention *is* the safety property.

**A registration landing in the enumeration gap is never reaped.** A clean's live-token enumeration runs with no lock held, so a `hook set` can be written after that enumeration was taken and before the deletion's exclusive hold opens — and its key would then be absent from the live set and token-shaped, which is stale by the rule. `internal/hooks` forecloses it structurally rather than by timing: `CleanStale` reads its **snapshot** of `hooks.json` *before* handing the enumeration out, and `deleteStale` (which derives its delete set from the file as it stands under its own hold) narrows that set to the snapshot via `narrowToSnapshot`. Narrowing only ever drops candidates, never adds one, so the worst case is a genuinely-stale key surviving to the next sweep — a key the snapshot never held can never be deleted, whatever the live set says.

**The `hooks.json.lock` sidecar is absent on every install in the wild.** It is created only by a mutation acquire (`acquireMutationLock`, `O_CREATE`) — a `hook set`, a `hook rm`, or a clean's deletion phase — so no existing install has one until its first such acquire after the release that introduced it, and `migrateConfigFile` renames `hooks.json` alone, so an install arriving from the old macOS Application Support path arrives without its sidecar too. The unlocked degraded read is therefore the **common** path immediately after release rather than an edge case: it is correct (`AtomicWrite` renames, so no reader sees a torn file) and it is why a read is never failed for want of the lock — expect `load-unlocked` DEBUG breadcrumbs in volume there, and do not read them as contention.

### Modern Vivid TUI

The picker is reskinned to **Modern Vivid (MV)** — a token-based design on an owned canvas. This is a *reskin, not a rebuild*: the list model, grouping, filtering, and persistence are behaviourally unchanged; the structure below is the styling layer.

- **Owned canvas.** Portal paints its own opaque backdrop on every cell — the **active theme's `canvas` token**, whichever theme that is (three built-ins ship; a drop-in supplies its own) — in two layers: leaf styles carry `.Background(canvas)`, and an **outer full-terminal fill** (the last layer in `model.go`'s `View`) pads to `termW × termH` so no edge bleeds and empty rows are painted. The fill never participates in the list's height budget, so a vertical change (e.g. a notice band appearing) re-pads underneath it without perturbing the one-row-per-delegate pagination invariant. `restore.go` set-and-restores the terminal *default* background via OSC 11 (see the `tui` row).
- **Light/dark detection (`appearance_gate.go`).** The loaded **nomination** decides whether detection runs at all: a **constant** skips the gate entirely and paints from frame one, while an **adaptive pair** arms it and it resolves exactly once before anything is painted. When armed, the canvas is chosen by a **detect-or-timeout first-paint gate**: an OSC 11 query (`tea.RequestBackgroundColor`) races a ~50ms timeout; the first to resolve wins (single-resolution — never paint-then-flip), with a **dark** no-answer fallback. `NO_COLOR` is the one carve-out: no canvas, no detection, colourless render on the terminal's native fg/bg (state stays glyph-backed — `●`/`▌`/`⚠`/`✓` — never colour-only).
- **Render structure (files in `internal/tui`).** Shared chrome: `header.go` (block `PORTAL` wordmark + `accent.primary` `▌` caret + subtitle + 2px rule), `section_header.go` (page label + count + `/ to filter` hint), `footer.go` / `filter_footer.go` (condensed keymap footer + right-aligned `? help`; `footer.go`'s `assembleRightAnchoredRow` is the shared left-cluster/right-anchor geometry). The **keymap descriptor** (`keymap.go`, `keymapEntry` with `Core` / `RightAligned` / `Destructive` flags) is the single source for **display** — it drives the footer, the `?` help body, and the theme panel's vertical footer (`themePanelKeymap`); `keymap_dispatch_guard_test.go` — and `keymap_dispatch_guard_theme_test.go` for the panel and its confirm — guards descriptor↔dispatch drift (dispatch is separate). Modals share a **blank-screen layer** (`modal.go` clears the page to the canvas + `placeModalOnClearedCanvas`) and a joined-panel frame (`panel.go`'s `renderJoinedPanel`): `help_modal.go` (descriptor-driven `?` help), `kill_modal.go` / `delete_modal.go` over the shared `destructive_confirm.go` builder, `rename_modal.go`, and the two-mode `edit_modal.go` (see grouping section). The **theme slide-over** is the one panel that is *not* a modal: a block spanning the content region's full height at its right edge, 24 or 30 columns wide (`themePanelWidthFor`'s two-stage ladder), with a left border only (no top, bottom or right edge), composited as an **opaque** layer over the already-composed page — the page beneath is deliberately not re-laid-out, so a theme swap stays an O(1) restyle and the previewed screen never reflows under the user. Its files: `theme_panel.go` (state, entry gate, list construction, key dispatch), `theme_panel_geometry.go` (width ladder, render floor, chrome/list height split), `theme_panel_render.go` (top-to-bottom block assembly + the z-layer composite), `theme_panel_commit.go` / `theme_panel_confirm.go` / `theme_panel_message.go` / `theme_panel_footer.go` (the commit keys, the slot-from-constant confirm, the single-slot message row, the vertical keymap footer), plus `theme_row.go` (row delegate + truncation), `theme_seams.go` (the `ThemeSource` seam) and `theme_state.go` (the model's theme machinery, outliving any one panel open). Notice bands route through a **single-slot arbiter** (`notice_band.go`) — the `▌` left-bar no-tags signpost / command-pending banner / inline flash (`sessions_flash.go`) — placed under the title separator, recomputing the list height when they appear/clear. Edge states: `empty_states.go`, `filtering_no_matches.go`. The honest loading screen is `loading_view.go` (+ `loading_progress.go`).
- **Keymap revision (§12.2).** Navigation is **arrows only** — all vim aliases (`h/j/k/l`, `g/G`), `PgUp/PgDn/Home/End`, and uppercase bindings are dropped (move `↑`/`↓`, page `Ctrl+↑`/`Ctrl+↓`); `pinArrowOnlyNav` strips them from the live `bubbles/list` keymap on **all three** lists — Sessions, Projects and the theme slide-over, where the pin is load-bearing for a further reason: the v2 default binds `l` and `d` to NextPage, and both collide with the panel's own commit keys. `k` = kill (Sessions); `d` = delete (Projects); `x` toggles Sessions⟷Projects in both directions; `s` is Sessions-only (cycle grouping); `t` opens the theme slide-over (Sessions and Projects); `?` is newly bound (it was previously swallowed so `bubbles/list` couldn't self-toggle help) and opens the per-page help modal.

### Session grouping & tags

The sessions list renders in three modes cycled by the `s` key on the sessions page: **Flat** → **By Project** → **By Tag** → Flat. The cycle is unconditional (always includes By Tag, even with zero tags or zero sessions) and the last-used mode persists in `prefs.json` on every press (best-effort; failure non-fatal). The mode shows in the title via `SessionListTitle()` (`Sessions` / `Sessions — by project` / `Sessions — by tag`); the footer adds only an `s switch view` hint. While the `/` filter is focused `s` is a literal filter character.

- **Tags are directory-anchored (v1).** Tags live on the `Project` record (`projects.json`), not per session. A session's effective tags = its directory's tags, looked up live at grouped-render time. Tags are managed only in the projects edit modal (a Tags chip-field beside Name/Aliases), never per session and with no CLI. The edit modal (`edit_modal.go`, spec §8.2) is a **two-mode (navigate/edit) immediate-persist** model uniform across all three fields — a deliberate behaviour change from the old "tags persist live, Name/Aliases batch" asymmetry, so **Name and Aliases now persist immediately too**. Navigate mode: `Tab`/`Shift+Tab` (or `↑`/`↓`) move between fields, `←`/`→` move across chips + the trailing `+ add` slot (entering a chip field lands on `+ add`); `x` deletes a focused chip; `Esc` closes. Edit mode (one element live, entered by `Enter`/`e`, or `Enter`/`+` on `+ add` which spawns an empty chip already in edit): `Enter` **commits & persists that single item** (no dirty state, no save key, no batch), `Esc` discards just that edit (a brand-new empty chip vanishes). Falling-out rules: empty-on-commit deletes, empty Name reverts to prior, duplicate-on-commit silently dedupes (tags case-sensitive). `Esc` never discards saved work. A tag change reloads projects so the grouping index refreshes. Deferred: per-session `@portal-tags` + `--tag=`, live-grouped filtering, tag exclusion.
- **Session → directory resolution.** Each live session is mapped to its directory via the `@portal-dir` session user-option (stamped at creation from the git-root — by both `create.go` and `QuickStart`, so a session stays anchored to its origin dir even after the pane `cd`s away). When absent (legacy sessions created before the stamp shipped), the grouped render derives the directory from the active pane's `current_path` → git-root and uses it for *this* render, caching the guess **in-memory** (into `m.sessions`, so later rebuilds in the same picker session skip the pane read) — gated to grouped modes only; Flat and the zero-tags signpost perform zero pane reads. The guess is never stamped back to tmux (drift would freeze a wrong dir); it re-derives on the next picker launch, so a session that has `cd`'d back self-corrects. The lookup key and stored `Project.Path` are both reduced via `project.CanonicalDirKey`.
- **Render-layer grouping (the key invariant).** Group headings are **real, non-selectable `HeaderItem` rows** interleaved before each group's session rows by `injectGroupHeaders` — every list row (header or session) is exactly one delegate line, so `bubbles/list` pagination is exact and a page can never render more lines than the viewport (the earlier in-`SessionItem` heading injection drew uncounted extra lines, overflowing the frame so the terminal scrolled the title and cursor off the top — the original cursor-invisible / missing-title / left-shift bug). `HeaderItem.FilterValue()==""` so headers vanish the moment a filter query is typed (flatten-on-filter for free); `ensureSessionRowSelected` + `skipHeaderRow` keep the cursor on session rows for initial selection and arrow/paging nav across group boundaries (the §12.2 keymap revision dropped `g`/`G` and the other vim/page-jump aliases — see "Modern Vivid TUI"). Indentation (delegate): group headers are indented to align with the title box's left edge (`groupHeaderIndent`, col 2); grouped session rows nest one level further in (`groupRowIndent` — cursor at col 2, name at col 4) when `GroupKey != ""`; Flat rows render flush at col 2 as before. By Project is Pattern A (one item per session under its project name; key is canonical path). By Tag is Pattern B (one item per `(session, tag)` pair — a multi-tag session repeats under each heading). Unresolved/untagged sessions collect in pinned **Unknown** (By Project) / **Untagged** (By Tag) catch-alls (counted, empty-suppressed, each with their own `HeaderItem`). Zero-tags-anywhere By Tag shows a "No tags yet" signpost over the plain list (degrade-with-message, not silent flatten). `internal/tui/model.go`'s `rebuildSessionList` is the single chokepoint all entry points (the `s` toggle, `SessionsMsg` refresh, `ProjectsLoadedMsg`, and the projects-edit → sessions transition) route through. **Build constraint:** the picker must not be routed through `lipgloss/tree` — grouping is pure `lipgloss` styling layered into the existing `SessionDelegate`.

### Multi-window spawn (`portal open` multi-target + multi-select)

`internal/spawn` is **one service reached two ways**: the **`portal open` multi-target burst** (`cmd/open_burst.go` / `cmd/open_burst_run.go`, driven when `open` gets 2+ targets or a K≥2-expanding glob) and the **in-process picker burst** (Sessions-page multi-select). Both run the identical flow: detect host terminal → pre-flight → sequential spawn of the N−1 external windows → self-connect the calling window to the Nth. **Net N windows, never N+1** (hard invariant): the trigger window is reused as one session (via the existing `AttachConnector` outside tmux / `SwitchConnector` inside, or a local mint when the trigger surface is a mint), so only the N−1 others are externally spawned. The spawned windows run `portal open --session <name> --ack …` (or `--path <dir>` for a mint), **not** a separate spawn CLI.

- **Detection** is a standalone op (not an adapter method — the unsupported banner needs identity without spawning): outside tmux → env fast-path (`GHOSTTY_*`/`__CFBundleIdentifier`) else self-walk the process tree; inside tmux → enumerate the session's clients via `list-clients`, then **select-winner-then-locality-check** (`detectInsideTmux`, `detect_inside.go`): pick the **triggering client** — the most-active by `client_activity` across **all** clients, local and remote alike, first-listed winning an exact tie — and walk **only that winner**. This gates locality on *the client the user is acting through*, not on "is any host-local client attached to the session" (the inverted filter-then-tiebreak order was the root cause of the remote-trigger-spawns-on-local-terminal bug: a remote trigger with a host-local bystander on the same session used to drive windows onto the wrong machine). Resolves the winner's `client_pid → process-tree → .app` to a macOS **bundle id** (via `defaults read` of Info.plist), **family-matched** (`dev.warp.Warp-*`). A remote/mosh winner (**even with a host-local client also on the session**), an empty client list, or a transient `ps`/`defaults` error on the winner walk → NULL → unsupported → honest no-op (the transient case **fails safe to NULL** — never spawn on uncertainty — and additionally logs a `spawn` WARN). Walking only the winner deliberately drops the old "one flaky `ps` cannot mask a resolvable local client" resilience for the winner — an owned trade of resilience for correctness. Runs **once per picker session**, cached, off the ~50ms first-paint gate; `rebuildSessionList` must not re-walk.
- **Adapters** implement `OpenWindow(command []string) Result` only. Resolution precedence: **config (`terminals.json`) → native Ghostty → unsupported** (within config, most-specific wins: exact bundle id → `.app`/alias → longer glob → bare `*`). The spawn layer composes the command (`<os.Executable()> open --session <session> --ack <batch>:<token>`, or `--path <dir>` for a mint surface) as an **env-self-sufficient argv** (`/usr/bin/env PATH=<picker's PATH> …` with `TMUX`/`TMUX_PANE` stripped — the spawned N−1 must run *out* of tmux) and hands `{command}` to the adapter verbatim, so no adapter/recipe needs an env slot. Using `os.Executable()` (not a PATH lookup) keeps the spawned binary version-identical so the warm-command latch (`state.BootstrappedLatchSatisfied`) stays satisfied → each spawned `open` is an abridged fast-path, not a full bootstrap. All OS/terminal specifics (osascript, `-1712`/`-1743` AppleEvent codes, TCC) are quarantined behind the typed `Result` taxonomy (`OutcomeSuccess`/`SpawnFailed`/`PermissionRequired` + an `OutcomeUnknown` zero-sentinel; opaque `detail`/`guidance`). The **native Ghostty adapter** (`internal/spawn/ghostty.go`) additionally wraps the argv it is handed in an explicit shell fallback — `ghosttyEmbed` renders `wrapWithShellFallback(command)` = `["bash", "-lc", "<rendered composed argv>; exec \"$SHELL\" -il"]` through the shared `renderCommandString` (which quotes every element through `internal/shellquote` — the nested `'\''` re-quoting; naive concatenation would corrupt the command) — so a burst-spawned window lands at the user's interactive login shell after its session's exec chain finishes instead of dead-ending on Ghostty's "Process exited. Press any key to close the terminal." keypress. `wait after command` is correspondingly **dropped** from `ghosttyScriptTemplate` (the record is now single-field `{command:"%s"}`); the exec'd `$SHELL`, not the flag, keeps the window alive-and-usable. The wrap is argv-agnostic (attach and mint surfaces alike) and Ghostty-scoped by design — the shared `composeOpenArgv`/`renderCommandString` are unchanged, so config `terminals.json` recipes still receive a plain `{command}` with no injected shell metacharacters (a custom terminal's own post-command behaviour is the user's business — an accepted residual).
- **Confirmation is an explicit token ack**, not osascript success: each spawned `portal open … --ack` writes a `@portal-spawn-<batch>-<token>` **tmux server option** immediately before its exec handoff (best-effort — it still execs if the write fails); the burster watches for it with a per-window `spawnAckTimeout` (~8s, timer starts at *each* window's own spawn, so cumulative sequential delay never eats a later window's budget). Missing marker at timeout = failed window. `<batch>`/`<token>` are option-name-safe nanoids (never the renameable session name). The `@portal-spawn-` prefix is namespaced away from `@portal-skeleton-`, so the only all-options enumerator (`ListSkeletonMarkers`) is blind to it; markers self-clean on every terminal path (success / pre-flight abort / reported failure / cancel).
- **Pre-flight + partial-failure contract:** pre-flight `has-session` gates all-or-nothing — any marked session gone ⇒ atomic abort (nothing opens), prune the gone one(s), keep survivors marked (a second Enter retries). Past pre-flight, a per-window failure is **leave-what-opened**: opened windows stay (Portal doesn't own/tear-down host windows), the trigger's self-attach is skipped, and the failed/un-acked sessions stay marked so a retry re-opens exactly those. A `permission-required` result **stops the burst** (every later window would hit the same per-`(source,target)` wall) and surfaces guidance once per batch. Result classification, message renderers, log emission, the exec boundary, and the net-N split are all single-sourced in `internal/spawn` so the open burst and picker burst cannot drift (byte-identical parity tests).
- **Multi-select mode** (`internal/tui`, `m` key) is a general selection mode on the Sessions list: `m` enters the mode marking the currently-highlighted session as the first selection, and a subsequent `m` toggles the highlighted row (zero-selected still reachable — double-`m` toggles the auto-marked row off, `Esc` clears, and entering while the cursor is on a group-header row enters with zero); `Enter` opens the marked set; `Esc` clears+exits. **Selection is keyed on session identity**, so a multi-tag By-Tag session (Pattern B, one row per tag) marks once and shows `●` on all its rows, and the banner counts distinct sessions. Sticky across filter/paging/regroup/`Space`-preview (pruning only an externally-killed session). N=0 Enter exits; N=1 degenerates to a plain attach; N≥2 dispatches the burst as an async `tea.Cmd` (input-locked while pending — only `Ctrl-C`/`Esc` live, which cancels). On a **resolved-unsupported** host terminal `m` is proactively blocked at entry — it sets a plain transient flash (`multi-select isn't available over a remote connection` for NULL/remote, `… on this terminal` for a named-undriven terminal) and never opens the walkable dead-end mode; the retained reactive `decideBurst` no-op still catches the async in-flight window (mode entered before detection resolved), and the `?` help drops the `m` row while it is blocked (call-site filter in `sessionsHelpKeymap()` — the static `sessionsKeymap()` descriptor is unchanged, so `keymap_dispatch_guard_test` stays green). The persistent **unsupported banner is named-only** — its gate `unsupportedBannerActive()` carries an `!m.detectIdentity.IsNull()` discriminator, so a NULL/remote client keeps its standard `Sessions ··· N` header and By-Tag signpost (there is nothing actionable to show), while a named-undriven terminal still gets the `⚠ unsupported terminal — <name> · <bundleID>` + `see docs` banner. The shared reactive-no-op / CLI-burst copy (`spawn.UnsupportedNoopMessage`) is plain language: `can't open new windows over a remote connection — nothing opened` (NULL) / `can't open new windows in <name> · <bundleID> — nothing opened` (named). Single-slot notice-band precedence: `Opening n/N…` → transient flash → multi-select banner → unsupported banner → no-tags signpost (the filter line is not a contender — it claims the section-header row, below the band, so the two co-render). Delivered Paper frames: `sessions-multi-select-active`, `sessions-multi-select-preflight-abort`, `sessions-unsupported-terminal` (dark-only; NO_COLOR glyph-backed).
- **State/observability footprint** is near-zero: reads `terminals.json`, writes only transient `@portal-spawn-*` server options; **does not touch** `sessions.json`, the daemon capture loop, `prefs.json`, or restore. The `spawn` component emits one INFO batch summary (`spawn: opened N/N`, `total` = N incl. the trigger's self-attach target; `opened` = sessions surfaced) + DEBUG per-window, from the chokepoint on both callers.

Uses goreleaser (`.goreleaser.yaml`). Version injected via ldflags: `-X github.com/leeovery/portal/cmd.version`. Tagged releases trigger GitHub Actions → homebrew tap update.
