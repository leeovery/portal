# Implementation Review: Killing All Sessions Wipes Restore State

**Plan**: killing-all-sessions-wipes-restore-state
**Verdict**: Pass

## Summary

All 39 tasks across the nine phases are delivered, and nothing is outstanding. This cycle verified the two remediation tasks, 9-1 and 9-2, and then checked the whole change-set against every specification section again. No verifier raised a finding or a blocking issue.

The previous cycle's replan item is closed. That item was the dump overwriting a positional scrollback name that another pane's committed record still named, after a restore that moved panes:
- A contested tokened pane now writes under its own token-named transcript.
- A contested pane with no usable token keeps its capture, and the capture is written at its positional name only once that cycle's `sessions.json` write has landed.
- A cycle that ends uncommitted writes nothing at a contested name.

The shutdown behaviour was measured again on real tmux:
- The kill-path regression suite passed 4/4 and 3/3, with every kill committed by the real `session-closed` hook's `commit-now`.
- The daemon SIGTERMed 10–30ms before the server preserved the full state in 33 + 22 trials.
- `tmux kill-server` during a save left the state byte-identical in 48 + 48 trials, with 8–11 landings in flight per run.
- The waiting-pane and hardened-pane shutdown suites passed 3/3 each.

The 10–30ms ordering test was also run against the pre-fix tree, and it failed there: a 28ms-lead flush committed `sessions=0`. So the test discriminates.

Linters are clean in both lanes. The host load average reached roughly 290 on 10 cores during these runs, so every timing result was taken under heavy contention. Only the whole-suite run is unmeasured.

The out-of-scope item held from the previous cycle (A4, an order-dependent lazy-resume paste test) stays held for the user's call.
