# Consolidation Tasks: Killing All Sessions Wipes Restore State (Phase 3)

## Task 1: An Answered Lazy Pane Keeps Its Transcript Until A Confirmed Save Replaces It
placement: phase 3
severity: behaviour

**Problem**: A lazy pane's transcript lives in its token-named file while it waits. The housekeeping pass of the first commit naming that path removed the positional name (`internal/state/scrollback.go:95-98`, `gcOrphanScrollback` at `internal/state/commit.go:124`), and the dump skips a waiting pane (`internal/state/scrollback.go:330-337`). Once the user answers the pane, its marker is clear, and `mergeFrozenPanes` carries a previous record only for panes still pending (`internal/state/capture.go:326-349`). So the next capture gives the pane a fresh record naming its positional path (`internal/state/capture.go:585`). Three things can then happen before the first dumping cycle after the answer has written that path with confirmed bytes, and each one commits a record off the token-named file whose housekeeping deletes the transcript:
- the pane's `capture-pane` comes back empty (tmux's shutdown answer to an in-flight read, after the cycle's own confirmation passed). `confirmEmptyCapture` judges the saved transcript at the positional path alone (`internal/state/scrollback.go:291`), finds no file, sends no confirmation, and the writer writes the empty bytes (`internal/state/commit_cycle.go:64-69`). This half contradicts §2.4: the pane's saved transcript is the file its previous record names;
- the pane's `capture-pane` is refused: `dumpPane` writes nothing (`cmd/state_daemon.go:332-341`), but the commit still names the absent positional file;
- the first commit after the answer is a `commit-now`, which dumps nothing (`cmd/state_commit_now.go:115-124` passes no `Dump`), and tmux exits before the daemon's next dump. That is §3.2's three-step loss, reached through a user answer shortly before shutdown instead of a marker cleared at it.

The window is a reboot or `kill-server` landing before the first dumping cycle after an answer (the daemon's idle cadence is 30s, `MaxGap` at `cmd/state_daemon.go:463`; a notify-driven `save.requested` shortens it). The restored pane comes back blank and its transcript is gone.
**Solution**: An answered lazy pane keeps the transcript it had while waiting until a save confirms its new capture. Settled by the user's choice at the phase 3 consolidation walk, on §1.1's rule that every session not killed stays restorable with its scrollback intact. Whatever a cycle does after the answer, a commit names the pane's token-named transcript until a dump has written the pane's new capture with confirmed bytes, so none of the three paths — an empty capture, a refused capture, or a dump-less commit before the next dump — leaves the pane's record off the file holding its bytes or lets housekeeping delete it. The empty-capture check judges the saved transcript at the file the pane's previous record names, not at the positional path alone. The specification records the guarantee beside §2.3's and §2.4's.

**Outcome**: From the moment a lazy pane is answered until a dump writes its new capture with confirmed bytes, every commit — the daemon's tick, its shutdown flush and `commit-now` alike — names the pane's token-named transcript and leaves it on disk, so a reboot or `kill-server` landing in that window restores the pane with its transcript. Once a dump writes the new capture, the commit names the pane's positional file holding it and the housekeeping pass reclaims the token-named file, as it does today.

**Acceptance Criteria**: Each scenario starts from a lazy pane carrying token `T` whose transcript was committed under its token-named file (`scrollback/pane-T.bin`) while it waited, and whose resume-pending marker the user has since cleared by answering it.
- [ ] In the first dumping cycle after the answer — the daemon's tick and its shutdown flush alike — the pane's `capture-pane` comes back empty, and the read sent after it is refused, answered by another server on the socket, or answered naming no server. Nothing is written, the existing `empty capture not confirmed; saved transcript kept` WARN names the pane in `pane_key`, and the commit names the token-named file, still on disk with its bytes. (§2.4, §4.2, §1.1)
- [ ] In the first dumping cycle after the answer the pane's `capture-pane` is refused, or its write fails. The commit names the token-named file, still on disk with its bytes, and every later committing cycle that has not written the pane's capture — a tick, a shutdown flush or a `commit-now` — keeps naming it. (§1.1)
- [ ] The first commit after the answer is a `commit-now`, and tmux exits before any dump runs. `sessions.json` names the token-named transcript, present with its bytes, so the next restore finds the transcript at the path the pane's record names. (§1.1, §3.2)
- [ ] The first dumping cycle after the answer writes the pane's capture with confirmed bytes: a non-empty capture, or an empty one the committer's own server confirms. An empty capture is judged against the token-named transcript, so its confirmation read is sent even though no positional file exists. The commit names the pane's positional file holding that capture, and its housekeeping pass removes the token-named file. (§2.4)
- [ ] However a cycle after the answer ends — committed, stood down, cancelled mid-dump, or with a failed `sessions.json` write, including one whose dump wrote the pane's capture before it ended uncommitted — `sessions.json` never names the pane's positional file while that file is missing from disk. Short of the pane being killed, the token-named transcript is deleted only by the housekeeping pass of a commit naming a positional file that holds the pane's capture. (§2.3, §1.1)
- [ ] A pane that never waited, and a pane still waiting, are saved as today: an ordinary pane's empty capture is judged at its own positional file, and a waiting pane is skipped by the dump and stays filed under its token. (§2.3, §2.4)

**Do**:
- The guarantee lives in `internal/state`'s commit cycle, which all three committers run (`RunCommitCycle`, `internal/state/commit_cycle.go:77-99`): the daemon's tick and shutdown flush through `captureAndCommit` (`cmd/state_daemon.go:255-293`) and `commit-now` (`cmd/state_commit_now.go:115-124`). The sites the findings trace are the fresh positional record a pane no longer pending gets (`buildPanes`, `internal/state/capture.go:573-590`, with `mergeFrozenPanes` at `:327-350` carrying a previous record only for a pending pane), the writer's empty-capture check (`ScrollbackWriter.Write`, `internal/state/commit_cycle.go:64-69`, and `confirmEmptyCapture`, `internal/state/scrollback.go:290-298`), and the commit's housekeeping pass (`gcOrphanScrollback`, `internal/state/commit.go:124`).
- The empty-capture check judges the saved transcript at the file the pane's previous record names, not at the positional path alone. A refusal still returns `ErrUnconfirmedEmptyCapture` and logs through the daemon's existing refusal line (`cmd/state_daemon.go:343-346`).
- Existing tests keep asserting what they assert today: the answered-pane cases of `TestCaptureAndCommit_RefilesResumePendingScrollback` (`cmd/state_daemon_resume_pending_test.go:515` and `:574`, both on the confirmed-write path), the writer suite in `internal/state/empty_capture_test.go`, and the daemon's empty-capture suite in `cmd/state_daemon_empty_capture_test.go`.
