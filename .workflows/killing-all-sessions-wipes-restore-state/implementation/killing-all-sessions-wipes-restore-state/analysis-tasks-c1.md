# Analysis Tasks: Killing All Sessions Wipes Restore State (Cycle 1)

## Task 1: The Commit Cycle Owns The Empty-Capture Confirmation Of Every Scrollback Write
severity: medium
sources: architecture

**Problem**: The capture confirmation is enforced inside `RunCommitCycle`. `captureAndRefile` is unexported, and the cycle carries its own `Client` and `OwnServer`. The scrollback half of the same rule is enforced only by the caller. The cycle hands its `Dump` a bare `CaptureCycle` (`internal/state/commit_cycle.go:46`), so the daemon's `dumpPane` (`cmd/state_daemon.go:331-352`) makes three exported calls in order and passes the confirmer, own-server pid, state dir and hash map again from `daemonDeps`: `state.CaptureAndHashPane`, `state.ConfirmEmptyCapture` (`internal/state/scrollback.go:285`), then `state.WriteScrollbackIfChanged` (`internal/state/scrollback.go:77`). `WriteScrollbackIfChanged` writes whatever it is handed. A second dumper, or a rework that reorders or merges the daemon's write, could write tmux's shutdown answer to `capture-pane` (exit 0, no output) over a live session's saved transcript. Nothing would stop it: no compile error and no guard. The user finds the restored pane blank after the reboot, and the bytes are gone. The save path's other irreversible write is already guarded structurally: `state.Commit` is reachable from production only through `RunCommitCycle`, and `internal/state/commit_guard_test.go` pins that.
**Solution**: `RunCommitCycle` hands the `Dump` a scrollback writer bound to the cycle's own `Client`, `OwnServer`, `Dir` and `HashMap`. For example, the dump becomes `func(CaptureCycle, ScrollbackWriter) (bool, error)`, where `Write(paneKey, data, hash)` runs the empty-capture confirmation before the dedup write. A refused write returns an error wrapping `ErrUnconfirmedEmptyCapture`. `ConfirmEmptyCapture` becomes unexported. `WriteScrollbackIfChanged` stays exported for test fixtures only. The commit guard's scan is extended to fail any non-test file outside `internal/state` that names it, the same way it refuses `state.Commit`. The daemon's `dumpPane` then makes one write call and no longer passes `OwnServer`, `Dir` or `HashMap` itself. It keeps its two existing WARN lines, `empty capture not confirmed; saved transcript kept` (the refusal line §4.2 requires) and `write scrollback failed`, and tells them apart with `errors.Is` against `ErrUnconfirmedEmptyCapture`. Behaviour is unchanged: the writes, refusals, tallies and log lines are the same, and only the place the rule lives moves. This direction follows the record: it is the finding's recommendation, and it matches the structural precedent the commit guard sets for `state.Commit`.
**Outcome**: The only route from production code to a saved scrollback file runs through a writer that has already applied the empty-capture rule. A production file outside `internal/state` that names `WriteScrollbackIfChanged` fails the unit-lane guard.

## Task 2: A Capture That Fails Because Tmux Stopped Answering Logs As A Back-Off Whichever Read Failed
severity: low
sources: architecture

**Problem**: A capture read is classed as a back-off only if its failure is wrapped at one of the chosen sites. Today those are the skeleton-marker read, the session listing, the pane listing and the confirmation (`internal/state/scrollback.go:345-348`, `internal/state/capture.go:94` and `:103`, `internal/state/scrollback.go:356`). The per-session `show-environment` reads (`internal/state/capture.go:115-127`) are not on that list. Sometimes tmux begins exiting after the pane listing and before any environment read has succeeded. Its refusals ("server exited unexpectedly", "no server running") are not no-such-session, so every read lands in `anomalousErrs`. `captureStructure` then returns the unwrapped `capture: all N sessions failed` aggregate (`internal/state/capture.go:135-140`). `captureAndRefile` returns it before sending the confirmation (`internal/state/scrollback.go:350-353`), so the one authoritative read is never consulted. `cycleFailureMessage` (`cmd/state_daemon.go:244-249`) then logs `tick failed`, `final flush failed` or `commit cycle failed` where §4.2 asks for the back-off line. A reboot log grepped for back-off lines (§4.3) misses that save, which was in flight as tmux went down, and shows it as a genuine fault instead. Any capture read added later would have the same gap.
**Solution**: In `captureAndRefile`, when `captureStructure` fails with an error that does not already match `ErrTmuxStoppedAnswering`, send the own-server confirmation before returning. If the confirmation is refused (the read fails, the answer is silent, or another server answers), wrap the capture's error in `ErrTmuxStoppedAnswering` so both the capture's error and the confirmation's cause stay reachable. If the committer's own server answers, return the capture's error unchanged, so it still logs `… failed`. If the own server is unknown, no confirmation is sent and the error also stays unchanged: an unsent read proves nothing about whether tmux answered. This carries the approved phase 1 consolidation's principle further (a refused read anywhere in the capture is a back-off, settled by §4.2) and keeps its line. On a healthy server, a parse failure, a carry collision onto a captured session's name, and every environment read failing anomalously all get an answered confirmation and still log `tick failed`, so that task's tests hold as they are. Widen the `ErrTmuxStoppedAnswering` and `captureAndRefile` docs to say a capture failure is classified by the confirmation. Writes, retries, `save.requested` and `flush_completed` do not change; only the logged message moves.
**Outcome**: When every environment read is refused by an exiting tmux, the tick, the shutdown flush and `commit-now` each log their back-off line with tmux's own words in `error`, and they write nothing.

## Task 3: CLAUDE.md Describes The Save Path And Resume Shells As They Were Before This Fix
severity: drift
sources: architecture

**Problem**: CLAUDE.md is the architecture reference agents are told to defer to. It contradicts the landed save path in four places.
- The `state` row (`CLAUDE.md:61`) has the waiting pane's re-file vacate its positional path. It says nothing of the own-server confirmation sent after the last capture read, the committing path's `ListSessionNamesProbe` listing, the `ErrTmuxStoppedAnswering` stand-down class, or the dump's refusal of an unconfirmed empty capture.
- The `tmux` row omits `ConfirmAnswering`, `ListSessionNamesProbe` and `ServerPIDFromEnv`.
- The Resume hooks section (`CLAUDE.md:192`) quotes the eager shell as `sh -c '<HOOK>; exec $SHELL'` and the parked chain as `trap : INT QUIT` running the draw once. It does not mention the draw or the waiter catching SIGTERM.
- `CLAUDE.md:194` says the re-file is a no-replace rename through `internal/state/rename_noreplace_{darwin,linux}.go`, and both files are deleted.

An agent that brings the code back in line with this text could restore the move, or add a committer or capture read without the confirmation, or drop the TERM handling. Any of those reopens the uncommitted-cycle and shutdown-wipe holes, and the result shows only as sessions and scrollback lost at a later reboot. No test reads CLAUDE.md.
**Solution**: Update CLAUDE.md in those four places to state what holds.
- **`state` row.** The re-file is a hard link (`link(2)`) that never overwrites an existing token-named file and leaves the positional name for the housekeeping pass of a commit naming the token-named path. Every committing cycle stands down unless the committer's own tmux server answers a confirmation sent after the last capture read. The committing path lists sessions through `ListSessionNamesProbe`, while the shared listing keeps its "no server, no sessions" reading. `ErrTmuxStoppedAnswering` is the stand-down class the back-off lines key on. An empty capture over a saved transcript is written only once the own server confirms it.
- **`tmux` row.** Add `ConfirmAnswering`, `ListSessionNamesProbe` and `ServerPIDFromEnv`.
- **Resume hooks section.** The hook shell runs `trap : TERM; <HOOK>; exec $SHELL` (`hookShellTrap`), and the parked chain traps `INT QUIT TERM` (`parkedChainTrap`). The chain re-runs the draw while the draw ends on SIGTERM and the pane's marker still reads pending (`parkedChainDraw`). The draw and the waiter catch SIGTERM (`catchSIGTERM`). Every one of these is a caught trap, never an ignore, and SIGHUP stays uncaught.
- **`CLAUDE.md:194`.** Delete the `rename_noreplace` sentence.

The wording states the rules, not which function calls which, so it holds whether or not Tasks 1 and 2 land.
