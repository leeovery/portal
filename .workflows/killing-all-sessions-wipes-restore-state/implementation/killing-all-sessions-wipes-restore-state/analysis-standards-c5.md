  FAILURE: Restore closes the gap a closed window leaves, so after a reboot every pane in a later window comes back one window lower than it was saved. Such a pane keeps naming its saved address's positional file until the first save that reaches it after its hydration. If tmux begins exiting during that save's dump (a tick or the shutdown flush) and the pane's capture comes back empty, the writer writes it with no confirmation, and the commit's housekeeping deletes the file holding the pane's transcript. At the next restore the user finds the pane with no scrollback, and the bytes cannot be recovered. The window is narrow: the first save to reach the pane after a restore, which is seconds to about 30s.

  DESCRIPTION: The latest §2.4 corrigendum defines a pane's saved transcript as "the file its last committed record names". §2.4 then requires two things. An empty capture over that file must be confirmed by the committer's own server. If it is not, "the saved transcript stands".

The cycle reads the measure from the committed record in one case only: when that record names the pane's token-named file (`keepAnsweredTranscripts` at commit_cycle.go:169, `heldTranscripts` at :185). For every other pane, `ScrollbackWriter.Write` measures the positional path of the pane's live address (:77).

Traced through the tree for an eager or hookless pane carrying a token, restored at `S:1.0` from a record saved at `S:2.0`:
1. While its skeleton marker is set, the merge keeps the record on `scrollback/S__2.0.bin`. `linkMovedSkeletonScrollback` deliberately leaves an unshared record there (scrollback.go:196-198; the "keeps the positional path while nothing occupies the saved address" case).
2. Once the marker clears, the fresh record names `scrollback/S__1.0.bin` (capture.go:593). Nothing holds the pane, because its committed record does not name its token-named file.
3. The writer judges an empty capture against `S__1.0.bin`, which does not exist. `savedTranscriptMayHoldBytes` answers false, so no confirmation is sent (scrollback.go:296, :305-312), and the empty bytes are written.
4. The commit names `S__1.0.bin`, and housekeeping removes `S__2.0.bin`.

Refusing the write would not be enough on its own. The record has already moved off the saved file, so the commit's housekeeping removes it either way. That is the same reason the answered pane needs its hold, not just the writer's refusal. CLAUDE.md's state row says "an unconfirmed one is not written, the saved transcript stands", which does not hold for this pane.
  RECOMMENDATION: Take the saved transcript, and the hold, from the pane's last committed record matched on its token, whatever file that record names. Today only a record naming the token-named file counts. Consider a pane whose committed record names a file other than its live positional path, where no other record in the capture names that file. It keeps naming that file, and its empty capture is judged against it, until a dump writes the pane's capture with confirmed bytes. Route this through the existing `held` / `fileAtPositional` hand-back, the same path an answered pane takes.
