- FINDING: The empty-capture rule depends on each caller, not on the commit cycle
  SEVERITY: medium
  FAILURE: A dump can write through state.WriteScrollbackIfChanged without first calling state.ConfirmEmptyCapture. That happens if a second committer gains a dump, or if a rework of the daemon's dumpPane reorders or merges the write. tmux's shutdown answer to capture-pane (exit 0, no output) is then written over a live session's saved transcript. No compile error or guard refuses it. The user finds out only after the reboot, when the restored pane comes back blank, and the bytes cannot be recovered.
  FILES: internal/state/scrollback.go:77, internal/state/scrollback.go:285, internal/state/commit_cycle.go:37, internal/state/commit_cycle.go:46, cmd/state_daemon.go:342, cmd/state_daemon.go:347
  DESCRIPTION: The capture confirmation is self-contained inside RunCommitCycle: captureAndRefile is unexported, and the cycle carries its own Client and OwnServer. The scrollback half of the same rule is not. The cycle hands its Dump only a CaptureCycle. So the daemon's dump supplies the confirmer, own-server pid, state dir and hash map a second time from daemonDeps, and runs three exported calls in order itself: CaptureAndHashPane, then ConfirmEmptyCapture, then WriteScrollbackIfChanged. The safety of an irreversible write therefore rests on every dump remembering the middle call. WriteScrollbackIfChanged still writes whatever it is handed. The project already enforces the equivalent save-path rule for the commit structurally: Commit is reachable from production only through RunCommitCycle, and commit_guard_test.go pins that. This rule is left to the caller even though the cycle already holds every input it needs. ConfirmEmptyCapture's five-parameter signature shows the cost: it passes the (Client, OwnServer) pair through again after the cycle was already given it.
  RECOMMENDATION: Have RunCommitCycle hand the Dump a scrollback writer bound to the cycle's own Client, OwnServer, Dir and HashMap. For example: Dump func(CaptureCycle, ScrollbackWriter) (bool, error), where Write(paneKey, data, hash) (bool, error) applies the empty-capture confirmation before the dedup write and returns an error wrapping ErrUnconfirmedEmptyCapture on refusal. Unexport ConfirmEmptyCapture. Keep WriteScrollbackIfChanged exported for test fixtures only, and extend the commit guard's pattern to fail any non-test file outside internal/state that names it. The daemon's dumpPane then makes one write call and no longer passes deps.OwnServer, deps.Dir and deps.HashMap through itself.
- FINDING: The back-off classification depends on which read failed, so a shutdown landing in the environment reads is logged as an ordinary failure
  SEVERITY: low
  FAILURE: Sometimes tmux begins exiting after the pane listing and before any session's show-environment has succeeded. Every environment read is then refused ("server exited unexpectedly" and "no server running" are not no-such-session). captureStructure returns "capture: all N sessions failed" unwrapped. The daemon's flush logs "final flush failed", and commit-now logs "commit cycle failed", instead of "... backed off: tmux stopped answering". A user who reads a reboot's log for back-off lines, which are the evidence for whether the deferred hold is needed, misses that save. Nothing shows that it was misclassified.
  FILES: internal/state/capture.go:94, internal/state/capture.go:103, internal/state/capture.go:136, internal/state/scrollback.go:249, internal/state/scrollback.go:349, internal/state/scrollback.go:356, cmd/state_daemon.go:244
  DESCRIPTION: "tmux stopped answering" is defined by a list. ErrTmuxStoppedAnswering is wrapped at four chosen sites across two functions: the marker read, the session listing, the pane listing and the confirmation, and its doc names exactly those. The per-session environment reads are not on the list. When an exiting server refuses all of them, the cycle takes the pre-existing all-sessions-failed path. The cycle already owns the one read that answers the question with authority: the own-server confirmation. It skips that read whenever the capture fails, so a failed capture is never classified by it. The implementation's own intent is that a refused read is a back-off, not a failure (TestDaemonTickReportsAFailureThatIsNoRefusedReadAsFailed). That holds only for the reads someone remembered to wrap, and any capture read added later will have the same gap.
  RECOMMENDATION: In captureAndRefile, when captureStructure fails with an error that does not already wrap ErrTmuxStoppedAnswering, call confirmOwnServer. If the confirmation is refused, wrap the capture's error in ErrTmuxStoppedAnswering. Keep the listing wraps that the failed-listing rule requires. A parse failure or a carry collision on a healthy server still gets its confirmation answered and stays "failed", so the existing failure-path tests hold.
