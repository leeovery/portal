# Consolidation Tasks: Killing All Sessions Wipes Restore State (Phase 7)

## Task 1: Every Moved Tokened Pane In A Shifted Run Keeps Its Transcript
placement: phase 7
severity: behaviour

**Problem**: Restore recreates windows in saved order with no index (`internal/restore/session.go:98-110`), so a gap in a session's window indices moves every later window down by one. When two or more windows follow the gap, each shifted pane's saved file is the next shifted pane's live positional file. That pane's fresh record names the file, so `keepAnsweredTranscripts` drops the hold (`internal/state/commit_cycle.go:186-190`, `named[file] == 0`) for every tokened pane in the run except the last window's. In the first save after hydration, any of these leaves the saved file unnamed: an empty capture during shutdown, which is judged at the pane's absent live positional file (`:77`) and written with no confirmation read; a refused `capture-pane`; or a dump-less `commit-now`. Housekeeping then deletes the file, and the next pane's write lands on that path anyway. The pane restores with empty scrollback after the next reboot, and nothing is logged: the `empty capture not confirmed` WARN (`cmd/state_daemon.go:345`) fires only on a refused confirmation, and none was sent. Swapped windows fail the same way, except that the refused pane's committed record keeps the other pane's transcript, so it restores showing the wrong scrollback. `renumber-windows on` produces the same consecutive shift live, when a middle window closes ahead of two or more others. Reproduced against HEAD: saved panes at `work:0.0`, `work:2.0` and `work:3.0`, live at `0.0`, `1.0` and `2.0`; A's (2→1) unconfirmed empty capture was written and `work__2.0.bin` was deleted, and a dump-less `commit-now` deleted it the same way. For a swap, X (1→2) had its empty capture refused, and its committed record named `work__2.0.bin`, holding Y's saved transcript. Task 7-1's fourth acceptance criterion and the `commit_cycle_moved_test.go:333-334` cases pin this outcome as expected.
**Solution**: Each held candidate's committed file, when it is not the pane's own token-named transcript and its token passes `PendingScrollbackPath`, is hard-linked to `PendingScrollbackFile(token)` through `linkStoredScrollback` before the writer is built, and the pane's record is pointed at the token-named path. The existing unconditional token-named hold then carries the pane, and `heldTranscripts`, `ScrollbackWriter.Write` and `fileAtPositional` are unchanged. The link covers every candidate, not only one whose file another record names, so a pane held on another address's positional file no longer loses its hold in the cycle a new pane appears at that address. Because the link lands before the dump, another pane's write to that positional path replaces the name atomically and leaves the moved pane's inode under the token name. A link that fails keeps today's judgement and emits one WARN with the existing `pane_key` / `path` / `error` attrs. Two candidates claiming one file stay excluded, since which pane's bytes the file holds cannot be known. `keepAnsweredTranscripts` takes the state directory and logger it needs to link. This reverses task 7-1's fourth acceptance criterion ("judged at its own positional file as today") on two grounds: the loss is measured against HEAD, and it contradicts §2.4's rule that a pane's saved transcript is the file its last committed record names. The `:333-334` test cases flip to assert the hold.
**Outcome**: Every moved tokened pane, at any position in a shifted run, in a swap, or beside a new pane at its vacated address, keeps its saved transcript until a dump writes its capture with confirmed bytes. Only then does a commit file it at its positional path and reclaim the old file.

**Acceptance Criteria**:

The moved panes below carry tokens the pane-token rule accepts, and the dump may write them: none is waiting, mid-restore or in a carried session. A pane's saved bytes are what the file its last committed record names held.

- [ ] Saved panes at `work:0.0`, `work:2.0` and `work:3.0` are live at `0.0`, `1.0` and `2.0`. A daemon tick or shutdown flush takes an empty capture of the pane moved 2→1, and the read after it is refused, answered by another server on the socket, or answered naming no server. The write is refused with `ErrUnconfirmedEmptyCapture` and logged as today, nothing is written at `work__1.0.bin`, and the commit names that pane's token-named transcript (`scrollback/pane-<token>.bin`) holding its saved bytes. This holds whether or not the pane moved 3→2 has its capture written to `work__2.0.bin` in the same dump.
- [ ] Over the same layout, a tick whose `capture-pane` is refused for every moved pane, a dump-less `commit-now` and a dump-less shutdown flush run one after another. Each commit names every moved pane's token-named transcript, which stays on disk holding that pane's saved bytes, and no saved transcript is deleted.
- [ ] Two tokened panes swap windows: X saved at `work:1.0` is live at `work:2.0`, and Y saved at `work:2.0` is live at `work:1.0`. X's empty capture is refused and Y's capture is written. X's committed record names its token-named transcript holding X's own saved bytes, never Y's, and Y's capture lands at `work__1.0.bin` without touching X's bytes.
- [ ] A tokened pane saved at `work:2.0` is live at `work:1.0`, and a new pane with no token is live at `work:2.0`, either in the same cycle or first appearing in a later cycle after the moved pane's record was committed. The moved pane's empty capture is refused and its committed record names its token-named transcript holding its saved bytes. The new pane's record names `work__2.0.bin`, and its write there leaves the moved pane's bytes intact. No commit names one file on two records.
- [ ] A dump writes a moved pane's capture: non-empty, or empty and confirmed by the committer's own server against its token-named transcript with one confirmation read. The commit names the pane's live positional file holding that capture, and that commit's housekeeping removes the token-named transcript, and the pane's saved file wherever no other record names it.
- [ ] A cycle that has linked a moved pane ends without committing: its dump fails after writing the capture of the pane now live at the moved pane's saved address, or its `sessions.json` write fails. `sessions.json` names only files on disk, and the next committing cycle names the moved pane's token-named transcript holding its saved bytes.
- [ ] When the link cannot be made for a reason other than a missing saved file or an existing token-named file, the pane is judged as before this change: held on its saved file only when no other record in the capture names it and no other moved pane claims it, otherwise at its own positional file. One WARN carrying `pane_key`, `path` and `error` is logged for it.
- [ ] Unchanged: two moved panes whose last committed records name one file are each judged at their own positional file, with no file on two records; a pane whose token the pane-token rule refuses is judged as before this change; an answered lazy pane whose last committed record names its token-named transcript is held exactly as today.

**Do**:
- The change lives in `keepAnsweredTranscripts` (`internal/state/commit_cycle.go:162-191`). `RunCommitCycle` calls it at `:131`, before the writer is built at `:135-143`, for every committing cycle, `commit-now`'s dump-less one included. It gains the state directory and logger it needs to link (`cycle.Dir`, `cycle.Logger`).
- Every candidate it collects (`:177-182`) whose file is not `PendingScrollbackFile(token)`, whose token passes `PendingScrollbackPath` (`internal/state/paths.go:108-113`), and which no other candidate claims, is linked through `linkStoredScrollback` (`internal/state/scrollback.go:148-157`) to `PendingScrollbackFile(token)`, and its record is pointed there, whatever `named` holds for the file. The unconditional token-named branch at `:187` then holds it.
- A link error leaves that pane to today's rule (`named[file] == 0 && claims[file] == 1`, `:187`) and emits one WARN with `pane_key`, `path` and `error`, the attrs `refilePendingPane` and `linkMovedPane` already log (`scrollback.go:137`, `:227`).
- `heldTranscripts`, `ScrollbackWriter.Write` and `fileAtPositional` stay as they are.
- In `internal/state/commit_cycle_moved_test.go`, both cases of `TestRunCommitCycleJudgesAMovedPaneAtItsOwnPositionalFileWhenAnotherRecordNamesItsSavedFile` (`:333`, `:334`) flip to assert the hold: the moved pane on `pane-<token>.bin`, its refused empty capture returning `ErrUnconfirmedEmptyCapture`, and in the `:334` case the other moved pane on its own token-named transcript rather than `work__3.0.bin`. `TestRunCommitCycleHoldsNeitherMovedPaneWhenBothLastRecordsNameOneFile` (`:401-450`) stands.
- `assertMovedKeptOnSaved` (`:179-195`), which the first two moved-pane tests assert through, checks that the committed record names the saved positional file and that this file still holds the bytes. Under the link the record names the pane's token-named transcript holding those bytes, and the positional name is reclaimed, so those assertions follow the transcript there.

## Task 2: A Pane With No Resume Hook Restored Away From Its Saved Address
placement: phase 7
severity: behaviour

**Problem**: Portal stamps a durable token on a pane only when `portal hook set` registers a resume hook, so most panes carry none. In a saved session with a gap in its window indices, restore brings such a pane back at a lower address (`internal/restore/session.go:98-110`). Neither the hold nor `takePrevRecord`'s by-address fallback (`internal/state/capture.go:441-454`) can find its last committed record. Until its first successful dump after hydration, an empty capture during shutdown is written to its absent live positional file with no confirmation read, a refused capture or a `commit-now` moves its record there too, and that commit's housekeeping deletes the saved file. The pane's live scrollback still holds the replayed bytes, so the next successful dump recovers it; the loss happens only when tmux goes down in that window, which runs from a few seconds to about 30s after restore. §2.4 and §6.1 say a saved transcript stands against an unconfirmed empty capture, and §5.2 (accepted residue) does not list this case. Task 7-1's fifth criterion pins the current outcome in `TestRunCommitCycleJudgesATokenlessPaneRestoredOneWindowLowerAtItsOwnPositionalFile` (`internal/state/commit_cycle_moved_test.go:374-399`).
**Solution**: Every pane restore brings back keeps its saved transcript through the first save after restore, whether or not it carries a resume hook. Settled by the user's choice at the phase 7 consolidation walk, on §1.1's rule that every session not killed stays restorable with its scrollback intact. Restore is where Portal creates these panes and knows which saved record each one was built from, so restore gives every pane it recreates without a saved token a durable identity tying it to that record, carried through the skeleton phase to the pane's first committed record. From then on the hold Task 1 sets out reaches the pane exactly as it reaches a pane registered with a hook: an unconfirmed empty capture, a refused capture or a dump-less `commit-now` leaves its saved transcript named and on disk until a dump writes its capture with confirmed bytes. The task author grounds the mechanism in the tree; where the identity is a pane token, CLAUDE.md's statement that stamping is lazy because Portal does not create panes is updated in the same task, and `hook set` keeps reusing a token a pane already carries. A pane at its own saved address keeps today's judgement. A later renumber or rename of a pane that has no token is outside this change. Task 7-1's fifth criterion and `TestRunCommitCycleJudgesATokenlessPaneRestoredOneWindowLowerAtItsOwnPositionalFile` flip to assert the hold. The specification records the guarantee beside §2.4's.
**Outcome**: Every pane restore recreates keeps its saved transcript through the first save after restore, whether or not it carries a resume hook. Until a dump writes its capture with confirmed bytes, every commit names that transcript and leaves it on disk. Only then does a commit file the pane at its positional path and reclaim the old file.

**Acceptance Criteria**:

The session below was saved with panes carrying no token at `work:0.0`, `work:2.0` and `work:3.0`, and restore brings them back at `work:0.0`, `work:1.0` and `work:2.0`.

- [ ] Each restored pane carries a token on its `@portal-pane-id`. Its first committed record after restore carries that token and names a file holding the bytes that pane was saved with, never another pane's, whether that commit lands while the pane still carries its skeleton marker or after hydration has cleared it. That commit's housekeeping deletes none of the session's saved transcripts.
- [ ] After hydration, the first save to reach a pane restored one window lower takes an empty capture, and the read after it is refused, answered by another server, or answered naming no server. Nothing is written, the refusal is logged as today, and the commit names a file holding that pane's saved bytes. A refused `capture-pane`, a dump-less `commit-now` and a dump-less shutdown flush each leave every later commit naming that transcript, on disk, the same way.
- [ ] Once a dump writes such a pane's capture with confirmed bytes, the commit files it at its live positional path, and that commit's housekeeping reclaims its old transcript.
- [ ] The pane restored at `work:0.0`, its own saved address, keeps today's judgement: its empty capture is judged against `work__0.0.bin`, which holds its saved transcript.
- [ ] Running `portal hook set --on-resume <cmd>` in a pane restored without a saved token registers the hook under the token restore gave it, and stamps nothing.
- [ ] A pane saved with a token is re-stamped with that same token, as today. A pane saved with no token comes back running the user's shell with no resume hook fired, as today.

**Do**:
- This task brings restored panes under the hold Task 1 lands, so it follows Task 1.
- Restore knows which saved record each pane was built from in `armPanes` (`internal/restore/session.go:122-155`). It pairs live panes with saved records by structural position and stamps a saved token through `restampPaneToken` (`:162-169`), which returns early on an empty token (`:163-165`). The identity is given there, to every recreated pane whose saved record carries no token.
- The identity is a pane token on the pane's `@portal-pane-id` (`state.PortalPaneIDOption`), minted by `nanoid.NewPaneTokenGenerator`. Task 1's hold matches the live pane's `PortalPaneID` against its committed record's, and links only a token `PendingScrollbackPath` admits (`internal/state/paths.go:108-113`). A pane token is therefore what lets the hold reach the pane exactly as it reaches a pane registered with a hook.
- The tie must reach the pane's first committed record. That commit's previous index is `sessions.json` read under the commit lock (`internal/state/commit_cycle.go:121-125`), and its record for the pane carries no token. The skeleton merge (`mergeSkippedPanes` → `takePrevRecord`, `internal/state/capture.go:303-327`, `:441-454`) and the hold (`keepAnsweredTranscripts` through `indexPrevPanes`, `capture.go:388-403`) find a previous record by token only when that record carries the token. A pane with no token falls back to the record saved at its own live address, which in a shifted run belongs to another pane. The first commit can land with the pane still skeleton-marked, or after the hydrate helper has cleared its marker (`markPendingThenUnsetSkeletonMarker`, `cmd/state_hydrate.go:389`), since bootstrap signals every helper while `@portal-restoring` still suppresses saves. How the tie reaches that record is the executor's.
- A saved token is re-stamped and baked as `--hook-key` as today. `hook set` still reads a pane's token and mints one only when it reads back empty (`stampPaneToken`, `cmd/hooks.go:106-121`).
- Tests that pin today's outcome: `TestRunCommitCycleJudgesATokenlessPaneRestoredOneWindowLowerAtItsOwnPositionalFile` (`internal/state/commit_cycle_moved_test.go:374-399`) flips to assert the hold. The "it stamps nothing for a saved pane with an empty token" subtest of `TestSessionRestorer_ReStampsSavedPaneToken` (`internal/restore/session_test.go:896-915`) pins restore stamping nothing on such a pane. `cmd/noncontiguous_window_reboot_integration_test.go:139-146` and `:153-167` pin the un-stamped sibling coming back carrying no token, beside firing no hook.
- Rewrite CLAUDE.md's "Resume hooks" statement that stamping is lazy because Portal does not create panes (`rg -n 'Stamping is \*\*lazy\*\*' CLAUDE.md` → 1 hit, line 190) to state that restore gives every pane it recreates a token, while `hook set` stays lazy for every other pane.
- The specification already records the guarantee (§2.4's closing paragraph and §5.2's third bullet, from the 2026-10-06 phase 7 corrigendum). No file under `.workflows/` changes.
