AGENT: architecture
FINDINGS:
- FINDING: One commit cycle builds its merges and carry from a caller index it concedes can lag the on-disk index it has already read under the lock
  SEVERITY: low
  FAILURE: An answered lazy pane can lose its only saved transcript. The sequence: a commit-now (a session closing) re-files a waiting pane to its token-named transcript before the daemon's next tick, and its housekeeping removes the positional name. The pane is then answered. On the daemon's next tick the pane's session misses the capture (renamed mid-capture, or its environment read fails) while another pane in it still waits, so the session is carried whole from the daemon's in-memory previous index, which still names the removed positional file. The hold skips carried panes, so the commit names the missing file and housekeeping deletes the token-named transcript. If tmux goes down before that session is captured again, the pane comes back after the reboot with no scrollback and nothing in the log says why. The window is narrow, because the in-memory index catches up on the daemon's first committed tick after the commit-now. But the loss is the irreversible kind this fix exists to prevent.
  FILES: internal/state/commit_cycle.go:116-124, internal/state/commit_cycle.go:159, internal/state/capture.go:161-167, internal/state/capture.go:245-270, cmd/state_daemon.go:271, cmd/state_commit_now.go:119-122
  DESCRIPTION: RunCommitCycle now reads sessions.json itself under the commit lock (`committed`) and uses it for the drop log, the structural-change test and the answered-pane hold. It still hands the caller's `LoadPrev` index to captureAndRefile, which feeds the skeleton merge, the frozen merge and the carry. RunCommitCycle's own doc comment says the caller's index "can lag behind". For commit-now the two reads are the same file read twice under one lock. For the daemon they differ exactly when a commit-now has committed since the daemon's last tick. Each path where the lag bites has needed its own local repair: refilePendingPane and linkMovedPane adopt the token path on ErrNotExist or ErrExist, and the hold reads `committed` rather than prev. The carry of a pane that is not waiting has no such repair, and any future merge that reads prev inherits the same exposure. The underlying fragility is a single cycle reasoning from two different previous indexes.
  RECOMMENDATION: Give captureAndRefile and the hold the same previous index: `cmp.Or(committed, cycle.LoadPrev())`, which is the on-disk index read under the lock, falling back to the caller's index only when sessions.json cannot be read. The merges and the carry then see every committer's last commit, the lag-repair paths stop being load-bearing, and commit-now's second read of sessions.json becomes redundant. Outside the unreadable-file case the daemon's in-memory index adds nothing: every successful commit it makes is already on disk.
SUMMARY: The save-path hardening composes cleanly. The listing probe, own-server confirmation, link-based re-file, cycle-owned scrollback writer, answered-pane hold, drop log and SIGTERM-hardened panes each sit at one seam and are enforced structurally: the source guard, the writer refusing skipped panes, and one hookExecArgs and one paneStillPending composition shared by every caller. The remaining design risk is that RunCommitCycle reasons from two previous indexes: the disk read it takes under the lock, and the lag-prone caller index it still uses for the merges and the carry.
