  SEVERITY: low
  FAILURE: Suppose sessions.json stops reading or decoding while the daemon runs. The realistic cause is a hand edit that breaks the JSON. The daemon's next tick then falls back to its in-memory index, and commitOver, handed a nil prior, overwrites the file unconditionally. Nothing in portal.log says the saved index was unreadable and has been replaced. That commit also writes no drop lines, because there is no prior to measure against. commit-now in the same state logs a WARN that names the cause. Someone rebuilding a state change from portal.log finds a `capture: tick complete` line with nothing to explain that the on-disk index was thrown away. The daemon is the committer that runs every tick, so it is the one most likely to hit this, and it is the silent one.
  FILES: internal/state/commit.go:62-74, internal/state/commit_cycle.go:120-124, cmd/state_daemon.go:271, cmd/state_commit_now.go:34, cmd/state_commit_now.go:117-120, cmd/state_commit_now.go:157-169
  DESCRIPTION: readPriorIndex turns every read or decode failure into nil, and RunCommitCycle then calls the caller's LoadPrev. The cycle had the diagnostic and discarded it, so each caller has to rebuild it or go without. commit-now rebuilds it. Its LoadPrev (loadPrevIndex) reads the same file a second time, under the same lock, through the CommitNowDeps.ReadIndex seam. It then discards the index that read returns and hands back a zero Index whatever the read found. The daemon's LoadPrev rebuilds nothing. As a result CommitNowDeps.ReadIndex is a seam whose only effect is one log line, though its signature still promises an index and the seam-convention tests still inject one. Whether a committer reports an unreadable saved index now depends on what its fallback callback happens to do, not on the cycle that found the problem.
  RECOMMENDATION: Have readPriorIndex return the read or decode error alongside its nil result, and have RunCommitCycle log one WARN before it calls LoadPrev, with an absent file kept at its current wording, so both committers report the same condition the same way. LoadPrev then only supplies the fallback: commit-now returns an empty index without reading anything. loadPrevIndex's re-read and the CommitNowDeps.ReadIndex seam, along with its seam-convention case, can then be removed.
SUMMARY: The save path holds together as one shared cycle. A failed listing stands the cycle down, the own-server confirmation runs before anything is linked or written, the empty-capture rule is enforced by the writer the cycle hands its dump, the hold and the restore-minted tokens read from the index read under the lock, and the SIGTERM handling stays caught and never ignored at every hand-off.
