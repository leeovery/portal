- FINDING: The answered-pane hold is decided from the caller's previous index, not the last committed one
  SEVERITY: low
  FAILURE: An answered lazy pane's token-named transcript is deleted by housekeeping, and after the next reboot the pane comes back with another pane's old scrollback, or none. The loss cannot be undone, and nobody sees it until that restore. Three things have to line up. First, the daemon commits with its in-memory previous index, and that index predates a `commit-now` that filed the pane under its token first (a session closing between the restore and the daemon's first tick, or while the daemon's ticks are failing). Second, the pane's live address names a positional file that is already on disk, for example after a sibling pane was killed and the window renumbered. Third, the pane's capture comes back empty and unconfirmed, or is refused, as tmux goes down. Then keepAnsweredTranscripts sees a previous record naming the positional path and does nothing. holdTokenFiledTranscripts finds the record's file on disk and also does nothing. The dump writes the positional file, or doesn't, and the commit's housekeeping deletes the token-named file, even though the last committed record names it.
  FILES: internal/state/capture.go:157, internal/state/capture.go:365, internal/state/scrollback.go:370, internal/state/scrollback.go:379, internal/state/commit_cycle.go:107, internal/state/commit.go:37, cmd/state_daemon.go:271
  DESCRIPTION: The rule being enforced is that a pane's saved transcript is the file its last committed record names. Inside one locked cycle there are two "previous" indexes. One is the caller's LoadPrev, which for the daemon is its in-memory index and does not see commit-now's writes. The other is the on-disk index that Commit reads at commit.go:37 under the same lock. The hold is decided from LoadPrev. holdTokenFiledTranscripts was added to make up for LoadPrev being stale, but it does this by checking whether a file exists, so it only helps when the record's positional file is absent. Its own test (commit_cycle_answered_test.go:332) pins that a positional file on disk wins over the token-named transcript. So whether the hold works depends on which committer happened to file the token first. The rule is also split across two passes with different inputs, and a third pass (heldTranscripts / fileAtPositional) has to agree with both.
  RECOMMENDATION: Move the hold out of captureStructure and into the cycle. RunCommitCycle reads the on-disk index once under the lock (readPriorIndex, which Commit already calls). The hold is decided from that index: a pane whose last committed record, matched on its token, names its token-named file keeps naming it. Then pass the same prior index to Commit so it does not read it a second time. LoadPrev then no longer affects the hold, holdTokenFiledTranscripts can be deleted, and one rule reads one input.
- FINDING: Listing failures are labelled "tmux stopped answering" before the cycle's own classifier sees them
  SEVERITY: low
  FAILURE: If the session listing fails while tmux is healthy, every daemon tick logs "tick backed off: tmux stopped answering" (WARN) and every session close logs "commit cycle backed off: tmux stopped answering" (ERROR), for as long as the cause lasts. One deterministic cause: a session name containing '|'. tmux accepts it, neither ValidateSessionName nor SanitiseProjectName refuses it, and it breaks parseSessionList's 4-field split. Someone grepping portal.log for back-off lines is pointed at tmux going down instead of the real cause. That includes the reboot-log reading that the deferred removal-hold decision depends on.
  FILES: internal/state/capture.go:97, internal/state/capture.go:106, internal/state/scrollback.go:355, internal/state/scrollback.go:408, cmd/state_daemon.go:244
  DESCRIPTION: The cycle already has a principled classifier. classifyFailedCapture sends a confirmation after a failed capture and calls it a back-off only if the committer's own server does not answer, because (as its comment says) an answer proves the failure was not tmux exiting. But captureStructure wraps both listing errors in ErrTmuxStoppedAnswering before returning them, and classifyFailedCapture returns early on that sentinel. So the classifier never runs for the two reads most likely to fail for some other reason. captureStructure is also inconsistent with itself: a pane-row parse failure (parsePaneRows) comes back unwrapped and goes through the confirmation, while a session-row parse failure (parseSessionList, reached through ListSessionsProbe) is called a back-off unconditionally. The skeleton-marker read failure is labelled the same way at scrollback.go:355. Stand-down behaviour does not change, since any capture error ends the cycle uncommitted. Only the label is wrong, and the label is all the back-off line says.
  RECOMMENDATION: Return the listing errors from captureStructure without the sentinel. Send the skeleton-marker read failure through classifyFailedCapture as well. Then the confirmation becomes the one place that decides a back-off: a failed read that the own server then answers is a plain failure, and one it does not answer is a back-off. ErrTmuxStoppedAnswering's doc comment would change to say this.
SUMMARY: The stand-down, own-server confirmation, empty-capture writer and SIGTERM hardening fit together cleanly, and every committer goes through the one locked cycle. Two seams are weak. The answered-pane transcript hold is decided from the caller's possibly stale previous index, with a disk-existence check covering only part of the gap, when the cycle already reads the authoritative on-disk index under the same lock. And listing failures are labelled as back-offs before the confirmation-based classifier gets a chance to run.
