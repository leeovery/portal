### Reconcile the record with the zmx backend
*From: filtering · discussion · 2026-11-18*

Between this discussion's conclusion and now, Portal moved off tmux onto zmx. The migration ran entirely outside the workflows, so no artifact of this epic records it. The filtering discussion checked the epic's three discussions against Portal on zmx (2026-11-10): tagging depends on nothing tmux-bound, and filtering has amended its own tmux-era claims. Project-link's decisions are product rules and read as still standing — a session records its folder and its project separately, the worktree rule, projects standing alone, the link chooser, tagged projects kept when their folder goes, folder-name case — but three things beneath them have moved, and the specification phase would inherit them as written.

**1. The reboot link loss no longer happens.** The record leans on a separate bugfix (inbox: `session-project-link-lost-on-reboot`) landing before this epic's implementation, because under tmux the recorded folder lived only on the live session and save/restore did not carry it. Under zmx, Portal keeps each session in its own session index, `sessions.json`, whose entry records `dir` (where Portal minted the session) and `cwd` (where the saver last saw it), and restore brings the entry back with the session. On the install no saved session lacks a recorded folder:

`jq '[.sessions[]|select((.name|startswith("_")|not) and ((.dir//"")==""))]|length' ~/.config/portal/state/sessions.json` → 0 (of `jq '[.sessions[]|select(.name|startswith("_")|not)]|length' ~/.config/portal/state/sessions.json` → 31), 2026-11-10

So the bugfix the record names as a prerequisite is owed nothing, and the inbox item is stale. Sessions Folder And Project's "Save and restore carry both" — the folder and the project — now means adding the project to the index entry beside the `dir` it already carries.

**2. The live guess now covers almost no sessions, and reads a different folder.** Unrecorded Sessions measured 30 sessions with no record on 2026-10-11 and decided to keep a live guess for them, from "the folder the session's active pane currently sits in". zmx has no panes: the guess for a session with no recorded folder is now the git root of the session's working folder as the saver last saw it (`grep -n 'GroupingDir(' internal/tui/model.go` → `session.GroupingDir(s.Cwd, m.dirRunner)`; `internal/session/dirresolve.go`: "the git root of its working directory"). And since every session Portal mints is recorded and survives restore, a session with no record is now only one started outside Portal (directly through zmx). The decision itself — keep a live guess, with the worktree rule applied, grouping-and-filtering only, silent when wrong — reads as unaffected; its measured population and its source folder are tmux-era. The same goes for Lookup Cost, whose measurements were tmux reads; its decision (no delay however many sessions are guessed) is a product rule.

**3. The measurement commands are tmux commands.** Several load-bearing measurements (Unrecorded Sessions, Lookup Cost, the recorded-session worktree count under Session Folder And Project) are `tmux list-sessions`, `tmux display-message` and `tmux list-panes` commands. Downstream phases re-run measured claims; these no longer measure anything on a zmx install.

Also noted, with no decision depending on it: zmx sessions cannot be renamed — `r` now sets a label, and the picker's text filter matches the label (when set and different from the name), the name and the recorded folder (`sed -n '/^func SearchFields/,/^}/p' internal/resolver/search.go`). Session Folder And Project's point that "session names are not a durable cue — sessions are routinely renamed" still holds, through labels.

The ask: correct the record for the zmx backend — the prerequisite bugfix, the guess's population and source, and the tmux measurement commands — and confirm whether any decision moves as a result.
