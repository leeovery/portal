# Consolidation Tasks: Lazy Resume On Attach (Phase 2)

## Task 1: A Frozen Pane's Scrollback Leaves the Positional Namespace
placement: phase 2
severity: behaviour

**Problem**: `mergeFrozenPanes` keeps a frozen pane's `ScrollbackFile` (`internal/state/capture.go:199`) — a path derived from an address the pane no longer occupies — while `buildPanes` (`internal/state/capture.go:473`) files every unfrozen pane under its **live** key and the daemon writes through `WriteScrollbackIfChanged(deps.Dir, paneKey, …)` (`cmd/state_daemon.go:290` → `internal/state/paths.go:84-86`), which never consults the record. So the retained name stays a live write address: the first pane to occupy the address the frozen pane vacated is captured into the frozen pane's file on the next tick. Displacement needs no exotic operation — closing a sibling pane in the same window shifts the panes above it down onto the vacated key, and a window close under `renumber-windows on` does the same one level up. Nothing reports it: `ComputeReferencedSet` (`internal/state/commit.go:65-75`) is a set of paths, so two records naming one are indistinguishable from one, the housekeeping pass keeps the file, and the frozen pane is skipped so no write of its own ever contests it. The dedup hash map is keyed by the same live address and `SeedHashMap` rebuilds it from filenames, so a daemon restart re-seeds the frozen pane's hash under the intruder's key and the collision survives it. It is noticed at the next reboot, when the user answers the panel and the pane replays a **different** pane's history while the intruder replays the same bytes — two restored panes showing one transcript, with the waiting pane's own having no copy anywhere and no route back. This is the same permanent loss §7.2 says the token match closes, arriving through the file name instead of the record lookup. The phase creates it: before it, `mergeSkippedPanes` only ever merged a previous record at the *same* address, so a record's path always matched its own live key and no two records could name one file. The phase's own coverage does not catch it, and not for want of coverage — `internal/state/resume_pending_durability_realtmux_test.go` drives exactly the six rearrangements that reach this state, but with a single marked pane, so nothing ever lands on the address it vacates.

**Solution**: Take the frozen pane's bytes out of the positional namespace for as long as it waits. At the tick a pane is first frozen, re-file its scrollback under a name derived from its durable token (`scrollback/pane-<PortalPaneID>.bin`) — one daemon-owned rename beside the skip it already applies — with the new path written onto the merged record. The two namespaces are disjoint by construction: every positional key ends `__<window>.<pane>` (`internal/state/panekey.go:25`), so no live address can produce a token-derived name and no later occupant can claim one. Restore and the housekeeping pass keep reading the stored path verbatim, so neither moves, which is the property §7.2 was reaching for. The un-freeze path is unchanged: the pane returns to ordinary capture, is re-filed under its current address on the first post-clear tick, and the token-named file falls out of reference and is reclaimed. A pending pane carrying no token — the hand-cleared-option degradation task 2-3 admits — keeps today's positional path and today's exposure, which is the pre-phase behaviour rather than a new one. Rejected: refusing the write when the target path is already claimed by another record, which keeps the intruder's bytes out of the frozen file but then loses the *intruder's* scrollback for the whole of the wait — one silent loss traded for another. The specification was corrected first (corrigendum 2026-09-21): §7.2's "Nothing downstream moves" was the sentence that authorised leaving the positional name in place, and it now names the write path as the third downstream and states this re-filing as the rule.

**Outcome**: A waiting pane's transcript cannot be overwritten by whatever pane later occupies the address it left, and two records can never name one scrollback file.

**Do**:
- Declare the token-derived scrollback name once in `internal/state/paths.go`, beside `ScrollbackFile` — `PendingScrollbackFile(token) → "scrollback/pane-<token>.bin"`, in the record's relative, forward-slashed shape (`filepath.ToSlash`), which is the shape `buildPanes` stores and the shape `gcOrphanScrollback` composes when it decides what is referenced. No other site restates the `pane-` prefix.
- Add `RefilePendingScrollback(dir string, idx *Index, pending map[string]struct{}, hm HashMap, logger *slog.Logger)` beside `WriteScrollbackIfChanged` in `internal/state/scrollback.go`. For every pane in `idx` whose `SanitizePaneKey` is in `pending`, whose `PortalPaneID` `nanoid.IsTokenShaped` accepts, and whose `ScrollbackFile` is not already the token form: `os.Rename` the stored path (joined onto `dir`) to the token path, set the record's `ScrollbackFile` to the token form, and `delete` the vacated stored path's key from `hm` — its base name with `.bin` trimmed, as `SeedHashMap` derives one. Dropping that dedup key is load-bearing, not tidying: the entry describes bytes that are no longer at that name, and leaving it suppresses the next write under it. A token the predicate rejects is treated exactly as an absent one — positional path kept, nothing renamed, nothing logged. Nil logger tolerated via `loggerOrDiscard`; a `nil` hash map is a legal argument (`delete` on it is a no-op).
- Make a source that does not exist (`errors.Is(err, fs.ErrNotExist)`) adopt the token path and drop the dedup key anyway — the bytes are already under the token name, which is the state a pane waiting across a reboot comes up in and the state a crash between rename and commit leaves. Any other rename error leaves that pane's record and dedup entry exactly as they were and emits one WARN through `logger` carrying only attr keys the daemon already uses (`pane_key`, `path`, `error`); the function returns no error, the tick finishes, and the next tick attempts the rename again. Nothing is emitted on the success path.
- Call it from `captureAndCommit` (`cmd/state_daemon.go`) immediately after `state.CaptureStructure` returns and **before** the capture loop, with `deps.Dir`, `&idx`, `pendingSet`, `deps.HashMap`, `deps.Logger` — before the loop so a pane that lands on the vacated address writes its own file in the same tick rather than being deduped against bytes that have moved.
- Call it from `portal state commit-now` (`cmd/state_commit_now.go`) too, on the `pendingSet` it currently discards, after its `CaptureStructure` and before its `Commit`, passing a `nil` hash map (it writes no scrollback). It merges a frozen record the same way the daemon does, and its `Commit` runs the same housekeeping pass — so a hook firing between the daemon's rename and the daemon's commit would otherwise commit an index still naming the vacated positional path and reclaim the token-named file the bytes had just been moved into.
- Extend the tick fixture's row builder (`daemonPaneRow`, `cmd/state_daemon_resume_pending_test.go`) to carry a token in the eleventh column; its existing callers keep the empty token they pass today.

**Acceptance Criteria**:
- [ ] On the first tick a waiting pane carrying a token is seen, its bytes sit at `scrollback/pane-<token>.bin`, its record names that exact relative path, and the positional name it left holds nothing.
- [ ] With a live pane occupying the address a waiting pane vacated, the two records name different files: the live pane's capture lands in the positional file and the token-named file's bytes are unchanged by that tick.
- [ ] The dedup map holds no entry for the name the bytes left, so the first write under that name lands whatever it hashes to — including the waiting pane's own write when it returns to that address and its capture is byte-identical to the frozen file.
- [ ] A commit taken while the pane waits keeps the token-named file: it is in the referenced set and the housekeeping pass leaves it in place.
- [ ] Re-filing is idempotent — a pane already at its token path is not renamed again, its record is unchanged, and the hash map is untouched — so a pane can wait through any number of ticks and reboots.
- [ ] A waiting pane whose record still names a positional file that is gone from disk adopts the token path, so the commit that follows keeps the file the bytes are actually in.
- [ ] A waiting pane whose `@portal-pane-id` is empty or not token-shaped keeps its positional path and its current exposure; nothing is renamed, no dedup key is dropped, and no WARN is emitted.
- [ ] A rename failing for any reason other than a missing source leaves the record on its stored path and the dedup entry in place, emits one WARN introducing no attr key the daemon does not already use, and neither aborts the tick nor blocks the commit.
- [ ] Once the marker clears, the pane is captured and filed under its live address again and the token-named file falls out of the referenced set and is reclaimed on that commit.
- [ ] A tick carrying a waiting pane emits no log message and no attr key a tick without one does not — `TestCaptureAndCommit_SkipsResumePendingPanes`'s taxonomy subtest stays green.
- [ ] `portal state commit-now` firing at any point during a wait commits a record naming the token path and reclaims no token-named file.

**Tests**:
- `"it re-files a waiting pane's scrollback under its token and points the record at that path"`
- `"it leaves a live pane landing on the vacated address writing its own file, with the frozen bytes untouched"`
- `"it drops the dedup entry for the name the bytes left, so the returning pane's identical capture still writes"`
- `"it keeps the token-named file through the housekeeping pass for as long as the pane waits"`
- `"it renames nothing on a second tick for a pane already filed under its token"`
- `"it adopts the token path when the record still names a positional file that is gone"`
- `"it keeps the positional path for a waiting pane whose token is absent or not token-shaped"`
- `"it warns once and leaves the record and the dedup entry alone when the rename fails"`
- `"it returns the pane to a file named for its live address once the marker clears and reclaims the token-named file"`
- `"it gives a tokened and an untokened pending pane matched to one previous record different files"`
- `"it commits the token path from commit-now and reclaims no token-named file"`
