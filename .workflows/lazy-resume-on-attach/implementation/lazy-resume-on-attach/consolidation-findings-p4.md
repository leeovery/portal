# Consolidation Findings: lazy-resume-on-attach (Phase 4)

## Findings

### F1: The resume chain's hand-off block is authored twice, and the rule holding its forensic marker in place is enforced by nothing
- **Class**: duplication
- **Failure**: The chain's last act before `syscall.Exec` is an INFO `exec` marker that must be the statement immediately before the hand-off, because the writer is unbuffered and the process image is about to be replaced. Every test in the phase fakes `ExecSelf`/`ExecShell`, so a site that emits the marker *after* the exec call, or omits it, fails no test and produces no symptom at all — until an operator reconstructing why a pane fell out of the panel finds the chain's last image unrecorded in `portal.log` and has no way to tell which hand-off broke. The rule is currently carried by seven hand-copied comments rather than by one function. Phase 5 adds at least two more sites (the discard answer and the confirm screen's redraws), each of which has to re-derive the shape from a neighbour.
- **Evidence**:
  - Full shape (resolve exe → wrap error → compose argv → emit marker → exec), twice: `cmd/state_resume_draw.go:56-68` and `cmd/state_resume_wait.go:226-239` (`resumeRedraw`).
  - Marker-immediately-before-exec, seven sites each with its own copy of the two-line comment: `cmd/state_hydrate.go:181-184`, `:262-264`, `:283-285`; `cmd/state_resume_draw.go:65-68`; `cmd/state_resume_wait.go:192-195`, `:235-238`; `cmd/state_resume_recover.go:59-62`.
  - The same consolidation removes a doubled error prefix the two full-shape copies produce: `cmd/state_resume_chain.go:81` returns `errors.New("resolve portal executable: empty path")` and both call sites wrap it again with `fmt.Errorf("resolve portal executable: %w", err)`, so the pane's stderr reads `resolve portal executable: resolve portal executable: empty path`.
- **Proposed shape**: One `resumeHandOff(logger, execSelf, subcommand string, p resumeChainPayload) error` in `cmd/state_resume_chain.go`, beside `resumeChainArgv`/`resumeChainExe` — resolve, compose, emit, exec — with `runResumeDraw` and `resumeRedraw` routed through it. Strip the duplicate prefix at the same time (either drop it from the sentinel at `:81` or stop wrapping at the call sites; only one of the two should carry it). The five bare-shell/hook sites keep their `hook_present` attr, which the plan deliberately omits from the chain hand-offs, so they are served by a sibling one-liner rather than folded into the same function.
- **Bank**: Confirms the 4-2 reviewer entry naming `cmd/state_resume_draw.go:56-68` / `cmd/state_resume_wait.go:96-109` and the doubled prefix at `cmd/state_resume_chain.go:81`; the entry explicitly asked for this to be taken at the phase boundary once the shape had stopped moving, which it now has.

### F2: The store-lookup degradation rule is written twice, and the two copies have already diverged
- **Class**: duplication
- **Failure**: The eager path and the panel path each decide independently that a miss, an empty command or a read error means a bare shell, and each emits its own `hook lookup` DEBUG and `lookup on-resume hook failed` WARN. They are already inconsistent: `execShellOrHookAndExit` treats a `Found` result carrying an empty command as a hit and would exec `sh -c "; exec $SHELL"`, while `resumeCommandAtAnswer` treats the same result as a miss and drops to a bare shell. The divergence is harmless today only because `LookupOnResume` never produces that state — which is evidence for one home, not against it. Any change to either copy (a new result value, a mode check, a different fallback) compiles and leaves both suites green, so a pane resumed from the panel behaves differently from the same pane resumed at hydrate; the user sees it only as "my hook ran on reboot but not when I pressed Enter", with nothing in the logs distinguishing the two.
- **Evidence**:
  - `cmd/state_hydrate.go:224-241` (`lookupOnResumeOrLog`) plus its consumer's hit branch at `cmd/state_hydrate.go:245-265` — `!lookup.Found` is the only miss test, so an empty command reaches `hookExecArgs`.
  - `cmd/state_resume_wait.go:202-215` (`resumeCommandAtAnswer`) — `!result.Found || result.Command == ""` is the miss test.
  - Held harmless by `internal/hooks/lookup.go:37-40`, which degrades a stored value carrying no command to the zero result.
- **Proposed shape**: One function over `(logger, lookup func(string) (hooks.OnResume, error), hookKey string) string` returning the command or the empty string, with both call sites routed through it, so the three-branch rule and its two breadcrumbs have a single declaration and the empty-command branch is decided once. `lookupOnResumeOrLog`'s dependence on `hydrateConfig` is what currently blocks reuse; taking the store/logger as parameters unblocks it and lets Phase 5's discard path reach the same rule. Note for whoever takes it: the empty-command branch is reachable only through a seam-level fake, since the production lookup cannot produce it.
- **Bank**: Folds the 4-3 executor entry (the rule written twice, one per resume path) and the 4-3 reviewer entry that sharpened it with the already-present divergence.

### F3: The chain's per-command flag reset is authored three times and `resetRootCmd` reaches none of it
- **Class**: duplication
- **Failure**: A `cmd` test that drives a resume-chain subcommand through `resetRootCmd()` + `Execute` — the pattern every other `cmd` test in the package uses — inherits flag values left `Changed` on the shared command instance by an earlier `Execute`, so its assertion passes while checking nothing. This is demonstrated, not hypothetical: the 4-1 executor hit it (the `--command` refusal subtest passed vacuously when run after its sibling) and patched it with a helper local to one file; tasks 4-2 and 4-4 then wrote the same helper again in their own files rather than discovering the canonical reset. Whoever writes Phase 5's `resume-discard` — same flag set, same shared-instance hazard — has no signal that a reset exists or must be called, and the defect it hides surfaces as a resume-chain command parsing a stale payload in a restored pane.
- **Evidence**:
  - `cmd/root_test.go:20-95` (`resetRootCmd`) is the canonical per-command reset; it already carries `stateHydrateCmd`'s three flags at `:92-97` and covers none of the three resume commands.
  - Three byte-identical local helpers, each reachable only from its own file: `cmd/state_resume_draw_test.go:348-353`, `cmd/state_resume_wait_test.go:488-493`, `cmd/state_resume_recover_test.go:286-291`.
- **Proposed shape**: Replace the hydrate-flag block and the three local helpers with one `VisitAll`-over-`stateChildCommands` loop inside `resetRootCmd` (`stateChildCommands` is declared at `cmd/state_test.go:217` in the same package, so it is directly reachable), setting each flag back to its `DefValue` and clearing `Changed`. That covers the hydrate flags, all three chain commands, and every chain command still to land, in one edit.
- **Bank**: Confirms the 4-1 reviewer entry, which predicted exactly the two further copies that then landed.

### F4: The frozen-pane capture cycle's ordering invariant is now restated in three places and checked in none
- **Class**: duplication
- **Failure**: The rule that cannot be violated silently is that the pending set must drive `RefilePendingScrollback` before anything commits, and that a pending pane is skipped by the dump. A later change to the daemon's cycle — a new step, a reordering, a change to what the dump skips — lands in `captureAndCommit` alone; `commit-now` and the integration fixture go on running the old sequence, and the fixture keeps passing while asserting against a route production no longer takes. The very loss it exists to catch — a frozen pane's transcript reclaimed or overwritten — then ships silently, and the user meets it as an empty restored pane two reboots after a pane was left waiting, with no copy of the transcript anywhere. Demonstrated in-phase: attempt 1 of task 4-7 shipped a copy missing two of the four steps and every assertion still passed.
- **Evidence**:
  - `cmd/state_daemon.go:244-309` — the full cycle (`ListSkeletonMarkers` → `CaptureStructure` → `RefilePendingScrollback` → per-pane dump skipping `skipSet ∪ pending` → `Commit`).
  - `cmd/state_commit_now.go:120-133` — the structural-only variant of the same ordering rule.
  - `internal/restore/lazy_resume_panel_integration_test.go:375-422` (`captureRound`) — the third, hand-written copy, added by this phase; its doc comment at `:370-374` states the fidelity the code has to keep having.
  - `internal/state/scrollback.go` / `internal/state/commit.go` hold the pieces the ordering is over.
- **Proposed shape**: A `state`-level composite that a caller cannot commit around — a `CaptureAndRefile(client, dir, skipSet, prev, hashes, logger) (Index, PendingSet, error)` that runs the structure read and the refile as one step and hands back the pending set — with the daemon, `commit-now` and the fixture all entering the cycle through it. That makes the omission unrepresentable the way `restoretest`'s constructors do for the `Exe` field, and leaves each caller owning only the part that genuinely differs (whether it dumps).
- **Bank**: Confirms the 4-7 reviewer entry. The two production copies are Phase 2's (`ca5a1b576`); the third copy and the demonstrated silent-pass are this phase's, and the consolidation reaches back to the other two.

### F5: `ResolveHookKey` and the new `ReadPaneOption` each carry the measured probe-then-read discrimination, in the same file
- **Class**: near-miss
- **Failure**: The two copies encode one tmux fact — a format read answers a gone pane with exit 0 and an empty string, so the option-less `show-options` probe is what separates "gone" from "unset". If either copy is simplified to a lone `display-message` (it looks redundant, and every test that only drives live panes stays green), a gone pane starts reading as a live pane carrying no option. On `ResolveHookKey`'s path that turns `portal hook set` against a vanished pane from a clean failure into a mint-stamp-write against nothing — the junk-key class of bug the probe was added to close. On `ReadPaneOption`'s path a gone pane reads as "answered, not pending" and the chain's tail silently declines to recover it, so the pane keeps a dead keyboard. Noticed only as a stray `hooks.json` entry, or a pane that stopped responding, long after the edit.
- **Evidence**: `internal/tmux/tmux.go:244-263` (`ResolveHookKey`) and `internal/tmux/tmux.go:350-369` (`ReadPaneOption`) — identical two-read sequences, each with its own multi-line comment restating the same measurement; they differ only in error wording and in passing the format positionally rather than under `-F`, which is behaviourally the same to tmux. `HookKeyFormat` (`internal/tmux/tmux.go:682`) is `"#{" + state.PortalPaneIDOption + "}"`, exactly what `ReadPaneOption` composes from its `name` argument.
- **Proposed shape**: Express `ResolveHookKey(paneID)` as `ReadPaneOption(paneID, state.PortalPaneIDOption)`, keeping its own error wording by wrapping the result, so one declaration of the probe rule remains and there is one place it can be wrongly removed from. `HookKeyFormat` stays — `paneHookRowFormat` (`:701`) still composes from it. The existing suites in `internal/tmux/resolve_hookkey_test.go` and `internal/tmux/pane_option_test.go` will need the error strings reconciled.
- **Bank**: Confirms the 4-4 executor entry.

### F6: The argv-to-shell-command-string renderer is declared twice, in two packages, outside the package that exists to hold that rule
- **Class**: near-miss
- **Failure**: `internal/shellquote` is the tree's declared single home of the POSIX quoting rule, precisely because naive composition corrupts a user-authored command — but it exports only the per-word half. The joining half is now declared separately in `cmd` and `internal/spawn`, with no exported route to it. The next site that has to render an argv into one shell command line — Phase 5's discard and confirm chains are the near-term candidates — finds no helper to reach for and either writes a third copy or concatenates. Noticed by a user whose resume command holds a space, a quote or a `$` reaching the panel's draw as several arguments, or truncated — and on the discard path, by the wrong registration being destroyed.
- **Evidence**: `cmd/state_resume_chain.go:72-81` (`shellWords`) and `internal/spawn/recipe.go:67-76` (`renderCommandString`) are byte-identical modulo variable names; `internal/shellquote/shellquote.go` declares only `Single`, and its package doc claims to hold "the rule" whole.
- **Proposed shape**: Export the joiner on `internal/shellquote` (both packages already import it and it stays stdlib-only, so no new edge appears) and route both call sites through it, deleting the two local copies. The `internal/shellquote` package doc and the `shellquote` row in CLAUDE.md both describe the package as the rule's only declaration; adding the joiner is what makes that true again.
- **Bank**: Confirms the 4-5 reviewer entry.

## Spec Defects

### S1: §4.2's estimate of the waiter's resident cost is four times the figure the landed work measures
- **Claim**: §4.2 — "Two figures the memory case rests on are estimates rather than measurements, because they cannot be taken until the code exists: the waiter's actual resident size on the settled path (~2 MB is the measured Go floor plus a guess at what Portal's startup touches) … At the estimate, a full waiting set of 41 costs some 80 MB against the 13.1 GB the eager path was measured at (§1)."
- **Observed**: `internal/restore/lazy_resume_panel_integration_test.go:137-149` now measures the real resting tree and reports it via `t.Logf` on every run. Measured 9.9–10.3 MB combined by the 4-7 executor and reproduced independently on the reviewer's own run at 9920 KB — 2096 KB for the parked `sh -c` and **7824 KB for `portal state resume-wait`** itself. At 41 waiting panes that is ~410 MB, not ~80 MB. The structural claims around it all hold: the draw hands off cleanly, exactly one shell and one waiter, no `resume-draw` survives, and the asserted 22 MB per-pane ceiling (`restingTreeCeilingKB`, `:57`) is comfortably clear.
- **Read**: Spec stale — the section labels the figure an estimate pending the code, and the code now exists and measures it. The design conclusion is unchanged (410 MB against 13.1 GB is still the case the feature rests on), so this is a number to replace, not a decision to revisit. The companion estimate in the same paragraph — whether the draw-then-hand-off split holds the resting state at the floor — is answered yes by the same measurement and can be recorded as settled.

### S2: §4.3's opening premise — the waiter is the pane's only process — is contradicted by what landed, and by §4.3 itself
- **Claim**: §4.3 — "**The waiter is the pane's only process, so anything that kills it takes the pane with it** — Ctrl-C, Ctrl-D, Ctrl-Z. It must refuse to die rather than exit."
- **Observed**: The landed chain parks the waiter *under* a shell: `cmd/state_hydrate.go:272-286` execs `/bin/sh -c '<exe> state resume-draw …; <exe> state resume-recover …'`, so the pane's own process is that shell and the waiter is its child. `internal/restore/lazy_resume_panel_integration_test.go:582-601` asserts exactly that two-process shape against a real restored pane. Killing the waiter therefore does **not** take the pane with it — `resume-recover` runs, clears the marker and gives the pane a shell, which is the whole point of §4.3's own later paragraph ("A waiter that exits without having handed the pane over drops the pane to a plain shell … The cost is a resident shell parent per waiting pane"). The two statements sit four paragraphs apart in one section.
- **Read**: Spec stale — the opening sentence predates the chain the same section goes on to specify. The rule it justifies (swallow everything but Enter and `d`) is correct and should stand, but on the reason §4.3 already gives for it a paragraph later: nothing accidental may *answer* the panel. Left as written, a later reader who takes the premise at face value concludes the swallow rule is redundant now that the tail recovers the pane, and removing it would let a stray paste or a mis-aimed `send-keys` drop a pane out of the panel and unfreeze its scrollback with nobody watching.
