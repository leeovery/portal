- FINDING: The resume panel's answer keys are declared twice, once for the footer and once for the waiter's dispatch
  SEVERITY: medium
  FAILURE: If either declaration of `d` or `y` changes and the other does not, a waiting pane's footer offers a key the waiter swallows. The user presses the key the panel names and nothing happens, because the waiter discards every byte outside its dispatch map. The pane stays frozen with its resume and discard out of reach unless the user guesses the real key. No test notices: the tui tests assert the footer against the tui constants, the cmd tests feed hard-coded "d" and "y" bytes to the waiter, and nothing compares the two sets. The picker's keymap descriptor has a dispatch guard for this kind of drift. The resume panel has none.
  FILES: internal/tui/resume_panel.go:14, internal/tui/resume_discard_confirm.go:10, cmd/state_resume_wait.go:24-25, cmd/state_resume_wait.go:131-143
  DESCRIPTION: The renderer tasks declared the displayed keys as strings (`resumeKeyDiscard = "d"`, `discardKeyConfirm = "y"`) and feed them to the footer builders. The waiter task separately declared the same keys as bytes (`resumeKeyDiscard = 'd'`, `resumeKeyConfirm = 'y'`) and keys `resumeKeysFor`'s dispatch maps by them. Both declarations encode one rule: the key the footer names on each screen is the key that acts on it. Enter (⏎ against CR/LF) and Escape (esc against 0x1b) have different display and byte forms, so they are not part of this duplication. `d` and `y` are the same character on both sides and are simply written twice.
  RECOMMENDATION: Declare the two act keys once, as exported typed byte constants in internal/tui beside the renderer (for example the panel's discard key and the confirmation's confirm key). Render the footer hints from them with string(key), and build cmd's `resumeKeysFor` dispatch maps from the same names in place of cmd's own `resumeKeyDiscard`/`resumeKeyConfirm`. cmd already imports internal/tui (state_resume_draw.go). The values are compile-time constants, so referencing them adds nothing to the waiter's resident floor.
- FINDING: The OSC string terminator is parsed twice, and the two parsers already disagree on C1 ST
  SEVERITY: low
  FAILURE: A terminal can end its background-colour reply with the 8-bit ST byte (0x9C). The pane probe accepts that terminator. If such a reply arrives after the probe's deadline, it reaches the waiter, whose OSC consumer does not recognise 0x9C. The consumer keeps reading to its 64-byte cap and blocks for the user's next keystrokes, so roughly the next 40 bytes typed, Enter and `d` included, are silently eaten before any key acts. No test covers it: the probe's tests use only BEL and ESC-backslash terminators, and so do the waiter's.
  FILES: internal/tui/pane_appearance.go:136-153, cmd/state_resume_wait.go:33-41, cmd/state_resume_wait.go:248-259
  DESCRIPTION: The appearance-probe task wrote `backgroundPayload`, which ends an OSC at BEL, C1 ST (`ansi.ST`, 0x9C) or ESC followed by a backslash. The waiter task later wrote its own streaming `oscTerminator` with private constants (`resumeOSCBell`, `resumeSTFinal`). It ends an OSC only at BEL or ESC followed by a backslash. Both implement the same rule for where an OSC string ends, and both apply it to the same bytes: the terminal's reply to the query the probe sends. The waiter's consumer exists to swallow exactly the late reply the probe could not read. The copies have already drifted.
  RECOMMENDATION: Declare OSC-terminator recognition once, as a streaming predicate in internal/tui beside `backgroundPayload`, built on the ansi package's BEL/ST/ESC constants. Have `backgroundPayload`'s scan and cmd's `consumeResumeSequence` both use it, replacing `oscTerminator` and cmd's `resumeOSCBell`/`resumeSTFinal` constants. cmd already imports internal/tui, so both sides then accept one terminator set.
- FINDING: The plain-shell fall-through is composed in four places, and the hook-or-shell choice in two
  SEVERITY: low
  FAILURE: The specification says a pane answered from the panel, whether by Enter on a gone entry or by a confirmed discard, and a pane recovered by the chain's tail each land on a plain shell exactly as an unregistered pane does. Suppose one site changes how that shell is launched, for example the hydrate helper's bare-shell path moves to a login shell so restored panes load the user's profile, and that site's test is updated. The other sites keep the old argv and their tests still pass, because each test pins its own literal `[]string{shell}`. Panes then differ by route with nothing reporting it. The user sees it only as environment differences between restored panes, such as a PATH present in one and missing in another.
  FILES: cmd/state_hydrate.go:180-183, cmd/state_hydrate.go:239-257, cmd/state_resume_wait.go:311-327, cmd/state_resume_wait.go:344-357, cmd/state_resume_recover.go:55-58
  DESCRIPTION: `execShellAndExit` takes a `hydrateConfig`, so the waiter's Enter and discard answers and the recovery tail could not call it. Each restated `shell := resolveShell(); execHandOff(logger, exec, shell, []string{shell}, false)` instead. The eager branch of `execShellOrHookAndExit` (found → `hookExecArgs`, else bare shell) and `resumeAnswerEnter` (command non-empty → `hookExecArgs`, else bare shell) are two copies of the same selection. The hook half is already shared through `hookExecArgs`. The bare-shell half is not.
  RECOMMENDATION: Add a `plainShellArgs()` beside `hookExecArgs` in cmd/state_resume_chain.go. Add one selector over both that answers prog, args and hook-present for a command, empty meaning the plain shell. Route `execShellAndExit`, the resolved branch of `execShellOrHookAndExit`, `resumeAnswerEnter`, `resumeAnswerDiscard` and `runResumeRecover` through them, so "exactly as an unregistered pane does" is one composition rather than five.
