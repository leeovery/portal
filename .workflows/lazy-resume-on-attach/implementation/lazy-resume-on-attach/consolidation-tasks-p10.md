# Consolidation Tasks: Lazy Resume On Attach (Phase 10)

## Task 1: A Pane Restored Away From Its Saved Address Keeps Its Own Transcript
placement: phase 10
severity: behaviour

**Problem**: Phase 10's token-keyed skeleton merge (`mergeSkippedPanes`, `internal/state/capture.go:162-170`, carrying `ScrollbackFile` through `carryPrevContent`) points a moved, tokened, mid-restore pane's record at the positional file of its *saved* address. After a renumbered restore another live pane can sit at that saved address, and the saver's dump writes that pane's scrollback to its live key (`cmd/state_daemon.go:286`, `WriteScrollbackIfChanged`) without consulting any record — so the committed index holds two live records naming one file, the collision §7.2 names ("The file name is a second address"), invisible to `ComputeReferencedSet`. Traced case: saved windows 0, 2, 3 restore as 0, 1, 2 (restore appends, `internal/restore/session.go:98-110`); Y is a tokened pane under a lazy registration that was not waiting at shutdown, so its saved record names `…__2.0.bin`, and it now sits at window 1; X, unregistered, was saved at window 3 and now sits at window 2. On the first capturing tick after `@portal-restoring` clears (which always captures, `cmd/state_daemon.go:183-190`), X has finished hydrating while Y is still skeleton-marked: Y's record takes `…__2.0.bin` by token, X's dump overwrites that file, and both records commit naming it. Once Y is pending, the re-file moves X's bytes into `pane-<Y token>.bin`. This boot looks right — Y's helper opened its baked path before X's atomic rename — but at the next reboot Y restores X's history, X's history exists twice, and Y's own transcript has no copy anywhere, with nothing logged. Before phase 10 the same case lost Y's transcript outright; phase 10 turned an empty restore into a misattributed one. No test catches it: the renumbered integration fixture and the daemon and commit-now unit tests each have one window above the gap, so no pane sits at the vacated address.
**Solution**: Take a moved tokened skeleton pane's bytes out of the positional namespace in the same cycle that first points its record at another address — inside `CaptureAndRefile`, before any caller's dump can run. For a token-shaped pane whose merged record names a positional file other than its own live key's, link that file to its token-named path (`os.Link`, refusing an existing name, as `moveNoClobber`'s fallback already does) and point the record at the token name. A link rather than a move, because the hydrate helper may not have opened its baked positional path yet (`cmd/state_hydrate.go:145`): the link leaves that path valid until the intruder's atomic rename replaces the directory entry, while the token name keeps the original inode. The later pending re-file then finds the record already on its token path and does nothing; a pane that resolves eager returns to ordinary capture after hydrating and its token file falls out of reference and is reclaimed, as §7.2 already describes for the end of a wait. Derivation: this extends phase 2's settled direction that a frozen pane's bytes leave the positional namespace (the two namespaces disjoint by construction) back to the skeleton stage phase 10 brought under the token match; deferring the intruder's dump instead moves a loss onto the intruder, the shape §7.2 rejected. Pin it first with a daemon test in the shape of `TestDaemonTick_KeepsARenumberedWaitingPaneTranscriptWhileSkeletonMarked` over saved windows 0, 2 and 3 with an unmarked pane at live window 2: tick once with only Y skeleton-marked, again with Y pending, and assert `pane-<Y token>.bin` holds Y's saved bytes and X's positional file holds X's capture.
**Outcome**: A pane that restore places away from its saved address keeps its own transcript through the hand-over to its wait, whatever pane now occupies the address it was filed under.
