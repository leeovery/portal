AGENT: standards
FINDINGS:
- FINDING: A multi-line paste larger than the terminal's input queue carries the discard through both screens
  SEVERITY: medium
  FAILURE: A user pastes a multi-line block of more than about 2 KB (a log excerpt, a stack trace, a code block) into a waiting pane they took for another pane. The first `d` in the paste opens the confirmation. The drop discards only what the pty's input queue holds at that moment, about 2 KB. tmux then delivers the rest of the paste line by line as the queue frees. The confirmation's waiter reads it, and the first `y` in it confirms the discard. Nobody sees the confirmation. The registration is gone from hooks.json, the marker clears, the pane drops to a shell, and the rest of the paste runs in that shell as commands. The user finds out at the next reboot, when the pane comes back with no panel. The command survives only in portal.log's `op=discard` line. Measured on the real chain: a scratch build ran `state resume-draw` in a disposable `-L ptl-*` socket with an isolated HOME, XDG and hooks file. A 2,565-byte multi-line paste (a `d` first, `yes` at the end) emptied hooks.json, cleared `@portal-resume-pending` and exec'd the shell about 20 ms after the confirmation's draw started. A 4,005-byte paste did the same, and zsh then ran `es`, the leftover of `yes`. A 4,004-byte single-line burst left the confirmation standing with the entry intact. The canonical line limit discards an unbroken line while the draw runs, which explains why single-line burst measurements pass.
  FILES: cmd/state_resume_wait.go:344-349, cmd/state_resume_wait.go:139-144, cmd/state_resume_wait.go:359-362, cmd/state_resume_draw.go:45-59, cmd/state_resume_draw.go:120-125, cmd/tty_flush_darwin.go:10-13, internal/tui/pane_appearance.go:62-68
  DESCRIPTION: The spec says: "Nor can a burst of input carry the discard through both screens … Input already in flight when the confirmation opened is dropped rather than read as agreement". It names the consequence it prevents: "destroying the only copy of a user-authored command with nobody seeing either screen". The implementation drops input once: a single `TIOCFLUSH` of the input queue in the draw that opens the confirmation (`dropStdinInputQueue`, run by `ResolvePaneTheme` after the appearance query). One flush empties only the bytes already in the kernel queue, which measured at 2,046 bytes on this machine. A paste larger than that is still in flight in tmux's write buffer when the flush runs. tmux writes the remainder as soon as the flush frees the queue. It arrives during the draw's own lifetime, before the waiter reads anything, and the waiter reads it as keystrokes on the confirmation screen. So the guarantee holds only for bursts that fit in one kernel queue's worth of input. The comment on `resumeOpenDiscardConfirm` ("The rest of a burst that carried the d is still queued on the tty") states the same assumption.
  RECOMMENDATION: Make the drop cover the whole burst the `d` arrived in, not one snapshot of the queue. After the appearance query, keep the probe-then-drop order and keep discarding input until the pane's input has been quiet for a short settle window. Bound the drain so that a continuous stream cannot hold it forever. When the bound elapses with input still arriving, treat it as a drop that could not be completed: put up the waiting panel with a report, as the draw already does for a drop that fails (`shown.Screen = resumeScreenPanel`). Do not put the confirmation up over that input. Add a regression case beside the existing `cd ~/dev && yarn` coverage: a multi-line paste larger than the pty input queue, delivered through `paste-buffer`.

- FINDING: A confirmed discard deletes a replacement registration the confirmation never showed
  SEVERITY: low
  FAILURE: A pane waits showing command X. While it waits, its entry is rewritten to command Y, by a hand edit of hooks.json or by `hook set` run with `$TMUX_PANE` aimed at that pane. The user then presses `d` and `y` on the panel. The confirmation still shows X, and `y` deletes Y, a user-authored command they never saw on either screen. They find out at the next reboot, when the pane comes back with no hook. Y survives only in the `op=discard value=Y` line in portal.log.
  FILES: cmd/state_resume_wait.go:359-362, cmd/state_resume_wait.go:435-443, internal/hooks/store.go:231-233, internal/hooks/store.go:254-266
  DESCRIPTION: The spec lists an entry "replaced by a re-registration" as a case where the entry "has already gone". That makes it "a discard that finds nothing to remove": the marker clears and the pane falls through to a shell, "because the end state the user asked for is the state the store is already in". The spec treats Enter the opposite way on purpose: Enter re-reads the store and runs what it holds then. The discard's target is the registration the confirmation named. `resumeAnswerDiscard` calls `store.Discard(hookKey, EventOnResume, ViaPanel)`, and `removeEntry` deletes whatever `on-resume` value the key holds, with no check of its command. The waiter carries the command it showed (`cfg.Command`) but never compares it with the stored one, so a replacement is removed as though it were the entry on screen. The spec also rules out "a pane that drops its panel while the registration it named survives". Deleting a different registration in its place is the other side of that rule. This persists from cycle 10, where it was set aside for severity rather than merit. It shares its failure class with the finding above: a discard destroying a registration the user did not confirm.
  RECOMMENDATION: Pass the command the confirmation showed into the discard. Remove the stored `on-resume` entry only when its command still equals that command. A differing command then answers as nothing-to-remove (`false, nil`): the marker clears, the pane falls through to a shell, and the replacement stays in the store. Keep the other outcomes as they are. A missing entry is nothing-to-remove. A lock or read failure is a refused write, reported on the confirmation.
