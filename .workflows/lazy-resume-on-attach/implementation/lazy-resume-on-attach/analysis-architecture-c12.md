- FINDING: A waiting pane's protection from the stale-hook sweep depends on restore's best-effort token re-stamp
  SEVERITY: low
  FAILURE: Restore re-stamps each pane's saved token with a best-effort write. If that write fails, restore logs `set pane token failed` and carries on. The hydrate helper still finds the registration under its baked key, resolves it lazy and parks the pane on the panel. About ten seconds after the daemon starts, the throttled hook sweep reads the live pane tokens. The baked key is token-shaped and no live pane carries it, so the sweep deletes the registration. The panel keeps showing the command, because it is carried in the chain's argv. When the user presses Enter, the waiter re-reads the store, finds nothing and gives them a plain shell. The resume never runs. The user notices when Enter lands on a bare prompt. The command survives only as the sweep's `clean-stale` INFO line in portal.log.
  FILES: cmd/state_hydrate.go:381-411, internal/restore/session.go:156-168, cmd/state_daemon.go:106, cmd/state_daemon.go:212-223, internal/hooks/store.go:336-351, cmd/state_resume_wait.go:302-313
  DESCRIPTION: The feature turns the gap between restore and firing from milliseconds into an indefinite wait. It relies on the premise that every waiting pane carries its registration's token. The capture's token merge, the re-file, the preview and the sweep's live-token protection all read that token. Nothing on the waiting path makes the premise hold. The only writer is `restampPaneToken` in internal/restore. It is best-effort by design, and its comment says a failure "costs that pane its hook rather than its session". Before this feature that cost fell on the next reboot, because the eager hook had already fired once from the baked key. Under lazy, which is the shipped default, the cost falls on the current wait instead. The sweep deletes the registration before the user can answer, and the panel goes on offering a command that no longer exists. `markResumePending` refuses to park a pane whose alternate-screen pin or pending marker cannot be written. It never checks the third precondition for an answerable wait, which is the token the sweep protects the registration by. So the property depends on a write that another package is allowed to drop.
  RECOMMENDATION: Make `markResumePending` write the baked hook key onto the pane as `state.PortalPaneIDOption`, using the same unconditional `SetPaneOption` it uses for the pin. Order the writes token, pin, marker. A token left behind is the pane's own saved identity, so it is harmless. Treat a refused token write the way a refused pin is treated: the pane does not wait, it fires eager, and the existing `set resume pending marker failed` WARN names the error. This adds no read of the live token, so the rule that the firing path never reads it still holds. Where restore's re-stamp succeeded, the write sets the same value again and changes nothing. The property that a parked pane carries its registration's token is then established by the process that decides the pane waits. Add a case beside the existing mark-step tests: a pane whose token write is refused does not park.
