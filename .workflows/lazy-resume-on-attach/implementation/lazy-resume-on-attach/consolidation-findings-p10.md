# Consolidation Findings: lazy-resume-on-attach (Phase 10)

## Findings

### F1: A pane restored away from its saved address can end up with its neighbour's transcript in its token-named file
- **Class**: behaviour
- **Failure**: The skeleton merge now carries a moved pane's saved `ScrollbackFile` onto its live address. For a pane that was not waiting at shutdown, that file is the positional file of its *saved* address. After a renumbered restore, another live pane can sit at that saved address, and the saver still writes that pane's scrollback there. So during the restore-to-wait window the committed index can hold two live records naming one file. The spec names this collision in section 7.2 ("The file name is a second address"), and it is the one the pending re-file exists to prevent. `ComputeReferencedSet` cannot see it.
  - **Walkthrough.** Saved windows 0, 2 and 3 come back as 0, 1 and 2, because restore appends windows. Y is a tokened pane under a lazy registration that the user resumed last boot, so its saved record names `scrollback/<s>__2.0.bin`. It now lives at window 1. X is an unregistered pane saved at window 3, now at window 2.
  - **First capturing tick after `@portal-restoring` clears.** A fresh daemon always captures on this tick. X has finished hydrating (small scrollback) and Y is still skeleton-marked (large scrollback, or inside its 100ms settle). Eager signalling does not wait for replay, so this ordering is ordinary.
    - The skeleton merge gives Y's live record `…__2.0.bin` by token.
    - The dump writes X's bytes over `…__2.0.bin`. The dedup hash held Y's bytes, so the write goes through.
    - Both records are committed naming that one file.
  - **Next capturing tick, Y now pending.** `mergeFrozenPanes` takes Y's record by token from the previous commit (`…__2.0.bin`). `RefilePendingScrollback` then moves X's bytes into `pane-<Y token>.bin` and drops the dedup entry, and X rewrites its positional file on the tick after.
  - **What the user sees.** This boot looks right: Y's helper opened its baked path before X's atomic rename replaced it. At the next reboot Y restores X's history under its panel, and X's history exists twice. The user's own transcript has no copy anywhere, and nothing logs it. That is the section 7.2 outcome word for word: "restores a stranger's history, the intruder restores the same bytes".
  - **Before this phase.** The same scenario lost Y's transcript outright. The address merge found no saved window-1 record, and the later re-file adopted a missing source. The overwrite itself is not new. What is new is that Y's record now names another live pane's write address, which turns an empty restore into a misattributed one.
  - **Why no test catches it.** The phase's tests cover only the no-intruder shape. The renumbered integration fixture has windows 0 and 2 (a single pane above the gap), and so do the daemon and commit-now unit tests.
- **Evidence**:
  - `internal/state/capture.go:162-170`: `mergeSkippedPanes` takes the record by token and carries its `ScrollbackFile` (`carryPrevContent`, `:207-211`) onto the live address, whatever address the file names.
  - `internal/state/capture.go:405-413`: every unfrozen pane's fresh record names its live key's positional file.
  - `cmd/state_daemon.go:269` and `:286`: the dump skips only `Skeleton`/`Pending` keys and writes to the live key (`WriteScrollbackIfChanged`, `internal/state/scrollback.go:76-84`), never consulting the record.
  - `internal/state/scrollback.go:219` and `:120-137`: the pending re-file moves whatever bytes the stored path names at that moment and deletes that dedup entry.
  - `internal/restore/session.go:98-110`: windows are recreated by `NewWindow` append, so indices compact. `:69` and the arm loop bake the saved `ScrollbackFile` into the helper.
  - `cmd/state_hydrate.go:145`: the helper opens its baked path only after the FIFO signal.
  - `cmd/state_daemon.go:183-190`: the first post-restore tick always captures.
  - `internal/state/commit.go:65`: `ComputeReferencedSet` is a set of paths.
  - `internal/restore/lazy_resume_renumbered_restore_integration_test.go:28-31`, `cmd/state_daemon_run_test.go` (`TestDaemonTick_KeepsARenumberedWaitingPaneTranscriptWhileSkeletonMarked`) and `cmd/state_commit_now_test.go` (`TestStateCommitNow_KeepsASkeletonMarkedWaitingPaneTranscript`): each has only one window above the gap, so none has an intruder.
- **Proposed shape**: Take a moved, tokened skeleton pane's bytes out of the positional namespace in the same cycle that first points its record at another address. That has to happen inside `CaptureAndRefile`, before the caller's dump can run.
  - **Which panes.** Tokened, token-shaped panes whose merged record names a positional file other than their own live key's.
  - **How.** Link (`os.Link`, refusing an existing name, as `moveNoClobber`'s fallback already does) the named positional file to `scrollback/pane-<token>.bin`, and point the record at the token name.
  - **Why a link and not a move.** The helper may not have opened its baked positional path yet, so a move would send this boot down the file-missing tail. A link leaves that path valid until the intruder's atomic rename replaces the directory entry, and the token name keeps the original inode.
  - **What follows.** The later pending re-file then finds `stored == tokenPath` and does nothing. A pane that turns out eager returns to ordinary capture after hydrating, and its token file falls out of reference and is reclaimed, as section 7.2 already describes for the end of a wait.
  - **Alternative.** Defer the dump of any live key whose file a skeleton-marked pane's merged record still names, until that record leaves it. That moves a bounded loss onto the intruder, which section 7.2 rejected for the length of a wait. Here it would last only for the handover.
  - **Regression test.** A daemon unit test in the shape of `TestDaemonTick_KeepsARenumberedWaitingPaneTranscriptWhileSkeletonMarked`, with saved windows 0, 2 and 3 and an untokened, unmarked pane at live window 2. Tick once with only Y skeleton-marked, then again with Y pending. Assert that `pane-<Y token>.bin` holds Y's saved bytes.

### F2: CLAUDE.md's `state` row still describes the capture cycle as it was before this phase
- **Class**: drift
- **Failure**: CLAUDE.md is loaded into every agent session as the architecture reference, and its `state` row now contradicts the code in three places:
  - It says `CaptureAndRefile` returns the index and the frozen-pane set, with the capture's error untouched. It actually reads the skeleton markers itself, returns `CaptureCycle{Index, Pending, Skeleton}`, and returns a wrapped marker-read error before any capture.
  - It places the dump skip on "the second return" of `CaptureStructure` rather than on the two `CaptureCycle` sets.
  - It says only a *pending* pane's record is merged by token. A skeleton-marked tokened pane now is too.

  An agent changing capture would reason from the retired contract. It might add a caller that reads the skeleton markers itself, or assume a mid-restore pane's record is still matched by address. It would find out only when that change misbehaves.
- **Evidence**:
  - `CLAUDE.md:61`: the three sentences quoted under OLD below.
  - `internal/state/scrollback.go:184-221`: `CaptureCycleClient`, `CaptureCycle` and `CaptureAndRefile`.
  - `internal/state/capture.go:150-174`: token-keyed `mergeSkippedPanes`.
  - `cmd/state_daemon.go:318-324`: the skip reads `capture.Skeleton` and `capture.Pending`.
- **Proposed shape**: Replace the three sentences in the `state` row. If F1 lands, add its skeleton-stage link to the `CaptureAndRefile` sentence in the same edit.
  - OLD: A pending pane's previous record is merged back on that durable token rather than on its address, so a pane tmux has moved still finds its own record, and the merged record keeps the scrollback path it was filed under — the live enumeration supplies the address (`Index`, `Active`) and the previous record the content (`CWD`, `CurrentCommand`, `ScrollbackFile`), so the file holding its bytes stays inside `ComputeReferencedSet` and survives the housekeeping pass. The saver's per-pane scrollback skip is mid-restore **or** pending — the positional skeleton marker as before, or membership of that second return, so a waiting pane is never capture-paned and never rewrites its scrollback file for as long as its marker stands. `CaptureAndRefile` is the entry point the capture cycle is taken through — the structure read and the pending re-file as one step, returning the index, the frozen-pane set the caller's own scrollback dump must skip, and the capture's error untouched with nothing re-filed — so a caller cannot commit an index that still names a waiting pane's vacated positional path; the daemon, `state commit-now` and the lazy-panel integration fixture all enter through it, and `CaptureStructure` stays exported for the structure-only callers.
  - NEW: A pending pane's previous record — and a skeleton-marked (mid-restore) pane's, when that pane carries a token — is merged back on that durable token rather than on its address, so a pane tmux has moved, or that restore placed away from its saved address, still finds its own record, and the merged record keeps the scrollback path it was filed under — the live enumeration supplies the address (`Index`, `Active`) and the previous record the content (`CWD`, `CurrentCommand`, `ScrollbackFile`), so the file holding its bytes stays inside `ComputeReferencedSet` and survives the housekeeping pass. A skeleton-marked pane carrying no token still takes the whole previous record at its own address. The saver's per-pane scrollback skip is mid-restore **or** pending — `CaptureCycle.Skeleton` (the positional skeleton markers, as before) or `CaptureCycle.Pending` (that second return), so a waiting pane is never capture-paned and never rewrites its scrollback file for as long as its marker stands. `CaptureAndRefile` is the entry point the capture cycle is taken through — it reads the skeleton markers itself, takes the structure merged against them and re-files every pending pane's scrollback as one step, returning a `CaptureCycle{Index, Pending, Skeleton}` whose two sets the caller's own scrollback dump must skip; a failed marker read returns its wrapped error before any capture is taken, and a failed capture returns the capture's error untouched with nothing re-filed — so no committing caller can leave out the skeleton set or commit an index that still names a waiting pane's vacated positional path; the daemon, `state commit-now` (which discards both sets and dumps nothing) and the lazy-panel integration fixture all enter through it, and `CaptureStructure` stays exported for the structure-only callers.
- **Bank**: Reviewer (task 10-1): CLAUDE.md's `state` row still describes the capture cycle as it was before the task, in three places (the `CaptureAndRefile` sentence, "membership of that second return", and the pending-only token merge).

## Spec Defects

### S1: Section 7.2 scopes the token match to waiting panes and treats the mid-restore window as positional and loss-free
- **Claim**: Section 7.2, `specification.md:304`: "Matched positionally, as every unfrozen pane's record is, a frozen pane loses its transcript permanently the first time tmux moves it … An unfrozen pane loses nothing to the same rearrangement — the next tick re-captures it under its new address a second later — so this loss exists only because the pane is frozen, and it runs for the whole of an indefinite wait rather than the few seconds §7.3 describes." Also `:306`: the token rule is described as reaching only panes that are waiting ("A pane can only be waiting if it carries a registration … so every pane this rule reaches is already stamped").
- **Observed**:
  - A mid-restore (skeleton-marked) pane is not frozen in the spec's vocabulary, yet its record is no longer matched positionally when it carries a token. `mergeSkippedPanes` takes it by token (`internal/state/capture.go:150-174`).
  - Every committing capture now reads the skeleton markers. `CaptureAndRefile` reads them itself (`internal/state/scrollback.go:209-213`), so `portal state commit-now` merges skeleton-marked panes where it previously passed a nil skip set.
  - The phase's premise, analysis cycle 4 task 1, is that the "few seconds" between restore and the pending mark are not loss-free for a pane that is about to wait. A positional miss there is permanent, because a pending pane is never re-captured. The landed tests pin the new rule: `TestCaptureStructureMergeSkippedPanesByToken`, `TestCaptureAndRefileKeepsARestoredWaitingPaneTranscript`, and `TestLazyResumePanel_RenumberedRestoreKeepsTranscriptThroughEarlyCaptures`.
  - No corrigendum records the extension; the latest is dated 2026-09-29 and covers only the preview.
- **Read**: Spec stale. Section 7.2 needs a corrigendum with three parts:
  - The token match covers the whole hand-over from restore to wait: a skeleton-marked pane carrying a token takes its previous record by token, and a tokenless one still takes it by address.
  - Every capture that commits reads the skeleton markers, commit-now included.
  - The restore-to-wait seconds are part of the exposure the token match closes, not outside it.

  If F1 is accepted, the same corrigendum should say that a moved pane's bytes leave the positional namespace at its first skeleton-stage capture, not only at its first frozen tick.
