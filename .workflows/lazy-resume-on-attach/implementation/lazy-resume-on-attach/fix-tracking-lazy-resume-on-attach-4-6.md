ISSUES:
- `cmd/state_resume_wait_resize_test.go:191-193` — reproduced flake. `elapse` writes into a 1-buffered timer channel (`:73`) and returns before the loop has consumed it; the following `h.resize()` at `:189` then queues a winch, and the loop's `select` — uniformly random among ready cases — can take the winch arm first, replace `settled` and discard the fired timer, so `Size` is never called and the assertion reads `sizes == 0`. Measured at default GOMAXPROCS (10 cores): 1 failure in 6000 runs, and reproduced again at `-count=20000` with the exact message `state_resume_wait_resize_test.go:192: the wait read the pane size 0 times, want 1`. The production loop is not at fault — the failure is the harness inferring "the settle branch ran" from a later rendezvous instead of observing it. With no CI and this sitting in the fast lane, it surfaces as an unexplained `cmd` FAIL that vanishes on re-run.
  FIX: make the settle branch observable and receive it before sending the next winch. Add a `sized chan struct{}` (capacity 1) to `resumeResizeHarness`, have the `cfg.Size` closure at `:77-80` do a non-blocking `select { case h.sized <- struct{}{}: default: }` after `h.sizes.Add(1)` (non-blocking is required — the redraw path calls `Size` and then execs, and tests that never receive would otherwise deadlock), and add `func (h *resumeResizeHarness) awaitSize()` mirroring `resize`'s budgeted receive. Then `:188-189` becomes `h.elapse(h.resize()); h.awaitSize(); h.resize()`. Apply the same `awaitSize()` between `:206` and `:207` in "it keeps waiting after a no-op settle" — that test currently has no assertion that the settle branch ran at all, so it can silently degrade into a plain "d acts" test and stop covering the criterion it exists for.
  ALTERNATIVE: make the harness's timer channel unbuffered (`:73` → `make(chan time.Time)`), so `elapse` returns only once the loop's select has committed to the settle case. One line, but "it restarts the settle window…" deliberately fires a superseded timer nothing is listening to (`:162`), which would then block forever — that call site needs a non-blocking variant. A third option is `testing/synctest` (the project's golang-testing skill recommends it for exactly this at `SKILL.md:215-262`, and the module targets Go 1.26), but the harness's `time.After` budget guards at `:93`, `:99` and `:119` would fire instantly inside a bubble and need replacing first. The reviewer recommends the `awaitSize` rendezvous: smallest change, no reliance on scheduler behaviour, and it strengthens two tests rather than one.
  CONFIDENCE: high

  ALTERNATIVE: delete the mid-test assertion at `:295-297` outright — the test's named property is still carried by the `len(p) != 1` check (`:27-29`) and the post-`wait()` `reads == 1` at `:306-308`, which is ordered by the hand-off and so deterministic. Cheaper, but loses the in-flight reading of the invariant across the resize round trip. The reviewer recommends the signal; the reading is worth keeping.
  CONFIDENCE: high

NOTES:
- Deliberate, sound deviation from the Do list: `reader.results` is capacity-1 (`state_resume_wait.go:158`) where the task said unbuffered. The buffer is load-bearing on the path this task adds — the settle→redraw return leaves a read outstanding, and an unbuffered send would park the reader goroutine forever once the loop has gone. The property the task attached to "unbuffered" (never read ahead) is held by the `outstanding` flag, not by the buffering, so nothing is lost. No change wanted.
- `trackedReader.overlaps` (`state_resume_wait_resize_test.go:31-33`, asserted at `:303-305`) cannot trip against the current structure: a single sequential reader goroutine serialises every `Read`, so two cannot overlap however many requests the loop issues. It only becomes live if a future change spawns a second reader — which is a reasonable thing to guard, but it is not what catches a double request today. The `len(p) != 1` check and the post-wait `reads` count are the assertions doing that work.
- The failed-`Size` branch carries the payload's original `--width`/`--height` rather than the errored reading. Behaviourally identical: `resume-draw` registers both flags and reads neither (`state_resume_draw.go:157-160`), re-measuring instead and letting `dimsOrFallback` bound a non-positive result. The executor's judgement call is right; the test name "redraws at the bounded fallback" describes the next process's behaviour rather than anything this argv encodes.
- `winchSignals()` is evaluated in `RunE`'s struct literal, so `TestStateResumeWaitCommand`'s Execute registers a real SIGWINCH handler in the `cmd` test binary that is never `signal.Stop`ped. Harmless — SIGWINCH's default disposition is already ignore, the channel is buffered, and nothing outside the test process is touched — but worth knowing it is there.
