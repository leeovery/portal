AGENT: architecture
FINDINGS:
- FINDING: Two unserialised committers each re-file scrollback during capture, and each one's housekeeping pass deletes by its own older view
  SEVERITY: medium
  FAILURE: A waiting pane can lose the only saved copy of its transcript in the first seconds after a cold boot, and nothing reports it. Take pane X, restored with a lazy registration and saved at `scrollback/K.bin` (it was not waiting before the reboot). The daemon tick starts while X is still mid-restore. Its capture merges X's record onto `K.bin`, and it then spends its dump phase capture-paning the eager and hookless panes that have finished hydrating. During that phase, X's helper marks it pending, and a `portal state commit-now` runs. commit-now fires on every `session-closed`, which includes the user culling finished sessions in the picker that has just appeared. commit-now sees X pending, moves `K.bin` to `pane-<token>.bin` and commits. The daemon then commits the index it captured earlier, which still names `K.bin`. Its `gcOrphanScrollback` finds `pane-<token>.bin` unreferenced and removes it. On the daemon's next tick, the re-file finds `K.bin` gone, treats that as nothing to move, and points the record at the token file that no longer exists. A frozen pane is never capture-paned again, so nothing rewrites the file. The picker preview shows the placeholder for the rest of the wait. If the pane is still waiting at the next reboot, the helper takes the file-missing tail and the panel comes up over an empty pane. Answering the pane before that reboot heals the loss, because the live buffer is then re-captured. The spec describes that as the uncommon path: most waiting panes are left waiting across reboots. The mirror interleaving loses the file the same way: the daemon re-files, and a commit-now whose capture predates the pending mark commits and collects after it. Two overlapping commit-now runs, from killing several sessions in quick succession, can do the same.

  DESCRIPTION: Before this feature, capture was a pure read. The daemon and commit-now could hold different views of the live panes, but every record named a positional file that the daemon rewrites from the live pane. So when a committer's housekeeping pass deleted a file only the other committer's view referenced, it cost something that could be re-captured. The feature changes two things. First, `CaptureAndRefile` now mutates the filesystem inside the capture (rename, or link, of a pane's scrollback onto its token), and both committers run it. Second, the record's path now depends on a marker (skeleton, then pending) that flips between the two committers' reads during the restore-to-wait hand-over. A token-named file is written exactly once, by the move, and never again while its pane is frozen. `gcOrphanScrollback` deletes every `.bin` its own index does not name. No lock orders one committer's capture, re-file, commit and collect against the other's. The design therefore only holds if a committer's view is never older than a re-file already on disk, and nothing enforces that. No test runs two committers across a skeleton-to-pending transition, so nothing would notice.
  RECOMMENDATION: Serialise the committing cycle in `internal/state`. Add one exclusive lock in the state directory, held from the capture through the re-file and the commit to the end of the housekeeping pass. Have the daemon tick and commit-now both take the cycle through a single locked entry point, so neither can capture or collect outside it. commit-now must read its previous index after acquiring the lock. The daemon's in-memory previous index can still lag behind a commit-now write, and that stays safe, because the re-file already adopts a source that has moved. Do not solve this by having the housekeeping pass protect token-named files: a leftover token file from an earlier wait would then be adopted over the pane's fresh positional capture at its next freeze. Add a test that interleaves the two committers across a pane's skeleton-to-pending transition and asserts the token-named file survives.
SUMMARY: This was a full fresh pass over the chain, the capture freeze, the stores, the picker and the capture harness. The shared vocabularies and single entry points still compose well, and the settled directions from earlier cycles were not re-raised. One new structural hazard stands: the scrollback re-file made capture destructive, and two independent committers (the daemon and commit-now) run it without mutual exclusion. A housekeeping pass working from a pre-freeze view can delete a waiting pane's only saved transcript during the post-boot hand-over.
