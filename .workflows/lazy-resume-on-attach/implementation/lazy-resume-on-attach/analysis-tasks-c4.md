# Analysis Tasks: Lazy Resume On Attach (Cycle 4)

## Task 1: A Waiting Pane's Transcript Survives the Captures Between Its Restore and Its Wait
severity: medium
sources: architecture

**Problem**: After a cold boot, a pane that was waiting at shutdown is restored from `scrollback/pane-<token>.bin`. It regains the token-keyed carry-forward only once its hydrate helper has replayed, slept its 100ms settle and set `@portal-resume-pending` (`cmd/state_hydrate.go:172-177`). Until then its previous record is carried forward only by the skeleton merge (`mergeSkippedPanes`, `internal/state/capture.go:147-172`). That merge matches by saved address and runs only when the caller passes the skeleton set. Two captures miss the pane in that window:
- `portal state commit-now` passes a nil skip set (`cmd/state_commit_now.go:121`). tmux's session-closed hook fires it whenever any session closes, for example when the user culls a finished session in the picker's first seconds. The pane gets a fresh positional record.
- The daemon's first tick after `@portal-restoring` clears always captures, because a fresh daemon's `LastSaveAt` is zero (`cmd/state_daemon.go:184`). Its address match misses any pane that restore placed somewhere other than its saved address: saved windows 0 and 2 come back as 0 and 1 (`cmd/noncontiguous_window_reboot_integration_test.go`). Eager signalling does not wait for replay (`cmd/bootstrap/eager_signal_hydrate.go:29-47`), so hydration routinely runs past the clear.

Either commit's housekeeping pass (`internal/state/commit.go:39`) then deletes `pane-<token>.bin` as unreferenced. The helper replays from the descriptor it already holds, so this boot looks right. The pane then goes pending and is never recaptured. The token merge adopts the missing file silently, since a missing source counts as adoption (`internal/state/scrollback.go:142-151`), and `sessions.json` names a file that no longer exists. At the next reboot the pane restores empty under its panel. The user's transcript is gone, with no copy anywhere and no log line. If the pane's FIFO signal failed, the file is deleted before the helper opens it, and the pane comes back blank on this boot too. Before this feature the miss cost nothing: a mid-restore pane was recaptured one tick after its skeleton marker cleared. A pane that goes pending is never recaptured, so the miss is now permanent loss of exactly the transcript the freeze exists to keep.

**Solution**: Key the hand-over from restore to wait on the pane's identity from start to finish, and make the skeleton set impossible to leave out.
- A skeleton-marked live pane carrying a token takes its previous record by that token, through the same `takePrevRecord` lookup `mergeFrozenPanes` uses. Its content (working directory, command, scrollback path) is carried onto its live address. The address match stays only for a pane with no token. Derivation: restore re-stamps the token before arming the pane (`internal/restore/session.go:146`), so the live row carries it throughout hydration. The specification already rules that a frozen pane's record is found by its token, not its position, and this extends that rule back to the seconds before the pane is marked. Like the frozen merge, it touches only panes the live enumeration returned, so the guard against resurrecting a gone pane stands.
- `CaptureAndRefile` reads the skeleton markers itself instead of taking them as a parameter. It hands them back beside the frozen set for the caller's dump skip, so the dump and its skip stay with the caller as phase 4 settled. Only the input no committing caller may omit moves inside. Derivation: phase 4 settled that the capture cycle's protective steps are not a caller's to omit. Two of the three callers, the daemon and the lazy-panel fixture, already read the live markers immediately before the call, and commit-now's nil is the omission. A failed marker read returns before the capture, as the daemon's does today, so each caller refuses to commit through its existing route. For commit-now that route is `failCommitNow`, which touches `save.requested` so the daemon retries. commit-now's own job, dropping a killed session, is unaffected, because the skeleton merge touches only live panes. commit-now still dumps nothing.
- Ground for changing commit-now's nil skip set, which phase 4's composite refactor carried over as unchanged behaviour: the behaviour it carried over is the loss above. The specification forbids that loss: a waiting pane is restored with its original content on every reboot it waits through.

**Outcome**: A pane that waited across a reboot keeps its token-named transcript through every capture taken between its restore and its pending mark. That covers a commit-now fired by a session close and the daemon's first tick over a renumbered restore. The pane restores with that transcript at the next reboot.

**Acceptance Criteria**:
- [ ] A waiting pane is saved at window 2 with its record naming `scrollback/pane-<token>.bin`. It is restored at window 1 and is still skeleton-marked when the daemon's tick captures it. The committed record at window 1 names `scrollback/pane-<token>.bin` and carries the saved working directory and command. The file is still on disk after the commit, and the daemon writes no scrollback for the pane.
- [ ] A restored waiting pane is still skeleton-marked when another session closes and fires `portal state commit-now`. The committed record names `scrollback/pane-<token>.bin` and the file is still on disk afterwards. The closed session is gone from `sessions.json`, and commit-now writes no scrollback file.
- [ ] The helper sets the pending marker before it unsets the skeleton marker, so the hand-over has three stages: skeleton marker only, both markers, pending marker only. A tokened waiting pane captured at each stage has a committed record naming `scrollback/pane-<token>.bin` at every stage, and the file is still on disk after each commit.
- [ ] A skeleton-marked pane carrying no token still takes the previous record at its own address, as it does today. A skeleton marker whose pane is gone brings no pane back into `sessions.json`, even when a previous record carries a token.
- [ ] When the skeleton-marker read fails, no capture is taken and nothing is committed. The daemon's tick logs its existing `tick failed` WARN and captures on a later tick. `portal state commit-now` exits non-zero with stderr silent, logs the failure and touches `save.requested`.
- [ ] A pane waited at shutdown under a lazy registration. It is restored under a renumbered window, and both a commit-now and the daemon's first post-restore tick capture it before its helper marks it pending. At the following reboot it restores with its original transcript above its panel.

The address match stays for a pane with no token. Only panes the live enumeration returned are touched.
