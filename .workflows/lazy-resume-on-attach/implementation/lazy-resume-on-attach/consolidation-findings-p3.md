# Consolidation Findings: lazy-resume-on-attach (Phase 3)

## Findings

### F1: The command clamp drops characters of the command with nothing on screen marking the loss

- **Class**: behaviour
- **Failure**: The user reads a command on the resume panel that differs from the one Enter will run, with no `…` and no other mark saying anything was cut, and decides whether to resume or permanently discard on that misread. `ansi.Wrap` over-packs a hyphen run past the width it was given; `clampToWidth` then cuts the overshoot away permanently instead of re-flowing it into the next line. Measured against the shipped helper at the exact widths the panel uses: for `a-b-c-d-e-f -- --port=3000 --resume` at width 12, `ansi.Wrap` returns a first line of display width 15 (`"a-b-c-d-e-f -- "`) and the clamp renders `"a-b-c-d-e-f "` — the standalone `--` argument is gone from the screen entirely, not shortened. At width 6 the same command loses the `--` from the second row (`"d-e-f -- "`, width 9 → `"d-e-f "`). The executor's bank measurement over 50,000 synthetic commands from realistic vocabulary puts this at 0.67% of commands at the card width and 1.97% at the narrow width. A pane's degraded stack (`resume_pane_canvas.go:34-47`) renders at the pane's own width, so the narrow figure is the one a small restored pane meets.
- **Evidence**: `internal/tui/resume_panel_parts.go:47-53` (`wrappedLines` — wrap, trim, clamp), `internal/tui/resume_panel_parts.go:55-60` (`clampToWidth` — `ansi.Truncate(line, width, "")`, empty tail, so the cut is unmarked), `internal/tui/resume_panel_parts.go:30-38` (`resumeCommandLines`, the only consumer), reached from `internal/tui/resume_panel.go:55` and `:65` (waiting panel, card and stack) and `internal/tui/resume_discard_confirm.go:44` (the discard confirmation's destructive target rows). The one place a cut *is* marked is the overflow row at `resume_panel_parts.go:37`, which uses `resumeEllipsis` — so the panel already has the vocabulary for "there is more", and the clamp path declines to use it.
- **Proposed shape**: Make the overshoot re-flow rather than disappear: when `ansi.Wrap` returns a line wider than the width, carry the excess into the following line and re-clamp, so the only text lost is text that ran past `resumeCommandMaxLines`, where `resumeEllipsis` already marks it. Truncating with `resumeEllipsis` instead of `""` is the smaller alternative and buys correctness of the *signal* but not of the text; re-flow buys both. Either lands inside `wrappedLines`, which is where F2 routes the other two sites, so F1 before F2 means one row-text change rather than two. This changes row text the task's own suite pins at widths 1-3 (`internal/tui/resume_panel_parts_test.go`), which is why it was held out of the fix rounds rather than because it was judged small. With re-flow, the property assertion a reviewer proposed and the executor measured as unwritable becomes true and is worth adding in the same task: no line `resumeCommandLines` returns begins or ends with a space (measured today: four such lines over 15 commands × widths 1-80, two of them the hyphen over-pack — `d-e-f ` at width 6 and `a-b-c-d-e-f ` at width 12 — and two on degenerate widths 1-2). The explanatory comment at `resume_panel_parts.go:40-46` must be rewritten with the change (see Comment Corrections, which stands independently if this finding is not taken).
- **Bank**: Two entries from `lazy-resume-on-attach-3-1` (executor), folded — they are one root cause with two costs. The first is the fidelity loss above, surfaced to the user at the escalation gate and explicitly scoped out of the fix rounds. The second is that the same over-pack blocks the stronger no-leading-or-trailing-space invariant, which could only be added today by writing carve-outs that encode the defect as expected behaviour.

### F2: The notice band and the theme panel hand over-wide wrapped rows into fixed-width frames, and only the phase's new copy clamps

- **Class**: behaviour
- **Failure**: A notice band renders a row one or more display cells wider than the terminal. Nothing downstream can recover it — `padRightWithStyle` (`internal/tui/header.go:119-121`) returns a segment unchanged once it is at or past the width, and `padLineToCanvasWidth` (`internal/tui/model.go:3287-3293`) states outright that it never truncates an over-width line. The terminal then wraps the row, so the picker paints one more line than its height budget counted, while `pageBandHeight` counts `\n`s and reports one. That is the frame-overflow class CLAUDE.md records as having pushed the title and cursor off the top of the screen. Reproduced by driving the real `renderNoticeBand` with a message carrying a long unbroken token (a path): off-width rows at widths 10, 15, 17, 21, 26, 29, 38, 51, 54, 58, 67, 74, 83, 95, 111, 113. Honest caveat, carried from the bank: today's shipped band copy does not reproduce it at widths 20-120 — the spawn unsupported and no-op messages are short and space-broken. It becomes live the moment a band message quotes a path, a bundle id (`dev.warp.Warp-Stable` is hyphen-dense and already in the spawn guidance vocabulary) or a user-chosen session name. `themePanelMessageText` is the same shape and goes over-width at `inner=47` with a slug-bearing message; its panel is 24-30 columns and its shipped copy is short, so it is the weaker of the two.
- **Evidence**: Three sites now write out the same rule and one of them clamps. `internal/tui/resume_panel_parts.go:30-60` — wrap, split, keep N-1, join the remainder, truncate with the ellipsis, **plus trim and clamp**. `internal/tui/theme_panel_message.go:127-139` — the same five steps, no trim, no clamp. `internal/tui/notice_band.go:123` — `ansi.Wrap` split straight into styled rows at `:130-145`, no clamp. The divergence is silent by construction: each site's suite pins its own copy's behaviour, so all three stay green whichever way the rule moves, and no test in any of the three asserts the property the rule exists for.
- **Proposed shape**: Route `themePanelMessageText` and `renderNoticeBand`'s wrapped rows through the phase's `wrappedLines` / `clampToWidth`, which collapses the wrap-to-at-most-N-rows-and-mark logic into one implementation and makes the "every row is no wider than the width asked for" promise hold at all three. Report this as behaviour rather than as a refactor because it is: routing the two older sites through the clamp changes what they render for an over-wide message, which is the point. Pair it with one assertion per adopted site that no returned row exceeds the width it was given — the property none of the three currently checks. Ordered after F1, whose remedy lands inside the helper this routes to.
- **Bank**: Two entries from `lazy-resume-on-attach-3-1` (reviewer), folded — the second names itself a near-duplicate of the first and asks the phase pass to fold them. Both propose the same three-file consolidation from the same measurements; the second adds that a prior round measured both older sites, found no overflow at today's copy and widths, and named the condition under which it becomes a consolidation ("if this clamp lands, a shared wrap-to-rows helper is the natural phase-boundary consolidation") — a condition this phase met.

### F3: The picker's canvas fill and the pane's now hold the same per-cell painting kernel twice

- **Class**: duplication
- **Failure**: A later correction to the per-cell background rule — a new SGR form that drops the background to default, a change in how trailing padding is emitted, a change to the clamp-and-blank-fill geometry — lands on one copy and not the other. Neither suite cross-checks the other: each pins today's behaviour of its own copy, so both stay green through the divergence. The symptom reaches the user as a stripe of their own terminal background showing through either the picker's canvas or the resume panel on a restored pane, which is exactly the bleed class the backfill was introduced to fix, and it appears on their terminal rather than in any test.
- **Evidence**: `internal/tui/model.go:3005-3022` (build canvas style → `canvasBgParams` → `ansi.NewParser` → loop with the break at the height → `backfillCanvasBackground` then `padLineToCanvasWidth` → blank-row padding) is the same eleven lines as `internal/tui/resume_pane_canvas.go:55-69`. Both colourless arms already delegate to the same `fillColourless` (`model.go:3002` and `resume_pane_canvas.go:52-53`), so the colourless half of the rule is shared and the coloured half is not.
- **Proposed shape**: Have `fillCanvas` call `fillPaneCanvas(view, contentW, contentH, m.themeState.active, m.colourless)` and then apply `overlayThemePanelOnContent` and the inset (`insetColourless` / `insetCanvasCanvas`) on top, leaving the gutter and the panel composite exactly where they are and in the order `model.go:3029-3031` records as load-bearing. Behaviour-preserving: the two loops are line-for-line equivalent (`strings.Split` versus `strings.SplitSeq` over the same input, same break condition, same blank fill), so the picker's existing frame assertions are the check that it stayed so. The single-copy suite obligation is that one of the two suites drives the shared helper through both callers' shapes rather than each pinning its own.
- **Bank**: One entry from `lazy-resume-on-attach-3-2` (reviewer), confirmed against the final state. It was out of scope in 3-2 because the fix reaches into the picker's pre-existing fill, which that task was told not to change.

### F4: A terminal reply that misses the appearance probe's deadline lands live keys on both of the phase's screens

- **Class**: behaviour
- **Failure**: The probe writes an OSC 11 query to the pane and abandons the read at 50ms. A terminal slower than that still answers — those bytes are not consumed by anyone and stay in the pane's tty input queue, because the queue belongs to the terminal rather than to the descriptor the probe closed. The reply is then read as keystrokes by whatever holds the pane next. Its leading byte is ESC, which is the discard confirmation's cancel key (`destructiveKeyCancel = "esc"`), so a confirmation the user has just opened backs itself out with no input from them: they press `d`, see the screen appear and vanish, and have no way to know why. The payload is worse on the waiting panel: the reply body is `]11;rgb:RRRR/GGGG/BBBB`, and `d` is a hex digit — a terminal whose background is `#0d1117` or `#2d2d2d` sends a `d` in its answer, which is the discard key. The user arrives at a restored pane already showing "Discard resume?" against a question nobody asked. Nothing user-authored is destroyed by this alone (`y` is not a hex digit and appears nowhere in the reply), but the screen that destroys it is presented by the terminal rather than by the user.
- **Evidence**: `internal/tui/pane_appearance.go:90-101` — the query is written, the deadline is set, and `readBackgroundReply` returns `("", false)` on the deadline with no drain attempted; `internal/tui/pane_appearance.go:82` closes the reader, which does not discard queued input. `internal/tui/resume_discard_confirm.go:18-24` is the screen whose cancel is ESC, via `internal/tui/destructive_confirm.go:16` and `:94-96`. Both halves landed in this phase, in different tasks (the probe in 3-5, the confirmation in 3-4), which is why neither task could see it. The probe's own design is correct on its face and the code says so at `pane_appearance.go:93-94`: a post-timeout drain could swallow a real keystroke, so the probe rightly does not attempt one. What is missing is anything downstream that knows the bytes may be there.
- **Proposed shape**: The remedy belongs to the input handling that guards these two screens, not to the probe. The phase's landed surface makes one ordering concrete that needs stating before that work is written: the tty input drop must run **after** the appearance probe resolves, not before it, because a drop taken first cannot reach a reply that arrives second — and the probe is the one thing on this path guaranteed to put bytes in the queue. The waiting panel's key handling needs the same protection for the same reason, since `d` is live there. Whoever writes the input-drop and key-swallow work needs to know the ESC and the `d` can arrive with no keypress behind them; today the only place that is written down is this finding.
- **Bank**: One entry from `lazy-resume-on-attach-3-5` (reviewer), confirmed and extended. The entry named the ESC-on-the-confirmation half and recorded it as not a defect in 3-5; reading the two screens side by side adds the hex-digit `d`-on-the-waiting-panel half, which is the more visible of the two.

## Spec Defects

### S1: §5.2 calls the pane's appearance gate the same gate the picker runs, which is true of its timing and not of what happens to a late answer

- **Claim**: §5.2 — "A light/dark pair runs the same detect-or-timeout appearance gate the picker runs — a query to the terminal raced against the same short timeout (`appearanceDetectTimeout`, `internal/tui/appearance_gate.go:12`), resolving dark when there is no answer — in the process that draws." The section states the fallback and the timeout and says nothing about a reply that arrives after the deadline.
- **Observed**: The two gates differ in a way the phase's implementation makes concrete. The picker's gate resolves inside a Bubble Tea program that owns stdin for the whole run, so a late `BackgroundColorMsg` is consumed by the program whenever it arrives and is discarded by `appearanceGate.resolve`'s first-call-only rule (`internal/tui/appearance_gate.go:62-70`) — the bytes can never be read as input. The pane's probe reads with a deadline from a fresh open of `/dev/tty` and closes it (`internal/tui/pane_appearance.go:78-101`), which it must, because there is no program loop to resolve into and a post-timeout drain would swallow a real keystroke. The consequence is that on the pane route, and only on the pane route, a late answer stays in the pane's input queue for the process that holds the pane next — where ESC is the discard confirmation's cancel key and a hex `d` is the waiting panel's discard key (see F4). §4.3's stale-input rule is written entirely around what a person can send ("a stray paste, an errant `send-keys`, or a key pressed in the wrong window") and protects only against confirmation, not against cancellation or against opening the confirmation in the first place; the byte source here is the terminal answering a question Portal asked.
- **Read**: Genuinely open. The spec is not wrong about the timeout, the fallback, or the token contract — every one of those holds in the landed code. It is silent on a consequence that is unique to the route it authorises, and the silence matters because the phase's other screen makes ESC a live key. What is owed is a sentence in §5.2 or §4.3 stating that the appearance query's own answer may arrive after the gate and is input like any other, so the protection §4.3 describes must cover it — which fixes the ordering the remedy needs (drop after the probe, never before) in the specification rather than leaving it to be rediscovered in a phase-5 task whose current wording reads the probe as harmless.
