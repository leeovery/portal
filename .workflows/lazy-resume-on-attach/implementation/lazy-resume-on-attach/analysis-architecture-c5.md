- FINDING: The hydrate helper's lazy decision reaches the exec through a mutable pointer and a side effect each tail has to remember
  SEVERITY: medium
  FAILURE: A tail can reach execShellOrHookAndExit without first running markPendingThenUnsetSkeletonMarker. That happens when a HandleTimeout or HandleFileMissing seam is replaced (several tests already replace them), or when a future tail is added. The pane is then parked on a chain with an empty executable and an empty pane id, because Decision.Exe and Decision.Pane are only filled by the mark step. The draw cannot start. The backstop's clear addresses no pane. The pane drops to a bare shell and its skeleton marker is never unset, so the saver skips that pane's scrollback until a bootstrap reclaims the marker, and the registration is neither offered nor fired. Separately, a nil Decision fires a lazy registration eagerly: that is the boot-time process this feature exists to hold back, and TestHydrateLazy_NilDecisionFallsBackToItsOwnLookup pins that behaviour. No log line tells either outcome apart from a pane configured eager, so the only way a user notices is memory creeping back up or a pane that never showed its panel.
  FILES: cmd/state_hydrate.go:61-75, cmd/state_hydrate.go:110-183, cmd/state_hydrate.go:239-252, cmd/state_hydrate.go:262-274, cmd/state_hydrate.go:308-342, cmd/state_hydrate.go:348-376, cmd/state_hydrate_lazy_test.go:454-479
  DESCRIPTION: The lazy path relies on one rule: a pane is parked on the chain only after its pending marker has been written, and the chain is composed from the pane id and executable that the write resolved. Nothing structural enforces that rule. runHydrate resolves a *resumeDecision onto a hydrateConfig that is passed by value. Each of the three tails is then trusted to call markPendingThenUnsetSkeletonMarker, which reaches back through the pointer to flip Wait and fill Exe and Pane. The exec step reads whatever state the pointer is left in. Two of the three calls sit inside injectable function seams (HandleTimeout, HandleFileMissing) whose type, func(hydrateConfig) error, says nothing about that obligation. A nil pointer is also handled, by a silent re-lookup that ignores the resolved mode. So the ordering the spec treats as load-bearing (mark before the skeleton clear, park only when marked) depends on each call site's discipline rather than on the data flow.
  RECOMMENDATION: Have runHydrate own the order for all three tails: run the handler (logging and reset only), then the mark, then the exec, in one function. Have the mark step return the decision the exec consumes, for example `decision = markPendingThenUnsetSkeletonMarker(cfg, decision)` followed by `execShellOrHookAndExit(cfg, decision)` taking the value. A Wait=true decision carrying Exe and Pane can then only come out of a successful mark. Remove the Decision pointer from hydrateConfig and delete the nil-decision fallback. Tests that drive the exec directly should construct the decision they mean.
- FINDING: Registration keeps two sources of truth, and MarshalJSON trusts the stale one
  SEVERITY: low
  FAILURE: Suppose a store method loads a registration, edits its Command or Resume, and saves the snapshot. This is the shape a mode-pinning path would take, for example a preferences surface or a "pin this entry" command. MarshalJSON emits the bytes the value was decoded from, so the old bytes are written back. The breadcrumb logs a modify and the edit never lands. The user sees the command succeed and then `hook list` still shows the old mode or command. Today the only writer, Set, avoids this solely because it rebuilds the value before storing it.
  FILES: internal/hooks/registration.go:14-24, internal/hooks/registration.go:53-64, internal/hooks/registration.go:66-70, internal/hooks/store.go:163-166
  DESCRIPTION: Registration holds both the modelled fields and the raw decoded bytes, and no rule ties them together. Each consumer picks one to trust: MarshalJSON trusts raw, sameRegistration trusts the fields, and Set drops raw by hand before storing (with a comment explaining why it must). The raw-preserving encoder is only correct in the narrow case where every mutation re-projects first, and that condition lives in a comment on an unexported field rather than in the type. The stored object is explicitly open-ended ("room for whatever comes later"), so more mutation paths over loaded entries are expected.
  RECOMMENDATION: Make the codec self-checking. At decode time, record the projection alongside raw (the decoded command and mode). MarshalJSON then emits raw only while the exported fields still equal that projection, and otherwise emits the string or object form. Set no longer needs its re-projection line, and any future edit of a loaded value marshals what it holds.
- FINDING: The recover tail's pane binding cannot be seen from runResumeRecover, so the tests of the $TMUX_PANE fallback check a field nothing reads
  SEVERITY: low
  FAILURE: Suppose the recover command body is refactored so the marker target is bound before the $TMUX_PANE fallback applies, for instance by hoisting `target := tmux.PaneIDTarget(pane)` above `if pane == ""`. A chain that passes no --pane (a chain parked by another build) would then read and clear the marker on an empty target. The failed read counts as pending, the clear fails with a WARN, and the pane gets its shell with @portal-resume-pending still set. Its saved transcript is frozen for the rest of the pane's life, and the picker dot and doctor count go on claiming it is waiting. TestStateResumeRecoverCommand_PaneFromEnvironment ("it recovers the pane $TMUX_PANE names") and the foreign-argv cases would keep passing, because they assert on resumeRecoverConfig.Pane and the probe's ReadMarker and ClearMarker take no target.
  FILES: cmd/state_resume_recover.go:13-23, cmd/state_resume_recover.go:75-97, cmd/state_resume_recover_test.go:428-430, cmd/state_resume_recover_test.go:439-467
  DESCRIPTION: resumeRecoverConfig carries Pane, but runResumeRecover never reads it. The pane that actually gets addressed is baked into ReadMarker and ClearMarker closures in the cobra body, which is the only place the $TMUX_PANE fallback exists. As a result, the value the unit sees and the value the side effects use are separate paths that only agree by construction in one function body. Tests can observe the first and never the second. resume-wait binds its ClearMarker the same way; its payload's Pane is at least used for the argv it hands on.
  RECOMMENDATION: Give the marker seams the target as a parameter, for example ReadMarker func(tmux.Target) (string, error) and ClearMarker func(tmux.Target) error. runResumeRecover then composes tmux.PaneIDTarget(cfg.Pane) itself, which makes cfg.Pane load-bearing and lets the probe record the target it was handed. Point the PaneFromEnvironment and foreign-argv assertions at that recorded target rather than at the parsed field.
SUMMARY: The lazy-resume pieces fit together well: shared leaf vocabularies (resumemode, resumekeys, shellquote), one presence rule for the pending marker, a single CaptureAndRefile entry point, and the pane screens built from the picker's own card grammar. The main weakness is in the hydrate helper, where the rule "park only after marking" depends on each tail calling the mark step and on a mutable optional pointer, rather than following from the data flow. Two smaller seams are only correct in their current narrow context: the raw-preserving Registration codec, and the recover tail's pre-bound marker target.
