FINDINGS:
- FINDING: A session renamed while a capture is running drops its waiting pane from the saved set, and the pane's transcript with it
  SEVERITY: low
  FAILURE: A user renames a session that holds a waiting pane, either with the picker's `r` or with `tmux rename-session`. A daemon tick (or a `commit-now`) is partway through its capture at that moment. That capture leaves the whole session out of the index it commits. The commit's housekeeping pass then deletes the pane's `scrollback/pane-<token>.bin`, because no record references it. On the next tick the session is back under its new name, but the daemon's previous index is the one just committed, so the token merge finds no record. The re-file then treats the missing positional source as nothing to move and points the record at the token-named file that was just deleted. The pane is frozen, so nothing ever re-captures it. The user notices after the next reboot: the pane comes back holding the panel over an empty pane, the transcript it was paused on is gone, and portal.log carries `scrollback file not found` for it. If the pane is answered before any reboot, it is re-captured from the live pane and nothing is lost.
  FILES: internal/state/capture.go:55-96, internal/state/capture.go:112-114, internal/state/capture.go:183-206, internal/state/scrollback.go:143-152, internal/state/commit.go:22-43, internal/state/commit.go:77-111, cmd/state_daemon.go:272
  DESCRIPTION: The spec says "A waiting pane keeps its place in the saved set throughout", "A frozen pane is not dropped from the saved set", and "a pane can wait indefinitely and still be restored on every subsequent reboot, with its original content … however many reboots it waits through". It also names a session rename as one of the rearrangements the freeze has to survive. The implementation survives a rename that falls between two captures, through the token merge. It does not survive a rename that lands inside one. CaptureStructure builds `keep` from `ListSessionNames` and then calls `ShowEnvironment` once per kept session in sequence, which takes roughly 100–200 ms on a 44-session install. A session renamed in that window has its rows either filtered out of the enumeration (they carry the new name) or skipped as a vanished session (`ShowEnvironment` on the old name fails). Either way the capture still succeeds, because other sessions captured. Before this feature that omission lasted one tick: every unfrozen pane is re-captured from the live pane on the next tick. A frozen pane has no second source. Its only copy is the token-named file, and `mergeFrozenPanes` can recover a record only from the previous index, which no longer holds it. This is the same class of loss the spec closes for the restore-to-wait window and for a renumbered restore. The one difference is that here the pane's session is missing from a single capture, not moved between two.
  RECOMMENDATION: Make a waiting pane's saved transcript survive a capture that skips its session. Take the pending panes' tokens from the whole enumeration, including rows under a session that was filtered out or skipped. Keep each live pending token's `pane-<token>.bin` out of that commit's housekeeping pass, for example by carrying the previous record forward or by having the pass spare those names. The next capture then recovers on its own: `placeStoredScrollback` already adopts an existing token-named file and treats a missing positional source as nothing to move. Put the fix in the shared capture cycle so that both the daemon tick and `commit-now` get it. Add a regression test: a capture in which a pending pane's session fails `ShowEnvironment` (or is renamed between the name read and the pane read), then a capture with the session back under a new name. Assert that the token-named file survives and that the record points at it.

One drift was found. A capture that skips a waiting pane's session for a single tick, which a rename landing mid-capture causes, lets the housekeeping pass delete that pane's frozen transcript, and nothing recovers it. That breaks the spec's statement that a frozen pane keeps its place in the saved set throughout. No comment needs correcting.
