- internal/state/rename_noreplace_darwin.go:12, internal/state/rename_noreplace_linux.go:12, internal/state/scrollback.go:147-151: the re-file now depends on a rename flag some filesystems reject outright. `renamex_np(RENAME_EXCL)` returns ENOTSUP where the volume lacks VOL_CAP_INT_RENAME_EXCL (per the man page: SMB/NFS/exFAT on macOS). `renameat2(RENAME_NOREPLACE)` returns EINVAL on Linux NFS and CIFS, which reject any rename flag. Neither error is ErrNotExist or ErrExist, so on those filesystems every re-file becomes a "rename failure".
  - **What goes wrong:** a waiting pane is never moved off its positional name. The ordinary displacement loss the re-file exists to prevent comes back on every wait: close a sibling pane and the next pane's capture overwrites the waiting pane's transcript. Closing a sibling is the common route; the four retry routes this task targets are the rare ones. The plain `os.Rename` this replaces worked on those filesystems.
  - **Who:** a Linux install whose `~/.config` is NFS-mounted (common on shared dev servers; goreleaser ships linux/amd64 and linux/arm64), or a macOS state dir on a network or FAT-family volume.
  - **How it's noticed:** portal.log gets one `refile pending scrollback failed … invalid argument` (or `operation not supported`) WARN per waiting pane per second for the whole wait, which can last days. The transcript loss itself stays silent until the next reboot restores another pane's history.
  FIX: Keep `renameNoReplace` as the primary path. When it fails because the platform does not support the flag (ENOTSUP on darwin, EINVAL on linux), fall back to `os.Link(src, dst)` then `os.Remove(src)`.
  - The mapping belongs in the platform files, e.g. each returns a shared `errNoReplaceUnsupported` sentinel, or exposes a per-platform `isNoReplaceUnsupported(err)`.
  - `link(2)` is itself an atomic no-clobber create (EEXIST when the name exists). So "never overwrite an existing token-named file" still holds as one atomic step, and link's ENOENT/EEXIST fall into the existing adopt branch.
  - Once the link succeeds the bytes are safe under the token name. Adopt even if the `Remove` fails: the dropped dedup entry lets the displacing pane take over the positional name.
  - Link-unsupported failures (e.g. exFAT) keep today's WARN rule.
  - Remaining race, on the fallback path only: a `commit-now` re-file whose link and remove straddle the daemon's write of the displacing pane deletes that fresh capture. It is recovered at that pane's next content change, which is strictly narrower than a transcript loss.

Stub it to return the unsupported error, then assert in `TestRefilePendingScrollback` that (a) the bytes move onto the token file, the record adopts it and the positional name is gone, and (b) an existing token-named file is still not overwritten.
  ALTERNATIVE: Accept the limitation and leave the code alone: the re-file is simply unavailable on those filesystems, with the per-tick WARN as the only signal. This avoids a second code path and a test seam. The cost is the always-on displacement exposure on those installs, plus the log volume.
