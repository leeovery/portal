- FINDING: A confirmed discard deletes a replacement registration the confirmation never showed
  SEVERITY: low
  FAILURE: A pane waits showing command X. While it waits, the user hand-edits hooks.json to change that key's command to Y, or runs `hook set` with $TMUX_PANE aimed at that pane. Later they press `d`; the confirmation still shows X, and `y` deletes Y, which is a user-authored command they wrote and never saw on the confirmation. They find out on the next reboot, when the pane comes back with no hook. The only copy left is the `op=discard value=Y` INFO line in portal.log.
  FILES: cmd/state_resume_wait.go:359-362, cmd/state_resume_wait.go:433-439, internal/hooks/store.go:207-209, internal/hooks/store.go:230-237
  DESCRIPTION: The spec lists a registration "replaced by a re-registration" as one case of "a discard that finds nothing to remove": the marker clears and the pane falls through to a shell "because the end state the user asked for is the state the store is already in". The user asked to remove the command the confirmation named, and that command is already gone. The spec treats Enter differently on purpose: Enter re-reads and runs what the store holds now. For discard, the target is the entry the panel named. The code does not do this. `discardResumeRegistration` calls `store.Discard(hookKey, EventOnResume, ViaPanel)`, and `removeEntry` deletes whatever `on-resume` value the key holds, whatever its command. The waiter already carries the command it showed (`cfg.Command`), but it never compares it with the stored one, so a replacement is removed as if it were the entry on screen. The spec also rules out "a pane that drops its panel while the registration it named survives". Deleting a different registration in its place is the other side of that rule.
  RECOMMENDATION: Pass the command the confirmation showed into the discard. Remove the stored `on-resume` entry only when its command still equals that command. A differing command then answers as nothing-to-remove (`false, nil`), so the marker clears and the pane falls through to a shell, and the replacement stays in the store. Keep the other outcomes as they are: a missing entry is nothing-to-remove, and a lock or read failure is a refused write reported on the confirmation.

- FINDING: The report row's truncation cuts off the reason for the failures the spec names
  SEVERITY: low
  FAILURE: A user answers a waiting pane and the answer cannot be carried out. With an unreadable hooks.json on discard, the confirmation's report row reads `failed to load hooks: open /Users/<name>/.config/p…`. When tmux refuses the marker clear on Enter or discard, the panel reads `failed to unset pane option @portal-resume-pending …`. In both cases the cause is cut away: `permission denied`, or tmux's own answer. The pane swallows every key except the act keys, so the user can only press the key again without knowing whether a retry can succeed. The full text survives only inside the `exec` marker's `args` attr in portal.log.
  FILES: cmd/state_resume_wait.go:393-399, cmd/state_resume_draw.go:55-58, internal/tui/resume_panel_parts.go:49-57, internal/tmux/tmux.go:329-335, internal/hooks/store.go:225-228
  DESCRIPTION: The spec says that when an answer cannot be carried out, "the reason is stated on a single line". It names the cases this row exists for: an unreadable store and an unavailable lock on the discard, and a freeze that will not lift on either answer. The report is `err.Error()` verbatim (`resumeReport`, and `dropErr.Error()` in the draw). Wrapped Go errors put the context first and the cause last. `resumeReportRow` then truncates to the card's 52-cell content width, or to the pane's width in the degraded stack. The tmux wrapper's prefix plus the option name is 50 cells before the target and the cause, and a hooks.json path runs past the width on its own. So for the marker clear and for an unreadable store, the row never reaches the reason. It shows an internal option name or a partial home-directory path. The plan chose to author no sentence for this row, and that is not the problem. The problem is that the rendering drops the one part the spec requires. The project's error-handling skill also says technical errors are not shown raw to users.
  RECOMMENDATION: Build the report text so the cause comes first and truncation cuts from the context end. For example: the innermost cause (tmux's stderr, or the OS error such as `permission denied`) followed by the failed act. Or map the reachable failure classes (lock held, store unreadable or malformed, marker clear refused, input drop refused) to short Portal-worded reasons that include the cause. Leave the full chain where it already lands in the log.
