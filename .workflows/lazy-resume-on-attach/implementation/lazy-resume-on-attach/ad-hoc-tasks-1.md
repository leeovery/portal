# Ad Hoc Tasks: Lazy Resume On Attach

## Task 1: A Pane Without an Id Never Takes Another Live Pane's Record
placement: new phase "Mid-Restore Record Ownership"

**Problem**: The previous-record lookup both capture merges share (`indexPrevPanes` / `takePrevRecord`, `internal/state/capture.go:214-277`) keeps two independent maps, one by token and one by address, and every previous record sits in both. A live pane carrying no token looks its record up by address alone. After a restore that renumbers windows, the address a moved tokened pane was saved at can be occupied by a different pane that carries no token — saved windows 1, 3, 4 of `work` restore as 1, 2, 3, so Y (token `T`, saved at window 3) now sits at window 2 and X (no token, saved at window 4) sits at window 3. While both are mid-restore, Y takes its record by token and X takes the record at `work:3.0` by address — Y's record — whole, token included (`*p = record`, `mergeSkippedPanes`, `:165-167`). The committed `sessions.json` then holds two records carrying `T`, and X's record carries Y's working directory, command and scrollback path. A reboot inside that window re-stamps `T` onto both panes and bakes Y's hook key into both, so one resume command runs in two panes and X comes back showing Y's history. The frozen merge (`mergeFrozenPanes`, `:181-204`) has the same shape for a waiting pane that carries no token. This predates the feature — the pre-feature address merge copied a record whole, token included — but the feature's restore-to-wait hand-over now runs through this lookup. Reproduced by the phase-10 reviewer in a scratch copy: X committed as `{CWD:/y ScrollbackFile:scrollback/work__2.0.bin PortalPaneID:ab12cd}` beside Y holding `ab12cd`.
**Solution**: An address match never takes a previous record whose token a live pane in the same capture carries: that record belongs to the pane answering to its token, which takes it by token. The rule lives in the shared lookup, so the skeleton merge and the frozen merge both obey it. A pane carrying no token that finds its address's record refused this way takes no previous record, and gets the fresh record the capture built for it, as any unmatched pane does. A record whose token no live pane carries is still taken by address as today — the case where restore's token re-stamp failed and the pane at that address is the record's own pane. Derivation: the specification holds that one live pane answers to a token, so a token-carrying record has exactly one rightful owner in any capture, and the address match for tokenless panes (§7.2) never meant to hand one pane another pane's identity.
**Outcome**: Every committed `sessions.json` holds each token on at most one record, so no reboot can bake one pane's resume hook or history into another.
**Acceptance Criteria**:
- Saved windows 1, 3 and 4 of `work` restore as 1, 2 and 3: Y, carrying token `T` and saved at window 3, sits skeleton-marked at window 2; X, carrying no token and saved at window 4, sits skeleton-marked at window 3. A capture commits exactly one record carrying `T` — Y's, with Y's saved working directory and command — and X's record carries no token and neither Y's working directory nor Y's command
- The same layout with X waiting (pending, no token) and Y pending by token commits exactly one record carrying `T`, on Y
- A skeleton-marked pane carrying no token whose address's saved record carries a token no live pane carries (restore's re-stamp failed) still takes that record whole, token included, as today
- A skeleton-marked pane carrying no token whose address's saved record carries no token still takes that record whole, as today
- Every existing capture, merge, re-file and link test stays green unchanged, among them `TestCaptureStructureMergeSkippedPanesByToken`, `TestCaptureStructureFrozenMerge` and `TestCaptureAndRefileLinksAMovedSkeletonPaneOntoItsToken`
**Do**:
- The rule goes in the shared previous-record lookup in `internal/state/capture.go` (`indexPrevPanes` / `takePrevRecord`), taking the set of tokens the live panes of the fresh index carry, so both `mergeSkippedPanes` and `mergeFrozenPanes` inherit it with no rule of their own
- Pin the layout above in `internal/state/capture_test.go` beside `TestCaptureStructureMergeSkippedPanesByToken`, and the waiting-pane case in `internal/state/capture_frozen_merge_test.go` beside `TestCaptureStructureFrozenMerge`
