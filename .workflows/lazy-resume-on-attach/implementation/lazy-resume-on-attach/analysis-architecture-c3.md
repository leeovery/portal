AGENT: architecture
FINDINGS:
- FINDING: The hydrate helper parks a pane on the resolved intent; whether the pending marker actually landed is left to each tail
  SEVERITY: medium
  FAILURE: Suppose one tail goes back to unsetting the skeleton marker directly (the shape all three had before this feature) instead of calling `markPendingThenUnsetSkeletonMarker`. Every eager-path test still passes, because the unset still happens. But every lazy pane is now parked with no executable and no pane resolved. The chain `'' state resume-draw …` cannot start, the shell backstop gives the pane a bare shell, the hook never fires and no WARN says why. The user sees a restored pane that neither waits nor resumed. There is a worse version of the same mistake. Moving the executable resolution up into the top-of-run resolution, to pay for it once, is the natural next edit. If that has happened, the same slip draws the panel with no pending marker. The next saver tick then saves the pane's transcript minus its last screen, plus a picture of the card, over the pane's saved file. Nobody notices until a reboot replays that file. Separately, a hydrateConfig that reaches the exec with no decision fires a lazy registration straight away. The nil branch is built to do this, and a test pins it.
  FILES: cmd/state_hydrate.go:61-75, cmd/state_hydrate.go:110-122, cmd/state_hydrate.go:147-152, cmd/state_hydrate.go:177-181, cmd/state_hydrate.go:196-200, cmd/state_hydrate.go:239-252, cmd/state_hydrate.go:348-376
  DESCRIPTION: `resolveResumeDecision` sets `Decision.Wait` from the registration and the install mode before any marker is written. After that, `Wait` is only ever lowered: `markPendingThenUnsetSkeletonMarker` sets it false when the mark fails. `execShellOrHookAndExit` parks the pane whenever `Wait` is true. So "a pane is parked only after its marker landed" holds only because the replay tail, `handleHydrateTimeout` and `handleHydrateFileMissing` each call the mark step before handing back to the exec. The last two of those are injectable seams. The decision travels as a pointer inside a by-value config ("held by pointer so a refusal taken inside a by-value handler reaches the exec"), and the mark step also fills in `Exe` and `Pane` on it as a side effect. Nothing about the data stops a tail reaching the exec without the mark. The only thing that makes that omission non-fatal today is that `Exe` happens to be filled in the same place. On top of that, the `Decision == nil` branch in `execShellOrHookAndExit` looks the registration up again and fires the hook whatever its mode. Production never reaches it; `TestHydrateLazy_NilDecisionFallsBackToItsOwnLookup` pins it as "the hook even for a lazy registration". So a production code path exists whose only behaviour is to undo lazy resume.
  RECOMMENDATION: Pass the decision as a value that the mark step returns, rather than a pointer the tails change. Resolve intent at the top (lazy or not). Then have the mark step return the hand-off itself: park the chain, with its executable and pane, only when the marker write succeeded; otherwise hand off to the hook or the shell. The exec then runs whatever the mark step returned, so no tail can reach it without going through the mark, and the pointer-in-a-value-config goes away. Delete the nil-decision branch: tests that drive the exec directly can build the hand-off they want.
- FINDING: The pane draw logs `theme: loaded` on every keypress and redraw, which the theme package's own resolution passes are built to avoid
  SEVERITY: low
  FAILURE: Every screen a waiting pane shows is drawn by a fresh process: the first draw at restore, `d`, Escape, a report, and every settled resize. Each one resolves its theme through the logging loader and writes one INFO line per slot (two for an adaptive pair) at the production default level. The measured install has 41 waiting panes, so each reboot writes about 41–82 `theme: loaded` lines before the user has touched anything, and each panel keypress or window resize adds more. Duplicate suppression is per process, so a broken drop-in theme logs its fallback WARN once per draw instead of once. The operator's `grep "theme:" portal.log` is supposed to reconstruct theme behaviour; after a reboot it is mostly lines restating one install setting.
  FILES: cmd/state_resume_draw.go:86-89, cmd/state_resume_wait.go:187-195, cmd/state_resume_wait.go:330-337, cmd/state_resume_wait.go:375-400, internal/theme/resolution.go:196-208
  DESCRIPTION: `paneDrawTheme` builds `newThemeLoader()`, the picker's per-launch logging loader, and resolves through `ResolveNomination`. That uses the by-name pass, whose `reportSlot` emits `Loaded` for every slot. The theme package deliberately keeps that line off repeated paths: `reportFallback` is used for re-resolution with the comment "Adding the load line here would put a per-load INFO on a per-keypress path". The pane draw is exactly that kind of path. It runs once per waiting pane per boot and again for every screen change, because each screen change is a new process by design. The loader's duplicate suppression only lasts one process, which is one screen here, not one launch as it is in the picker.
  RECOMMENDATION: Resolve the pane's nomination through a loader that does not report loads: either the silent loader doctor and capturetool already use, or a fallback-only report (the re-resolution cadence) if the broken-theme WARN is worth keeping from a pane. A pane draw repeats the install's theme; it does not choose one.
- FINDING: CaptureAndRefile builds the re-file into its entry point but leaves skipping the frozen panes to the caller
  SEVERITY: low
  FAILURE: The freeze has two halves: re-filing the waiting pane's scrollback, and not dumping it. Only the re-file is structural. Any scrollback-writing capture that skips the skeleton set but not the returned pending set will capture a waiting pane's alternate screen. That could be a second flush path, `state commit-now` gaining scrollback, or a harness copied from an existing tick. It then saves the pane's history minus its last screen, plus the card, into the pane's file. That is the loss the freeze exists to prevent, and it stays silent until the next reboot replays the damaged file. The integration lane's cmd/bootstrap tick copy already has this shape: it calls `CaptureStructure` and skips only the skeleton set. It is harmless today only because those suites pin their registrations to eager.
  FILES: internal/state/scrollback.go:160-173, cmd/state_daemon.go:249, cmd/state_daemon.go:273, cmd/state_daemon.go:319-328
  DESCRIPTION: `CaptureAndRefile` exists so "no caller can commit an index that still names a waiting pane's vacated positional path". The re-file cannot be forgotten. The other half of the same rule, keeping the saver's dump off a waiting pane, comes back as a second set with a doc-comment obligation: "which a caller's own scrollback dump must skip alongside the skipSet it passed". The one production dumping caller combines the two by hand in `paneSkipsScrollback`. So the freeze rule is split between `state` and `cmd`, and the two halves are enforced in different ways.
  RECOMMENDATION: Have `CaptureAndRefile` return the full set of panes whose scrollback must not be dumped (the skipSet it was given plus the frozen panes), or a predicate from `state`. Both halves of the freeze then come out of one entry point, and the daemon's `paneSkipsScrollback` becomes a single lookup.
SUMMARY: The resume chain, the pending marker and the re-file fit together cleanly across process and package boundaries. Three seams still depend on the caller doing the right thing. The most serious is the hydrate helper: whether it parks a pane follows a flag that starts true and that each tail must remember to correct, when it should follow a mark that actually succeeded. The other two are the pane draw repeating the per-launch theme log on every keypress, and the dump skip for frozen panes being left to the caller.
