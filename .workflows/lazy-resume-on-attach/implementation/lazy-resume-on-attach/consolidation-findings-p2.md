# Consolidation Findings: lazy-resume-on-attach (Phase 2)

## Findings

### F1: A frozen pane's retained scrollback path is still a live write address, so the next pane to land on that address overwrites the transcript the freeze exists to protect
- **Class**: behaviour
- **Failure**: A user whose waiting pane is displaced during the wait loses the transcript the freeze protects and gets a stranger's history in its place. The frozen record goes on naming `scrollback/<old-address>.bin`, while whichever live pane now occupies that address is captured into that same file on every tick. Displacement needs no exotic operation: closing a sibling pane in the same window shifts the panes above it down, so a pane that was `work:0.2` becomes `work:0.1` — the frozen pane's old key — and a window close under `renumber-windows on` does the same one level up; `break-pane` and `move-pane` reach it too. Nothing reports the collision. Both records name the path, so `ComputeReferencedSet` keeps the file and the housekeeping pass is satisfied; the frozen pane is skipped, so no write of its own ever contests it; the hash map is keyed by the same live address, so the intruder's first differing capture simply writes. It is noticed at the next reboot, when the user answers the panel and the pane replays a **different** pane's history — and the intruder's pane replays the same bytes, so two restored panes show one transcript. The waiting pane's own transcript has no copy anywhere and there is no route back. This is the same permanent loss §7.2 says the token match closes, arriving through the file name instead of the record lookup.
- **Evidence**:
  - `internal/state/capture.go:199` — `p.ScrollbackFile = record.ScrollbackFile`: the frozen pane's record keeps the path it was filed under, which is derived from an address it no longer occupies.
  - `internal/state/capture.go:473` — `buildPanes` derives every unfrozen pane's path from its **live** key, so the pane now sitting at the frozen pane's old address is filed under exactly the frozen pane's path.
  - `cmd/state_daemon.go:272-273` — the skip is keyed on the live `paneKey`, so the intruder (not pending, not mid-restore) is captured normally in the same tick the frozen pane is skipped.
  - `cmd/state_daemon.go:290` → `internal/state/scrollback.go:76-86` → `internal/state/paths.go:84-86` — the write path is `ScrollbackFile(dir, paneKey)` on the **live** key; the record's stored `ScrollbackFile` is never consulted on the write side, so nothing can notice that the path is already claimed.
  - `internal/state/scrollback.go:77` and `:34-64` — the dedup map is keyed by the same live pane key, and `SeedHashMap` rebuilds it from filenames, so a daemon restart re-seeds the frozen pane's hash under the intruder's key and the collision survives it.
  - `internal/state/commit.go:65-75` — `ComputeReferencedSet` collects stored paths verbatim into a set, so two records naming one path are indistinguishable from one; `gcOrphanScrollback` keeps the file and reports nothing.
  - `internal/restore/session.go:69` — restore replays each pane from `p.ScrollbackFile` verbatim, so both records replay the same bytes on the next boot.
  - Not caught by the phase's own coverage, and not because the coverage is thin: `internal/state/resume_pending_durability_realtmux_test.go:111-174` drives exactly the six rearrangements that reach this state, but the fixture holds one marked pane and nothing ever lands on the address it vacates, so every retained path stays uncontested. `internal/state/capture_frozen_merge_test.go` and `internal/state/commit_test.go:449-472` likewise stage the frozen pane alone.
- **Proposed shape**: Take the frozen pane's bytes out of the positional namespace, rather than leaving them under a name a later occupant can claim. At the tick a pane is first frozen, re-file its scrollback under a name derived from its durable token (`scrollback/pane-<PortalPaneID>.bin`) — one `os.Rename` owned by the daemon beside the skip it already applies, with the new path written onto the merged record. The namespaces are disjoint by construction: every positional key ends `__<window>.<pane>` (`internal/state/panekey.go:25`), so no live address can ever produce that name, and no later occupant can collide. Restore and the housekeeping pass keep reading the stored path verbatim, so neither moves — which is the property §7.2 was reaching for. The un-freeze path is unchanged: the pane returns to ordinary capture, is re-filed under its current address on the first post-clear tick, and the token-named file falls out of reference and is reclaimed. A pending pane carrying no token (the hand-cleared-option degradation task 2.3 admits) keeps today's positional path, and keeps today's exposure, which is the pre-phase behaviour rather than a new one. Rejected alternative: refusing the write when the target path is already claimed by another record keeps the intruder's bytes out of the frozen file but then loses the *intruder's* scrollback for the whole of the wait — one silent loss traded for another. The full migration off positional scrollback names is `durable-pane-identity` (§10); this is the narrow half §7.2 already claims to have done, finished on the write side. Whichever shape lands needs the spec corrected first (S1), because §7.2's "Nothing downstream moves" is the sentence the current code implements faithfully. Coverage the fix owes: a capture-level case staging a frozen pane at a new address **beside** a live pane at its old address, asserting the two records name different files; and a daemon-tick case asserting the intruder's capture does not land in the frozen pane's file and that the frozen file's bytes are unchanged after the tick. The second route to one file that the same guard closes: `takePrevRecord` (`internal/state/capture.go:257-270`) deletes a taken record from `byToken` only, so a tokened pending pane and an untokened pending pane at that record's old address can both take it and both point at one path — unreachable through Portal's own writers (a waiting pane always carries a registration and is therefore stamped), and recorded here only because a token-named frozen file removes it too.
- **Bank**: `lazy-resume-on-attach-2-4` (reviewer) — "A frozen pane's retained scrollback file is still addressed by pane position, so any live pane that lands on its old address silently overwrites it." **Confirmed** against the final state: `mergeFrozenPanes` still carries the previous `ScrollbackFile` across an address change, `buildPanes` still derives an unfrozen pane's path from its live key, and the daemon still writes through `WriteScrollbackIfChanged(dir, paneKey, …)`. Nothing in tasks 2-4 or 2-5 absorbed it. The entry also asks the boundary pass to settle whether task 2-3's reviewer was right to park this under §10's `durable-pane-identity`: it was not. §10 parks the *general* migration, whose absence costs nothing today because an unfrozen pane is re-captured under its new address a second later; the collision here exists only because this phase made one record keep a path it no longer writes, so the phase creates the loss rather than inheriting it.

## Spec Defects

### S1: §7.2 enumerates the downstreams of a retained scrollback path and omits the one that writes it
- **Claim**: §7.2 (specification line 304): "**The token match costs nothing and introduces no new state.** … One live pane answers to a token, so there is no collision to arbitrate … Nothing downstream moves: restore already replays from the path the record stores (`internal/restore/session.go:69`) and the housekeeping pass already builds its reachable set from those stored paths verbatim, so the file keeping its original name is invisible to both. When the wait ends the pane returns to ordinary capture and is re-filed under its current address, and the old file falls out of reference and is reclaimed on the next commit."
- **Observed**: There is a third downstream, and it is not invisible to the retained name. The saver's scrollback **write** derives its path from the pane's live address and never reads the record — `cmd/state_daemon.go:290` → `state.WriteScrollbackIfChanged(dir, paneKey, …)` → `state.ScrollbackFile(dir, paneKey)` (`internal/state/paths.go:84-86`) — and `buildPanes` (`internal/state/capture.go:473`) files every unfrozen pane under that same live key. So the frozen pane's file keeps a name that remains a live write address, and the first pane to occupy that address overwrites it on the next tick. The collision the sentence rules out is real; it is a collision over the **file name**, not over the token, so "one live pane answers to a token" does not reach it. `ComputeReferencedSet` (`internal/state/commit.go:65-75`) is a set of paths, so it cannot report two records naming one, and the closing sentence's clean hand-back ("the old file falls out of reference and is reclaimed") describes a file that by then holds a different pane's bytes. Phase 2's code implements the section as written — the defect is the section's, not the implementation's.
- **Read**: spec wrong. §7.2's enumeration of downstreams is incomplete, and the incompleteness is load-bearing: it is the sentence that authorised leaving the positional file name in place. A corrigendum is owed naming the write path as the third downstream and stating how a frozen pane's bytes are kept out of a live address's reach — without which the section's own stated purpose ("A waiting pane keeps its place in the saved set throughout", "restored on every subsequent reboot, with its original content") is not delivered for a pane tmux moves, which is precisely the case the 2026-09-19 corrigendum was written to close.
