# Consolidation Tasks: Lazy Resume On Attach (Phase 6)

## Task 1: Doctor Reports the Mode the Helper Would Resolve
placement: phase 6
severity: near-miss

**Problem**: `portal doctor`'s `resume mode` line is the only readback of the install-wide resume mode — `hook list` deliberately omits it and nothing in Portal writes it — and it restates the rule the hydrate helper applies at restore time rather than calling it. `checkResumeMode` (`cmd/doctor.go:365-372`) and `installResumeMode` (`cmd/state_hydrate.go:202-217`) each encode "no store gives `resumemode.Default`; otherwise `LoadResumeMode` with its error discarded", each with its own comment justifying the discard (`cmd/doctor.go:364`, `cmd/state_hydrate.go:214`), and doctor's nil-store half lives in `resolveDoctorDeps` (`cmd/doctor.go:130-138`). The doctor suites pin doctor's copy and the hydrate suites pin the helper's; nothing ties them together. If the helper's resolution moves, doctor keeps printing the old answer, and a user reading `lazy` reboots into panes that fire eagerly (or the reverse), discovering it only at that reboot.
**Solution**: One resolver in `cmd` — `installResumeModeOf(store *prefs.Store) resumemode.Mode`: nil answers `resumemode.Default`, anything else answers `LoadResumeMode` with the error discarded, carrying the single comment saying why. `installResumeMode` loads its store through `loadPrefsStoreNoMigrate` and hands it (nil on a load error) to the resolver; `checkResumeMode` renders `installResumeModeOf(store).String()`. Behaviour-preserving: both callers already reach the same answer for every `prefs.json`, and this makes that structural.
**Outcome**: Doctor's resume-mode line and the helper's restore-time decision cannot answer differently for the same `prefs.json`.

**Acceptance Criteria**:
- [ ] With `prefs.json` holding `"resume_mode":"eager"`, then `"lazy"`, `portal doctor` renders `resume mode: eager` / `resume mode: lazy`, and a restored pane whose registration names no mode resolves to that same mode — both exactly as before the change
- [ ] With the `resume_mode` key absent, `prefs.json` absent, unreadable, corrupt, or holding an unrecognised value (`"Eager"`), doctor renders the shipped default and the helper resolves the shipped default — unchanged
- [ ] With no prefs store to be had — doctor's `PrefsStore` left nil by a failed build, the helper's `LoadPrefsStore` returning an error or a nil store — both answer the shipped default — unchanged
- [ ] `rg -n 'LoadResumeMode\(' --type go --glob '!*_test.go'` reports the definition in `internal/prefs/store.go` and exactly one call site, the shared resolver in `cmd` (measured today: 3 lines — the definition at `internal/prefs/store.go:213` plus call sites `cmd/doctor.go:369` and `cmd/state_hydrate.go:215`)
- [ ] `cmd/doctor_resume_mode_test.go`, `cmd/state_hydrate_lazy_test.go` and `cmd/state_hydrate_test.go` pass without modification — a pure refactor, test semantics untouched

**Do**:
- The complete set is the two call sites the grep above measures; both route through the resolver, and no other production code reads the install-wide resume mode
- Add `installResumeModeOf(store *prefs.Store) resumemode.Mode` in `cmd`: nil answers `resumemode.Default`, anything else answers `store.LoadResumeMode()` with its error discarded. The one comment on why the error is discarded lives on the resolver; the two it replaces (`cmd/doctor.go:364`, `cmd/state_hydrate.go:214`) go
- `installResumeMode` (`cmd/state_hydrate.go:205-217`) keeps loading through its existing `cfg.LoadPrefsStore` seam (unset takes `loadPrefsStoreNoMigrate`) — the lazy hydrate suites drive that seam — hands the resolver nil on a load error, and returns the resolver's answer
- `checkResumeMode` (`cmd/doctor.go:365-372`) keeps its `*prefs.Store` parameter (the nil-store subtest calls it directly) and renders `installResumeModeOf(store).String()` as its detail, status `checkInfo` as today
- `resolveDoctorDeps`'s prefs construction (`cmd/doctor.go:130-137`) stays as it is — it already hands a nil store on a build failure, which is the resolver's nil branch

## Task 2: The Pending Dot's Contrast on the Selected Row Is Guarded
placement: phase 6
severity: behaviour

**Problem**: The pending dot keeps its `accent.attention` foreground on the cursor row, over `bg.selection` (`internal/tui/session_item.go:341-357` through `rowToken(…, tok, selected)`), and no contrast guard, swatch or theme doc covers that pairing. `TestForegroundOnTintPairings` (`internal/theme/contrast_test.go:188-209`) enrols `state.positive` on `bg.selection` but not `accent.attention`, so a drop-in theme can take the pending dot below any floor on the selected row with no failure anywhere. Measured on the built-ins: `tokyo-night` 7.36:1, `nord` 5.52:1, `tokyo-night-day` 3.64:1 (`#9A5200` on `#D0C6F0`). The contrast swatch — the human surface for fg-on-tint judgements — still renders the retired `● attached` worded marker as its `state.positive` sample (`internal/capture/swatch.go:109`, `:131`, `:180-190`) and shows no pending dot, and `docs/theming.md:73` tells drop-in authors `accent.attention` is the filter query, edit mode and the `⚠` glyph, so nothing tells them to tune it against `bg.selection`.
**Solution**: Enrol `accent.attention` on `bg.selection` in the contrast guard at `floorLargeUI` (3.0) — derived from the project's own precedent, which holds `accent.attention` as a bar against the canvas to `floorLargeUI` (`contrast_test.go:138`), and from WCAG's non-text contrast floor for a graphical indicator; on the selected row the token renders only the dot, never text. `TestForegroundOnTintPairings` currently asserts every pairing at `floorNormal`, so the pairing carries its own floor there rather than inheriting the text floor; every built-in clears 3.0 today, so no theme file changes. Bring the swatch's selection band to the row as it now renders — a bare `state.positive` `●` and an `accent.attention` `●` replacing `● attached` — adding the new pairing to its caption and to `TestSwatchCoversForegroundOnTintPairings` (`internal/capture/swatch_test.go:216-244`). Add the pending dot, which sits on both the canvas and the selected row, to the `accent.attention` row of `docs/theming.md`.
**Outcome**: A built-in theme whose pending dot would vanish on the selected row fails the guard, and the swatch and theme docs show the row the picker actually draws — the docs being what reaches a drop-in author, since the guard enumerates the embedded built-ins and the loader judges no contrast at all (`internal/theme/validate.go:19-20`: validity is syntactic only).

**Acceptance Criteria**:
- [ ] Rule: the contrast guard holds `accent.attention` on `bg.selection` to 3.0 for every embedded built-in, the pairing carrying its own floor rather than the 4.5 text floor — a built-in measuring below 3.0 on that pairing fails, the failure naming the theme and `accent.attention on bg.selection`
- [ ] Every shipped built-in clears the new pairing with no `.theme` file changed — measured today `tokyo-night` 7.36:1, `nord` 5.52:1, `tokyo-night-day` 3.64:1 (`#9A5200` on `#D0C6F0`)
- [ ] Rule: the five pairings the guard already holds — `text.on-selection`, `text.secondary`, `text.tertiary` and `state.positive` on `bg.selection`, `text.on-attention` on `bg.attention` — stay at 4.5; giving the new pairing its own floor lowers none of them
- [ ] Rendered under any theme, the contrast swatch's `bg.selection` band shows a bare `●` in `state.positive` and a `●` in `accent.attention`, both on the selection tint and packed as the picker's row packs them (attached, then pending, adjacent); the word `attached` appears nowhere on the swatch
- [ ] The swatch's selection-band caption names `accent.attention`, in the band's left-to-right order after `state.positive`
- [ ] `docs/theming.md`'s `accent.attention` row names the pending dot and tells an author it renders on both the canvas and the selected row

**Do**:
- `TestForegroundOnTintPairings` (`internal/theme/contrast_test.go:188-209`): each pairing carries its own floor; the five existing pairings at `floorNormal`, and `{"accent.attention", "bg.selection", …}` enrolled at `floorLargeUI`. `accent.attention` against the canvas stays at `floorNormal` in `TestForegroundFloorAgainstOwnCanvas` (`:83`), untouched
- No change to any file under `internal/theme/builtins/`
- `internal/capture/swatch.go`: retire `swatchAttached` (`"● attached"`, `:109`); `selectionBand` (`:180-190`) renders the bare `state.positive` `●` and the `accent.attention` `●` in its place; the caption at `:131` gains `accent.attention`
- `TestSwatchCoversForegroundOnTintPairings` (`internal/capture/swatch_test.go:216-244`): the `state.positive` entry expects the bare dot, and an `accent.attention` on `bg.selection` entry joins the table
- `docs/theming.md:73`: add the pending dot to the `accent.attention` role, with the note that it sits on both the canvas and the selected row

## Task 3: The Picker Opened Straight After a Reboot Shows Every Waiting Pane
placement: phase 6
severity: behaviour

**Problem**: On the cold reboot route the picker's first visible list is the post-restore refetch in `completeLoadingDismissal` (`internal/tui/model.go:1495-1500`, `:1533-1537`), which reads sessions and the pending set once; afterwards the pending set is re-read only on a kill, a rename or a preview dismissal (`:1381`, `:2815`, `:2878`). Bootstrap step 7 writes each helper's signal byte and does not wait (`cmd/bootstrap/eager_signal_hydrate.go:29-45`), and each helper marks its pane `@portal-resume-pending` only after its full scrollback copy plus a 100 ms settle, or after the 3 s `hydrateTimeout` on the signal-timeout tail (`cmd/state_hydrate.go:32-33`, `:153-172`, `:272-285`). When the restore runs past `LoadingMinDuration` (1.2 s) — the large-restore case the feature exists for — the gate dismisses on `BootstrapCompleteMsg` and the refetch lands before most helpers have marked, so the first picker after a reboot shows fewer pending dots than there are waiting panes, possibly none, until the user kills, renames or previews something. Re-opening the picker shows them all, so the route that misses them is exactly the one the dot exists for, and it does not meet the specification's rule that a row carries the dot when any pane in the session is waiting. This is read from the code, not yet measured.
**Solution**: Take the ordering every helper tail already guarantees — pending is set before the pane's `@portal-skeleton-*` marker is unset (`cmd/state_hydrate.go:314-322`), so once no skeleton marker remains the pending set is final. On the cold route only (the progress-receiver route), after the post-restore refetch, re-take the pending read on a short tick for as long as any skeleton marker remains, applying each reading through the one chokepoint that replaces the pending set (a pending-only variant of `applySessions` that leaves the session slice alone), bounded by `hydrateTimeout` plus a margin so a helper that never finishes cannot keep the tick alive. The read of the markers enters `tui.Deps` as a seam beside `PendingResumeReader`; the warm route and every non-picker path gain nothing. The task first pins the race — a test showing the post-restore refetch reading an unmarked pane that a helper marks a moment later — so the fix is driven by an observed failure.
**Outcome**: A picker opened straight after a reboot gains each pending dot as its helper marks the pane, and settles on the full set without the user having to touch anything.

**Acceptance Criteria**:
- [ ] Cold route: the post-restore refetch reads session `S` with no pending pane while `S`'s pane still carries its `@portal-skeleton-*` marker; a moment later the pane is marked `@portal-resume-pending` and its skeleton marker cleared. With no keypress, `S`'s row gains the pending dot — and panes marked at different moments each gain theirs as they are marked
- [ ] Cold route: when the last pane is marked and the last skeleton marker cleared between two re-reads — or between the refetch and the first re-read — the picker still ends showing that session's dot, so the set it settles on holds every session with a pane marked before the last skeleton marker cleared
- [ ] Cold route: once the picker has found no skeleton marker remaining, it takes no further skeleton-marker read and no further pending read beyond the existing kill, rename and preview-dismissal re-reads
- [ ] Cold route: a skeleton marker that never clears stops the re-reading once `hydrateTimeout` plus the margin has elapsed; the picker keeps the last pending set it read and stays fully usable
- [ ] A re-read landing while the user has moved the cursor or typed a filter changes only which rows carry the pending dot — the rows, their order, the cursor's row and the filter text are as the user left them
- [ ] Warm route (server already running when the picker opened): no skeleton-marker read is taken, and the pending set is read only alongside the session list, as today

**Do**:
- Pin the race first: a cold-route test (progress receiver wired) whose post-restore refetch reads a pane unmarked, with the pane marked a moment later, showing the dot never appearing against the tree as it stands; that observed failure drives the fix
- A skeleton-marker reader enters `tui.Deps` (`internal/tui/build.go`) beside `PendingReader`, nil-tolerant like the other optional seams, and is wired in `cmd/open.go` beside `pendingReader` (`:500`, `:574`, `:706`) over `state.ListSkeletonMarkers` (`internal/state/markers.go:59`), which the `*tmux.Client` already wired there serves
- The re-reading starts only on the route `refetchSessionsAfterRestore` already gates on (`progressReceiver != nil`, `internal/tui/model.go:1495-1500`), after the post-restore refetch lands, and runs on a short tick for as long as the marker read reports any marker
- Each pending reading is applied through a pending-only variant of `applySessions` (`internal/tui/model.go:1156-1165`) that replaces the pending set and leaves `m.sessions` alone, so the pending set has one place it is replaced
- The bound is `hydrateTimeout` plus a margin; `hydrateTimeout` is declared in `cmd` (`cmd/state_hydrate.go:32`), which `internal/tui` does not import
- Bootstrap, the eager signal pass (`cmd/bootstrap/eager_signal_hydrate.go`) and the hydrate helper stay unchanged — the fix lives in the picker
