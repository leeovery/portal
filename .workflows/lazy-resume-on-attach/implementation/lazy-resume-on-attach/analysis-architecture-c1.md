FINDINGS:
- FINDING: The parked recovery tail's argv is an unversioned protocol that outlives a Portal upgrade
  SEVERITY: medium
  FAILURE: A pane can wait for weeks, so a Portal upgrade can land while panes are still waiting. Later, a waiter ends: the user resizes the window, presses `d` or Esc, or the process is killed. The parked shell then runs `resume-recover` with the argv the old version baked in, but the binary answering at that path is the new one. If any release renames or drops `--pane` or `--pane-key`, cobra rejects the flag and the tail exits non-zero. `sh -c 'draw; recover'` then exits and tmux closes the pane. On the measured install (43 of 44 sessions hold one pane) that closes the session, and the next capture drops it from the saved set with its whole transcript. The user sees sessions vanish some time after upgrading. The single-version test suite cannot see any of this, because every round-trip test composes and parses with the same build.
  FILES: cmd/state_hydrate.go:271-274, cmd/state_resume_chain.go:66-70, cmd/state_resume_chain.go:100-114, cmd/state_resume_recover.go:66-99
  DESCRIPTION: `execResumeChainAndExit` bakes `'<exe>' state resume-draw …; '<exe>' state resume-recover --pane … --pane-key …` into the pane's own process. `<exe>` is whatever `os.Executable()` returned during hydrate (on a Homebrew install, the stable symlink), so each later hop re-enters whichever binary sits at that path at that moment. Every other exec chain in Portal lasts seconds (hydrate, spawn); this one lasts as long as the wait, which is indefinite by design. The draw/wait hops fail safe on skew: a failed parse falls through to the recovery tail. The recovery tail has no such fallback, so it is the one step whose argv must parse under any future version. Its source even notes that "a parse this command refuses closes the pane it exists to keep open". It avoids required flags, but it still refuses unknown ones, and version skew is exactly how unknown or renamed flags would arrive. The spec already ranks the outcomes: an extra shell is the lesser failure against a pane that closes.
  RECOMMENDATION: Make the tail unable to fail on argv. Do two things. First, have `resume-recover` accept any flags (`FParseErrWhitelist{UnknownFlags: true}`) and read its pane from `$TMUX_PANE` (it runs inside the pane) when `--pane` is missing or empty, so it needs no flag to do its job. Second, compose the parked chain as `<draw>; <recover> || exec "${SHELL:-/bin/sh}"`, so a tail that cannot even start still leaves a shell rather than a closed pane. This costs nothing for an answered pane, because recover exits 0 there. Keep refusing `--drop-input` on the waiter as it does today; that refusal protects the confirmation, and a draw/wait parse failure already degrades to the tail.

- FINDING: The resume decision is valid only after the mark step, which three sites must remember to run; a nil decision fires lazy hooks eagerly
  SEVERITY: low
  FAILURE: `resolveResumeDecision` returns `Wait: true` with an empty `Exe` and `Pane`. They are filled in later by `markResumePending`, which writes through a pointer shared by the by-value `hydrateConfig`. Suppose a tail reaches `execShellOrHookAndExit` without first calling `markPendingThenUnsetSkeletonMarker`: for example a new degraded tail, or a `HandleTimeout`/`HandleFileMissing` replacement that drops the call. The helper then execs `/bin/sh -c "'' 'state' 'resume-draw' …; '' 'state' 'resume-recover' …"`. Both commands fail, the pane's process exits and the pane closes (with a single-pane session, the session closes too), and the pane's skeleton marker is never unset. Separately, the production branch for `Decision == nil` fires the hook regardless of resume mode, and `TestHydrateLazy_NilDecisionFallsBackToItsOwnLookup` pins that as intended. Any caller that reaches the exec without a resolved decision therefore resumes every lazy registration eagerly, with no WARN. The user only notices when the memory cost this feature exists to remove comes back after a reboot.
  FILES: cmd/state_hydrate.go:56-70, cmd/state_hydrate.go:196-200, cmd/state_hydrate.go:239-257, cmd/state_hydrate.go:264-275, cmd/state_hydrate.go:279-293, cmd/state_hydrate.go:298-315, cmd/state_hydrate.go:321-349
  DESCRIPTION: The rule "the mode is resolved and the marker written once, ahead of whichever clear runs" is currently enforced by call-site discipline. `runHydrate`'s replay path and the two injected tail handlers each call `markPendingThenUnsetSkeletonMarker` themselves. So the obligation lives inside swappable seams rather than in the function that composes them. The decision type can represent an illegal state (a wait with no executable to wait in). It only becomes legal through a side effect elsewhere that mutates it through a shared pointer, and `execResumeChainAndExit` never checks. The nil branch is production code with no production caller, and it encodes the rule the feature forbids. It exists only so that older tests can drive `execShellOrHookAndExit` directly.
  RECOMMENDATION: Have `runHydrate` own the mark step: call it once, after whichever tail's handler returns, and leave the handlers with only their logging and FIFO cleanup. Have the mark step produce the wait state itself, for example as a `pendingChain{exe, pane}` value set on the decision only once the marker is written, so that `execResumeChainAndExit` takes that value and cannot be reached with an empty executable. Delete the `Decision == nil` branch. Tests should resolve a decision through `resolveResumeDecision`, or construct an eager one, instead of relying on a fallback that ignores the mode.

- FINDING: Registration's JSON encoding ignores its exported fields whenever it was decoded
  SEVERITY: low
  FAILURE: `MarshalJSON` returns `raw` whenever it is present. A registration loaded from hooks.json, changed through its exported `Command` or `Resume`, and saved therefore writes back its original bytes. The change is dropped with no error. Only `Set` avoids this, because it rebuilds a fresh value. Any later mutation added to the store that edits a loaded registration in place (for example, re-pinning a mode) would report success while hooks.json stays unchanged. The user would notice only when `hook list` or the next reboot shows the old command or mode.
  FILES: internal/hooks/registration.go:14-24, internal/hooks/registration.go:53-64, internal/hooks/store.go:160-162
  DESCRIPTION: Byte-preservation is a sound requirement: an untouched entry must keep attributes the reader does not model. But the type enforces it in a way that is only correct for callers who know the trap. Its visible state (`Command`, `Resume`) and its encoding can disagree, and the one guard is a comment in `Set`. The type's contract becomes "never modify a decoded value" rather than something the type holds by itself.
  RECOMMENDATION: Re-emit `raw` only when the value still carries what `raw` decoded to. Keep the decoded command and mode beside `raw` (or re-decode at marshal) and fall through to the fresh projection when `sameRegistration` fails. Untouched entries still round-trip byte-for-byte, an edited one encodes its edit, and `Set`'s rebuild and its comment are no longer needed.

- FINDING: The scrollback re-file renames on disk before the index that names the new path is committed
  SEVERITY: low
  FAILURE: `CaptureAndRefile` renames a waiting pane's positional file to `pane-<token>.bin` as soon as the capture returns. `captureAndCommit` then has three `ctx.Done()` checks that `return nil` without committing, and `Commit` can itself fail. If the daemon is cancelled or killed in that gap on a pane's first frozen tick, and the tmux server then goes away before any later tick commits (reboot or kill-server, so the shutdown flush cannot capture), sessions.json still names a positional path that no longer exists. After the reboot, restore replays a missing file, so the waiting pane comes back empty. The first post-boot commit's GC then deletes the unreferenced token-named file, so the transcript is gone permanently.
  FILES: internal/state/scrollback.go:136-147, internal/state/scrollback.go:166-172, cmd/state_daemon.go:249-262, cmd/state_daemon.go:266-272, cmd/state_daemon.go:303-305
  DESCRIPTION: Until now, every scrollback mutation was safe in either order against the index, because a write replaces bytes at the path the index already names. The re-file is the first step that changes a path the committed index names before that index is committed. It leaves the filesystem in a state that is only valid once the caller's later `Commit` lands. The window is narrow (one tick per pane per boot), and the tolerance for a missing source repairs it whenever a later tick commits against a live server. The damage when it is not repaired is the one this feature ranks worst.
  RECOMMENDATION: Hard-link the positional file to the token name instead of renaming it. Both names then hold the bytes until a committed index stops referencing the positional name, and the existing GC reclaims it on that commit. An address the pane vacated is still free to be rewritten, because `AtomicWrite` replaces the directory entry and leaves the linked inode alone. Handle an existing token-named file explicitly, as the rename did implicitly.

- FINDING: Callers must apply the waiting-pane scrollback skip themselves, unlike the re-file
  SEVERITY: low
  FAILURE: `CaptureAndRefile` makes the re-file impossible to skip, but it only hands back the frozen set and leaves it to each caller to skip those panes in its own scrollback dump. A writer that forgets captures a waiting pane through the card. It saves the transcript minus its last screenful plus a picture of the card, silently, and the next reboot replays the truncated file. The bootstrap suite's daemon-tick replica already drops the set (`idx, _, err := state.CaptureStructure(...)`) and skips only skeleton panes. Because lazy is now the default, any new test that registers a hook through it without pinning eager is modelling a daemon that does not exist.
  FILES: internal/state/scrollback.go:160-172, cmd/state_daemon.go:273, cmd/state_daemon.go:319-329, internal/restore/lazy_resume_panel_integration_test.go:394-399, cmd/bootstrap/daemon_tick_test_helpers_test.go:45-60
  DESCRIPTION: The freeze has two halves: moving the bytes off the positional name, and not overwriting them. `internal/state` owns the first. The second is a rule restated wherever scrollback is dumped: once in the daemon (`paneSkipsScrollback`) and again in the lazy-panel fixture, and it is missing from the bootstrap replica. The rule "skeleton-marked OR pending" belongs with the capture that established both sets.
  RECOMMENDATION: Return the skip decision from the capture rather than a raw set. For example, `CaptureAndRefile` could return the union of `skipSet` and the frozen panes as "the panes your dump must skip", or a small result type with a `SkipsScrollback(paneKey)` method. `paneSkipsScrollback` then moves into `internal/state`, and the daemon and every tick replica ask that one predicate.

SUMMARY: The pieces fit together cleanly. Hydrate, the chain, the store, the capture and the picker share single sources for resolution, the skip, lookups and rendering. What remains is a set of invariants held by caller discipline or by same-version assumptions. The most consequential is that the parked recovery tail's argv must parse under whatever binary answers weeks later. The others are a decision type that is illegal until a side effect fixes it, a registration whose encoding ignores its fields, a rename committed after the fact, and a scrollback skip left to each caller.
