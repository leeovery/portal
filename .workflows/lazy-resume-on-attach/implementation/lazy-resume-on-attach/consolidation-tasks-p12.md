# Consolidation Tasks: Lazy Resume On Attach (Phase 12)

## Task 1: A Save Request Made During a Tick Survives That Tick
placement: phase 12
severity: behaviour

**Problem**: Phase 12's bounded commit lock gives a timed-out `commit-now` one recovery: `failCommitNow` touches `save.requested` so "the daemon's next tick retries" (`cmd/state_commit_now.go:138-147`). The only committer that holds the lock for seconds is the daemon's own tick, since `commit-now` dumps nothing — and that tick removes `save.requested` unconditionally after a successful cycle (`cmd/state_daemon.go:196-200`). The timeout can only happen while the tick holds the lock, and the tick removes the flag only after releasing it, so the retry request is always erased: the tick commits a `sessions.json` captured before the session closed, deletes the flag, and nothing commits the removal until the next dirty event or the 30s `MaxGap` tick (`:184`, `:449`). A reboot or tmux server loss in that window brings a session the user killed back at the next bootstrap, scrollback included, with only an unanswered `commit-now` ERROR in `portal.log`. This machine's retained logs show 388 of 94,721 ticks at 5s or more, max 18.2s. The same unconditional removal also erases touches from `hook set` and `portal state notify` that land after the tick's capture. Not a regression — before phase 12 the long tick's commit overwrote `commit-now`'s result — but the phase's timeout route is what was meant to make this case recoverable, and no test covers a touch surviving a concurrent tick (`cmd/state_commit_cycle_lock_test.go:182-219` asserts only the touch).
**Solution**: Consume the flag before the cycle rather than after it: in `tick`, after the restoring check and the dirty/gap decision, remove `save.requested`, then run `captureAndCommit`; on a non-nil error re-touch it with `state.TouchSaveRequested` (WARN if that touch fails), and drop the post-commit removal. A touch landing during the cycle then survives to the next tick, which commits a capture taken after it; a touch landing between the removal and the capture costs one redundant commit; a cancelled cycle consumes the flag harmlessly, since the shutdown flush follows. This keeps phase 12's settled rule that a tick which cannot take the lock leaves `save.requested` for the next tick (`TestDaemonTick_StandsDownWhileAnotherCommitterHoldsTheCycle` stays green). Rejected: removing the flag only when its mtime is unchanged since the dirty check, which depends on timestamp granularity. Pin it with a daemon tick whose fake commander touches `save.requested` from its capture-pane dispatch, standing in for a `commit-now` that timed out mid-dump: after the tick returns the flag still exists, and the next tick commits.
**Outcome**: A save request made while a tick is running — a timed-out `commit-now`'s retry, a `hook set`, a `portal state notify` — is honoured by the next tick instead of waiting up to 30s, so a session killed during a long tick leaves `sessions.json` within a tick of the lock freeing.
**Acceptance Criteria**:
- [ ] A dirty tick during whose cycle a save request lands — the fake commander touching `save.requested` as it serves a `capture-pane`, standing in for a `commit-now` that timed out mid-dump — commits, and after it returns `save.requested` still exists
- [ ] The tick after that one, with the 30s gap not elapsed, runs a fresh capture and commits it, and leaves `save.requested` absent
- [ ] A dirty tick whose cycle commits with no request landing during it leaves `save.requested` absent and advances the last-save time, as today
- [ ] A dirty tick whose cycle fails — a capture error, or another committer holding `commit.lock` past the bound — logs its `tick failed` WARN, leaves `save.requested` set and does not advance the last-save time; once the lock frees, the next tick commits and leaves the flag absent (`TestDaemonTick_StandsDownWhileAnotherCommitterHoldsTheCycle` and `TestDaemonTick_PreservesSaveRequestedOnError` stay green unchanged)
- [ ] A failed cycle whose re-touch of `save.requested` also fails logs one WARN for the failed touch under the `daemon` component beside the `tick failed` WARN, and the tick returns normally
- [ ] A tick whose cycle is cancelled mid-dump emits no WARN and leaves `save.requested` consumed rather than re-raised
- [ ] A tick suppressed by `@portal-restoring` leaves `save.requested` in place, as today
**Do**:
- `cmd/state_daemon.go` `tick` (`:174-201`): after the restoring check and the dirty/gap decision (`:175-189`), remove `state.SaveRequested(deps.Dir)` — the removal now at `:198-200` moves here, keeping its not-exist-tolerant `remove save.requested failed` WARN — then run `captureAndCommit`
- On a non-nil `captureAndCommit` error: keep the `tick failed` WARN, re-touch through `state.TouchSaveRequested(deps.Dir)`, WARN on `deps.Logger` if that touch fails, and return without advancing `LastSaveAt`
- Drop the post-commit removal; `LastSaveAt` still advances on success. `defaultShutdownFlush` (`:363-382`) and the daemon-start clear (`:404-406`) are unchanged
- Pin the concurrent touch through `daemonFakeCommander`'s existing `dispatchHook` (`cmd/state_daemon_run_test.go:57`), touching `save.requested` on a `capture-pane` dispatch
- `cmd/state_commit_now_daemon_merge_integration_test.go:107-129`: `waitForSaveRequestedConsumed` takes the flag's disappearance as the forced tick having committed. After this change the flag goes before the cycle runs, so that wait no longer establishes the commit landed; the test must still read `sessions.json` only after the forced tick has committed
