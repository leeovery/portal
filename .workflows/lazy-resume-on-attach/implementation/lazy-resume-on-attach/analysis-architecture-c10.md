- FINDING: The shell backstop copies the recovery tail's steps but not the check that makes the tail do nothing on an answered pane
  SEVERITY: medium
  FAILURE: Take a pane resumed from its panel (Enter) or discarded from it (y). If the Portal binary at the path the chain baked is gone by the time the user exits that pane's shell, the pane takes two exits to close. This is the regression §4.2 rules out: "a pane that has been answered is handed no second shell". The path goes on a package-manager upgrade that removes the versioned install path. That happens on every upgrade on Linux, where os.Executable resolves to the real file, and wherever else the baked path is a versioned or temporary one. The sequence: the hook's shell exits, the parked shell tries `<exe> state resume-recover`, and sh returns 127. The backstop sees `[ ! -x exe ]`, resets the pane, clears a marker that is already clear, runs `stty sane` and execs `${SHELL:-/bin/sh}`. The user types `exit` and gets a fresh prompt instead of a closed pane. Nothing is logged, because no Portal binary is left to log it.
  FILES: cmd/state_hydrate.go:291, cmd/state_hydrate.go:296, cmd/state_hydrate.go:317, cmd/state_resume_recover.go:39
  DESCRIPTION: The recovery tail is written twice. runResumeRecover is the Go version. parkedChainBackstop is a shell copy of it for when that binary cannot start. The Go version begins with the decision that tells an answered pane from an abandoned one: it reads @portal-resume-pending, and returns without doing anything when the read succeeds and the marker is clear. The shell copy starts at the step after that decision. Its doc comment says it "takes the tail's own steps in the tail's order", but its only guard is "the tail could not start" (status 126/127 plus an executable that is no longer runnable). That guard only separates an abandoned pane from an answered one if the binary is always still present after an answer. Nothing ensures that: an answered pane can stay open for days, across upgrades, before its shell exits and the tail runs. The two copies share constants (option names, the poll bound) but not the gate. That gate is the one part of the tail that decides whether any of the other steps should run. The backstop test cases stage an unstartable binary only for a pane whose draw never ran, so the answered-then-binary-gone case is not tested.
  RECOMMENDATION: Open the backstop with the tail's own gate, composed like its other tmux calls from state.ResumePendingOption and tmux.PaneIDTarget(payload.Pane). Read `#{@portal-resume-pending}` for the pane. When that read succeeds and comes back empty, end with `exit $s` before any reset, clear, unpin or shell. When the read fails, treat the pane as still pending and run the existing steps, which is the rule runResumeRecover applies to a failed read. The unanswered path keeps its current order. Update parkedChainBackstop's doc comment in the same edit so it names the gate. Add a backstop case in which the draw has run and cleared the marker and the binary is gone when the tail runs.
- FINDING: The resume chain's records identify the pane only by its restore-time positional key, which this feature relies on going stale during a wait
  SEVERITY: low
  FAILURE: When a waiter dies unanswered and the recovery tail's marker clear fails, "unset resume pending marker failed" is the only record that the pane's saved transcript is now frozen for the rest of its life. §4.3 and §7.3 call that WARN "the whole of what makes that pane findable". The record names the pane by pane_key, the positional address baked from the FIFO path at restore time. If the session was renamed from the picker, a sibling window closed under renumber-windows, or the pane was broken out or moved during the wait, that address now belongs to another pane or to none. An operator searching portal.log for the frozen pane is sent to the wrong place. The pane's transcript stays frozen until a reboot restores it stale. The same applies to the chain's "alternate screen leave unconfirmed" and "unset alternate-screen pin failed" WARNs.

  DESCRIPTION: §7.3 moved the freeze off a positional server option onto a pane option because every part of a positional address changes over a wait that lasts days. The chain carries two identities that do not change: the pane's hook key (its @portal-pane-id token) and its pane id. Its records use neither. resumeChainArgv hands the recovery tail only --pane and --pane-key and drops the hook key that draw and wait both carry. So the tail has no durable name for the pane to log. The hook key would be enough: `portal hook list` already resolves a token to the pane's current `<session>:w.p` location, and the recovery path leaves the registration in place.   RECOMMENDATION: Add the hook key to the recovery tail's argv (resumeChainArgv's recover branch, plus a --hook-key flag on stateResumeRecoverCmd). The tail already accepts flags it does not register, so a chain parked by an older build still parses. Emit `hook_key` next to `pane_key` on the WARNs the wait and recovery paths write. hook_key is already part of the hydrate component's attribute vocabulary.
