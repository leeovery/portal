# Consolidation Tasks: Lazy Resume On Attach (Phase 1)

## Task 1: Set Re-Projects the Registration It Stores
placement: phase 1
severity: behaviour

**Problem**: `Store.Set` stores the `Registration` it is handed directly into the snapshot (`internal/hooks/store.go:160`), and `Registration.MarshalJSON` short-circuits to the retained `raw` bytes whenever they are present (`internal/hooks/registration.go:52-54`). `UnmarshalJSON` populates `raw` for every stored shape, so every value in a snapshot a caller loads carries it, and a plain struct copy carries it along — `raw` is unexported, so nothing at the call site shows it is there and nothing can compile-refuse it. A caller that loads a registration, adjusts it and hands it back therefore writes the bytes it loaded rather than the bytes it built, while `classifySet`/`sameRegistration` — which judge on `Command` and `Resume` alone — classify the write `modify`, rewrite the file, and emit the INFO breadcrumb carrying the command. The user sees a pin that silently does not take, a pane that comes back eager after being set lazy, with a log line saying it landed and a `hook list` mode column that never changes. Nothing in the tree fails. No live caller does this today — both non-test callers construct fresh (`cmd/hooks.go:222`, `internal/hookstest/hooks.go:79`) — so this is a latent trap the phase created rather than a reproducible defect, and the read-modify-write is the natural shape for the store work later phases reach for.

**Solution**: Re-project inside `Set` before storing — `h[key][event.String()] = Registration{Command: registration.Command, Resume: registration.Resume}` — so the method's own documented contract, "nothing the replaced value held survives a rewrite it was not given" (`internal/hooks/store.go:129-133`), is enforced by the store rather than assumed of every caller. Behaviour for every existing caller is unchanged, since none passes a raw-carrying value, and the preservation property is untouched: an entry the write did not name still comes out of the snapshot carrying its own retained bytes. A `NewRegistration` constructor was considered and rejected as the weaker shape — it does not foreclose the struct-copy path, which is the one a caller reaches by accident. In the same edit, replace the claim about distant callers in the `raw` field comment (`internal/hooks/registration.go:19-21`, "A registration a mutation builds carries none, so it is written in the shape its own content chooses") with the fact the code then enforces: a mutation's value is re-projected before it is stored.

**Outcome**: A registration that reaches `Set` carrying decoded bytes is written from its own content, so the write the breadcrumb reports is the write that lands — and a later read-modify-write caller cannot silently lose its edit.

**Do**:
- In `Set` (`internal/hooks/store.go:157-160`), store a re-projection rather than the value the caller handed in: `h[key][event.String()] = Registration{Command: registration.Command, Resume: registration.Resume}`. Leave the lock, the load, `classifySet`, the save and every breadcrumb exactly as they are — the classification already judges on command and mode alone, which is precisely what the re-projection carries through. Add one line warning that collapsing this back to the handed value reinstates the loaded bytes (wording the executor's).
- Replace the second sentence of the `raw` field comment (`internal/hooks/registration.go:19-21`) — "A registration a mutation builds carries none, so it is written in the shape its own content chooses" — with the property the code now enforces: a value a mutation stores is re-projected from its command and mode before it is stored, so a registration that reached `Set` carrying decoded bytes is written from its own content. Leave `MarshalJSON`'s raw-first branch and its doc comment untouched — that branch is what preserves an entry a rewrite did not name, and this change does not narrow it.
- Add the read-modify-write coverage to `internal/hooks/store_set_test.go`: stage string- and object-form seeds through `hookstest.StageStore(t, hookstest.Staging{Seed: …})`, read them back through `store.Load(hooks.ViaInternal)`, adjust the loaded `Registration`'s `Resume` and hand it to `Set`. That route — the only one by which a raw-carrying value reaches the method, and the one a later caller reaches by accident — is what the assertions must run through; a freshly-constructed registration cannot exercise the trap. Assert the on-disk bytes with the package's `storedValue` helper and the emitted record with `logtest.Install` + `logtest.AssertRecord`.
- Pin the two properties the re-projection must not break, in the same file: a rewrite whose value came out of the loaded snapshot still leaves every entry it did not name byte-identical (`storedValue` + `bytes.Equal`, over a sibling carrying an unmodelled attribute and one holding a value the reader cannot model), and a loaded registration handed straight back unchanged is still a `set-noop` that writes no file (`readFileBytes` + `modTime`, one DEBUG record).

**Acceptance Criteria**:
- [ ] A registration loaded from `hooks.json`, adjusted and handed back to `Set` is written from its command and mode, never from the bytes it was decoded from: a string-form entry pinned lazy comes back as `{"command":…,"resume":"lazy"}`, and an object-form entry seeded `eager` and adjusted to `lazy` carries `lazy` on disk.
- [ ] The write the breadcrumb reports is the write that lands — after a mode-only read-modify-write the INFO `modify` record and the file agree, with the op, `hook_key`, `via` and `value` vocabulary unchanged from today.
- [ ] A rewrite whose value came out of the loaded snapshot drops the replaced entry's unmodelled attributes, exactly as a freshly-constructed one does: the re-projection is the whole entry, not a merge with what was there.
- [ ] The preservation property is untouched. Every entry the write did not name comes back byte-identical — an unmodelled attribute, an unrecognised `resume` value, and a value that is neither string nor object alike — whether the value being written was constructed fresh or loaded from that same snapshot.
- [ ] Handing a loaded registration straight back unchanged is still a `set-noop`: no write, the file byte-unchanged and its mtime unchanged, one DEBUG record and no INFO — so an idempotent re-registration still leaves an object entry's unmodelled attributes on disk.
- [ ] Every existing caller is unchanged in behaviour: `cmd/hooks.go`'s `hooksSetCmd` (line 227) and `internal/hookstest`'s `SeedHooksJSON` (line 79) construct fresh registrations, and the existing `internal/hooks` suites — `store_set_test.go`, `registration_test.go`, `store_test.go` — pass untouched.
- [ ] The `raw` field comment no longer asserts a property of callers the store does not check.
- [ ] `go test ./...` passes and `go vet -tags integration ./...` is clean: the signature is unchanged, so no integration-tagged suite needs an edit.

**Tests**:
- `"it writes the mode a loaded registration was adjusted to rather than the bytes it was loaded from"` (table: string-form seed adjusted to lazy; object-form `eager` seed adjusted to lazy — each asserting both the stored bytes and the `modify` record)
- `"it drops the replaced entry's unmodelled attributes when the rewrite came out of the loaded snapshot"` (seed carrying `"nickname"`, load, adjust the mode, assert the stored value is the two-attribute object)
- `"it leaves every entry a loaded-value rewrite did not name byte-identical"` (siblings: one carrying an unmodelled attribute, one holding a value the reader cannot model)
- `"it treats a loaded registration handed straight back as a no-op and leaves the file untouched"` (object-form seed carrying an unmodelled attribute: no write, mtime unchanged, one DEBUG `set-noop` record, the attribute still on disk)
