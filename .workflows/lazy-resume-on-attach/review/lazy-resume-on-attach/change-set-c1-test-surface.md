FINDINGS:
- [in-scope] [spreading] internal/tui/pane_appearance_realtty_test.go:22 — The test that claims to prove "the production reader" against a real terminal opens the pty slave's own device node (`openTTYPath(grantedPTYSlave(t))`). Production opens the controlling-terminal indirection `/dev/tty` instead (`paneTTYPath`, internal/tui/pane_appearance.go:18, wired at :48), and internal/tui/pane_appearance_test.go:597-601 pins that constant. Measured on darwin inside a disposable tmux pane, `os.OpenFile("/dev/tty", O_RDONLY)` followed by `SetReadDeadline` returns `file type does not support deadline`, while the same pane's own node (`/dev/ttys001`) accepts the deadline and times out at 102 ms. So every production `detect()` takes the refused branch at pane_appearance.go:108-109 and resolves `MemberDark`, after the OSC 11 query has already been written at :103 with nothing left to read its reply. That is the branch the task's own criterion says "no production path takes". The fix has more than one defensible form. The probe needs a descriptor that honours a deadline, for example by opening the pane's terminal by its own device name resolved from fd 0 instead of `/dev/tty`. The real-terminal test then has to go through the production opener with the pty as the process's controlling terminal (a Setsid/Setctty child, as cmd/tty_signals_pty_test.go:44 already does), and the path pin at pane_appearance_test.go:597 has to follow. — FAILS: whenever the nomination is an adaptive pair (which is what an install with no theme key resolves to), every waiting panel and discard confirmation is painted in the dark member, even when a client on a light terminal is attached. That contradicts §5.2 ("a redraw with a client present resolves against the terminal in front of it"). Meanwhile the suite reports the production reader as proven against a real terminal, so nothing turns red.
