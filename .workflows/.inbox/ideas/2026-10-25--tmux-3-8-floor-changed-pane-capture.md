# Adopt tmux 3.8 as the floor and capture only changed panes

tmux on the machine was upgraded to 3.8, and Portal works on it: the restores on 3.8 applied geometry with no anomalies, the daemon commits normally, and the tmux surfaces Portal depends on (hook reads, option reads, layout capture and `select-layout`, hook firing) behave as before when probed on a sandbox server. Portal is built for Lee alone, so its minimum versions track what Lee runs. The idea is to make tmux 3.8 the floor outright and use what it adds, with one code path that assumes 3.8, and no fallback for older tmux.

The main part is cheaper commit cycles. Today every commit cycle runs a full-history `capture-pane` for each pane, hashes the output, and writes only what changed. Measured from the daemon log over an hour on 3.8, a cycle took about 620 ms at the median and 810 ms at p90, running roughly every 22 seconds. tmux 3.8 adds two per-pane counters: `#{pane_output_generation}`, which increments whenever the pane processes output, and `#{history_generation}`, which increments when the history is cleared or reflowed by a resize. A sandbox probe confirmed both hold still while a pane is idle. Adding them to the `list-panes -a` the cycle already runs (the `captureFormat` in `internal/state/capture.go`) would let the cycle skip `capture-pane` for any pane whose counters haven't moved since its last capture. The counters reset when the tmux server restarts, so they belong to the committer's own server. Beyond the saving itself, cheap cycles would make it affordable to save transcripts every tick. Today output alone doesn't mark state dirty, so a transcript can be up to the 30-second max gap stale.

The floor itself means raising Portal's version check (`internal/tmux/version.go`), which today compares only the major version against 3, to require 3.8 by comparing the minor too. Development builds report something like `tmux next-3.9`, which the current parser rejects.

A smaller optional cleanup: on 3.8, `show-options -F '#{option_name}…#{option_value}'` returns option values unquoted and unescaped, so the server-options read (`ShowAllServerOptions` and whatever parses its `@name "value"` rows) could drop its unquoting step. `show-hooks -F` doesn't expose a hook's array index, which hook convergence needs, so the `show-hooks` parser stays as it is.

Other 3.8 additions were considered and left out. Event waits (`wait-for -E`) instead of the notify hooks would leave the commit-now and signal-hydrate hooks in place anyway. Zoom already fires `window-layout-changed`, so the new `window-zoomed` and `pane-resized` hooks add nothing. The OSC 133 command-finished hooks depend on shell integration and nothing in Portal would use them.
