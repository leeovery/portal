FINDINGS:
- [in-scope] [spreading] internal/tui/search_filter.go:38 — `set` keys the map on `si.FilterValue()`, which is `name` and the home-abbreviated `dir` joined by a space (internal/tui/session_item.go:87-89 over `resolver.SearchFields`), so two rows whose joined value coincides but whose fields differ collapse onto one entry and the later item in the slice wins. A session renamed to `api ~/Code/api` (legal: `tmux.ValidateSessionName` refuses only `:`, a leading `$` and a leading `-`) sitting beside a session `api` whose recorded dir is `~/Code/api` both key on `"api ~/Code/api"`. Under the term `api ~`, `MatchesSearchTerm` should match the first (its *name* contains that run) and not the second (§4.4 tests the fields separately and never joins them — the rule `TestSearchContainmentMatchesASpacedNameOnItsOwnFields`, internal/tui/search_containment_test.go:161-172, exists to pin). With one shared entry both rows get the same verdict: whichever row lost the map write is ranked by the other's fields. The previous implementation read the fields off the item itself and could not collide. A fix has more than one defensible shape (hold `[]searchEntry` per key and rank a row only when the entry matching it is unambiguous; or key on something the pass can still resolve), and no current test or compiler check observes it — FAILS: with that pair of sessions live, a search either drops a row whose name contains the term or surfaces a row neither of whose fields contains it, which is the exact guarantee §4.4 and this task assert.
