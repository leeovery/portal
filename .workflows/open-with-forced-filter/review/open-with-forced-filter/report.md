# Implementation Review: Open With Forced Filter

**Plan**: open-with-forced-filter
**Verdict**: Fail

## Summary

The search form is delivered end to end and works: `x /port` recognises the sigil on shape alone, keeps it out of the resolution chain, counts live sessions by case-folded containment over name and home-abbreviated recorded directory, attaches outright on a single match and lands the picker on a committed filter otherwise, shows each row's directory beside its name, takes the loading page on a cold boot, refuses every composition the specification forbids before any server starts, and completes the term after the slash — including through the corrected `portal init` output, which was measured against real bash 3.2, bash 5.3 and zsh. All 58 plan tasks were verified and none carried a blocking issue; the whole unit lane, `-race` over `internal/tui`, `gofmt`, `go vet` (both lanes type-check) and `golangci-lint` are green.

Two things send it back to planning. The containment filter's item source keys its map on the joined filter value, which is not injective, so a session whose *name* is `api ~/Code/api` and a session `api` living in `~/Code/api` collapse onto one entry and one of them is ranked by the other's fields — the exact field separation the containment rule exists to hold. And task 5-5 gated its `cmd/init.go` bash-shim edit on a measurement against a real `bash-completion` install, with an explicit void condition if the measurement contradicted the derivation; no measurement result was ever recorded, the machine still lacks the package, and the guard now protecting the shim was authored from the same reading it is meant to check. Neither is a fix that can be edited in place — the first has more than one defensible shape and nothing in the suite observes the defect, the second cannot be settled from the tree at all.

Three contained corrections were applied, verified and committed in this session. One finding is banked as out of scope, and one was discarded with its reason.

**A4 — Search filter map key collides on two distinct rows** · `internal/tui/search_filter.go` · source `12-2-1` · spreading

`searchItemSource.set` keys its map on `si.FilterValue()` — the session name and the home-abbreviated directory joined by a space. That value is not injective: `resolver.SearchFields` drops an empty directory, so a session *named* `api ~/Code/api` (legal — `tmux.ValidateSessionName` refuses only `:`, a leading `$` and a leading `-`) and a session `api` whose recorded directory abbreviates to `~/Code/api` both key on `"api ~/Code/api"`. Both rows then hand the filter pass the same target string and receive the same verdict from whichever entry survived the map write.

**Fails:** with that pair live, a term like `api ~` either drops a row whose name contains it or surfaces a row neither of whose fields contains it — the exact field separation `internal/tui/search_containment_test.go:161-172` exists to pin.

**Why it spreads:** the filter pass receives only `[]string` targets, and those targets *are* the filter values, so no unambiguous key exists inside the present seam. Candidate shapes trade against each other — a `[]searchEntry` per key ranked only when unambiguous; a key the pass can still resolve; or a return to the positional slice with its generation guard, which is the property task 12-2 deliberately removed to hold the rule through overlapping rebuilds. Nothing in the suite observes the collapse, so the tests cannot decide between them.

**Constraint carried from the guard inventory:** fix inside `search_filter.go`. Do not re-key `SessionItem.FilterValue()` — `HeaderItem.FilterValue() == ""` is what makes group headings vanish under a filter, and `internal/tui/sessions_grouped_reskin_test.go` guards that flatten-on-filter invariant. Whatever shape is chosen must land with a covering case.
