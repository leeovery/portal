# Consolidation Findings: open-with-forced-filter (Phase 12)

## Findings

### F1: a cancelled loading page drops every bootstrap warning it had already taken
- **Class**: behaviour
- **Failure**: On the concurrent cold route the user hits Ctrl-C while the loading page is up — which task 12-3 turned into the designed escape from a decision that is waiting on a slow or wedged tmux server — and Portal exits writing nothing. The soft bootstrap warnings (`Portal's session saver is not running.`, `Saved state could not be restored.`) that the run had already accumulated are silently discarded, exactly in the case where they explain the wait the user just escaped. Noticed as a cold boot that hangs, is cancelled, and reports nothing; the same run left to finish reports both lines. The drop is provenance-blind: it takes the set staged before the TUI launched as well as the orchestrator's own.
- **Evidence**:
  - `internal/tui/model.go:1671-1677` — the `BootstrapCompleteMsg` arm moves the staged set into `bufferedWarnings` (task 12-1's union) and nils `pendingBootstrapWarnings`. From this instant the buffer is the only holder.
  - `internal/tui/model.go:481-493` — `WarningsOwedAtTeardown` answers with `bufferedWarnings` only when `searchAttached || searchErr != nil`, and with `pendingBootstrapWarnings` (now nil) otherwise. A cancel records neither, so it answers with nothing.
  - `internal/tui/model.go:1817-1827` — Ctrl-C on the loading page is a bare `tea.Quit`; no arm hands the buffer back.
  - `cmd/open.go:626` — `finishTUI` writes exactly `model.WarningsOwedAtTeardown()`, so nothing else can recover them.
  - `internal/tui/bootstrap_warnings.go:41-66` — both `flushBufferedWarningsCmd` and `surfaceBufferedWarnings` empty `bufferedWarnings` as they consume it, which is what makes the union below safe: a set still sitting in either field at teardown is by construction a set nobody surfaced.
  - `internal/tui/model.go:1514-1525` + `internal/tui/search_decision.go:36-46` — the in-flight hold that makes the cancel window unbounded rather than the ≤`LoadingMinDuration` sliver it was before the phase.
  - `internal/tui/search_decision_test.go:307` — `TestSearchDecision_CtrlCWhileInFlightSelectsNothing` pins the cancel path and asserts nothing about what is owed.
- **Proposed shape**: Collapse `WarningsOwedAtTeardown` to the disjoint union of the two fields — `slices.Concat(m.bufferedWarnings, m.pendingBootstrapWarnings)` — and drop the `searchAttached || searchErr != nil` discriminator with its doc comment. Each field is emptied by whoever consumes it (the notice band, the stderr flush, the gate's take), so the union already *is* "what no one surfaced" on every existing path: an attach still answers with the buffer, a painted picker still answers with nothing, a warm picker still answers with the staged set — and the cancel path stops being the one hole. Behaviour-changing, so it is its own task; a test on the cancel-during-decision path carries it.

### F2: file completion is dead for every word past `--` on `portal open`
- **Class**: behaviour
- **Failure**: A user completing a path argument for the trailing command — `portal open ~/Code/api -- ls src/<TAB>` — gets no candidates at all. The word is routed to the session-name completer, where no session name prefixes a path fragment, and that completer's `cobra.ShellCompDirectiveNoFileComp` suppresses the shell's own filename fallback. Noticed as Tab doing nothing where every other command in the shell completes files, on the one part of the line that is an arbitrary command's own argv.
- **Evidence**:
  - `cmd/completion.go:104-108` — `completeOpenPositional` sends a post-dash word to `completeSessionNames`.
  - `cmd/completion.go:32-40` — that completer returns `cobra.ShellCompDirectiveNoFileComp` (`:39`).
  - `cmd/completion.go:70-83` — the sigil arm returns the same directive (`:82`), so both arms suppress filenames and the bound discriminates on nothing where filenames are concerned.
  - `cmd/completion.go:101-103` — the doc comment task 12-4 authored states the opposite: "offering sigil candidates there would suppress the filenames the user wanted", i.e. that the arm it selects preserves them.
  - `cmd/completion_test.go:597-609` — `TestCompleteOpenPositionalSeparatorBound`'s "it answers a post-dash word exactly as the plain session-name completer does" pins the post-dash directive as identical to `completeSessionNames`', so a change here is visible rather than silent.
  - Specification §8.1 (`:332`, `:334`) and the 2026-09-15 §8.1 corrigendum (`:494`) make the same claim — see S1.
- **Causation, stated plainly**: the routing itself landed in phase 11 (`Topen-with-forced-filter-11-3`, commit `c797fc9b3`); what landed in phase 12 is the rationale — the doc comment and the spec corrigendum — that names preserving the user's filenames as the benefit the bound buys. The phase's own contract is what the code now contradicts; the subject reaches one phase back.
- **Proposed shape**: Give a post-dash word `cobra.ShellCompDirectiveDefault` (no candidates, shell filename fallback intact) instead of routing it to `completeSessionNames` — the trailing command's arguments are that command's business and session names are never right for them, so the completer answering with nothing-and-stepping-aside is both the honest behaviour and the one the comment already claims. Update the existing subtest (which pins identity with `completeSessionNames`) to pin the directive directly, and pair it with the §8.1 correction in S1. If instead the orchestrator decides the suppression stands, the remedy is comment-and-spec text only: the filenames clause at `cmd/completion.go:101-103` and the "corrects two wrongs" conclusion at §8.1 `:334` / `:494` must go, leaving the one reason that does hold — past the separator the word is not a search form.
- **Bank**: reviewer entry on `open-with-forced-filter-12-4` ("File completion is dead for every word past `--`"), verdicted against the final tree and confirmed — the directive, the routing and the pinning subtest are all as reported.

## Spec Defects

### S1: §8.1 credits the `--` bound with preserving filenames that neither arm preserves
- **Claim**: §8.1 `:332` — "offering one there would complete to a term the parser will not honour, **and would suppress the filenames the user actually wanted in the same breath**"; §8.1 `:334` — "past it the word is not a search form at all and offering sigil candidates costs the user their filenames, **so that bound corrects two wrongs where this one would correct none**"; and the 2026-09-15 §8.1 corrigendum `:494` — "offering **session names** there also suppresses the filenames the user wanted, **so that bound corrects two wrongs**".
- **Observed**: both arms of `completeOpenPositional` return `cobra.ShellCompDirectiveNoFileComp` — `completeSearchTerm` at `cmd/completion.go:82` and `completeSessionNames` at `cmd/completion.go:39` — so the arm the bound selects suppresses filenames exactly as the arm it rejects would. `cmd/completion_test.go:597-609` pins that equivalence. The bound corrects one wrong, not two, and no filename is preserved by taking it. The corrigendum at `:494` is additionally self-contradictory: it states that the selected arm also suppresses filenames and then draws the two-wrongs conclusion from it.
- **Read**: genuinely open, leaning **code wrong**. The factual half of the reason is true (offering sigil candidates does suppress filenames); the conclusion drawn from it is false while the alternative suppresses them too. Either the spec's reason narrows to the one wrong the bound corrects, or the code changes so the bound delivers what the spec twice calls "the filenames the user actually wanted" — and the spec naming that loss as a cost worth avoiding is the argument for the latter. The decision is the same one F2 turns on; they are two faces of one change and want one task, not two.
