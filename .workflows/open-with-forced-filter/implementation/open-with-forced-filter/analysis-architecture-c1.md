- FINDING: The containment filter's item source is shared mutable state written by the Update loop and read from a Bubble Tea command goroutine
  SEVERITY: medium
  FAILURE: `rebuildSessionList` writes `searchItemSource.items` on Bubble Tea's Update goroutine while the filter closure `list.SetItems` deferred into a `tea.Cmd` reads the same field on a command goroutine — bubbletea runs every `Cmd` in its own goroutine (`tea.go:721` `msg := cmd()`), and the write is reachable from the very next `Update` after the one that returned the cmd. Two concrete windows on every search-opened picker: `refetchSessionsAfterRestore`'s `SessionsMsg` rebuild dispatches the filter cmd, then `ProjectsLoadedMsg` (or a second `SessionsMsg`) rebuilds and re-points the source underneath it. Nothing in the unit lane drives the real program loop, so `-race` cannot see it today; a future end-to-end test that does will abort the run. In a running Portal the reader can resolve ranks against a slice the list is not holding — when the two slices happen to share a length (a rename, a refresh with the same session count), the length guard passes and `bubbles` maps each rank into the *captured* items, so the narrowed list shows rows that do not contain the term and the user Enters on the wrong session — and an unsynchronised slice-header read can tear.
  FILES: internal/tui/search_filter.go:12-22, internal/tui/search_filter.go:34-52, internal/tui/model.go:1230-1235
  DESCRIPTION: The pointer indirection is the right instinct — `Model` is a value Bubble Tea copies per `Update`, so a slice field captured in the closure would freeze at `New` time — but the design stops one step short. `searchItemSource` gives the filter a mutable cell and then relies on the Update loop and the command goroutine never overlapping, which nothing enforces; the correctness of the whole containment rule rests on caller discipline rather than being self-contained. The `len(items) != len(targets)` guard is a *proxy* for staleness, not a test of it: it catches a regroup (headers appear or vanish, so the count moves) and misses every same-length replacement, which is exactly the case the race produces.
  RECOMMENDATION: Make the source self-contained. Guard `set`/`current` with a `sync.RWMutex` (it is already an accessor-wrapped pointer type, so this is a two-line change) so the access is defined rather than racy, and have `set` store the item slice together with the `[]string` of `FilterValue()`s it was built from, returning both from `current()` under the same hold — the filter then compares `targets` against that recorded companion instead of against its length, which turns the fallback into a real identity check and closes the same-length window the mutex alone leaves open.

- FINDING: The set of fields a filter matches is authored twice instead of once, so the three entry points can silently diverge on what they search
  SEVERITY: medium
  FAILURE: `SessionItem.FilterValue()` states the searchable text as a join (name + " " + home-abbreviated dir) and `resolver.MatchesSearchTerm` states it again as an enumeration (name, then home-abbreviated dir). Add a field to the join — a project name, a tag — and `-f` and the hand-typed `/` widen while `/term`'s count and its committed list do not. The user types `/acme`, the sigil reports no match and opens a picker that shows nothing, while `-f acme` on the same machine lists the session; `/acme` can also open a picker on two rows while the same term under `-f` lists three. No compile error, no test failure: nothing pins the two field sets to each other, and the coupling is carried only by a prose warning on `FilterValue`.
  FILES: internal/tui/session_item.go:81-93, internal/resolver/search.go:12-27
  DESCRIPTION: The rule that diverges by entry point is the *matching rule* (fuzzy against containment); the *fields* are meant to be one thing shared by all three. The implementation makes the rule shared (both routes call `MatchesSearchTerm`/`DefaultFilter` over one value) but leaves the field set as two independent statements, and the joined form is derivable from the enumerated one rather than needing its own authorship. A comment is doing the work a derivation should — and the comment is itself a maintenance liability, since it asserts a coupling an ordinary additive change in either file falsifies.
  RECOMMENDATION: Give `internal/resolver` one function naming a session's searchable fields — `SearchFields(name, recordedDir) []string`, returning the name and, when non-empty, the home-abbreviated directory. Derive `FilterValue()` as `strings.Join(resolver.SearchFields(...), " ")` (a one-element slice joins to the bare name, so the no-trailing-separator case falls out) and rewrite `MatchesSearchTerm` as a case-folded containment loop over the same slice. The field set then exists in one place, the join stops restating it, and the `FilterValue` warning shrinks to the one thing still worth saying — that the two rules read the same fields by different rules.

- FINDING: The set a search term is counted over is implemented independently of the set the picker lists
  SEVERITY: low
  FAILURE: `cmd.searchCandidates` derives the candidate set as "the enumeration, less the current session when inside tmux" and `tui.Model.filteredSessions` derives the same set separately from `m.insideTmux`/`m.currentSession`. Change the picker's exclusion — hide gone-flagged sessions, stop hiding the current one — and the sigil's K stops describing the list it opens: K=1 attaches a session the picker would not have listed, or K≥2 opens a picker holding one row after promising the user a choice. Each side has its own test (`TestOpenCommand_SearchForm_ExcludesTheCurrentSessionFromTheCount` on one, the grouping suites on the other); nothing pins their agreement, so the drift lands green.
  FILES: cmd/open_search.go:99-112, internal/tui/model.go:1115-1126
  DESCRIPTION: "The searched set is the set the picker lists" is a single contract implemented as two parallel computations in two packages. The underscore-prefixed exclusion is already shared correctly — both routes reach it through `parseSessionList` — which makes the remaining hand-authored exclusion the odd one out rather than an unavoidable split.
  RECOMMENDATION: Move the exclusion into one place both sides call — a small `func VisibleSessions(sessions []tmux.Session, currentSession string) []tmux.Session` beside `Session` in `internal/tmux` (empty `currentSession` excludes nothing, which collapses the inside/outside-tmux branch into the argument) — and have `searchCandidates` and `filteredSessions` each become a call to it.

SUMMARY: The seam between the shell form, the picker and the matching rule is well factored — one `MatchesSearchTerm`, one `AbbreviateHome`, one `warning.WriteLines`, a deferred-decision closure that keeps the cold path's ordering explicit — but three shared rules stop one step short of being shared: the containment filter's item source is an unsynchronised cell read from a command goroutine, the searchable field set is authored twice rather than derived once, and the counted set is computed independently of the listed set.
