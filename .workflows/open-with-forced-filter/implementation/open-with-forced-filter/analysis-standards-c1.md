- FINDING: Soft bootstrap warnings are dropped on the warm picker route the search form now takes
  SEVERITY: medium
  FAILURE: On a warm install whose bootstrap latch is satisfied, a failed `_portal-saver` revive adds `SaverDownWarning` to the sink. `isTUIPath` now answers true for `portal open /term`, so the warning is deliberately withheld from stderr and staged onto the TUI model instead — but on that route the model never parks on the loading page, `Init` synthesizes no `BootstrapCompleteMsg`, `m.bufferedWarnings` is never populated, and `surfaceBufferedWarnings` never runs. The warning reaches neither the notice band nor stderr. For a user whose state daemon is down: `x /port` lands them in the picker with no sign that nothing is being captured; they find out at the next reboot, when `sessions.json` and every pane's scrollback are gone. The same silent drop now applies to `portal open -- ls` (a command-only line with no target), which the classification change also moved onto the picker path — both were lines that previously carried a positional and so emitted to stderr from `PersistentPreRunE`.
  FILES: cmd/root.go:169-176, cmd/open_search.go:180-190, internal/tui/model.go:1522-1540, internal/tui/bootstrap_warnings.go:55-66
  DESCRIPTION: The specification requires the search form be classified as a picker invocation so its soft warnings "take the in-TUI route rather than stderr", and rests that on the picker path already having "somewhere safe to land". That landing place exists only on the concurrent bootstrap route (`progressReceiver != nil`, notice band) and on the cold loading-gate route; on the abridged latch-satisfied route there is no loading page, so the one call site of `surfaceBufferedWarnings` — `dismissLoadingGate` — is never reached and `stageBootstrapWarningsOnModel`'s staged slice dies on the model. The classification itself is correct and must not be reverted; what is missing is a delivery path for the warm picker. The hole predates this work (bare `portal open` and `-f` already fall into it), but the search form's classification is what newly routes lines like `portal open /tmp` and `portal open /term` into it, so the specified guarantee for this form is not met on the warm route. `finishTUI` already owns a post-teardown writer and already writes there for the K=1 and read-failure teardowns, so the alt-screen corruption the classification exists to prevent cannot occur at that point.
  RECOMMENDATION: In `finishTUI`, after the terminal background restore and alongside `emitSearchTeardownWarnings`, write `model.PendingBootstrapWarnings()` to the warnings writer whenever the model never reached the loading gate (no `BootstrapCompleteMsg` consumed), so the staged warnings surface post-teardown on the warm picker route exactly as they do on the attach and read-failure routes. Leave the concurrent route's notice band as it is.
