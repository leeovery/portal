- FINDING: A sigil-opened list can fall back to the picker's fuzzy rule when two list rebuilds overlap
  SEVERITY: low
  FAILURE: On a picker opened by `x /port`, two rebuilds dispatched close together (e.g. `Space`-preview dismiss queues a sessions refresh and the user presses `s` before it lands) leave two `SetItems` filter commands in flight against different item slices. The older command finds `recorded != targets`, falls through to `list.DefaultFilter`, and — if its result is delivered last — the narrowed list ends up showing subsequence matches: sessions whose name and recorded directory contain no run of "port" (the `~/Projects/rust-tools` case the containment rule exists to exclude). Nothing re-filters afterwards, so the wrong set stands until the next rebuild, and `Enter` on one of those rows attaches a session the search never matched. The user notices rows they cannot account for in a list they were told was narrowed by the term they typed.
  FILES: internal/tui/search_filter.go:57-78, internal/tui/model.go:1250-1255
  DESCRIPTION: The spec's containment guarantee is unconditional for as long as the filter text stands untouched — a preview round-trip, an `s` regroup and a refresh after an external kill are each named as events that reproduce the containment set, and only a hand edit of the filter text returns the list to the picker's rule. The implementation holds the item slice in a single-generation `searchItemSource` and, on any mismatch between the recorded filter values and the `targets` a filter pass was handed, degrades to `list.DefaultFilter`. That degradation is documented as deliberate, but its chosen fallback is exactly the rule the sigil's list must not use; the source going out of step is a scheduling accident rather than a hand edit, so the escape hatch is reachable without the user touching the filter text. Each rebuild in isolation is correct — the hole is only the overlap.
  RECOMMENDATION: Make the containment rule answerable from `targets` alone so a stale source cannot force the fallback: have `searchItemSource` retain a `map[string]struct{name, dir string}` keyed on the filter value alongside the slice (rows sharing a session share one entry, so By-Tag duplicates collapse harmlessly), and resolve each target through that map instead of indexing the item slice. Keep the index-based rank, drop the `slices.Equal(recorded, targets)` gate and the `list.DefaultFilter` fall-through with it, so `query != term` remains the single route back to the picker's own rule — which is the test the spec names.
