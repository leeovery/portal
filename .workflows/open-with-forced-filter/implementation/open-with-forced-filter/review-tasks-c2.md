# Review Tasks: Open With Forced Filter (Cycle 2)

## Task 1: Close the containment filter's cross-generation borrowing of a colliding target's verdict
severity: high
sources: report-13-1 (13-1-1)

**Problem**: `containmentFilter` (`internal/tui/search_filter.go:74-88`) ranks a handed target by whatever generation `searchItemSource` currently holds, so task 13-1's withholding rule is applied to the entries the *source* holds rather than to the session the handed *target* came from. When a filter pass runs behind a list rebuild **and** the target's filter value is one two distinct sessions can produce, the held generation's entry decides the rank for a live row from a different generation. Verified against the code: a source holding `{name:"api ~/Code/api", dir:""}` and a pass handed targets built from `{name:"api", dir:"<home>/Code/api"}` both key on `"api ~/Code/api"`; under the term `api ~` the held entry matches at `:82` and the row ranks — surfacing a session neither of whose fields contains the term, the exact outcome `resolver.MatchesSearchTerm`'s field separation and the withholding rule exist to prevent. In a picker opened by `portal open /term` the search form's one guarantee — every row shown contains the term — silently does not hold, and the doc comment at `:68-70` states the opposite as an unqualified guarantee, so the next maintainer builds on a false invariant.

**Solution**: Keep the value-keyed map and make it **cumulative** rather than last-generation-wins: `set` builds the next map from the entries already held plus the rows of the generation it is given, so a key carries every *distinct* field pair any generation has produced for it (identical pairs still collapsing, as they do today for a session repeated across By-Tag groups). `containmentFilter`'s rule is unchanged — a target ranks only when its key is held and every pair under it matches — so a cross-generation collision now finds both sessions' pairs under the one key, they disagree, and every row behind it is withheld. The direction is derived, not chosen. Of the three shapes the review named, (b) — generation-equality falling through to `list.DefaultFilter` — is refused by the specification's own rule that the sigil's fields are never joined and a non-matching row is the forbidden outcome, since the fuzzy rule surfaces such rows by construction; (a) — generation-equality with rank-nothing on skew — reverts the shape task 12-2 deliberately removed, inverts the delivered pin `TestContainmentFilterRanksAStaleGenerationsTargetsByContainment`, can leave the filtered list transiently empty with no ordering guarantee that a later pass corrects it, and still does not close the case where two generations yield identical ordered filter values from different field pairs; (c) preserves 12-2's property and closes the case. The residual the review left open in (c) — the retention rule — is settled by the source's own lifetime: the source is constructed once per picker run at `installSearchFilter` (`:101-109`) and `rebuildSessionList` records each generation **before** handing it to `SetItems` (`internal/tui/model.go:1249-1254`, the single chokepoint every entry point routes through), so every generation a pass can be handed is one the source has held, and retaining all of them makes the withholding complete rather than window-limited; growth is bounded by the distinct field pairs observed in one picker run, since an unchanged session set re-recorded on every regroup, refresh and preview dismiss adds no entry. A bounded window would reopen the hole for any pass older than it, which is why the retention is the source's life and not N generations. Guard conditions carried from the review: the change stays inside `internal/tui/search_filter.go` and `internal/tui/search_filter_test.go`; `SessionItem.FilterValue()` and `HeaderItem.FilterValue()` stay byte-unchanged (the empty header value is what flattens the grouped view the moment a query is typed); `set` keeps building a fresh map and swapping it under the write hold so the map `current()` hands back is never mutated and the lock-free read stays race-free; ranks keep indexing the targets the pass was handed and `query != term` stays the only route to `list.DefaultFilter`; and the file's doc comments — the type comment at `:18-27` and the guarantee at `:68-70` — are restated to the rule that actually holds, since the false clause is half of what the finding reports.

**Outcome**: With the source holding one generation and the pass carrying the other's targets, the term `api ~` ranks neither row rather than surfacing the row neither of whose fields contains it — so omission becomes the only failure direction in every combination of a stale pass and a colliding value, which is what the specification's §4.4 carve-out and the file's own contract already fix as the sanctioned one. Every key on an ordinary install is non-colliding and ranks exactly as it does today; a stale generation's targets still rank by containment at the targets' own indexes, every row of a multi-tag session still ranks, a header row and a target no generation has produced still rank nothing, and the file's comments no longer assert a guarantee the code does not hold.

**Do**:
- Make `set` (`internal/tui/search_filter.go:35-51`) cumulative rather than last-generation-wins: take the write hold for the whole call, build a fresh map sized from the entries already held plus `items`, seed it with a `slices.Clone` of each held key's slice (cloned, never shared, so no published slice is ever appended into), then fold this generation's `SessionItem` rows in through the existing `slices.Contains` dedupe, and assign the fresh map to `s.entries` before releasing. Read `s.entries` directly inside the write hold — routing through `current()` would re-enter the same `RWMutex`.
- Leave the ranking rule and its neighbours untouched: `containmentFilter` still ranks on `len(held) > 0 && everyEntryMatches(held, query)` with ranks indexing the targets the pass was handed and `MatchedIndexes` nil, `query != term` stays the only route to `list.DefaultFilter`, and `current`, `everyEntryMatches`, `installSearchFilter`, `SessionItem.FilterValue()` and `HeaderItem.FilterValue()` are unedited.
- Restate the `searchItemSource` type comment (`:18-27`) to the rule that now holds: the map accumulates every distinct field pair any generation of the list has produced for a filter value, for the life of the source — one source per picker run, written at `rebuildSessionList`'s single chokepoint (`internal/tui/model.go:1249-1254`) before the items reach `SetItems`, so every generation a pass can be handed is one the source has held. Keep the existing pointer-and-mutex paragraphs.
- Restate the guarantee in `containmentFilter`'s comment (`:68-70`), which currently claims an absolute the code did not hold: a target ranks only when the source holds its key and every pair recorded under that key contains the term, so a pass running behind a rebuild and a pass answering for a target two distinct sessions produced can each only omit a row, never surface one the term does not match.
- Add the cross-generation tests to `internal/tui/search_filter_test.go`, reusing the existing `collidingSessions` helper (`:192-198`) and driving both assignments of the two sessions to the held generation and the handed one, plus a test that re-recording one unchanged generation repeatedly leaves each key holding exactly one entry per distinct field pair. Edit no existing test in the file.
