# Consolidation Findings: Open With Forced Filter (Phase 4)

## Findings

### F1: The loading-to-picker dismissal is two verbatim copies, and the ordering rule that governs it is written on one of them

- **Class**: duplication
- **Failure**: The two gates that dismiss the loading page now run the same four-step sequence — `resolveSearchDecision` → `transitionFromLoading` → `tea.Batch(surfaceBufferedWarnings, refetchSessionsAfterRestore, maybeDispatchDetectionCmd)` — as two independent copies. Which copy executes is decided by a race the user cannot observe: whichever of the 1.2s minimum-display span and the bootstrap's terminal event lands second. A later edit to one arm therefore produces a cold boot whose behaviour differs by machine speed and by how long restore took. The two losses are concrete: move or drop `resolveSearchDecision` in one arm and `x /solo` attaches directly on a slow boot and opens the picker on a fast one; reorder it against `surfaceBufferedWarnings` in one arm and the saver-down warning a cold-boot search attach is owed is emptied out of the buffer before `emitSearchTeardownWarnings` can read it, so it reaches the user after some reboots and vanishes after others. Nothing fails in either case: both arms compile, and the ordering constraint is stated only on the `BootstrapCompleteMsg` copy, so an editor working in the `LoadingMinElapsedMsg` arm has no signal that the order is load-bearing at all.
- **Evidence**:
  - `internal/tui/model.go:1596-1602` — the `LoadingMinElapsedMsg` arm: the four-step sequence with no comment.
  - `internal/tui/model.go:1620-1629` — the `BootstrapCompleteMsg` arm: the same four steps, carrying the ordering comment at `:1621-1623` ("The decision must precede surfaceBufferedWarnings…").
  - `internal/tui/search_decision.go:38-56` — `resolveSearchDecision`, whose pre-emption of the transition is what both arms must honour.
  - `internal/tui/bootstrap_warnings.go:55-66` — `surfaceBufferedWarnings`, the helper that empties the buffer the attach route still needs.
- **Proposed shape**: Extract the sequence onto the model as one pointer-receiver helper — e.g. `func (m *Model) dismissLoadingGate() tea.Cmd`, which returns `resolveSearchDecision`'s `tea.Quit` when the decision pre-empts and otherwise calls `transitionFromLoading` and returns the batch. Both arms collapse to `return m, (&m).dismissLoadingGate()` behind their unchanged `bootstrapComplete && activePage == PageLoading` / `minElapsed && activePage == PageLoading` guards. The ordering comment moves onto the helper, where it is the only copy and governs both gates. Behaviour-preserving: every callee is compatible with an addressable `m` (`transitionFromLoading` and `surfaceBufferedWarnings` are pointer-receiver, `refetchSessionsAfterRestore` value-receiver), and each guard stays in the arm that owns it.
- **Bank**: `open-with-forced-filter-4-1` / reviewer — "Fold the two loading-gate dismissal blocks into one helper so the decision-before-warnings ordering is stated once". Confirmed against the final state: the pair is still verbatim at `:1596-1602` and `:1620-1629`, the comment is still on the `BootstrapCompleteMsg` copy alone, and tasks 4-2…4-5 landed nothing on those branches.

### F2: `openTUI`'s three-step teardown carries two load-bearing orderings that no test can reach

- **Class**: complexity
- **Failure**: `openTUI` ends in three ordered statements — restore the terminal background, emit the search teardown warnings, then connect — and the order of all three is load-bearing, because outside tmux `processTUIResult` reaches `syscall.Exec` and the process never returns. They sit inside a function that runs a real Bubble Tea program against the real terminal, so the unit lane cannot drive it and nothing does. Moving `emitSearchTeardownWarnings` below `processTUIResult`, or letting a later edit interleave anything between them, leaves the whole suite green while a cold-boot `x /solo` attach silently drops every soft bootstrap warning it accumulated — the one route on which those warnings have nowhere else to go, since no picker frame is ever painted for the notice band to carry them. The user notices it as a saver that is down and says nothing about it, for exactly the invocation this phase made routine. The same reach covers the canvas restore that sits above it: moved below the connect, the terminal keeps Portal's canvas colour after the attach, again with nothing failing.
- **Evidence**:
  - `cmd/open.go:715-721` — the untestable tail: `tui.RestoreTerminalBackground(os.Stdout, model)` / `emitSearchTeardownWarnings(cmd.ErrOrStderr(), model)` / `return processTUIResult(model, connector)`.
  - `cmd/open.go:572-586` — `processTUIResult`, which reaches `connector.Connect` and does not return on the outside-tmux path.
  - `cmd/open_search.go:180-190` — `emitSearchTeardownWarnings`, the step this phase inserted into that tail.
  - `cmd/open_search_warnings_test.go:278-293` — `"it writes before connecting"`, the only test of the ordering: it re-composes `emitSearchTeardownWarnings` then `processTUIResult` by hand rather than driving `openTUI`, so it stays green under any reordering of the production tail.
  - `cmd/open_theme_construction_test.go:470` — the same shape for the canvas restore: `RestoreTerminalBackground` is exercised standalone, never as `openTUI`'s first teardown step.
- **Proposed shape**: Extract the tail into a function the unit lane can drive — e.g. `func finishTUI(model tui.Model, connector SessionConnector, canvas, warnings io.Writer) error`, holding the three statements in order and returning `processTUIResult`'s result. `openTUI` becomes `return finishTUI(model, connector, os.Stdout, cmd.ErrOrStderr())`. Behaviour-preserving; the writers become parameters so a test can pass buffers and an `observingConnector` (already declared at `cmd/open_search_warnings_test.go:296-305`) and assert that both writes had happened by the time `Connect` ran. The existing `"it writes before connecting"` subtest then drives the production function instead of a hand-composed copy of it.

### F3: `isTUIPath` strips a `--` separator on its search arm and not on its no-target arm, so `portal open -- <cmd>` is still classified as a non-picker invocation

- **Class**: behaviour
- **Failure**: `portal open -- claude` — no target, a command after the separator — opens the picker, on the Projects page with the command pending. `isTUIPath` answers `false` for it, because its first arm asks `len(args) == 0` against the raw slice, which still holds the post-dash words. Two consequences on a cold server, both of them the ones the classification exists to prevent: `shouldRunConcurrentBootstrap` refuses the concurrent route, so the user gets a blank terminal for the whole of server start, hook registration, restore and scrollback replay with no loading page; and the accumulated soft warnings are written straight to `cmd.ErrOrStderr()` immediately before the picker claims that terminal with its alternate screen, so a saver-down warning is painted over and lost. The flag spelling of the identical invocation, `portal open -e claude`, takes the loading page and buffers its warnings for the notice band — so which of the two documented ways to scope a command the user typed decides whether their cold boot looks like a hang. This is the phase's to consolidate rather than merely adjacent to it: task 4-4 rewrote `isTUIPath` into two arms and brought `--` awareness into it through `searchFormPositionals` → `preDashPositionals`, leaving one arm dash-aware and one dash-blind inside a single four-line function, and its own new subtest pins the dash rule for the search arm only.
- **Evidence**:
  - `cmd/root.go:172-177` — `isTUIPath`: `return len(args) == 0 || len(searchFormPositionals(cmd, args)) > 0`. With `args = ["claude"]` and `ArgsLenAtDash() == 0`, the first disjunct is false on a slice that holds no positional target, and the second is false because `preDashPositionals` correctly yields nothing.
  - `cmd/open_search.go:27-34` — `preDashPositionals`, the dash-stripping the second disjunct already routes through.
  - `cmd/open.go:347-355` — `parseCommandArgs`: `dashIdx == 0` yields no destination, which is what makes this a picker invocation.
  - `cmd/open.go:193-195` — the no-destination branch that calls `openTUIFunc` with the zero landing.
  - `cmd/open_test.go:2486-2493` — `TestOpenCommand_CommandNoTarget_DashDash_OpensProjectsPicker`, the project's own assertion that `open -- claude` reaches the picker.
  - `cmd/concurrent_bootstrap_gate_test.go:69-78` — `"open -e cmd (command, no target) IS the TUI path"`, the flag spelling pinned to the opposite verdict.
  - `cmd/concurrent_bootstrap_gate_test.go:122-131` — `"words after a -- separator are never inspected"`, which pins the dash rule for a line that does carry a pre-dash target, and so never reaches this case.
  - `cmd/root.go:145-147` and `cmd/root.go:188-193` — the two consumers whose verdict this decides.
- **Proposed shape**: Take the first disjunct through the same helper as the second — `return len(preDashPositionals(cmd, args)) == 0 || len(searchFormPositionals(cmd, args)) > 0` — so the function answers "which positionals are this invocation's own?" once. Verified against every case the phase's own table already pins: bare `open` → true (unchanged); `open -f text` / `open -e cmd` → true (unchanged, no positionals); `open ~/dir` → false (unchanged); `open api blog` → false (unchanged); `open ~/Code/api -- ls /tmp` → false (unchanged — a pre-dash target survives the strip); `open /port` → true (unchanged, via the second disjunct); `open /port -s api` → false (unchanged, the pin gate short-circuits first). The one verdict that moves is `open -- <cmd>`, from false to true. Behaviour-changing, so it is reported as its own finding and carries its own regression row: `open -- claude` classified as the TUI path, beside the existing `-e` row.
