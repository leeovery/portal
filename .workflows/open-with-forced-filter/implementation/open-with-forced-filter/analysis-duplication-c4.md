- FINDING: The concurrent bootstrap's progress subscription is restated per Init branch
  SEVERITY: medium
  FAILURE: A picker route whose `Init` branch omits the `m.progressReceiver` append never receives `BootstrapCompleteMsg`, `BootstrapProgressMsg` or `BootstrapFatalMsg` from the goroutine running behind it. The orchestrator's soft warnings (a down saver daemon, corrupt state) are silently dropped, and a bootstrap fatal never ends the run — the picker keeps acting against a half-bootstrapped server and mints into it. Noticed only on a cold boot, as a warning line that never appears or a session created against a server whose restore failed; every warm-path test passes with no receiver wired at all.
  FILES: internal/tui/model.go:1542, internal/tui/model.go:1555
  DESCRIPTION: `Init` dispatches into three shapes — command-pending, loading page, and the plain warm picker — and the rule "if a bootstrap is running behind this model, subscribe to its channel" is authored separately inside two of them. The third pair of returns (model.go:1571-1574) carries no subscription at all; it is correct today only because `openTUI` never sets `cfg.progressReceiver` on that route, which is a fact about a different package. This is the exact shape that already failed once in this work unit: the command-pending arm shipped without the receiver and needed a dedicated task to add it, and the spec carries a corrigendum for the behaviour it left broken. The divergence is silent because a missing subscription changes nothing observable on any route where the receiver is nil, which is every route the unit lane exercises.
  RECOMMENDATION: Give `Init` one place where the receiver enters the batch. Build the branch-specific `cmds` as now, then append `m.progressReceiver` once on the common tail before `tea.Batch` — `tea.Batch` drops nil commands (`compactCmds`), so the warm routes need no guard and a newly added branch cannot omit it. Leave the loading branch's warm-route `BootstrapCompleteMsg` synthesis where it is, keyed on the same `m.progressReceiver == nil` test, since that arm is a genuine per-branch decision rather than a restatement.

- FINDING: The search completer re-derives the sigil shape rule instead of asking the recogniser
  SEVERITY: medium
  FAILURE: `completeSearchTerm` decides which candidates would compose a legal search word with its own `strings.Contains(name, "/")` test rather than through `resolver.IsSearchSigil`, the declared home of that shape. If the recognition rule is ever narrowed or widened — the spec's whole point in giving it one named function — the completer keeps its old answer and offers a word the parser then reads as a path. Noticed as an unexplained mint from a keystroke sequence that has always searched; nothing in the tree fails.
  FILES: cmd/completion.go:76, internal/resolver/path.go:25
  DESCRIPTION: `IsSearchSigil` is the single declaration of "a leading slash and no further slash", and both the parser (`resolver.IsPathArgument`, path.go:14) and the completer's own dispatch (`completeOpenPositional`, completion.go:92) route through it. `completeSearchTerm`'s hold-back is the one site that restates the rule instead — it asks a different question (`does the name contain a slash`) that happens to give the same answer today. The same function carries a second restatement beside it — the attached-session exclusion at completion.go:79, which `tui.PickerSessions` declares for the other two surfaces — so the completer is drifting into a second, parallel statement of what the search form can reach.
  RECOMMENDATION: Replace the `strings.Contains(name, "/")` hold-back with a question put to the recogniser — `if !resolver.IsSearchSigil("/" + name) { continue }` — so the offered set is shaped by the same function that parses the accepted word. That change alone leaves the rule with one home and needs no new API.
