# Analysis Tasks: Open With Forced Filter (Cycle 5)

## Task 1: Make the search-form collision check fail closed on a flag it does not name
severity: medium
sources: duplication

**Problem**: `validateSearchFormCollisions` (`cmd/open_search.go:58-79`) decides "is a search form sharing this line with one of `open`'s own flags?" from three string literals — `"exec"`, `"filter"`, `"ack"` — beside the `anyOpenDomainPin` arm. Together those four arms happen to cover all seven flags `openCmd.Flags()` registers today (`cmd/open.go:774-781`), but the set is restated rather than derived, and the restatement is what decides the verdict. A flag registered on `openCmd` after this work and not added to the switch makes `portal open /term --newflag value` run the search and discard the flag instead of refusing the line: exit 0, nothing on stderr, no failing test — the collision suite drives today's seven flags by name, so it grows only when someone remembers to grow it. The user gets a picker or an attach for a command line they wrote expecting a refusal, with no account of the flag they typed. `open` has gained a flag before (`--ack` arrived with the spawn feature), so the path is live. This is the third hand-maintained mirror of that flag set in the package and the only one that is unprotected: `openTargetPins` (`cmd/open_targets.go:22-30`) is held in both directions by `TestOpenTargetPinsCoverValueTakingFlags` / `TestOpenTargetPinsKeysAreLiveFlags`, and `openDomainPinFlags` (`cmd/open.go:250`) breaks the RunE dispatch loudly when a pin leaves it. This one fails open.

**Solution**: Keep every named arm exactly as it stands, in its current order — a refusal must name what collided, and the fixed order is what makes a line colliding several ways always name the same one — and add one final arm that derives the rest of the verdict from the registration: walk the flags the line actually set (`cmd.LocalFlags().Visit`, which reports `open`'s own flags and not the root persistent ones the rule exempts) and refuse any set flag no earlier arm covered, naming it in the message. Settled as derive-the-verdict rather than the guard-test remedy the package already uses for `openTargetPins`, on the record's own ground: the specification states this rule as a closed one over the set ("any of `open`'s own flags on the same line is a usage error"), so the registration is the authority the verdict should be read from, and a derived arm refuses a new flag on the day it is registered rather than on the day someone runs the suite. The derived arm fires for no line that exists today — all seven current flags are covered by a named arm ahead of it — so every refusal `open` emits now stays byte-identical, and the new arm is reachable only by a flag that does not yet exist.
**Outcome**: The collision rule's set is the flag set, read from the one place it is declared. A flag added to `openCmd` is refused beside a search form with no second edit, and the hand-authored wording survives for the flags that have it.

## Task 2: Give the four staging methods the value-in/value-out shape the package's handlers already use
severity: medium
sources: architecture

**Problem**: Four methods this work added or converted mutate the model through a pointer receiver while returning only a `tea.Cmd`: `dismissLoadingGate` (`internal/tui/model.go:1508`), `resolveSearchDecision` (`internal/tui/search_decision.go:38`), `createSession` (`internal/tui/model.go:1823`) and `createSessionInCWD` (`internal/tui/model.go:2859`). The state they write is load-bearing for a step that runs later — `resolveSearchDecision` sets `selected`/`searchAttached`/`searchErr` that `processTUIResult` reads after the program returns, and `createSession` stages `stagedMint`/`stagedMintDir` that the terminal `BootstrapCompleteMsg` arm reads to perform the mint. Every caller is a value-receiver handler returning its own copy of `m` (`model.go:1628`, `:1671`, `:1942`, `:2855`), so the mutation survives only because each site spells it `cmd := (&m).method(...)` on its own line: in `return m, (&m).method(...)` Go leaves the relative order of the plain operand `m` and the mutating call unspecified, so the obvious one-line spelling compiles and can return the pre-mutation copy. All four sites are spelled correctly today; the contract is held by a prose warning above `createSession` plus convention, not by the compiler, a guard or the signature. Every other state-mutating handler in the package (`handleProjectEnter`, `handleNewInCWD`, `handleThemePanelKey`, …) is value-in/value-out, so these four are the odd shape a later edit is most likely to normalise back to the losing spelling — and the failure it produces is silent: a `portal open /term` whose single match was already decided exits 0 having attached nothing, or a project pick taken during a cold-boot `portal open -- <cmd>` is dropped with no band, no mint and no error.

**Solution**: Convert all four to `func (m Model) x(...) (Model, tea.Cmd)` and update the four call sites to `m, cmd = m.x(...)`, so a caller reads `m, cmd := m.createSession(dir); return m, cmd` and the losing spelling (`return m, m.createSession(dir)`) fails to compile rather than silently dropping the staged state. The warning comment above `createSession` and the `(&m).` idiom both go with it; `createSessionInCWD` stays the one-line delegation it is, threading the model through. Behaviour-preserving on every route — the same state is written and the same commands are returned, only the route the written state travels changes from an address to a return value. This corrects the receiver clause of phase 4's approved "fold the two loading-gate dismissal blocks into one helper", which chose the pointer receiver on the ground that "every callee is compatible with an addressable receiver"; that task's actual direction — one helper holding the ordering for both gates — is untouched and stays exactly as it is. The ground for moving off the receiver is a project rule plus the language's own: the surrounding handlers are uniformly value-in/value-out, and Go specifies no order between a return statement's plain operand and its mutating call, so the shape's correctness cannot be stated in the signature it has.
**Outcome**: The staging contract is carried by the compiler. There is no spelling of these calls that drops the state, so no guard test or prose warning is needed to protect it.

## Task 3: Bound the positional completer's sigil arm where the parser bounds it
severity: low
sources: architecture

**Problem**: Recognition of the search form is bounded by the `--` separator on the parse side — `searchFormPositionals` (`cmd/open_search.go:14-22`) scans only `preDashPositionals`, so a `/word` among a trailing command's own arguments is never a sigil. The completer restates that recognition without the bound: `completeOpenPositional` (`cmd/completion.go:84-89`) is registered as `func(_ *cobra.Command, _ []string, toComplete string)` (`cmd/open.go:785-787`), discarding both the command — whose `ArgsLenAtDash()` cobra has already populated by the time `ValidArgsFunction` runs — and the preceding positionals, and dispatches on `resolver.IsSearchSigil(toComplete)` alone. So `portal open ~/Code/api -- ls /po<TAB>` offers live session names (`/portal-a1b2`) for a word `open` will hand verbatim to `ls`: the user accepts the completion and the trailing command fails on a path that does not exist, and on a shell honouring `ShellCompDirectiveNoFileComp` the filenames they actually wanted are suppressed in the same breath, so the only offer on screen is the wrong one. The two surfaces this work touched answer "is this word a sigil?" from two rules, and they disagree.

**Solution**: Take the `*cobra.Command` and `args` cobra already supplies at the registration site instead of discarding them, and gate the sigil arm on the same boundary the parser applies — the word is a search form only when it is a pre-dash positional, which `preDashPositionals` / `ArgsLenAtDash()` already decides for `searchFormPositionals`. A post-dash word falls through to the completer's other arm, so the trailing command's own arguments complete the way every other non-sigil word does. Settled as moving the completer onto the parser's bound rather than the reverse: the parse-side bound is what the specification decided and what the user's line is actually resolved by, so the completer is the surface that must agree. Behaviour is unchanged for every pre-dash word, which is where the sigil is reachable at all.
**Outcome**: One rule decides what is a sigil, and the completer offers only what the parser will honour.
