- `README.md:175` — the bash version threshold is wrong. The text reads "Switching that fallback off needs a shell that supports it — bash 4.4+ with `bash-completion`". Cobra's emitted V2 script gates the switch-off on `[[ $(type -t compopt) == builtin ]]` (`bash_completionsV2.go:133-136`), and `compopt` has been a builtin since bash 4.0 — so bash 4.0 through 4.3 do switch the fallback off. The `4.4` figure belongs to a different gate in the same script: the `BASH_VERSINFO` check at `bash_completionsV2.go:121-123`, which guards `compopt -o nosort` for the KeepOrder directive, something Portal's completions never request (every branch of `cmd/completion.go` returns `ShellCompDirectiveNoFileComp`). The failure this prevents: a user on bash 4.0–4.3 reads that their shell cannot suppress filename completion, concludes the documented behaviour does not apply to them, and is contradicted by their own terminal in ten seconds — the same class of disprovable claim the phase-review finding asked this sentence to stop making, in the opposite direction. The macOS `/bin/bash` 3.2 half of the sentence is accurate (verified: `type -t compopt` is empty there, `builtin` on 5.3).
  FIX: change `bash 4.4+ with \`bash-completion\`` to `bash 4+ with \`bash-completion\``. Nothing else in the sentence needs to move.
  ALTERNATIVE: name the mechanism instead of a version — "a bash with the `compopt` builtin (4.0 and later), plus `bash-completion`" — which is more durable and also stops implying the `bash-completion` requirement is specific to the fallback switch-off (without that package the whole script bails at `_get_comp_words_by_ref` and falls through to filenames in any bash version). The reviewer recommends the plain `bash 4+` edit: smallest true change, keeps the sentence readable, and the broader nuance is not something this paragraph owes.
  CONFIDENCE: high

- `cmd/open_docs_test.go:42` — the term-less example assertion can never fail. The token for "the term-less example" is `"x /"`, and the section contains `x /port` on `README.md:128`, so `strings.Contains(section, "x /")` is satisfied whether or not the `x /` example line exists. The same weakness, less absolutely, applies to `"x /port"` at line 41: neither token is anchored to the fenced example block, and both strings appear in the surrounding prose (`README.md:143` carries `` `x /port` ``; `README.md:155` carries `x /tmp`). So the named case "examples present" currently asserts only that the section mentions the form somewhere, and the criterion "each with a one-line comment" is unguarded. The failure this prevents: a later editor trims the `x /` line as redundant with `x /port`, the guard stays green, and the term-less form loses its only discoverable example — noticed only when a user asks what `x /` does.
  FIX: slice the section's first fenced block (between the ```` ```bash ```` fence opened after the heading and its closing fence) and assert over its lines rather than over the whole section — require one line whose first field is exactly `x` and second exactly `/port`, and one whose second is exactly `/`, each carrying a `#` comment. That makes both example assertions independent of each other and of the prose, and covers the comment half of the criterion in the same pass.
  ALTERNATIVE: keep the whole-section scan but make the tokens line-anchored and mutually exclusive — `"\nx /port "` and `"\nx / "`. Cheaper, but it silently couples the guard to the block's column alignment, so a re-alignment of the example comments breaks it for no real reason. The reviewer recommends the fenced-block slice.
  CONFIDENCE: high
