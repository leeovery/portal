  SEVERITY: medium
  FAILURE: A flag registered on `openCmd` after this work is not added to `validateSearchFormCollisions`, so `portal open /term --newflag value` runs the search and discards the flag instead of refusing the line. Nothing reports it: exit 0, no stderr, no test failure — the collision suite drives today's seven flags by name, so it grows only when someone remembers to grow it. The user sees a picker (or an attach) for a command line they wrote expecting a refusal, with no account of the flag they typed. The mirror fails open, not closed.
  FILES: cmd/open_search.go:70-77, cmd/open.go:774-781, cmd/open_targets.go:22-30, cmd/open_targets_guard_test.go:65-71
  DESCRIPTION: `openCmd.Flags()` (cmd/open.go:774-781) is the authoritative set of `open`'s own flags. Two hand-maintained mirrors of it already existed — `openTargetPins` (cmd/open_targets.go:22-30), whose own doc comment names it "a hand-maintained mirror of openCmd's live flag set", and `openDomainPinFlags` (cmd/open.go:250, reached through `anyOpenDomainPin` at cmd/root.go:182). This work adds a third: `validateSearchFormCollisions`'s switch names `"exec"`, `"filter"` and `"ack"` as string literals beside the `anyOpenDomainPin` arm, and those four arms together are the whole implementation of a rule the specification states as a closed one over the set ("any of `open`'s own flags on the same line is a usage error"). The set is therefore restated rather than derived, and the restatement is what decides the verdict.

  What makes this consequential rather than cosmetic is the asymmetry in how the three copies are protected. `openTargetPins` is guarded in both directions by `TestOpenTargetPinsCoverValueTakingFlags` / `TestOpenTargetPinsKeysAreLiveFlags`, which walk `openCmd.Flags().VisitAll` and fail the day a registration and the mirror disagree — the project has already judged this exact mirror shape to need a structural guard rather than discipline. `openDomainPinFlags` is at least a single list with two consumers, so a pin dropped from it breaks the RunE dispatch loudly. The new copy has neither property: it is a literal list read once, by one caller, with no enumeration behind it, and drift in it produces a silently-accepted command line rather than a broken one. `open` has gained flags before (`--ack` arrived with the spawn feature), so this is a live path, not a hypothetical one.

  RECOMMENDATION: Stop restating the set in `validateSearchFormCollisions` and derive it. Keep the named arms for their wording — a refusal must name what collided — but decide the "search form beside a flag" verdict from the registration itself, walking the flags the line actually set (`cmd.LocalFlags().Visit`, which reports `open`'s own flags and not the root persistent ones the rule exempts) rather than from three literals. Where deriving the verdict is not wanted, take the remedy the package already uses for its other mirror: a guard beside `TestOpenTargetPinsCoverValueTakingFlags` that enumerates `openCmd.Flags()` and fails on a flag no collision arm covers, so the third mirror is held to the same standard as the first.
SUMMARY: The search feature's shared rules — the searched session set (`tui.PickerSessions`), the match fields and containment predicate (`resolver.SearchFields` / `MatchesSearchTerm`), the sigil shape (`IsSearchSigil`), the list-sessions argv (`listSessionsArgs`), the derived-directory lookup (`effectiveDir`), the loading-gate dismissal (`dismissLoadingGate`), the teardown tail (`finishTUI`) and the shell function's expansion (`openFunctionExpansion`) — each have exactly one home and are reached by every consumer, so the cross-file surface this work introduced is consolidated. The one exception is the search-form collision check, which restates `open`'s flag set as literals and is the only one of the package's three mirrors of that set with no guard behind it.
