# Consolidation Findings: open-with-forced-filter (Phase 5)

## Findings

### F1: the bash completion shim throws the cursor position away; the zsh shim keeps it
- **Class**: behaviour
- **Failure**: `COMP_POINT` is bash's byte offset of the cursor *into `COMP_LINE`*. The shim replaces the line the user typed (`x /po extra`) with a longer, re-joined one (`portal open /po extra`) and then asserts the cursor sits at its end — which is true only when the user's cursor was already at the end of the original line. Every other Tab press hands bash-completion a line and an offset that disagree with the `COMP_CWORD` the shim just incremented. bash-completion derives the current word `cur` from `COMP_LINE`/`COMP_POINT` (`_init_completion` → `_get_comp_words_by_ref` → `__get_cword_at_cursor_by_ref`), and cobra's script feeds that `cur` to `compgen -W "${completions[*]}" -- "$cur"` — so with the offset pinned to end-of-line, `cur` becomes the whole tail of the line from the cursor's word onward, no candidate matches it, and `-o default` drops the user through to filename completion. For a user: move the cursor back to fix an earlier word on an `x` line and press Tab, and Portal offers nothing while `xctl` on the same line in the same shell completes correctly. Cobra supports exactly this case deliberately (`bash_completionsV2.go:444-448`, "The user could have moved the cursor backwards on the command-line"); the shim defeats half of that support — `cword` stays right, `cur` goes wrong. The same rewrite also normalises the user's spacing (`"${COMP_WORDS[*]}"` re-joins with one space), so `x   api` is reported as a line the user never typed. The zsh shim (`cmd/init.go:63-68`) has no equivalent defect: it adjusts `words`/`CURRENT` only, and zsh derives `PREFIX`/`SUFFIX` from the real cursor itself. fish's `-w 'portal open'` wrap never touches the line. So this is one shell out of three, and it is the one the phase hand-wrote the most machinery for.
- **Evidence**:
  - `cmd/init.go:54-61` — `bashOpenCompletionShim`; lines 57-58 are `COMP_LINE="${COMP_WORDS[*]}"` / `COMP_POINT=${#COMP_LINE}`.
  - `cmd/init.go:63-68` — `zshOpenCompletionShim`, the cursor-preserving counterpart.
  - `cmd/init.go:93` — the registration that makes the bash shim live (`complete -o default -F __start_portal_open %s`).
  - `cmd/init_completion_shell_test.go:32-38` — the driver's `_init_completion` stand-in derives `cur` from `COMP_WORDS[COMP_CWORD]` alone, ignoring `COMP_LINE`/`COMP_POINT`; `cmd/init_completion_shell_test.go:44-45` then sets the driver's own `COMP_POINT` to end-of-line. The guard therefore models away precisely the half of bash-completion the shim disagrees with, and structurally cannot fail for this reason.
  - `$(go env GOMODCACHE)/github.com/spf13/cobra@v1.10.2/bash_completionsV2.go:44-50` (cobra's own fallback `__<name>_init_completion` forwards to `_get_comp_words_by_ref`, described as "a minimal version of that function" from bash-completion), `:432-438` (the `_init_completion`/fallback call), `:444-448` (the backwards-cursor truncation), `:311-317` (`compgen -W … -- "${cur}"`).
- **Proposed shape**: keep the `COMP_LINE` rewrite — it is load-bearing, since bash-completion walks the line against the rewritten word array and a stale line would make `cur` empty — but shift the offset instead of pinning it: `COMP_POINT` must become the user's own offset plus the length difference between the rewritten prefix (`portal open`) and the word they typed, and `COMP_LINE` must be that prefix substituted into the line rather than the word array re-joined (which loses their spacing). Roughly:

  ```
  __start_portal_open() {
      local __typed=${COMP_WORDS[0]}
      COMP_WORDS=(portal open "${COMP_WORDS[@]:1}")
      (( COMP_CWORD += 1 ))
      (( COMP_POINT += ${#COMP_WORDS[0]} + 1 + ${#COMP_WORDS[1]} - ${#__typed} ))
      COMP_LINE="portal open${COMP_LINE#"$__typed"}"
      __start_portal "$@"
  }
  ```

  A line with leading whitespace needs handling (`${COMP_LINE#"$__typed"}` strips nothing there) — either preserve the head or accept and state the limit. Two things the task owes beyond the edit: (a) **measure before changing** — this machine has no `bash-completion` installed, so the claim that `cur` comes from `COMP_POINT` is read off bash-completion's and cobra's sources rather than observed; a machine with the package should be asked directly before the shim is touched. (b) Give it a guard it can fail: teach `bashCompletionDriver`'s `_init_completion` stand-in the cursor-aware derivation (walk `COMP_LINE` up to `COMP_POINT` the way `__get_cword_at_cursor_by_ref` does) and drive one mid-line case, or — cheaper and weaker — assert on the emitted shim text that the offset is shifted rather than assigned. A fix landed without either is unguarded, which is how the shim reached this state.

### F2: the README's open section makes two claims that ordinary change falsifies with nothing to catch it
- **Class**: behaviour
- **Failure**: The README is a reference document that outlives any one release, and the phase put two dated claims into it.
  1. `README.md:175` opens "**This release corrects `portal init`** so that Tab after the session-opening function reaches Portal's completer at all — **until now** the request it emitted was answered by the shell instead", and follows with "**An existing install picks the correction up only once the output of `portal init` is re-evaluated**". A reader two versions later cannot tell which release "this release" is, whether "until now" describes their binary, or whether the re-eval instruction is an upgrade step they still owe. They will either re-run the eval needlessly or assume the whole paragraph is historical and skip the part that is permanently true. The rollout fact itself is durable and must stay — completion changes only reach a shell that has evaluated the current `portal init` output — but it is a standing property of `portal init`, not a release note, and stating it as a release note is what dates it.
  2. `README.md:161` says "The last three rows are not pins" of the table immediately below. That is positional, unguarded, and correct only for the table's present seven rows. Adding a pin — or another non-pin row anywhere but the tail — silently makes it name the wrong rows, and a reader then mis-reads which forms hard-fail on a miss. Nothing in `cmd/open_docs_test.go` covers the sentence, and no plausible guard would.
- **Evidence**: `README.md:161`; `README.md:175`. Both authored by the phase (`git show a8fc419d3 -- README.md`). The `5-4` reviewer recorded the first one in its own NOTES ("time-relative in a reference document that outlives the release; it reads as stale the moment the next version ships") and the second ("positional and unguarded: a row added anywhere silently falsifies it") and raised neither, because the task's acceptance criterion was met as written — which is exactly why they arrive here.
- **Proposed shape**: one prose pass over the section, no code. Re-cast `README.md:175`'s opening as a standing statement of what the emitted script does and what a shell must have evaluated for it to apply — the completion behaviour after the session-opening function, and that a shell picks it up only once it has evaluated the current `portal init` output (start a new shell, or re-run the `eval`) — dropping "This release", "until now" and the before/after framing. Everything downstream in that paragraph (what `x <TAB>` and `x /po<TAB>` offer, the deliberate filename-fallback loss, the bash-version parenthetical) is already timeless and stays. At `README.md:161`, replace the positional count with the rows named: `-f`, `/<term>` and `-e/--` are not pins.

## Spec Defects

### S1: "the filename fallback is off wherever Portal is asked for completions" is not true of every bash
- **Claim**: §2.2 — "Portal switches the shell's filename fallback off wherever it is asked for completions (`portal completion bash | grep -n 'compopt +o default'`), so `portal open /tm<TAB>` never becomes `/tmp/`, and neither does `x /tm<TAB>` once the corrected `portal init` output is live in the user's shell". Restated as a requirement at §8.3 — "once Portal answers, it switches that fallback off (§2.2), and it must, since a filename fallback on the same word is what would turn `x /tm<TAB>` into `/tmp/` and a search into a mint."
- **Observed**: the switch-off is conditional on the shell, two ways, and the spec states it unconditionally. (a) Cobra gates `compopt +o default` on `[[ $(type -t compopt) == builtin ]]` (`bash_completionsV2.go:132-138`); `compopt` is a bash 4.0 builtin, so on macOS's stock `/bin/bash` 3.2 the script logs "No file completion directive not supported in this version of bash" and the standing `complete -o default` (`bash_completionsV2.go:457`, and `cmd/init.go:93,96` for `x`/`xctl`) supplies filenames — `/tm<TAB>` becomes `/tmp/`, and a search becomes a mint. The `5-2` reviewer measured this directly on this machine (`type -t compopt` empty on `/bin/bash` 3.2.57, `builtin` on the Homebrew 5.3) and recorded it in `fix-tracking-open-with-forced-filter-5-2.md`. (b) Without the `bash-completion` package, `_init_completion` is undefined and cobra's own fallback calls `_get_comp_words_by_ref`, also from that package, so the completion function returns early (`bash_completionsV2.go:432-438`) and `-o default` supplies filenames in *any* bash version. Note the exposure is not confined to the `x` function the spec hedges about: it applies to `portal open /tm<TAB>` itself, which the sentence names as the safe case. Phase 5 landed the qualification in the README (`README.md:175`: "bash 4+ with `bash-completion`, zsh, or fish. macOS's stock `/bin/bash` 3.2 cannot, so filenames still complete there") — so the shipped documentation and the specification now disagree.
- **Read**: spec stale — the claim is overstated rather than out of date, and the document is the side that is wrong. There is no code change available: the gate is cobra's, Portal already returns `ShellCompDirectiveNoFileComp` from every branch of `cmd/completion.go`, and dropping `-o default` from the registration to force the issue would leave a bash-3.2 user with no completion at all rather than the wrong one. §2.2 and §8.3 should carry the shell condition the README now carries.
