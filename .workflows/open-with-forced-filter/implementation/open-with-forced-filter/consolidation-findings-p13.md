# Consolidation Findings: open-with-forced-filter (Phase 13)

## Spec Defects

### S1: §3.2 and §4.4 state the narrowed list as the whole containment set, which the collision rule this phase landed makes untrue
- **Claim**:
  - §3.2 `:92` — "| >= 2 | The picker opens on the Sessions page, landing as §3.3 sets it, **with the cursor on the first matching row**. |", over a K the same section defines as "the number of live sessions matching the term under §4".
  - §4.4 `:176` — "**The containment set holds for as long as the sigil's filter text stands untouched.** … every one of those reproduces the containment set. **The list the user is choosing from is the list they were handed.**"
  - §4.4 `:178` — "Rows keep the order the sessions list gives them in whatever grouping mode is current, **with non-matching rows removed** and nothing re-ranked … The first matching row (§3.2) is the first surviving row of that existing order."
  - §4.4 `:182` — "The divergence is therefore visible only by rows appearing, **never by rows the user expected going missing**."
- **Observed**: the picker's containment filter now judges a *filter value*, not a session, and withholds every row behind a value whose sessions disagree about the term — so a session inside the containment set can be absent from the narrowed list.
  - `internal/tui/search_filter.go:82` — `if held := entries[target]; len(held) > 0 && everyEntryMatches(held, query)`; `:92-99` — `everyEntryMatches` returns false as soon as one field pair under the value fails `resolver.MatchesSearchTerm`.
  - `internal/tui/session_item.go:87-89` — `FilterValue()` is `strings.Join(resolver.SearchFields(name, dir), " ")`, so two distinct sessions collide on one value whenever one is named for the text the other's home-abbreviated directory renders as (tmux names are unique, but the joined form is not injective).
  - `cmd/open_search.go:186-194` — `searchMatches` counts **per session** (`MatchesSearchTerm(term, s.Name, s.Dir)` once per session), so K and the row count the picker then shows are derived by two different rules and can disagree.
  - `internal/tui/search_filter_test.go:200-220` — `TestContainmentFilterOnTwoSessionsSharingOneFilterValue` / "it ranks neither row when only one of them contains the term" pins the withholding in both row orders, so this is the landed contract rather than an accident.
  - Measuring case: live sessions `api ~/Code/api` (no recorded directory), `api` (recorded `~/Code/api`) and `xapi ~x`, with `portal open '/api ~'`. K = 2 — the first matches on its name, the third matches on its name, the second matches neither field — so §3.2's `>= 2` row opens the picker. The first two collide on the joined value `api ~/Code/api`, their pairs disagree, and both are withheld: the list holds `xapi ~x` alone and the cursor lands on it, not on "the first matching row". The withheld session is unreachable from that screen until the user edits the filter text away from the term, at which point the picker's own fuzzy rule applies to a different value.
  - Second instance of the same falsified claim, **predating this phase** and noted for completeness: `internal/tui/search_filter.go:66-70` states that a filter pass running behind a rebuild answers for targets the source no longer holds and "can only omit a row" — also a row the user expected, going missing. That behaviour landed with the value-keyed source in phase 12 (`Topen-with-forced-filter-12-2`); this phase is what makes the collision half deterministic and test-pinned.
- **Read**: **spec stale** — the sections owe a carve-out; the code's choice is the only safe one available to it. `list.FilterFunc` is handed target *strings* and returns ranks indexing that slice, so two identical targets at different indexes are indistinguishable to it: the filter cannot rank one and withhold the other. The alternative — rank both when any pair matches — would surface a session neither of whose fields contains the term, which is precisely the outcome §4.3 separates the fields to prevent ("a term matching across the join would return a session that neither field contains"), and on a subsequent `Enter` would attach it. Withholding both keeps the rule's guarantee in the direction that matters and pays for it with a rare omission. What the specification cannot keep is the absolute form of `:176`/`:178`/`:182` and the identity between K and the narrowed row set at `:92`; it should name the collision (and, in the same breath, the stale-generation omission at `:66-70`) as the one case where the list is a subset of the containment set. The alternative reading — that the spec is right and the design of installing a value-keyed `FilterFunc` is wrong — would reopen the cross-rebuild property task 12-2 was built to hold, and is not what this phase's evidence argues for.
