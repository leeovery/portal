- FINDING: BootstrapCompleteMsg.Warnings carries two different provenances, so no single merge rule is correct and the loading arm silently discards the staged set
  SEVERITY: medium
  FAILURE: A soft bootstrap warning staged in the sink before a concurrent (cold + TUI) launch is dropped without a trace — the user is never told the saver is down or that restore degraded, and nothing on any surface records that a warning existed. The two arms of the same switch already disagree about the rule, so the next person to add a pre-bootstrap warning has no way to know which one governs.
  FILES: internal/tui/model.go:1648-1660, internal/tui/model.go:1555-1556, internal/tui/model.go:485-490, cmd/bootstrap_warnings.go:46-52, cmd/root.go:143-148
  DESCRIPTION: `BootstrapCompleteMsg.Warnings` means two different things depending on which route produced it. On the warm-sync route Init synthesizes the message from the model's own staged set (`model.go:1555-1556` — `pending := m.pendingBootstrapWarnings; … BootstrapCompleteMsg{Warnings: pending}`), so the field *is* the staged set. On the concurrent route the progress pipe supplies the orchestrator's own warnings, which are disjoint from anything staged. The `PageLoading` arm resolves this by assigning and then nil-ing (`m.bufferedWarnings = msg.Warnings` then `m.pendingBootstrapWarnings = nil`), which is lossless on the first route only because the two sets are the same slice, and on the second only because the sink happens to be empty there today (`cmd/root.go` adds to the sink solely on the synchronous branch). The `commandPending` arm two lines below reaches the opposite conclusion for the same message — `append`, with a comment stating the two sets are disjoint and both owed. Neither arm states the invariant it depends on, and the invariant lives in a different package (`cmd/root.go`'s branch structure). Add any pre-bootstrap warning to the sink on the deferred route and the loading arm silently eats it; the search-attach exit (`WarningsOwedAtTeardown`, which returns `bufferedWarnings` alone on that path) then has nothing to write. The design fault is the message field, not the arms: a single field carrying "what was already staged" on one route and "what the orchestrator just produced" on another cannot have one correct merge rule.
  RECOMMENDATION: Give the terminal event one provenance. Stop routing the staged set through the synthesized message — have Init emit `BootstrapCompleteMsg{}` (or a warnings-free variant) on the warm route and let the `PageLoading` arm read the staged set off the model itself, so both arms can use the same disjoint-union rule (`bufferedWarnings = append(staged, msg.Warnings...)`, then clear staged). That makes the arms identical and removes the unstated cross-package invariant.

- FINDING: The positional completer offers a search-form candidate on lines the Args validator refuses
  SEVERITY: low
  FAILURE: A user typing `x api /po<TAB>` is offered `/portal-a1b2`, accepts it, presses Enter, and is answered with `cannot use a /term search with another target`. The completion actively assembles a command line Portal will not run — noticed as a refusal immediately after an accepted suggestion, which reads as Portal contradicting itself.
  FILES: cmd/completion.go:93-98, cmd/open_search.go:77-107, cmd/completion_test.go:621-629
  DESCRIPTION: `completeOpenPositional` gates the sigil arm on shape (`IsSearchSigil`) and on the `--` bound (`completingPreDashPositional`), and on nothing else. The `--` bound exists for exactly one stated reason — offering a sigil there "would complete to a term the parser will not honour" — but the same reasoning applies to every other non-composing case the Args validator enforces: another pre-dash positional already on the line, `-f`, a domain pin, `-e`, `--ack`. The validator owns the composition rule in `validateSearchFormCollisions`; the completer restates a one-clause fragment of it and lets the rest through. `cmd/completion_test.go:621-629` pins the divergent case as intended behaviour, so this is a decision rather than an oversight — but it is a decision that contradicts the principle the `--` bound was added under, and it leaves the completer and the validator as two independent readings of one rule. The second-positional session-name arm is correct and must stay (multi-target bursts are legal); only the sigil arm is affected.
  RECOMMENDATION: Gate the sigil arm on the same predicate that decides whether a sigil is legal on this line — reuse the validator's rule rather than restating a fragment of it: offer sigil candidates only when the line carries no other pre-dash positional and no colliding flag, falling through to `completeSessionNames` otherwise. One helper shared by `validateSearchFormCollisions` and `completeOpenPositional` keeps the two from drifting.

- FINDING: The search decision runs blocking tmux subprocess I/O inside Update, on the one transition the loading page exists to cover
  SEVERITY: low
  FAILURE: On a cold boot, at the instant the loading page would lift, the event loop blocks on two tmux round-trips (`list-sessions`, then `display-message` for the attached session). The spinner stops and queued input — including Ctrl-C — is not processed until they return. Against a tmux server that is slow or wedged straight after start, the user sees a frozen loading page with no way out but killing the terminal, which is precisely the "reads as a hang" failure the loading page was introduced to prevent.
  FILES: internal/tui/search_decision.go:38-56, internal/tui/model.go:1508-1516, cmd/open_search.go:177-211
  DESCRIPTION: Every other tmux read the model performs on this path goes through a `tea.Cmd` and lands as a message (`fetchSessionsCmd`, `loadProjects`, `refetchSessionsAfterRestore`), and the whole ten-step bootstrap runs in a goroutine for the same reason. `resolveSearchDecision` breaks that shape deliberately — the comment explains that a `tea.Cmd` would let the transition fire before the decision could pre-empt it — but the pre-emption problem is a gating problem, not a synchrony problem. The model already has a two-condition dismissal gate (`minElapsed` && `bootstrapComplete`); the decision is a natural third condition, resolvable by a command that emits its own message. As written, correctness is bought by putting unbounded subprocess I/O on the render goroutine, and the closure that performs it is supplied by `cmd` — so `internal/tui` has no control over how long it may take or whether it can be cancelled. It also re-reads the attached session name that `openTUI` already resolved and handed the model as `CurrentSession`, so one of the two round-trips is for a value the model is holding.
  RECOMMENDATION: Make the decision a third gate condition rather than a synchronous call at dismissal: dispatch it as a `tea.Cmd` when the other two gates are satisfied, hold the loading page until its message arrives, and act on that message. The single-shot property then comes from the gate's own state rather than from clearing a field mid-call, and a slow server leaves the page animating and Ctrl-C live.
SUMMARY: The search form composes cleanly with the existing surface — one recognition rule in `resolver`, one matching rule shared by the count and the picker's filter, one candidate-set rule in `PickerSessions`, and the derived-directory separation that §4.1 demands is held structurally. The three findings are seam-quality rather than structural: a bootstrap-warning message field carrying two provenances with no merge rule that fits both, a completer that restates one clause of the validator's composition rule, and a blocking tmux read placed on the render goroutine at the loading-page transition.
