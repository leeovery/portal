# Review Tasks: Open With Forced Filter (Cycle 1)

## Task 1: Close the containment filter's map-key collision on two distinct rows
severity: high
sources: report-12-2 (12-2-1)

**Problem**: `searchItemSource.set` (`internal/tui/search_filter.go:38`) keys its map on `si.FilterValue()` — the session name and the home-abbreviated recorded directory joined by a space (`internal/tui/session_item.go:87-89` over `resolver.SearchFields`, which drops an empty directory). That value is not injective, so two rows whose joined value coincides but whose fields differ collapse onto one entry and the later item in the slice wins: a session *named* `api ~/Code/api` with no recorded directory (legal — `tmux.ValidateSessionName` refuses only `:`, a leading `$` and a leading `-`) sitting beside a session `api` whose recorded directory abbreviates to `~/Code/api` both key on `"api ~/Code/api"`. Both rows then present the same target to the filter pass and receive the same verdict from whichever entry survived the write. Under the term `api ~`, `MatchesSearchTerm` should match the first on its name and not the second on either field — the field separation `internal/tui/search_containment_test.go:161-172` exists to pin. Nothing in the suite or the compiler observes the collapse.

**Solution**: Keep the value-keyed map — the cross-rebuild property task 12-2 installed (ranks resolve for a generation the source no longer holds, and `list.DefaultFilter` is reached on exactly one condition) must survive — and let a key hold every *distinct* field pair that produced it (`map[string][]searchEntry`, identical pairs collapsing so a session repeated across By-Tag groups still contributes one entry and still ranks). `containmentFilter` then ranks a target only when its key is held and **every** entry under that key matches the term; a key whose entries disagree ranks nothing. That ambiguity rule is derived rather than chosen: the file's own contract (`search_filter.go:58-59` — "A target the source does not hold ranks nothing, so a pass running behind can only omit a row, never surface one the term does not match") and task 12-2's criterion "a target the map does not hold ranks nothing, so the worst a stale pass can do is omit a row already gone" already fix omission as the sanctioned failure direction and surfacing a non-matching row as the forbidden one, and a colliding key is the same class of uncertainty. The two rival shapes fall to that same rule: ranking on *any* matching entry surfaces a row neither of whose fields contains the term, and returning to the positional slice with its generation guard gives up the overlapping-rebuild property 12-2 was written to hold. Guard conditions carried from the review: the fix lands inside `internal/tui/search_filter.go`; `SessionItem.FilterValue()` is **not** re-keyed (`HeaderItem.FilterValue() == ""` is what makes group headings vanish the moment a filter query is typed, guarded by `internal/tui/sessions_grouped_reskin_test.go`); and it lands with a covering case, since nothing observes the collapse today.

**Outcome**: With that pair of sessions live, the term `api ~` surfaces neither row rather than surfacing the row neither of whose fields contains it; every non-colliding key — which is every key on any ordinary install — ranks exactly as it does today, and a stale pass still ranks by containment at the targets' own indexes.

## Task 2: Run the bash-completion measurement the `init.go` shim edit was gated on
severity: high
sources: report-5-5 (5-5-1)

**Problem**: Task 5-5 gated its `cmd/init.go:65-72` bash-shim edit on a measurement against a real `bash-completion` install, with an explicit void condition in criterion 2 — a measurement contradicting the derivation closes the task with `cmd/init.go` unedited. No measurement *result* is recorded anywhere: `tick-aceea8` carries zero notes, both of the task's commits (`4da790b0f`, `4067537e1`) are single-line with no body, and the implementation directory holds fix-tracking files for 5-2, 5-3 and 5-4 but none for 5-5. The machine still lacks the package (`/usr/share/bash-completion` absent; `/opt/homebrew/share/bash-completion` holds only a `completions` drop directory, and no file on the standard paths defines `_init_completion`), so the precondition the task stated has not changed. The only evidence the shipped shell integration needed changing is a reading of cobra's and bash-completion's sources, and the guard now protecting it (`cmd/init_completion_shell_test.go:36-48`) declares its own `_init_completion` stand-in authored from that same reading — it models the derivation in, so it confirms the shim agrees with the stand-in, never that either agrees with the package a user actually has.

**Solution**: Take the measurement on a bash that carries the `bash-completion` package and let its result decide the shim. Obtain that environment first — a container image carrying the package, or a local `bash-completion` install; neither exists on this machine and a local install changes the developer's machine, so the route is confirmed with the user before anything is installed, and an environment that cannot be obtained is reported back rather than worked around. Run the staging the task prescribes against **both** the pre-edit and the post-edit shim: the emitted `portal init bash` script over the recording stub, **no** `_init_completion` declared, `COMP_WORDS=(x /po extra)` / `COMP_CWORD=1` / `COMP_LINE='x /po extra'` with `COMP_POINT` at the end of `/po`, calling `__start_portal_open`. Record into the task's implementation record the bash and `bash-completion` versions, the `cur` cobra traced, the request the stub recorded, `COMPREPLY`, and whether file completion supplied filenames in its place. If the measured `cur` is the word under the cursor rather than the tail of the line, the finding the edit answered is void: revert `cmd/init.go:66,69-70` to the pinned form per criterion 2 and record that outcome; otherwise the shim stands with the measurement behind it. Guard condition carried from the review: the measurement keeps the unit-lane, no-binary shape it has today — the in-process emitter plus the recording stub — because `internal/portalbintest/lane_guard_test.go` (`TestBuildHelpersStayInTheIntegrationLane`) fails any `_test.go` calling a build helper that does not carry `//go:build integration`, so building or exec'ing `portal` to take the measurement breaches the lane rule.

**Outcome**: The shipped `portal init bash` shim is either confirmed against the package a user actually has or reverted to the pinned form, and the record names the versions, the traced `cur` and the recorded request — so a later reader can tell the gate was run rather than skipped, and the task's void condition is one a measurement could still have triggered.
