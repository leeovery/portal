- Notes:
  - The stall-arming rule is correct and load-bearing for AC2: the `first` guard stops the zero-value `last` from counting as a change, so a never-changing observation (the "daemon never comes up" shape) never arms the stall and therefore always runs to the ceiling. Removing `first` would silently move AC2's case to the stall.
  - `ready()` is evaluated before the stall/ceiling test in the same iteration, so a poll that lands after a deadline but reads ready still returns nil — the barrier cannot fail a daemon it has just seen come up.
  - Both remaining production callers convert the new error into the existing user-visible warning and neither aborts: `cmd/bootstrap/bootstrap.go:177-180` (step 5 → `SaverDownWarning()` + a step-failed WARN) and `cmd/abridged_saver.go:20-23` (warm path → the same warning). I enumerated the non-test callers of `BootstrapPortalSaver`/`EnsurePortalSaverVersion`: those two are the only ones, so no path turns the new error into a fatal.
  - Accepted consequence, not a finding: the worst case on the abridged warm path (`cmd/abridged_saver.go:20`, reached only when the saver probe says absent) grows from the old 2s to the 10s ceiling, because a state directory whose `daemon.pid` stays constantly absent never arms the stall. That is the shape the task explicitly asked for ("fails the wait at the ceiling, not at the stall"), and the trade it buys is that a merely-slow revive now succeeds where it used to silently fail.
  - Pre-existing and untouched by this task: `observeSaverReadiness` reads readiness from `daemon.pid`, so a *previous* still-alive daemon recorded there reads ready on the first poll even if the freshly respawned one never starts. The task's Do list prescribed exactly this observation ("the pid-file read's error-or-pid and the `IdentifyDaemon` verdict"), so the hole is inherited from the old `isSaverDaemonReady`, not introduced here.
